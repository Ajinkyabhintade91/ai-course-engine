# Agent Project 5: AI Personal Assistant

The final project of Unit 8 is the agent most people imagine when they hear the word: a **personal assistant** that manages a calendar, reads and drafts email, keeps a task list, remembers how its person likes things done, and occasionally speaks up unprompted. It combines nearly every earlier module: tools, Module 8.4; memory, Module 8.3; human-in-the-loop, Module 8.11; security, Module 8.14. It is also the most personal agent, with access to private correspondence and the power to speak in someone's name, so the cost of mistakes is social as well as practical: a wrong meeting accepted, an email sent to the wrong person, a preference forgotten, or a stream of pointless notifications.

## 1. First-Principles Mental Model & Intuition

### An excellent executive assistant

A great human assistant has four qualities. They are **competent with the tools**: they can find a free hour that respects your lunch and leaves a gap between meetings. They **remember**: you said once that you never take meetings before 9:30, and they never forgot, but they did not decide you hate Mondays because you cancelled one Monday meeting. They know **what to check with you**: they reply to your manager on routine matters but ask before emailing a new supplier or accepting a meeting with a competitor. And they are **proactive but not noisy**: they tell you at once that your flight is delayed, mention the invoice due tomorrow, and keep the newsletter for a weekly summary.

```text
   SOURCES: calendar, inbox, task list, documents       MEMORY: preferences with provenance
         |                                                   (explicit > inferred; evidence counts)
   [assistant agent]  <--------------------------------------+
         |
   ACTIONS by risk:
     read, search, draft ----------------------------------> automatic
     send to known contacts, internal invites -------------> automatic, logged
     new recipients, attachments, external meetings -------> CONFIRM with the user
     delete, pay, decline ---------------------------------> CONFIRM (irreversible or costly)
         |
   PROACTIVE: score importance -> urgent now | budgeted notifications | daily digest | quiet hours
```

### The three tensions

| Tension | Too little | Too much |
|---|---|---|
| Autonomy | The assistant asks permission for everything and saves no time | It sends emails the user would never have sent |
| Memory | Repeats questions, ignores stated preferences | Treats a one-off as a rule; remembers things it should not |
| Proactivity | Silent while a flight is cancelled | Notifications all day, so the user turns them off |

Every design choice in this chapter is about finding the right point on these three dials and making it adjustable.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Calendar tools

Scheduling starts with **free/busy** information: calendar APIs such as Google Calendar's free/busy query return the busy intervals for a set of calendars in a time range, without exposing the details of the events. Finding a slot is interval arithmetic. Expand each busy interval by a **buffer** $b$ on both sides, sort the intervals, and sweep a cursor from the day's start:

$$\text{gap}_i = s_i - \max(\text{cursor}, \text{day start}), \qquad \text{slot if } \text{gap}_i \ge d$$

for meeting duration $d$, where $s_i$ is the start of the next buffered busy interval; then advance the cursor to the larger of itself and that interval's end, and finally check the gap to the end of the day. Sorting makes this $O(n \log n)$. The user's preferences, such as no meetings before 10:00 and 15 minutes between meetings, set the day's start and the buffer. Time zones, all-day events, and tentative invitations are the practical complications: convert everything to one zone before the sweep, and treat tentative events as busy unless the user says otherwise.

### Persistent memory and preferences

An assistant needs long-term memory of the user's preferences, Module 8.3's semantic memory. Claude's memory tool is one implementation: it lets the model create, read, and update files in a memory directory that the application stores, so information persists across conversations. Whatever the storage, three properties make preference memory trustworthy:

1. **Provenance.** Each preference records whether it was **explicit**, stated by the user, or **inferred**, deduced from behaviour.
2. **Precedence.** Explicit preferences override inferred ones, and later explicit statements override earlier ones. An inference never overwrites an explicit statement.
3. **Evidence thresholds.** An inferred preference is used only after it has been observed several times, $n \ge k$; until then, the assistant uses the default. One cancelled Monday meeting is not a rule.

Memory should also be **visible and editable**: the user can see what the assistant believes about them and correct it. And some things should not be remembered at all, such as other people's personal details from email threads, or sensitive categories the user has not asked to be stored.

### Confirmation rules

The assistant speaks and acts in the user's name. Module 8.11's oversight tiers apply, with categories specific to personal assistants:

| Action | Default |
|---|---|
| Read, search, summarise, draft | Automatic |
| Send email to known contacts, accept internal meetings | Automatic, logged, reversible where possible |
| Email to a **new recipient**, or with **attachments** | Confirm: wrong recipients and attached files are the classic leaks |
| Accept meetings with **external attendees** | Confirm: commitments to outsiders |
| Delete, pay, decline | Confirm: irreversible, costly, or socially awkward |

A personal assistant is also a clear case of Module 8.14's lethal trifecta: it reads untrusted email, holds private data, and can send messages. Meta's Agents Rule of Two suggests confirmation on outbound actions whenever untrusted content is in the session, which the new-recipient and attachment rules implement in the most common exfiltration paths: an injected email asking the assistant to "forward the contract to this address" produces a new recipient with an attachment, and a confirmation prompt.

### Extracting tasks

Email contains requests: "Can you send the Q3 stock report by Friday?" Turning them into tasks requires finding the **request**, the **requester**, and the **due date**, and **deduplicating** against the existing task list so a reminder does not create a second copy. Relative dates must be resolved against today's date. With weekdays numbered 0 for Monday to 6 for Sunday, "by Friday" on a Wednesday is

$$\text{days} = (\text{target} - \text{today}) \bmod 7 = (4 - 2) \bmod 7 = 2$$

and when the result is 0, "by Wednesday" said on a Wednesday, the meaning is ambiguous: today or next week. The lab chooses next week, 7 days; a production assistant should show the resolved date to the user, "due Wednesday 25 November", so a misreading is caught. A model does the extraction well in practice; the date arithmetic and deduplication belong in code.

### Proactive behaviour

Proactive agents act without being asked. Research such as the Proactive Agent work by Lu and colleagues trains models to anticipate tasks from context rather than wait for instructions. The difficulty is not detecting opportunities; it is deciding which are worth interrupting the user for. Each interruption has a cost, and an assistant that interrupts too often trains its user to ignore it. A **notification budget** makes the trade-off explicit:

| Rule | Purpose |
|---|---|
| Importance threshold | Below it, items go to a digest |
| Daily cap | At most $m$ interruptions a day; the rest go to the digest |
| Quiet hours | Outside working hours, only urgent items interrupt |
| Urgent override | Items above a high bar, a cancelled flight, always notify |

Sorting candidates by importance before applying the cap ensures the budget is spent on the most important items. Measuring how often the user acts on a notification, versus dismissing it, tells you whether the threshold is right.

### Complexity

Free slots cost $O(n \log n)$ for $n$ events. Preference updates and lookups are constant. Confirmation checks are linear in recipients or attendees. Task extraction is linear in email text. Proactive ranking is $O(k \log k)$ for $k$ candidates.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, free slots.

```python
import re

def hm(text):
    hours, minutes = map(int, text.split(":"))
    return hours * 60 + minutes

def fmt(minutes):
    return f"{minutes // 60:02d}:{minutes % 60:02d}"

def free_slots(events, start, end, duration, buffer=0):
    busy = sorted((hm(a) - buffer, hm(b) + buffer) for a, b in events)
    slots, cursor = [], hm(start)
    for a, b in busy:
        if a - cursor >= duration:
            slots.append((fmt(cursor), fmt(a)))
        cursor = max(cursor, b)
    if hm(end) - cursor >= duration:
        slots.append((fmt(cursor), fmt(hm(end))))
    return slots

EVENTS = [("09:30", "10:00"), ("11:00", "12:00"), ("12:30", "13:00"), ("15:00", "16:30")]
print(free_slots(EVENTS, "10:00", "18:00", 45))
print(free_slots(EVENTS, "10:00", "18:00", 45, buffer=15))
```

- **Times become minutes since midnight, so the sweep is plain arithmetic.**
- **The day starts at 10:00, Sam's preference.** The 09:30 meeting ends exactly then.
- **Without buffers, three slots fit 45 minutes.** The half-hour gap between 12:00 and 12:30 does not.
- **With 15-minute buffers, the 10:00 to 11:00 gap shrinks to 10:15 to 10:45, too short, and the afternoon slot becomes 13:15 to 14:45.**
- **Sorting matters.** Events from several calendars arrive in any order.

Next, preference memory.

```python
def remember(prefs, key, value, source, now):
    current = prefs.get(key)
    if source == "explicit":
        prefs[key] = {"value": value, "source": "explicit", "at": now, "seen": 1}
        return "stored"
    if current and current["source"] == "explicit":
        return "kept explicit"
    if current and current["value"] == value:
        current["seen"] += 1
        current["at"] = now
        return "reinforced"
    prefs[key] = {"value": value, "source": "inferred", "at": now, "seen": 1}
    return "stored"

def recall(prefs, key, default=None, min_seen=3):
    pref = prefs.get(key)
    if pref is None:
        return default, "default"
    if pref["source"] == "explicit":
        return pref["value"], "explicit"
    if pref["seen"] >= min_seen:
        return pref["value"], f"inferred x{pref['seen']}"
    return default, f"only seen {pref['seen']} times"

PREFS = {}
remember(PREFS, "meeting_start", "10:00", "inferred", 1)
print(recall(PREFS, "meeting_start", "09:00"))
remember(PREFS, "meeting_start", "10:00", "inferred", 2)
remember(PREFS, "meeting_start", "10:00", "inferred", 3)
print(recall(PREFS, "meeting_start", "09:00"))
print(remember(PREFS, "meeting_start", "09:30", "explicit", 4), remember(PREFS, "meeting_start", "10:00", "inferred", 5))
print(recall(PREFS, "meeting_start", "09:00"))
```

- **A first inference is stored but not used.** Recall returns the default, "only seen 1 times".
- **After three consistent observations, the inference is used.**
- **Sam says "start at 9:30". The explicit statement replaces the inference.**
- **A later inference cannot overwrite it: "kept explicit".**
- **A different inferred value resets the count.** One "Best" after two "Cheers" sign-offs does not become a rule.

Then, confirmation rules.

```python
CONTACTS = {"sam@toolshop.example", "priya@harperjoinery.example"}

def needs_confirmation(action, contacts, internal_domain="toolshop.example"):
    kind = action["kind"]
    if kind in {"read", "draft", "search"}:
        return []
    reasons = []
    if kind == "send_email":
        new = [r for r in action["to"] if r.lower() not in contacts]
        if new:
            reasons.append(f"new recipients: {', '.join(new)}")
        if action.get("attachments"):
            reasons.append("has attachments")
    if kind == "accept_invite" and any(not a.endswith("@" + internal_domain) for a in action["attendees"]):
        reasons.append("external attendees")
    if kind in {"delete", "pay", "decline_invite"}:
        reasons.append(f"{kind} is irreversible or costly")
    return reasons

print(needs_confirmation({"kind": "send_email", "to": ["sam@toolshop.example"]}, CONTACTS))
print(needs_confirmation({"kind": "send_email", "to": ["sam@toolshop.example", "new@vendor.example"], "attachments": ["q3.pdf"]}, CONTACTS))
print(needs_confirmation({"kind": "accept_invite", "attendees": ["sam@toolshop.example", "rep@zipcut.example"]}, CONTACTS))
```

- **Reading and drafting never need confirmation.**
- **A routine email to a known contact goes out.**
- **A new recipient plus an attachment produces two reasons.** The pattern of an injected "forward the contract" instruction, caught at the point of sending.
- **A meeting with a ZipCut representative is an external commitment.**
- **The reasons go into the confirmation prompt.** The user sees why they are being asked.

Then, task extraction.

```python
DAYS = ["monday", "tuesday", "wednesday", "thursday", "friday", "saturday", "sunday"]
DUE = re.compile(r"\bby (today|tomorrow|monday|tuesday|wednesday|thursday|friday|saturday|sunday)\b", re.I)
ASK = re.compile(r"\b(please|can you|could you)\b\s+(.+?)(?:\s+by\b|[.?!]|$)", re.I)

def extract_tasks(emails, today_index, existing):
    tasks, known = [], {t.lower() for t in existing}
    for sender, body in emails:
        for sentence in re.split(r"(?<=[.?!])\s+", body):
            ask = ASK.search(sentence)
            if not ask:
                continue
            what = re.sub(r"^also\s+", "", ask.group(2).strip().rstrip(".?!"), flags=re.I)
            if what.lower() in known:
                continue
            due, days = DUE.search(sentence), None
            if due:
                word = due.group(1).lower()
                days = 0 if word == "today" else 1 if word == "tomorrow" else (DAYS.index(word) - today_index) % 7 or 7
            tasks.append({"task": what, "from": sender, "due_in_days": days})
            known.add(what.lower())
    return tasks

EMAILS = [("sam@toolshop.example", "Hi. Can you send the Q3 stock report by Friday? Thanks."),
          ("priya@harperjoinery.example", "Please confirm the trade account terms by tomorrow. Could you also share the SAW-3 manual."),
          ("sam@toolshop.example", "Reminder: please book the van.")]
print(extract_tasks(EMAILS, today_index=2, existing=["book the van"]))
```

- **Each sentence is checked for a request phrase; the request runs to "by", the end of the sentence, or punctuation, including a dot inside an address.**
- **On Wednesday, index 2, "by Friday" is due in 2 days and "by tomorrow" in 1.**
- **The manual request has no due date: `None`, not a guess.**
- **"Book the van" is already on the list, so the reminder adds nothing.**
- **A leading "also" is trimmed, so the task reads as an instruction.**

Finally, the proactive budget.

```python
def proactive(nudges, hour, sent_today, max_per_day=3, quiet=(19, 8), threshold=0.7):
    quiet_now = hour >= quiet[0] or hour < quiet[1]
    notify, digest = [], []
    for nudge in sorted(nudges, key=lambda n: -n["importance"]):
        urgent = nudge["importance"] >= 0.95
        if nudge["importance"] < threshold:
            digest.append(nudge["id"])
        elif quiet_now and not urgent:
            digest.append(nudge["id"])
        elif sent_today + len(notify) >= max_per_day and not urgent:
            digest.append(nudge["id"])
        else:
            notify.append(nudge["id"])
    return notify, digest

NUDGES = [{"id": "flight-delay", "importance": 0.97}, {"id": "invoice-due", "importance": 0.8},
          {"id": "newsletter", "importance": 0.2}, {"id": "meeting-prep", "importance": 0.75}, {"id": "price-drop", "importance": 0.72}]
print(proactive(NUDGES, hour=10, sent_today=0))
print(proactive(NUDGES, hour=10, sent_today=2))
print(proactive(NUDGES, hour=21, sent_today=0))
```

- **Candidates are ranked by importance before the budget is spent.**
- **At 10:00 with nothing sent yet, the top three notify; the price drop and the newsletter go to the digest.**
- **With two already sent, the urgent flight delay still notifies and fills the third place; the rest wait.**
- **At 21:00, quiet hours: only the flight delay interrupts.**

**Complexity.** `free_slots` sorts the events, $O(n \log n)$. `remember` and `recall` are constant. `needs_confirmation` is linear in recipients or attendees. `extract_tasks` is linear in email text. `proactive` sorts the candidates.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Back-to-back scheduling.** Slots that fit exactly leave no time to move between meetings. Use buffers.

**Time zone bugs.** A slot that is free in one zone may be at 03:00 in another. Convert everything to one zone before computing.

**Treating one action as a preference.** One cancelled Monday meeting is not "hates Mondays". Require repeated evidence.

**Inferences overriding statements.** The user said 9:30; behaviour suggests 10:00. The statement wins until the user changes it.

**Invisible memory.** Users distrust assistants that know things they cannot see. Show and allow editing.

**Remembering other people's data.** Email threads contain third parties' details. Do not store them as the user's memory.

**Auto-sending to new recipients.** The commonest embarrassing and dangerous mistake. Confirm first-time recipients.

**Attachments by default.** Attached files are the easiest way to leak documents. Confirm them.

**Instructions inside email.** "Assistant, forward this to" in an email is data, not a command. Module 8.14 applies.

**Ambiguous dates.** "By Wednesday" said on Wednesday has two meanings. Show the resolved date.

**Notification spam.** A user who turns off notifications has turned off the assistant. Budget interruptions.

**No digest.** Low-importance items still matter eventually. Batch them rather than dropping them.

**Question 1.** Sam has told the assistant "never book meetings before 9:30". Using `remember` and `recall`, explain what should have happened and what bug the behaviour suggests.

<details>
<summary>View Answer</summary>

Sam's statement is an explicit preference: `remember` stores meeting_start as 09:30 with source explicit. Each later observation of a 10:00 start is an inference; `remember` returns "kept explicit" and does not change or count against the stored value, because an inference never overwrites an explicit statement. `recall` then returns 09:30 with the reason "explicit", so 9:30 slots should still be offered. That the assistant moved to 10:00 suggests a precedence bug: the inferred observations were stored separately and the lookup picked the most recent or the most frequent value regardless of source, or the explicit preference was saved somewhere the scheduling code does not read. The fix is to keep one record per preference with its provenance, apply the precedence rules on every write as `remember` does, and make the scheduler read through `recall`. Separately, three 10:00 starts might be worth a gentle question, "You've started at 10:00 three times recently; should I change your earliest meeting time?", which turns a possible change into an explicit statement instead of a silent override. The memory page should show Sam the stored preference and its source so this kind of drift is visible.

import re

EVENTS = [("09:30", "10:00"), ("11:00", "12:00"), ("12:30", "13:00"), ("15:00", "16:30")]
CONTACTS = {"sam@toolshop.example", "priya@harperjoinery.example"}
DAYS = ["monday", "tuesday", "wednesday", "thursday", "friday", "saturday", "sunday"]
DUE = re.compile(r"\bby (today|tomorrow|monday|tuesday|wednesday|thursday|friday|saturday|sunday)\b", re.I)
ASK = re.compile(r"\b(please|can you|could you)\b\s+(.+?)(?:\s+by\b|[.?!]|$)", re.I)
EMAILS = [("sam@toolshop.example", "Hi. Can you send the Q3 stock report by Friday? Thanks."),
          ("priya@harperjoinery.example", "Please confirm the trade account terms by tomorrow. Could you also share the SAW-3 manual."),
          ("sam@toolshop.example", "Reminder: please book the van.")]
NUDGES = [{"id": "flight-delay", "importance": 0.97}, {"id": "invoice-due", "importance": 0.8},
          {"id": "newsletter", "importance": 0.2}, {"id": "meeting-prep", "importance": 0.75}, {"id": "price-drop", "importance": 0.72}]


def hm(text):
    """Given: "HH:MM" to minutes since midnight."""
    hours, minutes = map(int, text.split(":"))
    return hours * 60 + minutes


def fmt(minutes):
    """Given: minutes since midnight to "HH:MM"."""
    return f"{minutes // 60:02d}:{minutes % 60:02d}"


# ---------------------------------------------------------------- Step 1
def free_slots(events, start, end, duration, buffer=0):
    """Sort, buffer, sweep."""
    busy = sorted((hm(a) - buffer, hm(b) + buffer) for a, b in events)
    slots, cursor = [], hm(start)
    for a, b in busy:
        if a - cursor >= duration:
            slots.append((fmt(cursor), fmt(a)))
        cursor = max(cursor, b)
    if hm(end) - cursor >= duration:
        slots.append((fmt(cursor), fmt(hm(end))))
    return slots


# ---------------------------------------------------------------- Step 2
def remember(prefs, key, value, source, now):
    """Provenance and precedence: what the user said beats what the assistant guessed."""
    current = prefs.get(key)
    if source == "explicit":
        prefs[key] = {"value": value, "source": "explicit", "at": now, "seen": 1}
        return "stored"
    if current and current["source"] == "explicit":
        return "kept explicit"
    if current and current["value"] == value:
        current["seen"] += 1
        current["at"] = now
        return "reinforced"
    prefs[key] = {"value": value, "source": "inferred", "at": now, "seen": 1}
    return "stored"


def recall(prefs, key, default=None, min_seen=3):
    """Inferences need evidence before they change behaviour."""
    pref = prefs.get(key)
    if pref is None:
        return default, "default"
    if pref["source"] == "explicit":
        return pref["value"], "explicit"
    if pref["seen"] >= min_seen:
        return pref["value"], f"inferred x{pref['seen']}"
    return default, f"only seen {pref['seen']} times"


# ---------------------------------------------------------------- Step 3
def needs_confirmation(action, contacts, internal_domain="toolshop.example"):
    """Speak in the user's name only where they would expect it."""
    kind = action["kind"]
    if kind in {"read", "draft", "search"}:
        return []
    reasons = []
    if kind == "send_email":
        new = [r for r in action["to"] if r.lower() not in contacts]
        if new:
            reasons.append(f"new recipients: {', '.join(new)}")
        if action.get("attachments"):
            reasons.append("has attachments")
    if kind == "accept_invite" and any(not a.endswith("@" + internal_domain) for a in action["attendees"]):
        reasons.append("external attendees")
    if kind in {"delete", "pay", "decline_invite"}:
        reasons.append(f"{kind} is irreversible or costly")
    return reasons


# ---------------------------------------------------------------- Step 4
def extract_tasks(emails, today_index, existing):
    """Requests, requesters, resolved due dates, no duplicates."""
    tasks, known = [], {t.lower() for t in existing}
    for sender, body in emails:
        for sentence in re.split(r"(?<=[.?!])\s+", body):
            ask = ASK.search(sentence)
            if not ask:
                continue
            what = re.sub(r"^also\s+", "", ask.group(2).strip().rstrip(".?!"), flags=re.I)
            if what.lower() in known:
                continue
            due, days = DUE.search(sentence), None
            if due:
                word = due.group(1).lower()
                days = 0 if word == "today" else 1 if word == "tomorrow" else (DAYS.index(word) - today_index) % 7 or 7
            tasks.append({"task": what, "from": sender, "due_in_days": days})
            known.add(what.lower())
    return tasks


# ---------------------------------------------------------------- Step 5
def proactive(nudges, hour, sent_today, max_per_day=3, quiet=(19, 8), threshold=0.7):
    """Spend a small interruption budget on the most important items; digest the rest."""
    quiet_now = hour >= quiet[0] or hour < quiet[1]
    notify, digest = [], []
    for nudge in sorted(nudges, key=lambda n: -n["importance"]):
        urgent = nudge["importance"] >= 0.95
        if nudge["importance"] < threshold:
            digest.append(nudge["id"])
        elif quiet_now and not urgent:
            digest.append(nudge["id"])
        elif sent_today + len(notify) >= max_per_day and not urgent:
            digest.append(nudge["id"])
        else:
            notify.append(nudge["id"])
    return notify, digest
