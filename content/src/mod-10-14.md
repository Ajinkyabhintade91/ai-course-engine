# Troubleshooting

Most problems with local models fall into a handful of patterns: **slow generation**, **out-of-memory errors**, a **GPU that is not used**, **truncated context** that makes the model forget, and **prompt-template mismatches** that produce strange output. Each has characteristic symptoms, a place where the evidence shows up, and a standard fix. This module builds a systematic approach: gather evidence from `ollama ps`, the response metrics, and the server log; match it against known patterns; and work through a checklist in order of likelihood and cost, instead of reinstalling things at random.

Commands and log locations are from Ollama's documentation at the time of writing (November 2026). Log messages change between versions; the lab uses simplified lines modelled on the kinds of messages server logs contain.

## 1. First-Principles Mental Model & Intuition

### A machine that makes strange noises

Troubleshooting a local model is like diagnosing a workshop machine that is running badly. An experienced engineer does not start by taking it apart. They **listen and look first**: Is it running at all? Is it running on the right power supply? Is it overloaded? Did it just start up from cold? Then they read the **service log**, which records what the machine detected when it started. Only then do they change one thing at a time, check again, and write down what fixed it.

```text
 SYMPTOM                       FIRST LOOK                       LIKELY CAUSE                     FIX
 slow every time               ollama ps: 100% CPU              GPU not used                     driver, hardware support, logs
 slow every time               ollama ps: 40%/60% CPU/GPU       does not fit GPU                 smaller model / quant / context
 slow first time only          load_duration in metrics         cold start                       keep-alive, preload
 crash / "out of memory"       server log                       too big for memory               smaller model / context
 forgets earlier messages      prompt tokens vs num_ctx         context truncated                set num_ctx, trim history
 odd tokens, talks as user     raw output                       template / stop mismatch         official tag, fix TEMPLATE
 connection refused / in use   curl localhost:11434, log        server down / port taken         start service, free port

 evidence: ollama ps | response metrics | server log (OLLAMA_DEBUG=1) | ollama show --modelfile | nvidia-smi
```

### One change at a time

The most valuable habit is to change **one** thing, re-measure with the same test prompt, and record the result. Changing the model, the context, and the driver at once makes it impossible to know which change mattered.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Where the evidence is

- **`ollama ps`** shows each loaded model's size, its PROCESSOR, `100% GPU`, `100% CPU`, or a CPU/GPU split, and how long it stays loaded, Module 10.2.
- **Response metrics**, Module 10.11: `load_duration`, `prompt_eval_count` and `prompt_eval_duration`, `eval_count` and `eval_duration`, all in nanoseconds.
- **The server log**: on macOS `~/.ollama/logs/server.log`; on Linux `journalctl -u ollama`; on Windows `server.log` under `%LOCALAPPDATA%\Ollama`. Setting `OLLAMA_DEBUG=1` adds detail. At start-up the log records the GPUs detected; when loading a model it records how many layers were placed on the GPU.
- **`ollama show --modelfile <model>`** prints the model's template, parameters, and stop sequences.
- **Vendor tools** such as `nvidia-smi` show whether the driver sees the GPU and what is using its memory.

### Slow generation

Decode speed is bounded by memory bandwidth, Module 10.10, so the main causes of slowness are about **where** the model runs:

1. **On the CPU although a GPU exists:** driver missing or too old, unsupported card, or a missing package such as ROCm on Linux, Module 10.3.
2. **Split between CPU and GPU:** the model, its KV cache, and overhead do not fit; even a small share on the CPU slows every token.
3. **Cold start:** a large `load_duration` means the model was loaded for this request.
4. **Long prompts:** prompt processing scales with prompt length; on a CPU, thousands of tokens can take many seconds before the first output token.
5. **Other causes:** another program using the GPU, thermal throttling on laptops, or power-saving modes.

A useful rule: if generation runs at under half the speed expected from Module 10.10's estimate and none of the first four causes applies, look at the machine itself.

### Out of memory

Out-of-memory errors happen when the weights, KV cache, and buffers exceed available memory. Causes include a larger context than before, `OLLAMA_NUM_PARALLEL` above one multiplying the cache, several models loaded at once, or another application holding GPU memory. Fixes, in order of cost: reduce the context, unload other models with `ollama stop`, quantize the KV cache, choose a smaller quantization or model.

### Context truncation

When the prompt, including the system prompt, history, and documents, exceeds the context window, something is cut and the model appears to **forget**. Because the default context depends on version and memory, Module 10.2, a conversation that worked on one machine can be truncated on another. The fix is to set `num_ctx` explicitly and, in the application, to fit conversations deliberately: keep the system message, keep the newest messages that fit, and drop or summarise older ones, leaving room for the answer:

$$\text{system} + \sum_{\text{kept}} \text{tokens}(m) \le n_{ctx} - \text{reserve}_{\text{output}}$$

Token counts can be estimated at about four characters per token for English text when a tokenizer is not available; that is rough, so leave margin.

### Template and stop-sequence problems

Each model is trained with a specific **chat template**: special tokens that mark the start and end of each turn. If the template is wrong, typically for a GGUF file imported without its template, Module 10.4, the model sees malformed input and produces symptoms such as special tokens like `<|im_end|>` or `<end_of_turn>` appearing in the output, the model writing the user's next turn itself, or never stopping. `ollama show --modelfile` reveals the template and stop parameters; the fix is to use the official tag or copy the correct `TEMPLATE` and `PARAMETER stop` lines into the Modelfile.

### Server and connection problems

"Connection refused" means no server is listening: start the service or the app. "Address already in use" means another process holds port 11434, often a second Ollama, a Docker container, or a forgotten `ollama serve`. Permission errors on Linux often come from a custom models directory the `ollama` service user cannot write, Module 10.3.

### A systematic checklist

1. Reproduce with a fixed test prompt and record the metrics.
2. `ollama ps`: where is the model running?
3. Response metrics: cold start? long prompt? tokens per second?
4. Server log with `OLLAMA_DEBUG=1`: GPU detection, offload, memory, truncation.
5. `ollama show --modelfile`: template, stop sequences, `num_ctx`.
6. Change one thing, re-run the test, record the result.
7. If unresolved, update Ollama and drivers, then search the troubleshooting docs and issue tracker with the exact log lines.

### Complexity

Scanning a log is linear in lines times patterns; diagnosis rules are constant time; fitting a conversation is linear in messages; template checks are linear in output length.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, scanning the server log for known signatures.

```python
import re

SIGNATURES = [
    (r"no compatible GPUs", "GPU not detected: check driver, then hardware support"),
    (r"out of memory|cudaMalloc failed|failed to allocate", "out of memory: smaller model, quantization, or context"),
    (r"offloaded (\d+)/(\d+) layers", None),
    (r"truncating input prompt", "prompt truncated: raise num_ctx or shorten input"),
    (r"address already in use", "port 11434 taken: another server is running"),
    (r"permission denied", "file permissions: check the models directory owner"),
]

def scan_log(lines):
    found = []
    for line in lines:
        for pat, msg in SIGNATURES:
            m = re.search(pat, line, re.I)
            if not m:
                continue
            if msg is None:
                done, total = int(m.group(1)), int(m.group(2))
                if done < total:
                    msg = f"partial offload {done}/{total} layers: model split between GPU and CPU"
                else:
                    continue
            if msg not in found:
                found.append(msg)
    return found

LOG = ['time=1 level=INFO msg="no compatible GPUs were discovered"',
       'time=2 msg="offloaded 20/37 layers to GPU"',
       'time=3 level=WARN msg="truncating input prompt" limit=4096 prompt=6100',
       'time=4 msg="offloaded 37/37 layers to GPU"',
       'time=5 level=ERROR msg="cudaMalloc failed: out of memory"',
       'time=6 msg="out of memory"']
print(scan_log(LOG))
```

- **Four findings from six lines.** Repeated signatures are reported once.
- **A full offload, 37 of 37 layers, is not a problem,** so it is skipped; 20 of 37 means a split.
- **The lines are simplified.** Real wording varies by version, so patterns should be kept loose and updated.

Next, diagnosing slow generation from observations.

```python
def diagnose_speed(obs):
    causes = []
    if obs["processor"] == "100% CPU" and obs.get("has_gpu"):
        causes.append("model on CPU although a GPU exists")
    elif "CPU/GPU" in obs["processor"]:
        causes.append("model split between CPU and GPU")
    if obs["load_s"] > 5:
        causes.append("cold start: model loaded for this request")
    if obs["prompt_tokens"] > 4000 and obs["prompt_tps"] < 500:
        causes.append("long prompt processed slowly")
    if obs["tps"] < 0.5 * obs["expected_tps"] and not causes:
        causes.append("below expectation with no obvious cause: check thermals and other GPU load")
    return causes or ["speed as expected"]

print(diagnose_speed({"processor": "100% CPU", "has_gpu": True, "load_s": 8.2, "prompt_tokens": 6000,
                      "prompt_tps": 300, "tps": 4, "expected_tps": 40}))
print(diagnose_speed({"processor": "100% GPU", "has_gpu": True, "load_s": 0.1, "prompt_tokens": 200,
                      "prompt_tps": 2000, "tps": 15, "expected_tps": 40}))
```

- **Three causes at once in the first case:** CPU-only, a cold start, and a long prompt. Each has its own fix.
- **In the second case the model is on the GPU, warm, with a short prompt, yet slow:** look at the machine.
- **The expected speed comes from Module 10.10's estimate,** so the diagnosis is relative to what the hardware should do.

Then, fitting a conversation into the context.

```python
def fit_messages(messages, num_ctx, reserve=512):
    budget = num_ctx - reserve
    est = lambda m: len(m["content"]) // 4 + 4
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    used = sum(est(m) for m in system)
    kept = []
    for m in reversed(rest):
        if used + est(m) > budget:
            break
        kept.insert(0, m)
        used += est(m)
    return system + kept, len(rest) - len(kept), used

MSGS = [{"role": "system", "content": "S" * 400}] + \
       [{"role": "user" if i % 2 == 0 else "assistant", "content": "x" * 2000} for i in range(10)]
kept, dropped, used = fit_messages(MSGS, 4096)
print(len(kept), dropped, used, kept[0]["role"])
```

- **With a 4,096-token context: the system message and the newest six messages are kept, four dropped,** using about 3,128 tokens and leaving room for the answer.
- **The system message is always kept,** so instructions are never the part that silently disappears.
- **Four characters per token plus a small overhead per message is an estimate;** use the model's tokenizer when precision matters.

Then, detecting template problems in output.

```python
LEAKS = ["<|im_start|>", "<|im_end|>", "<|eot_id|>", "<|start_header_id|>", "[INST]",
         "<start_of_turn>", "<end_of_turn>", "</s>"]

def template_check(output):
    issues = []
    leaked = [t for t in LEAKS if t in output]
    if leaked:
        issues.append("special tokens in output (" + ", ".join(leaked) + "): chat template mismatch")
    if re.search(r"(?im)^\s*(user|human)\s*:", output):
        issues.append("model writes the user's turn: missing stop sequence")
    return issues

print(template_check("Sure!<|im_end|>\n<|im_start|>user\nNext"))
print(template_check("The blade fits.\nUser: and the guard?"))
```

- **Leaked special tokens point to a template mismatch,** typically an imported model without its template.
- **"User:" lines in the answer mean the model continued the conversation itself:** a stop sequence is missing.
- **Clean output returns no issues.**

Finally, a triage playbook.

```python
PLAYBOOK = {
    "model on CPU although a GPU exists": ["ollama ps", "nvidia-smi", "set OLLAMA_DEBUG=1 and read the server log"],
    "model split between CPU and GPU": ["ollama ps", "use a smaller model or quantization", "lower num_ctx or quantize the KV cache"],
    "cold start: model loaded for this request": ["raise OLLAMA_KEEP_ALIVE", "preload the model"],
    "prompt truncated: raise num_ctx or shorten input": ["set num_ctx in a Modelfile", "retrieve less context"],
    "chat template mismatch": ["ollama show --modelfile <model>", "use the official tag or copy the model's TEMPLATE"],
}

def triage(findings):
    steps = []
    for f in findings:
        key = next((k for k in PLAYBOOK if f.startswith(k) or f.endswith(k)), None)
        for s in PLAYBOOK.get(key, ["record the symptom and search the troubleshooting docs"]):
            if s not in steps:
                steps.append(s)
    return steps

print(triage(["model on CPU although a GPU exists", "cold start: model loaded for this request",
              "special tokens in output (<|im_end|>): chat template mismatch"]))
```

- **Findings from any tool map to concrete next steps,** without duplicates.
- **Template findings match by their ending,** since the leaked tokens vary.
- **Unknown findings get a fallback,** so nothing is silently ignored.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Reinstalling first.** It rarely helps. Gather evidence first.

**Changing several things at once.** You learn nothing. One change, one test.

**Not checking `ollama ps`.** Most speed problems show there. Check it first.

**Ignoring cold starts.** First-request slowness is normal. Keep-alive or preload.

**Defaults that differ between machines.** Context defaults vary. Set `num_ctx`.

**Parallel requests eating memory.** Each slot needs its own cache. Check `OLLAMA_NUM_PARALLEL`.

**Imported GGUF files.** Missing templates cause odd output. Prefer official tags or set `TEMPLATE`.

**Missing stop sequences.** The model keeps talking as the user. Add `PARAMETER stop`.

**Two servers fighting.** A desktop app and a Docker container on one port. Run one.

**Laptop on battery.** Speeds drop sharply. Test plugged in.

**Old versions.** New models need new Ollama versions. Update before deeper debugging.

**Not writing it down.** The same problem returns. Keep a troubleshooting log.

# ---------------------------------------------------------------- Step 1
def scan_log(lines):
    """Known signatures in server log lines, each reported once."""
    found = []
    for line in lines:
        for pat, msg in SIGNATURES:
            m = re.search(pat, line, re.I)
            if not m:
                continue
            if msg is None:
                done, total = int(m.group(1)), int(m.group(2))
                if done < total:
                    msg = f"partial offload {done}/{total} layers: model split between GPU and CPU"
                else:
                    continue
            if msg not in found:
                found.append(msg)
    return found


# ---------------------------------------------------------------- Step 2
def diagnose_speed(obs):
    """Placement, cold start, and prompt length before blaming the machine."""
    causes = []
    if obs["processor"] == "100% CPU" and obs.get("has_gpu"):
        causes.append("model on CPU although a GPU exists")
    elif "CPU/GPU" in obs["processor"]:
        causes.append("model split between CPU and GPU")
    if obs["load_s"] > 5:
        causes.append("cold start: model loaded for this request")
    if obs["prompt_tokens"] > 4000 and obs["prompt_tps"] < 500:
        causes.append("long prompt processed slowly")
    if obs["tps"] < 0.5 * obs["expected_tps"] and not causes:
        causes.append("below expectation with no obvious cause: check thermals and other GPU load")
    return causes or ["speed as expected"]


# ---------------------------------------------------------------- Step 3
def fit_messages(messages, num_ctx, reserve=512):
    """Keep the system message and the newest turns that fit, leaving room for the answer."""
    budget = num_ctx - reserve
    est = lambda m: len(m["content"]) // 4 + 4
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    used = sum(est(m) for m in system)
    kept = []
    for m in reversed(rest):
        if used + est(m) > budget:
            break
        kept.insert(0, m)
        used += est(m)
    return system + kept, len(rest) - len(kept), used


# ---------------------------------------------------------------- Step 4
def template_check(output):
    """Leaked special tokens and runaway user turns point to template or stop problems."""
    issues = []
    leaked = [t for t in LEAKS if t in output]
    if leaked:
        issues.append("special tokens in output (" + ", ".join(leaked) + "): chat template mismatch")
    if re.search(r"(?im)^\s*(user|human)\s*:", output):
        issues.append("model writes the user's turn: missing stop sequence")
    return issues


# ---------------------------------------------------------------- Step 5
def triage(findings):
    """Ordered, de-duplicated next steps for a set of findings."""
    steps = []
    for f in findings:
        key = next((k for k in PLAYBOOK if f.startswith(k) or f.endswith(k)), None)
        for s in PLAYBOOK.get(key, ["record the symptom and search the troubleshooting docs"]):
            if s not in steps:
                steps.append(s)
    return steps
