# Practical ChatGPT Workflows

You now know the individual tools: models, custom instructions, memory, prompting, deep research, data analysis, image generation. Real work rarely uses one of them alone. A proposal, a report, a campaign, or a lesson plan passes through several stages, and the quality of the final product depends on how those stages are connected and checked. This closing chapter of the unit is about putting the pieces together into workflows that are reliable enough to depend on, and about recognising the jobs you should not hand to an AI at all.

## 1. First-Principles Mental Model & Intuition

### A kitchen line, not a magic oven

There are two ways to imagine making a meal with help. In the first, you put ingredients into a magic oven, press a button, and a finished dish appears. In the second, the meal moves along a line of stations: one preps, one cooks, one plates, and at the end a head chef looks at every plate before it leaves the kitchen.

People use ChatGPT like the magic oven. They paste in a request, "write a market report on electric scooters", and expect a finished product. Sometimes it looks fine. It is never dependable, because one enormous step gives no opportunity to notice that something went wrong in the middle.

Professional work with AI looks like the kitchen line:

```text
 +----------+    +---------+    +---------+    +----------+    +-----------+
 | RESEARCH | -> |  BRIEF  | -> |  DRAFT  | -> |  REVIEW  | -> |  RELEASE  |
 | gather   |    | decide  |    | write   |    | check    |    | a person  |
 | facts    |    | what to |    | it      |    | against  |    | signs off |
 | and data |    | say     |    |         |    | criteria |    |           |
 +----+-----+    +----+----+    +----+----+    +----+-----+    +-----------+
      |               |              |              |
    gate            gate           gate           gate
  sources ok?    brief clear?   meets brief?   facts verified?
```

Three things make the line better than the oven.

- **Each stage does one job**, which a model does far better than five jobs at once.
- **You see the intermediate products.** A weak brief is obvious and cheap to fix. A weak brief hidden inside a finished report is neither.
- **There is a gate at each handoff.** An error caught after the research stage costs a minute. The same error caught by a client costs a relationship.

### Why errors compound

Each stage can introduce an error, and a later stage builds on whatever it receives. A wrong figure collected during research is carried into the brief, written fluently into the draft, and polished in review. This is the compounding arithmetic from Module 1.6, now applied to your own work process. Section 2 puts numbers on it and shows what gates buy you.

### The head chef does not leave

In every version of this picture a person is at the end of the line. That is not a temporary limitation waiting for better models. Someone has to be accountable for what goes out, and accountability cannot be delegated to software. The practical question is never "can the AI do this?" It is "how do I arrange the work so that my checking is quick and catches what matters?"

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Two workflow patterns

Anthropic's engineering guide on building AI systems names several reusable patterns. Two of them cover most everyday work and apply equally in ChatGPT.

**Prompt chaining.** Break a task into a sequence of steps, where each step's output becomes the next step's input, with a check between steps. The guide describes the trade plainly: it takes longer, and in exchange each step is an easier task done more accurately. It suits any job with fixed, identifiable sub-tasks.

**Evaluator-optimiser.** One pass produces a draft. A second pass evaluates it against stated criteria and lists the faults. A third revises. Repeat until the criteria are met. This is the self-critique technique from Module 2.5, and it works when you can say clearly what "good" means.

```text
 PROMPT CHAINING                         EVALUATOR-OPTIMISER

 step 1 --> check --> step 2 --> ...       +--> draft --+
                                           |            v
                                        revise      evaluate against
                                           ^        written criteria
                                           |            |
                                           +-- faults --+   (stop when it passes)
```

### An end-to-end example

Here is a client proposal produced as a workflow, with the feature from this unit that serves each stage.

| Stage | What happens | Feature | Gate before moving on |
|---|---|---|---|
| Research | Gather facts about the client and their market | Search or deep research (Module 2.7) | Have I opened and read the key sources? |
| Brief | Decide the argument, structure, and audience | An ordinary chat, using a structured prompt (2.5) | Would a colleague understand what we are proposing and why? |
| Data | Work out figures: costs, timelines, savings | Data analysis (2.8) | Do the row counts and totals reconcile? |
| Draft | Write the proposal from the brief and data | Canvas, inside a project holding the client's files (2.1) | Does every section follow the brief? |
| Visuals | A diagram or cover image | Image generation (2.9) | Is all text in the image correct? |
| Review | Critique against criteria, then revise | Evaluator-optimiser in a fresh chat | Has every number been traced to its source? |
| Release | Final read and sign-off | You | Would I put my name to this? |

Two details repay attention. The review stage uses a **fresh chat**: a conversation that produced a draft is primed to defend it, while a new one, given only the draft and the criteria, is a sharper critic. And a **project** holds the client's files and instructions for the whole job, so no stage has to be re-briefed from nothing.

### The arithmetic of gates

Suppose a workflow has $k$ stages and stage $i$ introduces an error with probability $e_i$, independently. The chance that the final product is clean is

$$
P(\text{clean}) = \prod_{i=1}^{k} (1 - e_i)
$$

With four stages each at a 5 percent error rate:

$$
0.95^{4} \approx 0.815
$$

Nearly one product in five has a fault somewhere. Now add a gate after each stage that catches an error with probability $c_i$. An error survives only if it occurs and the gate misses it, so the effective error rate of the stage is

$$
e_i^{\text{eff}} = e_i \,(1 - c_i)
$$

With gates that catch 70 percent of errors, each stage's effective rate falls from 5 percent to 1.5 percent, and

$$
P(\text{clean}) = 0.985^{4} \approx 0.941
$$

The share of faulty products drops from about 18.5 percent to about 5.9 percent, a reduction of roughly two thirds, from checks that are far from perfect.

Two caveats keep this honest. Errors are not really independent: a mistake early in the line contaminates everything after it, which is an argument for putting the strongest gate earliest. And a gate's catch rate depends on someone actually performing the check. A gate that is ticked without looking has a catch rate of zero.

### Why checklists work

A gate is only as good as the discipline of applying it, and the most reliable tool for that is the plainest: a written checklist.

The strongest evidence comes from surgery. In 2009 a study in the *New England Journal of Medicine* introduced a short safety checklist in eight hospitals around the world, covering nearly 7,700 patients. After the checklist was adopted, major complications fell from 11.0 percent to 7.0 percent and deaths from 1.5 percent to 0.8 percent. The surgeons had not become more skilled. The checklist made sure that known, simple steps were not skipped under pressure. The study compared before and after without randomisation, so the exact size of the effect is debated, and the lesson has held up well: experts skip steps, and a list prevents it.

A release checklist for AI-assisted work can be very short.

```text
 [ ] Every figure traced to a source I have seen
 [ ] Every name, date, and quotation checked
 [ ] Nothing confidential included that should not be
 [ ] The piece answers the brief
 [ ] A named person has read it start to finish
```

The items share a property: each is a specific yes-or-no question about the output. "Check quality" is not a checklist item.

### The opposite of a workflow: workslop

In 2025 researchers writing in the *Harvard Business Review* gave a name to something many office workers had noticed: **workslop**, AI-generated work that looks polished and lacks the substance to advance the task. In their survey of over a thousand workers, around 40 percent said they had received such material in the previous month, and each instance took, on average, close to two hours to deal with.

Workslop is what the magic-oven approach produces at scale. The sender saves ten minutes and the recipient loses two hours. The damage goes beyond time, since people who receive it think less of the sender's competence and reliability. A workflow with gates is the direct remedy, because it puts the cost of checking where it belongs, with the person who produced the work.

A related finding comes from a 2025 Microsoft Research study of 319 knowledge workers. The more confidence people had in the AI, the less critical thinking they reported applying to its output. The more confidence they had in their own ability, the more they applied. Trust in the tool crowds out scrutiny, which is exactly why the scrutiny needs to be written into the process and not left to mood.

### When not to use AI

Part of mastering a tool is knowing when to leave it in the drawer. Ethan Mollick's widely read guidance, and the experience behind this whole unit, point to the same cases.

| Do not use AI when | Because |
|---|---|
| You need to learn the material | The struggle is the learning (Module 2.11) |
| An error would be severe and you cannot check the output | Fluency hides mistakes, and you have no way to find them |
| The data is confidential and the tool is not approved for it | Module 2.10 |
| The value is in it being from you | A condolence note, a difficult conversation, a personal reference |
| The task is trivially quick by hand | Writing the prompt costs more than the task |

And three cases where it is nearly always worth using:

| Use AI when | Because |
|---|---|
| You need a first draft of something you will rework | Editing is faster than starting from nothing |
| You need many options to choose from | Generating twenty ideas costs seconds |
| You are an expert who can check the output at a glance | Review time is small, so the net saving is large |

The pattern underneath is a pair of questions: **what does an error cost, and how easily can I detect one?** High stakes with easy checking is fine, with review. High stakes with hard checking is where AI should not be trusted. Low stakes is where it can run freely.

```text
                        easy to check             hard to check
                  +------------------------+------------------------+
   high stakes    |  use AI WITH REVIEW    |  DO NOT rely on AI     |
                  +------------------------+------------------------+
   low stakes     |  use AI freely         |  use AI, spot-check    |
                  +------------------------+------------------------+
```

**Cost of a workflow.** A chain of $k$ stages costs $k$ model calls instead of one, plus $k$ short checks. An evaluator-optimiser loop with $r$ rounds costs about $2r$ calls. The time is real. It is small compared with the cost of one faulty deliverable reaching a client.

## 3. Production-Grade Implementation & Annotated Walkthrough

A workflow with gates is easy to express in code, and seeing it as code clarifies the idea. The stages here are simple functions standing in for model calls.

```python
def run_pipeline(stages, gates, data):
    """Run stages in order. After each, run its gate; halt at the first failure."""
    for name, stage in stages:
        data = stage(data)
        problems = gates[name](data) if name in gates else []
        if problems:
            return {"status": "halted", "stage": name, "problems": problems, "data": data}
    return {"status": "done", "data": data}

def research(d):
    return {**d, "facts": {"subscribers": 4200, "open_rate": 0.31}}

def brief(d):
    return {**d, "brief": "Lead with subscriber growth; keep it under 150 words."}

def draft(d):
    return {**d, "draft": "We now have 4,800 subscribers and a 31% open rate."}   # a wrong figure

def facts_gate(d):
    return [] if d.get("facts") else ["no facts gathered"]

def draft_gate(d):
    expected = f"{d['facts']['subscribers']:,}"
    return [] if expected in d["draft"] else [f"draft does not contain the verified figure {expected}"]

stages = [("research", research), ("brief", brief), ("draft", draft)]
print(run_pipeline(stages, {"research": facts_gate, "draft": draft_gate}, {"client": "Northwind"}))
print(run_pipeline(stages, {}, {"client": "Northwind"})["status"])
```

- **`stages` is an ordered list of name and function pairs.** Each function takes the accumulated data and returns it with something added. `{**d, "facts": ...}` builds a new dictionary, leaving the original untouched, so each stage's input can be inspected afterwards.
- **`gates` maps a stage name to a check.** A gate returns a list of problems, and an empty list means pass. Returning the problems, and not just true or false, tells the person what to fix.
- **The pipeline halts at the first failed gate.** It returns the stage, the problems, and the data so far. Nothing downstream runs on a faulty input.
- **The draft stage contains a planted error.** It writes 4,800 subscribers where the research found 4,200. With the gate in place, the run halts at the draft stage and names the discrepancy. Without gates, the second call reports "done", and the wrong figure goes out. The model did the same thing in both runs. The process was different.
- **The gate checks against verified facts.** This is the general design: carry the checked facts forward as data, and test later stages against them.

The arithmetic from Section 2, and a release checklist:

```python
def p_clean(error_rates, catch_rates=None):
    """Probability that no error survives. A gate with catch rate c cuts a stage's error to e * (1 - c)."""
    catch_rates = catch_rates or [0.0] * len(error_rates)
    result = 1.0
    for e, c in zip(error_rates, catch_rates):
        result *= 1 - e * (1 - c)
    return result

def release_check(checks, results):
    """checks: list of (name, required). Returns (ok, failed required check names)."""
    failed = [name for name, required in checks if required and not results.get(name)]
    return (not failed, failed)

rates = [0.05] * 4
print(f"no gates: {p_clean(rates):.3f}   gates catching 70%: {p_clean(rates, [0.7] * 4):.3f}")

CHECKS = [("figures traced to a source", True), ("names and dates checked", True),
          ("nothing confidential", True), ("read by a named person", True), ("spell-checked", False)]
print(release_check(CHECKS, {"figures traced to a source": True, "names and dates checked": True,
                             "nothing confidential": True}))
```

- **`p_clean` multiplies the survival probabilities.** With no gates it gives 0.815. With gates catching 70 percent it gives 0.941. The function treats errors as independent, so the order of the gates does not change its result. Section 2 explains why the strongest gate belongs earliest. That effect comes from contamination, which this function does not model.
- **`release_check` separates required from optional.** A missing spell-check does not block release. A missing human read does. The function returns the failed items so that the answer to "why can't I send this?" is specific.
- **An unanswered check counts as failed.** `results.get(name)` returns `None` for a check nobody performed, which is treated as not passed. A checklist item that was skipped must not be assumed done.

Finally, the decision about whether to use AI at all, as a rule that can be read and argued with:

```python
def suitability(task):
    """stakes and verifiability are rated 1 (low) to 5 (high)."""
    if task.get("learning_is_the_point") or task.get("unapproved_confidential_data"):
        return "do not use AI"
    if task["stakes"] >= 4 and task["verifiability"] <= 2:
        return "do not use AI"
    if task["stakes"] >= 3 or task["verifiability"] <= 3:
        return "use AI with review"
    return "use AI"

for name, task in [("brainstorm taglines", {"stakes": 1, "verifiability": 5}),
                   ("client proposal", {"stakes": 4, "verifiability": 4}),
                   ("legal opinion I cannot check", {"stakes": 5, "verifiability": 1}),
                   ("my exam revision essay", {"stakes": 2, "verifiability": 4, "learning_is_the_point": True})]:
    print(f"{name:>30}: {suitability(task)}")
```

The hard stops come first: learning, and confidential data in an unapproved tool, rule AI out whatever the scores. Then the dangerous quadrant, high stakes with output you cannot check. Everything else is a question of how much review. Writing the rule as code forces the vague phrase "use your judgement" into something a team can agree on and apply the same way.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**One giant prompt is the root of most disappointment.** Asking for a finished deliverable in one step produces the average of everything, with errors you cannot locate. Break the job into stages and look at each output.

**Do the research before the writing.** A draft written without verified facts invents plausible ones, and they are very hard to remove later because the prose has been built around them. Collect and check the facts first, then tell the model to write only from them.

**Review in a fresh chat.** A conversation that wrote a draft tends to approve of it. Start a new chat, give it only the draft and the criteria, and ask what is wrong. The same model that wrote a flawed piece will often find the flaw when it comes to the text cold.

**The same model misses its own mistakes.** Self-review catches style and structure problems well and factual errors poorly, because the model's wrong belief is the same in both passes. Facts need an outside source: a document, a search, or you.

**Polish is not evidence.** Well-formatted output with confident headings triggers trust. It is the cheapest thing a model produces. Judge the content, and be most careful when the piece looks finished.

**Do not forward what you have not read.** Sending unread AI output to a colleague or client transfers your work to them and spends your reputation. If you would not sign it, do not send it.

**Checklists fail when they become theatre.** A list ticked without checking is worse than no list, because it creates false confidence. Keep the list short enough to be done properly every time: five real checks beat twenty ignored ones.

**Long projects drift.** Over many turns, earlier decisions fall out of context or get quietly contradicted. Keep the brief and the verified facts in a file or project, and restate them at the start of each stage.

**Keep your own copies of the intermediate products.** The research notes, the brief, and the verified figures are the valuable assets. Save them outside the chat, so the work survives a lost conversation and can be rerun with a different tool.

**Know your mode.** Some people divide work cleanly, handing specific sub-tasks to the AI and doing the rest themselves. Others work back and forth with it continuously. Both work. What does not work is drifting into the second mode on a task that sits outside the tool's competence, where its fluency carries you past the point where you should have stopped trusting it.

**The skill that lasts is judgement.** Features and models will change within months of your reading this. Breaking work into stages, checking at the handoffs, verifying in proportion to the stakes, and knowing when to do it yourself will apply to whatever replaces them.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Reliable AI-assisted work is a line of stages, each doing one job, with a check at every handoff and a person accountable at the end. Prompt chaining breaks a task into steps with checks between them, and the evaluator-optimiser loop drafts, critiques against written criteria, and revises. Because each stage can introduce an error, the chance of a clean result is the product of the stages' success rates, and even imperfect gates raise it sharply. Checklists make gates dependable, as they did in surgery. Skipping the gates produces workslop, which moves the cost of checking to the recipient. The decision to use AI at all rests on two questions, what an error costs and how easily it can be detected, with hard stops for learning and for confidential data in unapproved tools. Features will change. This way of working will not.

"""
Lab solution: Build a Workflow with Quality Gates
Standard library only.

A STAGE is a function that takes a dict of data and returns a new dict with something added.
A GATE is a function that takes the data and returns a list of problems (empty = pass).
"""
import random


def research(d):
    """Stage: gather verified facts."""
    return {**d, "facts": {"subscribers": 4200, "open_rate": 0.31}}


def brief(d):
    """Stage: decide what to say."""
    return {**d, "brief": "Lead with subscriber growth; keep it under 150 words."}


def draft(d):
    """Stage: write the text. It contains a WRONG figure on purpose."""
    return {**d, "draft": "We now have 4,800 subscribers and a 31% open rate."}


def facts_gate(d):
    """Gate: research must have produced facts."""
    return [] if d.get("facts") else ["no facts gathered"]


def draft_gate(d):
    """Gate: the draft must contain the verified subscriber figure."""
    expected = f"{d['facts']['subscribers']:,}"
    return [] if expected in d["draft"] else [f"draft does not contain the verified figure {expected}"]


STAGES = [("research", research), ("brief", brief), ("draft", draft)]


# ---------------------------------------------------------------- Step 1
def run_pipeline(stages, gates, data):
    """A kitchen line: each station does one job, and nothing moves on past a failed check.

    Halting returns the stage and the problems, so the person knows where to look and
    nothing downstream is built on a faulty input.
    """
    for name, stage in stages:
        data = stage(data)
        if name in gates:
            problems = gates[name](data)
            if problems:
                return {"status": "halted", "stage": name, "problems": problems, "data": data}
    return {"status": "done", "data": data}


# ---------------------------------------------------------------- Step 2
def p_clean(error_rates, catch_rates=None):
    """An error survives only if it occurs AND the gate misses it: e * (1 - c)."""
    if catch_rates is None:
        catch_rates = [0.0] * len(error_rates)
    result = 1.0
    for error, catch in zip(error_rates, catch_rates):
        result *= 1 - error * (1 - catch)
    return result


# ---------------------------------------------------------------- Step 3
def simulate(error_rates, catch_rates, trials, seed):
    """Monte Carlo check of the formula. Seeded, so the experiment is repeatable."""
    rng = random.Random(seed)
    clean = 0
    for _ in range(trials):
        survived = False
        for error, catch in zip(error_rates, catch_rates):
            if rng.random() < error:                 # an error occurred at this stage
                if not rng.random() < catch:         # and the gate missed it
                    survived = True
        if not survived:
            clean += 1
    return clean / trials


# ---------------------------------------------------------------- Step 4
def release_check(checks, results):
    """A check nobody performed counts as failed. Optional checks never block release."""
    failed = [name for name, required in checks if required and not results.get(name)]
    return (not failed, failed)


# ---------------------------------------------------------------- Step 5
def suitability(task):
    """Two questions decide it: what does an error cost, and how easily can it be detected?

    Hard stops first, then the dangerous quadrant (high stakes, cannot check), then
    how much review everything else needs.
    """
    if task.get("learning_is_the_point") or task.get("unapproved_confidential_data"):
        return "do not use AI"
    if task["stakes"] >= 4 and task["verifiability"] <= 2:
        return "do not use AI"
    if task["stakes"] >= 3 or task["verifiability"] <= 3:
        return "use AI with review"
    return "use AI"
