# Deployment

**Deployment** is getting your code from your machine to a server where users can reach it, at your own domain, over HTTPS, with configuration and secrets in place, and in a way you can repeat safely every time the code changes. AI tools can generate deployment configuration in seconds, but deployment is where small misunderstandings, a secret committed, a DNS record wrong, a database migration that cannot be undone, turn into outages. Module 8.13 covered the special needs of agents in production; this module covers deploying ordinary web sites and applications, the kind built in Modules 9.7 and 9.8.

## 1. First-Principles Mental Model & Intuition

### Opening a shop on a high street

Moving from a workshop at home to a shop on the high street involves choosing **premises**, a stall, a rented unit, or your own building; putting up a **sign** with the right address, so people can find you; getting a **licence** that customers can check, so they trust you; arranging **supplies** that differ from home, the business bank account rather than your personal one; and a routine for **restocking** without closing the shop, with a way to put the old stock back if the new delivery is faulty.

In deployment terms: the **hosting target**, the **domain and DNS**, the **HTTPS certificate**, **configuration and secrets** per environment, and **continuous deployment with rollback**.

```text
   git push to main
        |
   CI/CD pipeline:  build -> test -> deploy to staging -> smoke test -> deploy to production
        |                (stop at the first failure; production only from main)
        v
   HOSTING TARGET:  static host | serverless functions | container platform | VPS
        |     config: defaults < .env file (local only) < environment variables set on the host
        |     secrets: environment variables / secret store, never in Git, masked in logs
        v
   DOMAIN + DNS:    toolshop.example  A -> 203.0.113.10      www  CNAME -> toolshop.example
   HTTPS:           certificate valid (Let's Encrypt: 90 days, auto-renewed), HSTS
        |
   ROLLBACK:        redeploy the last healthy version; beware irreversible database migrations
```

### Repeatable beats heroic

A deployment done by hand, at night, from someone's laptop, following steps remembered rather than written down, works until it does not. The aim of this module is a deployment that is boring: automated, identical every time, verified at each step, and reversible.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Deployment targets

| Target | What you get | Fits | Watch out for |
|---|---|---|---|
| **Static host** | Files served from a global network | Websites without server code, Module 9.7 | No backend; forms need a service |
| **Serverless** | Functions run per request, scale automatically | APIs with variable traffic | Time limits, cold starts, no local state |
| **Container platform** | Your app in a container, kept running | Apps with long-running processes, websockets, workers | More configuration; paying while idle |
| **VPS** | A virtual machine you control completely | Custom software, root access, fixed-cost hosting | You patch, secure, back up, and monitor it |

The rule of thumb is to choose the **least** control that meets your needs: a static host if there is no server code, serverless or a platform for typical apps, and a VPS only when you need control and are prepared to operate it. Tools that install platform features onto your own VPS narrow the gap, but the operating responsibility remains yours.

### Configuration and secrets

The Twelve-Factor App methodology recommends storing configuration, everything that varies between deployments such as database addresses and API keys, in **environment variables**, strictly separated from code. A common layering, from lowest to highest precedence:

$$\text{config} = \text{defaults} \;\oplus\; \text{.env file} \;\oplus\; \text{environment variables}$$

where each layer overrides the ones before it. The `.env` file is a convenience for local development and must be in `.gitignore`, Module 9.10; on the server, the host's environment variables or secret store provide the real values. Two practices prevent most incidents: **fail fast** when a required setting is missing, at start-up rather than at the first customer's request, and **never print secrets**: logs and error pages should show at most the last few characters.

### Domains and DNS

The **Domain Name System** maps names to addresses. The records you will meet:

| Record | Maps | Example |
|---|---|---|
| A / AAAA | Name to an IPv4 / IPv6 address | `toolshop.example` to `203.0.113.10` |
| CNAME | Name to another name, an alias | `www.toolshop.example` to `toolshop.example` |
| TXT | Name to text, often for verification | `verify=abc` |
| ALIAS or ANAME | Provider-specific: CNAME-like behaviour at the apex | `toolshop.example` to a host name |

One rule causes endless confusion: a **CNAME cannot coexist with other records for the same name**, a restriction from the DNS specification, RFC 1034. The bare domain, the **apex**, always has other records, at least the name-server and start-of-authority records, so it **cannot be a CNAME**. Point the apex at an IP address with A or AAAA records, or use your DNS provider's ALIAS feature, and use a CNAME for `www`. DNS changes take time to propagate, governed by each record's time-to-live.

### HTTPS and certificates

HTTPS encrypts traffic and proves the site's identity with a **certificate** issued by a certificate authority. Let's Encrypt's default certificates, at the time of writing, are valid for **90 days**, designed to be renewed automatically; most hosts do this for you. Certificate lifetimes across the industry are shrinking: the CA/Browser Forum's ballot SC-081 sets a schedule that reduces the maximum validity from 398 days to **47 days** by March 2029. Manual renewal is therefore not a viable plan; automate it, and monitor expiry, renewing well before the end, for example with 30 days left:

$$\text{days left} = \text{expiry} - \text{today}, \qquad \text{renew if } \text{days left} \le 30$$

The **Strict-Transport-Security** header, HSTS, tells browsers to use HTTPS for your domain in future, preventing downgrade to unencrypted HTTP.

### Continuous deployment

A **pipeline**, run by a service such as GitHub Actions, turns a push into a deployment through a fixed sequence of stages: build, run tests, deploy to a **staging** environment, run **smoke tests** against staging, then deploy to production. Two rules make it safe: **stop at the first failure**, so broken code never reaches production, and **deploy production only from the main branch**, which, with Module 9.10's protected branches, means only reviewed, tested code. If $p_i$ is the probability that stage $i$ catches a given kind of defect, the chance it slips through all $k$ independent stages is

$$\prod_{i=1}^{k} (1 - p_i)$$

so several modest checks in a row are far stronger than one; two stages each catching 70 percent let only 9 percent through.

### Rollback

When a deployment goes wrong, the fastest fix is usually to **roll back**: redeploy the last version that was known to be **healthy**, then investigate calmly, Module 9.9. Most platforms keep previous deployments for instant rollback. The dangerous exception is the **database**: if a newer version ran an **irreversible migration**, such as dropping a column, the old code may not work against the new schema. Safe practice is to make migrations backward-compatible, adding before removing, in separate releases, and to check for irreversible migrations before rolling back across them, Module 9.6's lesson that code and data roll back differently.

### Complexity

Choosing a target is constant. Loading configuration is linear in settings. DNS checks are linear in records. Certificate checks are constant. A pipeline runs at most its number of stages. Finding a rollback target is linear in deployments.

def choose_target(app):
    if not app["server_code"]:
        return "static host", "files only; cheapest and fastest"
    if app["needs_root"] or app["custom_software"]:

    if app["long_running"]:

BASE = {"server_code": True, "needs_root": False, "custom_software": False, "long_running": False}
print(choose_target({**BASE, "server_code": False}), choose_target(BASE))
print(choose_target({**BASE, "long_running": True}), choose_target({**BASE, "custom_software": True}))

- **The portfolio site from Module 9.7 has no server code: static host.**
- **The lead tracker's API with uneven traffic: serverless.**
- **A live pipeline board pushing updates over websockets: container platform.**
- **An app needing a custom PDF renderer installed on the machine: VPS.** And with it, the job of patching and backing it up.

Next, layered configuration.

```python
def parse_env(text):
    values = {}
    for line in text.splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, value = line.split("=", 1)
        value = value.strip()
        if len(value) >= 2 and value[0] == value[-1] and value[0] in "\"'":
            value = value[1:-1]
        values[key.strip()] = value
    return values

def load_config(defaults, env_file, environ, required, secret_suffixes=("_KEY", "_SECRET", "_PASSWORD", "_TOKEN")):
    config = {**defaults, **parse_env(env_file), **environ}
    missing = [k for k in required if not config.get(k)]
    shown = {k: ("****" + v[-4:] if len(v) > 4 else "****") if k.endswith(secret_suffixes) else v
             for k, v in sorted(config.items())}
    return config, missing, shown

ENV_FILE = '# local settings\nDATABASE_URL=postgres://localhost/shop\nSTRIPE_KEY="sk_test_51abcd1234"\nDEBUG=true\n'
config, missing, shown = load_config({"DEBUG": "false", "PORT": "8000"}, ENV_FILE,
                                     {"DEBUG": "false", "DATABASE_URL": "postgres://prod-db/shop"},
                                     ["DATABASE_URL", "STRIPE_KEY", "SENTRY_DSN"])
print(missing)
print(shown)
```

- **Comments, blank lines, and quotes in the `.env` file are handled.**
- **Environment variables override the file, which overrides defaults.** Production's database address wins over the local one; DEBUG ends up false.
- **SENTRY_DSN is required and missing.** The app should refuse to start, not fail later.
- **The Stripe key is shown as `****1234`.** Logs can confirm which key is loaded without exposing it.
- **The key that loaded is a test key.** Module 9.6's environment check would flag that for production.

Then, DNS records and certificate expiry.

```python
def dns_check(records, apex):
    issues = []
    for name, rtype, value in records:
        if name == apex and rtype == "CNAME":
            issues.append(f"CNAME at apex {apex} is not allowed; use A/AAAA or ALIAS")
    for name in sorted({n for n, t, v in records if t == "CNAME"}):
        others = sorted({t for n, t, v in records if n == name and t != "CNAME"})
        if others:
            issues.append(f"{name} has a CNAME and {', '.join(others)} records")
    if not any(n == apex and t in ("A", "AAAA", "ALIAS") for n, t, v in records):
        issues.append(f"{apex} has no address record")
    if not any(n == "www." + apex for n, t, v in records):
        issues.append(f"www.{apex} is not configured")
    return issues

def cert_status(expiry_day, today, renew_at=30):
    left = expiry_day - today
    if left < 0:
        return "expired", left
    return ("renew now" if left <= renew_at else "ok"), left

GOOD = [("toolshop.example", "A", "203.0.113.10"), ("www.toolshop.example", "CNAME", "toolshop.example"),
        ("toolshop.example", "TXT", "verify=abc")]
BAD = [("toolshop.example", "CNAME", "host.example.net"), ("www.toolshop.example", "CNAME", "host.example.net"),
       ("www.toolshop.example", "TXT", "x")]
print(dns_check(GOOD, "toolshop.example"))
print(dns_check(BAD, "toolshop.example"))
print(cert_status(90, 10), cert_status(90, 65), cert_status(90, 91))
```

- **The good setup has an A record at the apex and a CNAME for www.** TXT at the apex is fine alongside an A record.
- **The bad setup puts a CNAME at the apex,** the classic mistake when a host's instructions say "add a CNAME".
- **www has both a CNAME and a TXT record, which is not allowed.**
- **With the apex CNAME removed, there is no address record at all.**
- **A certificate expiring on day 90 is fine on day 10, 80 days left, due for renewal on day 65, 25 left, renewal starting at 30 left, and expired on day 91.**

Then, the pipeline.

```python
STAGES = ["build", "test", "deploy_staging", "smoke_test", "deploy_production"]

def run_pipeline(results, branch):
    log = []
    for stage in STAGES:
        if stage == "deploy_production" and branch != "main":
            log.append((stage, "skipped: not main"))
            return "stopped", log
        ok = results.get(stage, False)
        log.append((stage, "ok" if ok else "failed"))
        if not ok:
            return "failed at " + stage, log
    return "deployed", log

ALL_OK = {stage: True for stage in STAGES}
print(run_pipeline({**ALL_OK, "smoke_test": False}, "main"))
print(run_pipeline(ALL_OK, "feature/csv-export"))
```

- **Stages run in order and the pipeline stops at the first failure.** A failing smoke test on staging means production is never touched.
- **A feature branch goes through staging but not production.** Production comes only from main.
- **Missing results count as failures.** A stage that did not report did not pass.

Finally, choosing a rollback target.

```python
def rollback_target(deploys, current):
    index = next(i for i, d in enumerate(deploys) if d["id"] == current)
    for candidate in reversed(deploys[:index]):
        if candidate["healthy"]:
            crossed = deploys[deploys.index(candidate) + 1: index + 1]
            blocked = [d["id"] for d in crossed if d.get("irreversible_migration")]
            return candidate["id"], (["irreversible migration in " + ", ".join(blocked)] if blocked else [])
    return None, ["no healthy earlier deploy"]

DEPLOYS = [{"id": "v1", "healthy": True}, {"id": "v2", "healthy": True}, {"id": "v3", "healthy": False},
           {"id": "v4", "healthy": False, "irreversible_migration": True}]
print(rollback_target(DEPLOYS, "v4"))
print(rollback_target(DEPLOYS, "v2"))
```

- **From v4, the last healthy version is v2.** v3 was also bad.
- **But v4 ran an irreversible migration.** Rolling the code back to v2 may break against the new schema; check before rolling back, or roll forward with a fix.
- **From v2, the target is v1, with no warnings.**

**Complexity.** `choose_target` and `cert_status` are constant. `load_config` is linear in settings. `dns_check` is linear in records times CNAME names. `run_pipeline` is linear in stages. `rollback_target` is linear in deployments.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Deploying from a laptop.** Manual steps differ every time. Automate through a pipeline.

**Secrets in the repository.** Configuration files with real keys end up in Git. Use environment variables.

**`.env` files on the server by copy and paste.** They drift and leak. Use the host's secret settings.

**Missing settings discovered by customers.** The app starts and fails on the first request. Fail fast at start-up.

**Secrets in logs.** Error pages and logs print configuration. Mask them.

**CNAME at the apex.** Not allowed by the DNS rules. Use A records or ALIAS.

**Impatient DNS changes.** Records take time to propagate. Lower the TTL before a planned move.

**Expired certificates.** A forgotten renewal takes the site down with a scary warning. Automate and monitor.

**Deploying without staging.** Production becomes the test environment. Use staging and smoke tests.

**Deploying feature branches to production.** Unreviewed code goes live. Production from main only.

**Destructive migrations shipped with code.** Rollback breaks. Add first, remove later, separately.

**Choosing a VPS for control you do not need.** You become the operations team. Choose the least control that works.

**Question 1.** A host's setup guide says "add a CNAME record pointing your domain to app.hostname.net". The owner adds a CNAME for `toolshop.example`, and email stops working. Explain using `dns_check` and the DNS rules, and give the correct configuration.

<details>
<summary>View Answer</summary>

A CNAME record cannot coexist with any other record for the same name, a rule from the DNS specification, RFC 1034. The bare domain, the apex, always has other records, such as its name-server and start-of-authority records, and usually MX records for email and TXT records for verification. Adding a CNAME at the apex breaks those rules; depending on the DNS provider, it is rejected, or it is accepted and other records for the apex stop being served, which is why email stopped working. `dns_check` reports "CNAME at apex toolshop.example is not allowed; use A/AAAA or ALIAS", and, once the CNAME is removed, "toolshop.example has no address record". The correct configuration points the apex at the host with A, and AAAA if offered, records using the IP addresses the host publishes, or uses the DNS provider's ALIAS or ANAME feature, which behaves like a CNAME but resolves to addresses; keeps the MX and TXT records at the apex; and uses a CNAME only for `www.toolshop.example`, pointing to the host name or to the apex, with no other records on `www`. Host guides that say "CNAME your domain" usually mean a subdomain such as www.

</details>

**Question 2.** On launch day the lead tracker starts, then fails with an error the first time anyone tries to report a bug, and the error page shows the full Stripe key. Use `load_config` to explain both problems and how to prevent them.

<details>
<summary>View Answer</summary>

The application read SENTRY_DSN, the error-reporting setting, only when an error occurred, so a missing value went unnoticed until the first error, the worst possible moment. `load_config` returns the list of missing required settings, here SENTRY_DSN, so the application can refuse to start, failing fast during deployment, where the pipeline's smoke test catches it, instead of in front of users. The error page printed the raw configuration, exposing the Stripe key to whoever triggered the error, and possibly to logs and monitoring tools. `load_config`'s masked view shows keys ending in _KEY, _SECRET, _PASSWORD, or _TOKEN as asterisks plus the last four characters, `****1234`, which is enough to confirm which key is loaded without revealing it. Prevention: declare required settings and check them at start-up; print only the masked view in logs and never on error pages, which in production should be generic; set real values in the host's environment or secret store rather than copying `.env` files; and, because the key was exposed, rotate it immediately. The masked value also shows a test key was loaded, which production should not use.

</details>

**Question 3.** Version v4 of the lead tracker is failing in production; v3 was also unhealthy and v2 was fine, but v4 dropped the old `stage_name` column. Use `rollback_target` to decide what to do.

<details>
<summary>View Answer</summary>

`rollback_target` from v4 skips v3, which was unhealthy, and returns v2 as the last healthy version, with the warning "irreversible migration in v4". Redeploying v2's code is fast, but v2 expects the `stage_name` column that v4 dropped, so rolling back the code alone may produce a second outage on top of the first. Options, in order of preference: if the failure is small and understood, roll forward with a fix to v4 rather than back; if rolling back, first restore the dropped column, from a backup or the database's point-in-time recovery, Module 9.6, or by re-adding it and backfilling the data, and confirm v2 works against the result in staging; and if neither is quick, put the app into a maintenance state while restoring. The lasting lesson is migration discipline: make schema changes backward-compatible, adding the new column and writing to both in one release, switching reads in the next, and dropping the old column only in a later release once rollbacks past that point are no longer needed, so that any recent version can be rolled back to safely.

</details>

def parse_env(text):
    """Given: KEY=VALUE lines; skips blanks and comments; strips matching quotes."""
    values = {}
    for line in text.splitlines():
        line = line.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        key, value = line.split("=", 1)
        value = value.strip()
        if len(value) >= 2 and value[0] == value[-1] and value[0] in "\"'":
            value = value[1:-1]
        values[key.strip()] = value
    return values


# ---------------------------------------------------------------- Step 1
def choose_target(app):
    """The least control that meets the need."""
    if not app["server_code"]:
        return "static host", "files only; cheapest and fastest"
    if app["needs_root"] or app["custom_software"]:
        return "VPS", "full control of the machine"
    if app["long_running"]:
        return "container platform", "always-on processes and websockets"
    return "serverless", "short requests that scale with traffic"


# ---------------------------------------------------------------- Step 2
def load_config(defaults, env_file, environ, required, secret_suffixes=("_KEY", "_SECRET", "_PASSWORD", "_TOKEN")):
    """Layered config, fail fast on missing settings, never show secrets."""
    config = {**defaults, **parse_env(env_file), **environ}
    missing = [k for k in required if not config.get(k)]
    shown = {k: ("****" + v[-4:] if len(v) > 4 else "****") if k.endswith(secret_suffixes) else v
             for k, v in sorted(config.items())}
    return config, missing, shown


# ---------------------------------------------------------------- Step 3
def dns_check(records, apex):
    """No CNAME at the apex, no CNAME sharing a name, an address for the apex, a www record."""
    issues = []
    for name, rtype, value in records:
        if name == apex and rtype == "CNAME":
            issues.append(f"CNAME at apex {apex} is not allowed; use A/AAAA or ALIAS")
    for name in sorted({n for n, t, v in records if t == "CNAME"}):
        others = sorted({t for n, t, v in records if n == name and t != "CNAME"})
        if others:
            issues.append(f"{name} has a CNAME and {', '.join(others)} records")
    if not any(n == apex and t in ("A", "AAAA", "ALIAS") for n, t, v in records):
        issues.append(f"{apex} has no address record")
    if not any(n == "www." + apex for n, t, v in records):
        issues.append(f"www.{apex} is not configured")
    return issues


def cert_status(expiry_day, today, renew_at=30):
    """Renew well before expiry; certificates are getting shorter."""
    left = expiry_day - today
    if left < 0:
        return "expired", left
    return ("renew now" if left <= renew_at else "ok"), left


# ---------------------------------------------------------------- Step 4
def run_pipeline(results, branch):
    """Stop at the first failure; production only from main."""
    log = []
    for stage in STAGES:
        if stage == "deploy_production" and branch != "main":
            log.append((stage, "skipped: not main"))
            return "stopped", log
        ok = results.get(stage, False)
        log.append((stage, "ok" if ok else "failed"))
        if not ok:
            return "failed at " + stage, log
    return "deployed", log


# ---------------------------------------------------------------- Step 5
def rollback_target(deploys, current):
    """Last healthy version, with a warning about migrations you would cross."""
    index = next(i for i, d in enumerate(deploys) if d["id"] == current)
    for candidate in reversed(deploys[:index]):
        if candidate["healthy"]:
            crossed = deploys[deploys.index(candidate) + 1: index + 1]
            blocked = [d["id"] for d in crossed if d.get("irreversible_migration")]
            return candidate["id"], (["irreversible migration in " + ", ".join(blocked)] if blocked else [])
    return None, ["no healthy earlier deploy"]
