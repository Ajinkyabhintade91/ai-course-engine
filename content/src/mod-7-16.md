# Project 1: Automated Email Assistant

This is the first of six projects that bring Unit 7 together. Each one takes a common business need and builds it properly: requirements first, then an architecture, then the pieces, then testing and monitoring. The skills come from earlier modules; the projects show how they combine.

The first project is an **AI email assistant** for a support inbox. It reads incoming mail, classifies it, labels it, drafts replies for routine questions, sends the hard ones to a person, and lets a person approve every draft before it goes out. Module 7.11 covered the Gmail mechanics, scopes, quotas, parsing, threading, and a send gate. This project adds what makes the assistant trustworthy: validated model output, explicit routing rules, an evaluation set, a review loop that measures quality, and a cost model.

## 1. First-Principles Mental Model & Intuition

### A new support hire on probation

Think of the assistant as a capable new hire in their first month. They read every email, sort it into the right pile, and write draft replies, but a senior colleague checks each draft before it is sent. The senior colleague keeps notes: how many drafts were fine as written, how many needed small edits, how many were thrown away. After a month, those notes decide whether the new hire may send some routine replies alone.

The assistant is built on exactly that arrangement.

```text
   NEW EMAIL
      |
      v
   PARSE           plain text of today's message only                      (Module 7.11)
      |
      v
   CLASSIFY        small model -> JSON {category, urgency, confidence}
      |            validate; anything invalid -> needs_review
      v
   ROUTE           rules table: category -> actions
      |
      +--> label --> draft (larger model, in the thread) --> REVIEW QUEUE --> approve / edit / reject --> send
      |
      +--> escalate to a person (complaints, low confidence, invalid output)
      |
      +--> archive (spam)
      |
      v
   MEASURE         accuracy on a labelled set; approval and edit rates; cost per email
```

### Requirements before code

Every project in this unit starts with a short requirements list. For the assistant:

| Requirement | Decision |
|---|---|
| Which emails? | The support address only, excluding promotions and auto-replies |
| Which categories? | Order status, refund, product question, complaint, spam |
| What happens to each? | A rules table, below |
| Who approves replies? | The support team, in a review queue |
| What must never happen? | A reply sent without approval; a complaint answered by a draft |
| How is quality measured? | Classifier accuracy on 200 labelled emails; reviewer approval rate |
| What may it cost? | Under USD 25 a month in model fees for 3,000 emails |

Writing these down first prevents the commonest project failure: building something impressive that does the wrong thing.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Architecture: a workflow, not an agent

Anthropic's guide "Building effective agents" distinguishes **workflows**, where code decides the sequence of steps and the model fills in particular steps, from **agents**, where the model decides what to do next. It recommends starting with the simplest arrangement that works. An email assistant is a natural workflow: its steps are known in advance, so the model classifies and drafts while ordinary code decides what happens. The guide names this shape **routing**: classify an input, then send it down a specialised path. It also describes **human checkpoints**, points where the system pauses for a person's judgement, which is what the review queue is.

Keeping the routing in code, not in a prompt, has three benefits. The rules are visible and testable. Changing a rule does not require re-testing a prompt. And the model can never decide on its own to send something that the rules forbid.

### Two models, two jobs

Classification and drafting have different needs. Classification produces a few tokens from a fixed list, and small models usually do it well and cheaply. Drafting produces a paragraph in the company's voice, where quality matters more. Using a small model for the first and a larger one for the second, only for emails that need a draft, is the main cost lever, as the lab's last step shows.

### Validated structured output

The classifier is asked to reply with JSON only:

```text
   {"category": "refund", "urgency": "high", "confidence": 0.92}
```

Models usually comply, but not always: they may add a sentence before the JSON, invent a category, or write "high" where a number belongs. Many APIs now offer **structured outputs**, constraining the model's response to a JSON schema, which removes most of these problems; Module 5.10 covered the techniques. Either way, the workflow must validate what comes back, and the rule is simple: **anything that does not validate becomes "needs review"**, routed to a person. An invalid classification must never be treated as a valid one, and must never stop the workflow.

| Check | If it fails |
|---|---|
| The text parses as JSON | needs_review |
| `category` is one of the allowed labels | needs_review |
| `urgency` is low, normal, or high | default to normal |
| `confidence` is a number from 0 to 1 | treat as 0, which routes to a person |

### Routing rules

| Category | Actions |
|---|---|
| order_status | label, draft |
| product_question | label, draft |
| refund | label, draft, notify finance |
| complaint | label, escalate |
| spam | archive |
| needs_review | label, escalate |

Two overrides apply on top of the table. If the classifier's confidence is below a threshold, a category that would be drafted is escalated instead. If urgency is high, someone on call is notified, unless the email is already being escalated. The rules encode business judgement, "complaints always go to a person", and keep it out of the model's hands.

### Evaluating the classifier

Before trusting the classifier, test it on a **labelled sample**: a few hundred real emails, each labelled by a person with the correct category. Run the classifier on them and compare. Module 5.9 described this evaluation loop for prompts; here it is applied to a whole step.

**Accuracy**, the share of emails classified correctly, is the headline number but hides what matters. A **confusion matrix** shows, for each true category, which categories the classifier predicted:

```text
                     predicted:  order_status   refund   complaint
   true order_status                  9            1          0
   true refund                        0            5          1
   true complaint                     0            2          2
```

From it, two measures per category, as Google's Machine Learning Crash Course defines them:

$$\text{precision} = \frac{\text{correctly predicted as this class}}{\text{all predicted as this class}} \qquad \text{recall} = \frac{\text{correctly predicted as this class}}{\text{all truly in this class}}$$

In the matrix above, accuracy is 16 of 20, 0.8. But complaint recall is only 2 of 4, 0.5: half the complaints were classified as refunds. Under the routing rules, a complaint classified as a refund gets a draft reply instead of a person, which is exactly what the requirements said must never happen. The errors that matter most are not the commonest ones but the ones with the worst consequences, and a confusion matrix shows them. The fix here might be clearer category definitions in the prompt, examples of complaints that mention refunds, or a rule that escalates any refund email expressing anger.

### The review queue and its measures

Every draft goes to a queue where a person approves it as written, edits it, or rejects it. Those decisions are the best quality data the project will ever have:

| Measure | Meaning |
|---|---|
| Approval rate | Share of drafts sent unchanged |
| Edit rate | Share of drafts changed before sending |
| Mean edit share | For edited drafts, the fraction of characters changed |
| Rejection rate | Share of drafts thrown away |

A rising approval rate with small edits suggests the drafts are good; frequent large edits suggest the prompt, the context, or the model needs work. Looking at approval rates per category is how a team decides, with evidence, that one category, perhaps order status, could be sent automatically through the send gate of Module 7.11, while others stay under review.

### Cost

With $N$ emails a month, a classifier cost $c_{\text{class}}$ per email, a drafting cost $c_{\text{draft}}$ per draft, and a share $d$ of emails needing drafts:

$$\text{monthly cost} = N \, c_{\text{class}} + N \, d \, c_{\text{draft}}$$

Each per-call cost comes from Module 7.10's formula, tokens times rates. For 3,000 emails, a small classifier at about 700 input and 60 output tokens, and a mid-sized drafter at about 1,500 input and 350 output tokens for 60 percent of emails, the bill at the rates used in Module 7.10 is about USD 12 a month, comfortably within the requirement. The lab computes it, and shows how much more it costs to classify with the larger model or to draft for everything.

### Monitoring in production

| Signal | Why |
|---|---|
| Share of emails classified needs_review | A rise means the model or the emails changed |
| Category mix per week | A sudden spike in complaints is a business signal, not just a technical one |
| Approval and edit rates per category | Draft quality over time |
| Time from arrival to reply | The point of the whole project |
| Cost per email | Catches prompt growth or wrong model settings |
| Errors and dead letters | As Module 7.14 described |

### Complexity

Parsing, routing, and cost per email are constant time. Evaluation is linear in the size of the labelled set, with a matrix whose size is the square of the number of categories. Review statistics are linear in the number of decisions.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, validating the classifier's output.

```python
import json

LABELS = ["order_status", "refund", "product_question", "complaint", "spam"]

def parse_classification(text, labels=LABELS):
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return {"category": "needs_review", "urgency": "normal", "confidence": 0.0, "error": "not_json"}
    if not isinstance(data, dict) or data.get("category") not in labels:
        return {"category": "needs_review", "urgency": "normal", "confidence": 0.0, "error": "bad_category"}
    urgency = data.get("urgency") if data.get("urgency") in ("low", "normal", "high") else "normal"
    confidence = data.get("confidence")
    valid = isinstance(confidence, (int, float)) and not isinstance(confidence, bool) and 0 <= confidence <= 1
    return {"category": data["category"], "urgency": urgency, "confidence": float(confidence) if valid else 0.0, "error": None}

print(parse_classification('{"category": "refund", "urgency": "high", "confidence": 0.92}'))
print(parse_classification('Sure! Here is the JSON: {"category": "refund"}'))
print(parse_classification('{"category": "billing"}'))
print(parse_classification('{"category": "spam", "urgency": "urgent!!", "confidence": "high"}'))
```

- **Valid output passes through, tidied.** The confidence becomes a float and the error is None.
- **Text around the JSON fails to parse and becomes needs_review.** The workflow does not try to dig the JSON out of a chatty reply; with structured outputs this case largely disappears.
- **An invented category becomes needs_review.** "billing" is not one of the five labels.
- **Bad optional fields get safe defaults.** An unknown urgency becomes normal; a confidence that is not a number becomes 0, which will route the email to a person.
- **The `error` field records why.** Counting errors by kind is how you notice that a prompt change broke the output format.

Next, routing.

```python
RULES = {"order_status": ["label", "draft"], "product_question": ["label", "draft"],
         "refund": ["label", "draft", "notify_finance"], "complaint": ["label", "escalate"],
         "spam": ["archive"], "needs_review": ["label", "escalate"]}

def plan_actions(classification, threshold=0.75):
    actions = list(RULES[classification["category"]])
    if classification["category"] not in ("spam", "needs_review", "complaint") and classification["confidence"] < threshold:
        actions = ["label", "escalate"]
    if classification["urgency"] == "high" and "escalate" not in actions:
        actions.append("notify_on_call")
    return actions

print(plan_actions({"category": "refund", "urgency": "high", "confidence": 0.92}))
print(plan_actions({"category": "order_status", "urgency": "normal", "confidence": 0.5}))
print(plan_actions({"category": "spam", "urgency": "normal", "confidence": 0.3}))
```

- **The rules table gives the base actions.** A copy is taken, so the table itself is never modified.
- **Low confidence on a drafting category escalates instead.** The order-status email at 0.5 confidence goes to a person rather than getting a draft.
- **Spam is archived whatever the confidence.** Low confidence on spam is not worth a person's time; a weekly check of the archive catches mistakes.
- **High urgency adds an on-call notification.** The urgent refund is labelled, drafted, flagged to finance, and someone is told now.

Then, evaluation on a labelled sample.

```python
def evaluate(predicted, gold, labels):
    matrix = {truth: {guess: 0 for guess in labels} for truth in labels}
    for guess, truth in zip(predicted, gold):
        matrix[truth][guess] += 1
    correct = sum(matrix[label][label] for label in labels)
    per_class = {}
    for label in labels:
        hits = matrix[label][label]
        predicted_as = sum(matrix[truth][label] for truth in labels)
        actually = sum(matrix[label].values())
        per_class[label] = (round(hits / predicted_as, 2) if predicted_as else 0.0, round(hits / actually, 2) if actually else 0.0)
    return round(correct / len(gold), 3), per_class, matrix

CLASSES = ["order_status", "refund", "complaint"]
GOLD = ["order_status"] * 10 + ["refund"] * 6 + ["complaint"] * 4
PREDICTED = ["order_status"] * 9 + ["refund"] + ["refund"] * 5 + ["complaint"] + ["complaint"] * 2 + ["refund"] * 2
accuracy, per_class, matrix = evaluate(PREDICTED, GOLD, CLASSES)
print(accuracy, per_class)
print(matrix["complaint"])
```

- **The matrix counts, for each true class, how often each class was predicted.** Rows are the truth, columns the guesses.
- **Accuracy is 0.8.** Sixteen of twenty correct.
- **Each class gets precision and recall.** Order status: precision 1.0, recall 0.9. Refund: precision 0.62, five of eight predictions, and recall 0.83.
- **Complaint recall is 0.5.** The complaint row shows two complaints predicted as refunds, which under the routing rules would have received drafts. That is the error to fix first.
- **Zero divisions are guarded.** A class never predicted gets precision 0 instead of a crash.

Finally, review statistics and cost.

```python
def review_stats(decisions):
    total = len(decisions)
    counts = {kind: sum(1 for d in decisions if d["decision"] == kind) for kind in ("approved", "edited", "rejected")}
    edited = [d for d in decisions if d["decision"] == "edited"]
    mean_edit = round(sum(d["chars_changed"] / d["draft_chars"] for d in edited) / len(edited), 3) if edited else 0.0
    return {**{kind: round(count / total, 3) for kind, count in counts.items()}, "mean_edit_share": mean_edit}

DECISIONS = ([{"decision": "approved", "chars_changed": 0, "draft_chars": 400}] * 30
             + [{"decision": "edited", "chars_changed": 60, "draft_chars": 400}] * 12
             + [{"decision": "edited", "chars_changed": 200, "draft_chars": 400}] * 3
             + [{"decision": "rejected", "chars_changed": 0, "draft_chars": 400}] * 5)
print(review_stats(DECISIONS))

PRICES = {"haiku": (0.10, 0.50), "sonnet": (2.00, 10.00)}

def monthly_cost(emails, draft_share, classify=("haiku", 700, 60), draft=("sonnet", 1500, 350)):
    def per_call(spec):
        model, tokens_in, tokens_out = spec
        price_in, price_out = PRICES[model]
        return (tokens_in * price_in + tokens_out * price_out) / 1_000_000
    return round(emails * per_call(classify) + emails * draft_share * per_call(draft), 2)

print(monthly_cost(3000, 0.6), monthly_cost(3000, 0.6, classify=("sonnet", 700, 60)), monthly_cost(3000, 1.0))
```

- **Fifty decisions: 60 percent approved, 30 percent edited, 10 percent rejected.**
- **Edited drafts changed 22 percent of their characters on average.** Twelve small edits of 15 percent and three large ones of 50 percent. Small edits suggest good drafts; the large ones are worth reading to see what was wrong.
- **The model names stand for the current small and mid-sized models.** Their rates, USD 0.10 and 0.50, and USD 2 and 10, per million tokens, are those used in Module 7.10.
- **The planned design costs USD 12.00 a month.** USD 0.30 to classify 3,000 emails, and USD 11.70 to draft 1,800 replies.
- **Classifying with the larger model raises it to USD 17.70.** Twenty times the classification cost for little gain on a five-label task.
- **Drafting for every email raises it to USD 19.80.** Routing spam and complaints away from the drafter saves money as well as risk.

**Complexity.** `parse_classification` is linear in the text. `plan_actions` is constant. `evaluate` is linear in the sample plus the square of the number of classes. `review_stats` is linear in the decisions. `monthly_cost` is constant.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Letting the model choose the action.** "Decide whether to reply" in a prompt hands policy to the model. Keep routing in code.

**Trusting accuracy alone.** Eighty percent accuracy can hide a disastrous error type. Read the confusion matrix.

**Labelled sets that are too easy.** Clean, typical emails flatter the classifier. Include the messy ones: forwards, mixed languages, angry customers.

**Category definitions nobody wrote down.** If two team members label the same email differently, the model will too. Write definitions with examples.

**Drafts that invent facts.** A model asked "where is order A1234?" without order data will guess. Fetch facts with code and put them in the prompt.

**Auto-sending too soon.** Weeks of review data are what justify automation. Without them, it is a guess.

**No needs_review path.** If invalid output stops the workflow, one bad response blocks the queue. Route it to a person instead.

**Reviewers rubber-stamping.** A queue that is approved without reading gives false confidence. Spot-check approved drafts.

**Classifying the quoted history.** Earlier replies in the thread confuse the classifier. Parse out today's message.

**Ignoring urgency.** A high-urgency email sitting in a queue until morning defeats the purpose. Notify someone.

**One model for everything.** Using the largest model to classify spam is waste. Match model to task.

**No monitoring of category mix.** A surge of complaints after a product change is the most valuable thing the assistant can tell the business.

**Summary.** The email assistant is a routing workflow with a human checkpoint: code parses each email, a small model classifies it into a fixed set of categories as JSON, the workflow validates that output and sends anything invalid to "needs review", a rules table in code decides the actions for each category, with overrides for low confidence and high urgency, a larger model drafts replies only where the rules say so, and every draft waits in a review queue where a person approves, edits, or rejects it. Cost is the number of emails times the classification cost plus the drafted share times the drafting cost, about USD 12 a month for 3,000 emails in the worked design. In production, the needs-review share, category mix, review rates, response time, and cost per email are monitored.

"""
Lab solution: Parse, Route, Evaluate, Review, and Cost an Email Assistant
Standard library only. No network calls.
"""
import json

LABELS = ["order_status", "refund", "product_question", "complaint", "spam"]
RULES = {"order_status": ["label", "draft"], "product_question": ["label", "draft"],
         "refund": ["label", "draft", "notify_finance"], "complaint": ["label", "escalate"],
         "spam": ["archive"], "needs_review": ["label", "escalate"]}
PRICES = {"haiku": (0.10, 0.50), "sonnet": (2.00, 10.00)}


# ---------------------------------------------------------------- Step 1
def parse_classification(text, labels=LABELS):
    """Anything that does not validate goes to a person; it never stops the workflow and is
    never treated as a valid answer."""
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return {"category": "needs_review", "urgency": "normal", "confidence": 0.0, "error": "not_json"}
    if not isinstance(data, dict) or data.get("category") not in labels:
        return {"category": "needs_review", "urgency": "normal", "confidence": 0.0, "error": "bad_category"}
    urgency = data.get("urgency") if data.get("urgency") in ("low", "normal", "high") else "normal"
    confidence = data.get("confidence")
    valid = isinstance(confidence, (int, float)) and not isinstance(confidence, bool) and 0 <= confidence <= 1
    return {"category": data["category"], "urgency": urgency, "confidence": float(confidence) if valid else 0.0, "error": None}


# ---------------------------------------------------------------- Step 2
def plan_actions(classification, threshold=0.75):
    """Policy lives in code: complaints always reach a person, low confidence escalates,
    and urgency wakes someone up."""
    actions = list(RULES[classification["category"]])
    if classification["category"] not in ("spam", "needs_review", "complaint") and classification["confidence"] < threshold:
        actions = ["label", "escalate"]
    if classification["urgency"] == "high" and "escalate" not in actions:
        actions.append("notify_on_call")
    return actions


# ---------------------------------------------------------------- Step 3
def evaluate(predicted, gold, labels):
    """Accuracy hides which errors happen; the matrix and per-class recall show them."""
    matrix = {truth: {guess: 0 for guess in labels} for truth in labels}
    for guess, truth in zip(predicted, gold):
        matrix[truth][guess] += 1
    correct = sum(matrix[label][label] for label in labels)
    per_class = {}
    for label in labels:
        hits = matrix[label][label]
        predicted_as = sum(matrix[truth][label] for truth in labels)
        actually = sum(matrix[label].values())
        per_class[label] = (round(hits / predicted_as, 2) if predicted_as else 0.0, round(hits / actually, 2) if actually else 0.0)
    return round(correct / len(gold), 3), per_class, matrix


# ---------------------------------------------------------------- Step 4
def review_stats(decisions):
    """Reviewer decisions are the best quality data the project has."""
    total = len(decisions)
    counts = {kind: sum(1 for d in decisions if d["decision"] == kind) for kind in ("approved", "edited", "rejected")}
    edited = [d for d in decisions if d["decision"] == "edited"]
    mean_edit = round(sum(d["chars_changed"] / d["draft_chars"] for d in edited) / len(edited), 3) if edited else 0.0
    return {**{kind: round(count / total, 3) for kind, count in counts.items()}, "mean_edit_share": mean_edit}


# ---------------------------------------------------------------- Step 5
def monthly_cost(emails, draft_share, classify=("haiku", 700, 60), draft=("sonnet", 1500, 350)):
    """Small model for every email, larger model only for drafts."""
    def per_call(spec):
        model, tokens_in, tokens_out = spec
        price_in, price_out = PRICES[model]
        return (tokens_in * price_in + tokens_out * price_out) / 1_000_000
    return round(emails * per_call(classify) + emails * draft_share * per_call(draft), 2)
