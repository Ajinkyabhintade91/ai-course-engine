# Connecting Local Models to Applications

A model in a terminal is a demo; a model behind an API is a component. Ollama's server, Module 10.2, exposes the model over HTTP on `localhost:11434`, in its own **native API** and in **compatibility APIs** shaped like OpenAI's and Anthropic's. That means almost any application or library that talks to a hosted model can talk to a local one, often by changing one URL. This module covers the native and compatible endpoints, streaming, tool calling, structured outputs, calling local models from Python and JavaScript, and front ends and integrations, along with the small configuration mistakes that cause most integration failures.

Endpoint details are from Ollama's API documentation at the time of writing (November 2026). The lab runs offline: it parses recorded responses and uses a scripted stand-in for the model, so no server is needed.

## 1. First-Principles Mental Model & Intuition

### Adapters on a power socket

The Ollama server is a **power socket** in your workshop. Its native shape is its own, but it also accepts the **adapters** that popular appliances expect: an OpenAI-shaped plug and an Anthropic-shaped plug. An appliance built for a hosted service, a chat app, a coding agent, a library, works when you give it the right adapter and point it at the local socket instead of the one across town: change the **base URL**, give it any **key** because the socket does not check, and keep the **path** right, because an adapter in the wrong slot does not fit.

```text
 your app / library / agent
   |                                      |                                   |
   | native: POST /api/chat               | OpenAI-style: /v1/chat/completions | Anthropic-style: POST /v1/messages
   | base http://localhost:11434          | base http://localhost:11434/v1    | base http://localhost:11434
   | stream: NDJSON lines                 | stream: SSE "data:" lines, [DONE] | stream: SSE events
   v                                      v                                   v
 +-------------------------------- OLLAMA SERVER :11434 -----------------------------------+
 |  model (Module 10.2)   tools (function calling)   format (JSON schema)   think on/off  |
 +------------------------------------------------------------------------------------------+
 front ends: Open WebUI and others      agents: ollama launch (Claude Code, OpenCode, more)
```

### Three questions for any integration

Which API shape does the client speak? What base URL does it need for that shape? And does it need streaming, tools, or structured output? Answer those and most integrations are configuration, not code.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### The native API

The main endpoints are `POST /api/chat` for conversations, `POST /api/generate` for single prompts, and `POST /api/embed` for embeddings, plus model-management endpoints such as `/api/tags`, `/api/ps`, `/api/show`, and `/api/pull`. A chat request carries the model, a list of messages with roles `system`, `user`, `assistant`, and `tool`, and optional fields: `stream`, `think`, `tools`, `format`, `options` for parameters such as `temperature` and `num_ctx`, and `keep_alive`.

**Streaming is on by default.** The response is **newline-delimited JSON**: one JSON object per line, each with a piece of `message.content`, and, for thinking models, `message.thinking`. The final object has `"done": true` and the **usage metrics**: `prompt_eval_count`, input tokens; `eval_count`, output tokens; and durations, all in **nanoseconds**: `total_duration`, `load_duration`, `prompt_eval_duration`, and `eval_duration`. From them:

$$\text{generation speed} = \frac{\text{eval\_count}}{\text{eval\_duration} / 10^9} \text{ tokens/s}$$

A large `load_duration` means a cold start, Module 10.2.

### The OpenAI-compatible API

Ollama serves OpenAI-shaped endpoints under `/v1`, including `/v1/chat/completions`, `/v1/embeddings`, `/v1/models`, and `/v1/responses`. The documentation's examples set the client's base URL to `http://localhost:11434/v1/` and an API key of `ollama`: the client library requires a value, but Ollama ignores it. Streaming uses **server-sent events**: lines beginning `data: ` carrying JSON chunks, where each chunk's `choices[0].delta.content` holds new text, ending with `data: [DONE]`. Blank lines separate events, and lines starting with a colon are comments.

### The Anthropic-compatible API

Ollama also serves an Anthropic-shaped `/v1/messages` endpoint. For tools that expect the Anthropic API, such as Claude Code, the documentation sets `ANTHROPIC_BASE_URL` to `http://localhost:11434`, without `/v1`, because the client adds the path, and `ANTHROPIC_AUTH_TOKEN` to `ollama`, again required by the client but ignored by Ollama.

### Tool calling

A request may include `tools`: function definitions with a name, description, and JSON Schema parameters. A model that supports tools, Modules 10.5 to 10.7, may answer with `tool_calls` instead of text, each naming a function and giving arguments. The application, not the model, runs the function, then appends a message with role `tool`, the `tool_name`, and the result as `content`, and calls the model again. The loop repeats until the model answers in text:

```text
 messages --> model --> tool_calls? --yes--> run each tool --> append tool results --+
                 ^                                                                   |
                 +-------------------------------------------------------------------+
                         no --> final answer
```

A **maximum number of rounds** stops a model that keeps calling tools, and unknown tool names must produce an error result rather than a crash. Module 8.3 covered the general pattern.

### Structured outputs

Setting `format` to a JSON Schema asks Ollama to constrain generation to JSON matching it. Even so, an application should **validate** what comes back: parse it, check required fields and types, and handle failures, because a truncated response, a wrong schema, or a client that ignored `format` can still produce invalid output, Module 8.5.

### Calling from Python and JavaScript

Three routes, from least to most portable:

1. **Plain HTTP** with any library: post JSON to `/api/chat`.
2. **Ollama's own libraries**, `ollama` for Python and JavaScript, with `chat`, `generate`, `embed`, and helpers that turn Python functions into tool definitions.
3. **Provider SDKs** pointed at Ollama: the OpenAI or Anthropic SDK with a local base URL. Code written this way can switch between local and hosted models by configuration alone.

### Front ends and integrations

Chat front ends such as **Open WebUI** connect to the native API and add conversations, users, document upload, and retrieval. Ollama's integrations page lists coding agents, desktop assistants, editors, and automation tools, and `ollama launch` starts supported coding agents, such as Claude Code or OpenCode, preconfigured for a local model. When exposing a front end to other people, the server's security still matters, Modules 10.3 and 10.13.

### Complexity

Parsing a stream is linear in its lines. The tool loop costs one model call per round, at most the round limit, plus the tools' own costs. Validating structured output is linear in the fields.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, parsing the native NDJSON stream.

```python
import json

NDJSON = [
    '{"model":"qwen3:8b","message":{"role":"assistant","content":"","thinking":"Stock question."},"done":false}',
    '{"model":"qwen3:8b","message":{"role":"assistant","content":"SAW-3 is "},"done":false}',
    '{"model":"qwen3:8b","message":{"role":"assistant","content":"in stock."},"done":false}',
    '{"model":"qwen3:8b","message":{"role":"assistant","content":""},"done":true,"done_reason":"stop","total_duration":2400000000,"load_duration":1800000000,"prompt_eval_count":42,"eval_count":24,"eval_duration":480000000}',
]

def parse_ndjson(lines):
    text, thinking, stats = [], [], {}
    for line in lines:
        if not line.strip():
            continue
        chunk = json.loads(line)
        msg = chunk.get("message", {})
        text.append(msg.get("content", ""))
        thinking.append(msg.get("thinking", ""))
        if chunk.get("done"):
            stats = {"prompt_tokens": chunk.get("prompt_eval_count", 0), "output_tokens": chunk["eval_count"],
                     "tokens_per_s": round(chunk["eval_count"] / (chunk["eval_duration"] / 1e9), 1),
                     "load_s": round(chunk.get("load_duration", 0) / 1e9, 2)}
    return "".join(text), "".join(thinking), stats

print(parse_ndjson(NDJSON))
```

- **Text and thinking are collected separately,** so the interface can hide the trace.
- **24 tokens in 0.48 seconds is 50 tokens per second.** Durations are nanoseconds.
- **1.8 of the 2.4 seconds were loading.** A cold start dominated this request, Module 10.2.

Next, parsing the OpenAI-style SSE stream.

```python
SSE = ['data: {"choices":[{"delta":{"role":"assistant","content":""}}]}', '',
       'data: {"choices":[{"delta":{"content":"Blades "}}]}', ': keep-alive',
       'data: {"choices":[{"delta":{"content":"are in aisle 4."}}]}',
       'data: {"choices":[{"delta":{},"finish_reason":"stop"}]}', 'data: [DONE]',
       'data: {"choices":[{"delta":{"content":"IGNORED"}}]}']

def parse_sse(lines):
    out, finish = [], None
    for line in lines:
        if not line.startswith("data: "):
            continue
        data = line[6:]
        if data == "[DONE]":
            break
        choice = json.loads(data)["choices"][0]
        out.append(choice.get("delta", {}).get("content") or "")
        finish = choice.get("finish_reason") or finish
    return "".join(out), finish

print(parse_sse(SSE))
```

- **Only `data: ` lines carry events.** Blank lines and comment lines are skipped.
- **`[DONE]` ends the stream.** Anything after it is ignored.
- **The finish reason, `stop`, arrives in the last real chunk.** `length` would mean the answer was cut off by the token limit.

Then, a tool-calling loop with a scripted model.

```python
def run_tools(chat, messages, tools, max_rounds=5):
    messages = list(messages)
    for rounds in range(1, max_rounds + 1):
        msg = chat(messages)
        messages.append(msg)
        calls = msg.get("tool_calls") or []
        if not calls:
            return msg["content"], messages, rounds
        for call in calls:
            name, args = call["function"]["name"], call["function"]["arguments"]
            result = tools[name](**args) if name in tools else f"error: unknown tool {name}"
            messages.append({"role": "tool", "tool_name": name, "content": str(result)})
    return None, messages, max_rounds

def scripted(responses):
    it = iter(responses)
    return lambda messages: next(it)

STOCK = {"SAW-3": 4, "BLADE-10": 0}
TOOLS = {"stock": lambda sku: STOCK.get(sku, "unknown sku")}
chat = scripted([
    {"role": "assistant", "content": "", "tool_calls": [
        {"function": {"name": "stock", "arguments": {"sku": "SAW-3"}}},
        {"function": {"name": "stock", "arguments": {"sku": "BLADE-10"}}}]},
    {"role": "assistant", "content": "SAW-3: 4 in stock; BLADE-10: out of stock."},
])
final, msgs, rounds = run_tools(chat, [{"role": "user", "content": "Stock of SAW-3 and BLADE-10?"}], TOOLS)
print(final, rounds, len(msgs))
```

- **`scripted` stands in for the model.** In production, `chat` would post `messages` and `tools` to `/api/chat` and return `message`.
- **Two tool calls in one turn, then a text answer: two rounds, five messages.** User, assistant with calls, two tool results, final answer.
- **Unknown tools return an error string** the model can read, and the round limit stops endless calling.

Then, validating structured output.

```python
def check_structured(text, schema):
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return ["not valid JSON"]
    if not isinstance(data, dict):
        return ["top level must be an object"]
    errors = [f"missing {k}" for k in schema.get("required", []) if k not in data]
    types = {"string": str, "integer": int, "number": (int, float), "boolean": bool, "array": list}
    for k, spec in schema.get("properties", {}).items():
        if k in data:
            v, t = data[k], spec["type"]
            ok = isinstance(v, types[t]) and not (t in ("integer", "number") and isinstance(v, bool))
            if not ok:
                errors.append(f"{k} should be {t}")
    return errors

SCHEMA = {"required": ["sku", "qty", "in_stock"],
          "properties": {"sku": {"type": "string"}, "qty": {"type": "integer"}, "in_stock": {"type": "boolean"}}}
print(check_structured('{"sku":"SAW-3","qty":4,"in_stock":true}', SCHEMA))
print(check_structured('{"sku":"SAW-3","qty":"4"}', SCHEMA), check_structured('Sure! {"sku": 1}', SCHEMA))
```

- **A good answer passes with no errors.**
- **A quoted number and a missing field are both caught.** The same schema goes in the request's `format` and in this check.
- **Python's `True` is an `int`,** so booleans are excluded from numeric types explicitly.

Finally, checking client configuration.

```python
def check_client(kind, base_url, api_key=None):
    issues = []
    url = base_url.rstrip("/")
    if url.startswith("https://") and ("localhost" in url or "127.0.0.1" in url):
        issues.append("local server speaks http, not https")
    if kind == "openai" and not url.endswith("/v1"):
        issues.append("OpenAI clients need the /v1 base path")
    if kind in ("native", "anthropic") and url.endswith("/v1"):
        issues.append("remove /v1 for this client")
    if kind in ("openai", "anthropic") and not api_key:
        issues.append("client requires an API key value (any string; Ollama ignores it)")
    return issues

print(check_client("openai", "http://localhost:11434/v1/", "ollama"))
print(check_client("openai", "http://localhost:11434", None))
print(check_client("anthropic", "http://localhost:11434/v1", ""))
```

- **The documented OpenAI setup passes.** A trailing slash is fine.
- **Forgetting `/v1` and the key are the two most common OpenAI-client mistakes.**
- **Anthropic clients take the base without `/v1`.** They add the path themselves.

**Complexity.** Linear in lines, messages, and fields; the tool loop is bounded by its round limit.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Missing `/v1` with OpenAI clients.** The requests 404. Add the path.

**Adding `/v1` to Anthropic or native clients.** The paths double up. Remove it.

**Empty API key.** OpenAI and Anthropic clients refuse to start. Use any string.

**Treating streams as one JSON document.** NDJSON is one object per line. Parse line by line.

**Assuming durations are milliseconds.** They are nanoseconds. Divide by a billion.

**Forgetting the final chunk carries usage.** Read metrics from the `done` chunk.

**Showing thinking to users.** It arrives separately. Hide it or summarise it.

**Unbounded tool loops.** A confused model can call tools forever. Cap the rounds.

**Trusting tool arguments.** The model chose them. Validate before acting, Module 8.14.

**Trusting `format` alone.** Validate the JSON anyway.

**Default context in integrations.** Clients rarely set `num_ctx`. Set it in a Modelfile, Module 10.2.

**Browser apps calling the API.** Cross-origin rules block them unless `OLLAMA_ORIGINS` allows the origin. Allow only what you need.

**Question 1.** A developer reports that their Python script using the OpenAI SDK returns "404 Not Found" from the local server, and when they fix that it complains about a missing API key. Using `check_client`, explain both problems and the correct configuration.

<details>
<summary>View Answer</summary>

`check_client("openai", "http://localhost:11434", None)` returns two issues. First, OpenAI clients need the `/v1` base path: the SDK appends paths such as `/chat/completions` to the base URL, so without `/v1` it requests `/chat/completions` at the server root, which does not exist, hence the 404. Ollama serves its OpenAI-compatible endpoints under `/v1`, so the base URL must be `http://localhost:11434/v1`, with or without a trailing slash. Second, the OpenAI SDK refuses to run without an API key value, even though Ollama ignores it; the documentation's examples use `ollama`. The working configuration is a base URL of `http://localhost:11434/v1/` and an API key of `ollama`, for which `check_client` returns no issues. The same code can then target a hosted service by changing those two settings and the model name, which is the main advantage of using the OpenAI-shaped API.

</details>

**Question 2.** The shop's stock chat sometimes takes three seconds to answer a short question. The final chunk of one stream shows `load_duration` 1.8 seconds, `eval_count` 24, and `eval_duration` 0.48 seconds. Using `parse_ndjson`, diagnose the delay.

<details>
<summary>View Answer</summary>

`parse_ndjson` on that stream reports 24 output tokens at 50 tokens per second and a load time of 1.8 seconds, out of a total of 2.4 seconds. Generation itself took under half a second, which is fine; most of the time went into loading the model into memory, a cold start, because the model had been unloaded after its keep-alive period expired, five minutes by default, Module 10.2. Short questions arriving after quiet periods will always pay this cost. The fixes are operational, not in the application code: lengthen the keep-alive during opening hours with `OLLAMA_KEEP_ALIVE` or a `keep_alive` value on requests, or send a warm-up request at opening time. The remaining time, the prompt evaluation of 42 input tokens and the network, is small. Logging `load_duration` and tokens per second for every request, from the final chunk, makes this kind of diagnosis routine instead of guesswork.

</details>

**Question 3.** During testing, the model asked for a tool called `price`, which the shop never defined, and in another test kept calling `stock` for the same item. Using `run_tools`, explain how the loop handles each case and why both safeguards matter.

<details>
<summary>View Answer</summary>

When the model requests `price`, `run_tools` finds no such function in its tools dictionary and appends a tool message with `tool_name` "price" and content "error: unknown tool price", instead of crashing with a missing-key error. The model then sees, in its next call, that the tool does not exist and can answer that it cannot check prices, or try a valid tool. When the model keeps calling `stock`, each round appends another assistant message and tool result, and the loop stops after `max_rounds`, returning no final answer; with a limit of three, the loop ends after three model calls and six messages. Both safeguards matter because the model, not the application, decides what to call: models sometimes invent tool names or get stuck repeating a call, and without the error result the application would fail, and without the round limit it would spend time and compute indefinitely, or keep triggering side effects. The application should treat a missing final answer as a failure, log it, and give the user a fallback reply.

</details>

def scripted(responses):
    """A stand-in for the model: returns the scripted messages in order."""
    it = iter(responses)
    return lambda messages: next(it)


# ---------------------------------------------------------------- Step 1
def parse_ndjson(lines):
    """Native streaming: one JSON object per line; usage in the final chunk, durations in nanoseconds."""
    text, thinking, stats = [], [], {}
    for line in lines:
        if not line.strip():
            continue
        chunk = json.loads(line)
        msg = chunk.get("message", {})
        text.append(msg.get("content", ""))
        thinking.append(msg.get("thinking", ""))
        if chunk.get("done"):
            stats = {"prompt_tokens": chunk.get("prompt_eval_count", 0), "output_tokens": chunk["eval_count"],
                     "tokens_per_s": round(chunk["eval_count"] / (chunk["eval_duration"] / 1e9), 1),
                     "load_s": round(chunk.get("load_duration", 0) / 1e9, 2)}
    return "".join(text), "".join(thinking), stats


# ---------------------------------------------------------------- Step 2
def parse_sse(lines):
    """OpenAI-style streaming: server-sent events ending with [DONE]."""
    out, finish = [], None
    for line in lines:
        if not line.startswith("data: "):
            continue
        data = line[6:]
        if data == "[DONE]":
            break
        choice = json.loads(data)["choices"][0]
        out.append(choice.get("delta", {}).get("content") or "")
        finish = choice.get("finish_reason") or finish
    return "".join(out), finish


# ---------------------------------------------------------------- Step 3
def run_tools(chat, messages, tools, max_rounds=5):
    """The application runs tools the model asks for, with an error for unknown tools and a round limit."""
    messages = list(messages)
    for rounds in range(1, max_rounds + 1):
        msg = chat(messages)
        messages.append(msg)
        calls = msg.get("tool_calls") or []
        if not calls:
            return msg["content"], messages, rounds
        for call in calls:
            name, args = call["function"]["name"], call["function"]["arguments"]
            result = tools[name](**args) if name in tools else f"error: unknown tool {name}"
            messages.append({"role": "tool", "tool_name": name, "content": str(result)})
    return None, messages, max_rounds


# ---------------------------------------------------------------- Step 4
def check_structured(text, schema):
    """Validate model JSON against a small schema even when format was set."""
    try:
        data = json.loads(text)
    except json.JSONDecodeError:
        return ["not valid JSON"]
    if not isinstance(data, dict):
        return ["top level must be an object"]
    errors = [f"missing {k}" for k in schema.get("required", []) if k not in data]
    types = {"string": str, "integer": int, "number": (int, float), "boolean": bool, "array": list}
    for k, spec in schema.get("properties", {}).items():
        if k in data:
            v, t = data[k], spec["type"]
            ok = isinstance(v, types[t]) and not (t in ("integer", "number") and isinstance(v, bool))
            if not ok:
                errors.append(f"{k} should be {t}")
    return errors


# ---------------------------------------------------------------- Step 5
def check_client(kind, base_url, api_key=None):
    """The base-URL and key mistakes behind most integration failures."""
    issues = []
    url = base_url.rstrip("/")
    if url.startswith("https://") and ("localhost" in url or "127.0.0.1" in url):
        issues.append("local server speaks http, not https")
    if kind == "openai" and not url.endswith("/v1"):
        issues.append("OpenAI clients need the /v1 base path")
    if kind in ("native", "anthropic") and url.endswith("/v1"):
        issues.append("remove /v1 for this client")
    if kind in ("openai", "anthropic") and not api_key:
        issues.append("client requires an API key value (any string; Ollama ignores it)")
    return issues
