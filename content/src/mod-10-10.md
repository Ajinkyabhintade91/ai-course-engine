# Hardware Requirements

"Will it run on my machine?" is the first question anyone asks about local models, and "how fast?" is the second. Both have answers you can work out with arithmetic before downloading anything. Memory decides whether a model runs fully on the GPU, split between GPU and CPU, or not at all. Memory **bandwidth**, not raw compute, mostly decides how many tokens per second it generates. This module derives both, covers the differences between discrete GPUs, CPUs, and Apple silicon's unified memory, and ends with a way to choose upgrades.

Hardware figures are manufacturers' published specifications at the time of writing (November 2026), and prices in the lab are illustrative. The estimates are first approximations; `ollama ps` and a timed run on the real machine are the final word.

## 1. First-Principles Mental Model & Intuition

### A workbench and a store room

Picture a carpenter working from plans. The **workbench** is GPU memory: anything on it is within arm's reach and can be worked on quickly. The **store room** down the corridor is system RAM: plenty of space, but every trip takes time. Generating each token is like the carpenter having to consult **every page of the plans** once: the model's weights. If all the pages fit on the bench, each token is quick. If some pages are in the store room, every token requires walking there and back, and the walk dominates the time. And the carpenter's **notes on the job so far**, the KV cache, also take bench space, growing with the length of the job: the context.

```text
            weights (all read once per generated token)        KV cache (grows with context)
                 |                                                    |
   +-------------v----------------------------------------------------v-------------+
   | GPU memory (VRAM)  -- bandwidth 270 to 1,800 GB/s --> GPU cores                 |  fast
   +---------------------------------------------------------------------------------+
   | system RAM         -- bandwidth ~90 GB/s (dual-channel DDR5) --> CPU cores      |  slow
   +---------------------------------------------------------------------------------+
   Apple silicon: one pool of unified memory shared by CPU and GPU (273 to 546 GB/s on M4 Pro/Max)

   tokens/s  ~  efficiency x bandwidth / bytes read per token
```

### Two numbers to remember

**Memory needed** is roughly the model file plus the KV cache plus a little overhead. **Speed** is roughly memory bandwidth divided by the model size. Almost every hardware question about local models reduces to these.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Memory for the weights

As in Modules 10.1 and 10.4, the weights take about

$$M_w \approx \frac{P \times b}{8} \text{ GB}$$

for $P$ billion parameters at $b$ effective bits per weight. Qwen3 8B at `q4_K_M` is 5.2 GB; a 70B model at `q4_K_M` is about 42 GB.

### Memory for the KV cache

During generation, the model keeps the **keys and values** for every previous token at every layer, so it need not recompute them. Its size is

$$M_{kv} = 2 \times L \times H_{kv} \times d_{head} \times n_{ctx} \times B$$

with $L$ layers, $H_{kv}$ key-value heads, $d_{head}$ dimensions per head, $n_{ctx}$ tokens of context, and $B$ bytes per value, 2 for 16-bit. The factor 2 counts keys and values. Modern models use **grouped-query attention**, GQA, in which several query heads share each key-value head, which shrinks $H_{kv}$ and the cache.

Qwen3 8B's configuration lists 36 layers, 8 key-value heads, and a head dimension of 128. Per token that is $2 \times 36 \times 8 \times 128 \times 2 = 147{,}456$ bytes, about 0.15 MB. At 8,192 tokens of context the cache is about 1.21 GB; at 32,768, about 4.83 GB, nearly the size of the weights. A 70B model with 80 layers and the same head layout needs about 2.68 GB at 8,192 tokens.

The cache grows linearly with context, which is why raising `num_ctx` can push a model that fitted out of the GPU. Ollama's FAQ describes quantizing the KV cache, through `OLLAMA_KV_CACHE_TYPE` set to `q8_0` or `q4_0` with flash attention enabled, which roughly halves or quarters it at a small quality cost.

### Total and placement

$$M_{total} \approx M_w + M_{kv} + M_{overhead}$$

with overhead for buffers and the runtime, taken here as 0.8 GB. Qwen3 8B with 8K context needs about $5.2 + 1.21 + 0.8 = 7.21$ GB; the 70B model about $42 + 2.68 + 0.8 = 45.48$ GB.

Placement follows:

- **Fits in GPU memory:** runs fully on the GPU, `100% GPU` in `ollama ps`.
- **Fits in GPU plus system RAM:** split; the share on the GPU is $\text{GPU memory} / M_{total}$, with the rest on the CPU.
- **Otherwise:** does not fit.

### Discrete GPU, CPU, and unified memory

**Discrete GPUs** have their own memory: 16 GB on an RTX 4060 Ti 16 GB, 24 GB on an RTX 4090, 32 GB on an RTX 5090, with bandwidths of 288, 1,008, and 1,792 GB/s respectively. **CPUs** use system RAM: plentiful but slow, about 89.6 GB/s for dual-channel DDR5-5600 ($5{,}600 \times 10^6 \times 8 \text{ bytes} \times 2$ channels). **Apple silicon** has **unified memory**, one pool shared by CPU and GPU with high bandwidth, 273 GB/s on the M4 Pro and up to 546 GB/s on the M4 Max. But macOS does not let the GPU use all of it: by default the GPU can use roughly two thirds on machines with up to 36 GB and about three quarters on larger ones, as commonly reported; the limit can be raised, with care. A 64 GB Mac therefore offers about 48 GB to the GPU, more than any single consumer graphics card, at lower bandwidth.

### Speed: why bandwidth rules

Generating text has two phases. **Prefill** processes the whole prompt in parallel; it is compute-bound and fast on GPUs. **Decode** generates one token at a time, and each token requires reading every weight once. For decode, the time per token is about the bytes read divided by bandwidth:

$$t_{token} \approx \frac{M_w}{\text{bandwidth}}, \qquad \text{tokens/s} \approx \eta \times \frac{\text{bandwidth}}{M_w}$$

with an efficiency $\eta$ below 1, taken here as 0.6, for overheads and imperfect bandwidth use. Qwen3 8B, 5.2 GB, on an RTX 4090 gives about $0.6 \times 1008 / 5.2 \approx 116$ tokens per second; on an RTX 4060 Ti about 33; on the CPU of a laptop with DDR5 about 10.

For a **split** model, each token reads the GPU part at GPU speed and the CPU part at CPU speed:

$$t_{token} = \frac{f \, M_w}{\text{bw}_{gpu}} + \frac{(1 - f) \, M_w}{\text{bw}_{cpu}}$$

The slow part dominates: the 70B model on an RTX 4090 with 53 per cent on the GPU manages about 2.5 tokens per second, because the 47 per cent in system RAM takes ten times longer to read than the part on the GPU.

### Mixture of experts

A **mixture-of-experts** model, Module 10.4, has many experts but uses only a few per token. Memory depends on the **total** parameters, because all experts must be loaded; speed depends on the **active** parameters, because only those are read per token. Qwen3 30B-A3B, with 30.5B total and 3.3B active, needs about 19 GB at 5 bits per weight but reads only about 2.06 GB per token: about 26 tokens per second even on that DDR5 laptop CPU, compared with about 2.8 for a dense model of the same file size. This is why MoE models are popular for machines with lots of ordinary RAM.

### Upgrade paths

In rough order of cost: a smaller quantization or model; a shorter context or a quantized KV cache; more system RAM, which helps CPU and split runs; a GPU with more memory; a second GPU, which Ollama can spread a model across; or a Mac with more unified memory, trading bandwidth for capacity. The right choice is the cheapest option that meets both memory and speed targets for the models you actually need.

### Complexity

Every estimate here is constant time per model and device; choosing among $n$ upgrade options is linear.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, the KV cache.

```python
def kv_cache_gb(layers, kv_heads, head_dim, ctx, bytes_per_value=2.0):
    return round(2 * layers * kv_heads * head_dim * ctx * bytes_per_value / 1e9, 3)

QWEN3_8B = dict(layers=36, kv_heads=8, head_dim=128)
LLAMA_70B = dict(layers=80, kv_heads=8, head_dim=128)
print(kv_cache_gb(**QWEN3_8B, ctx=8192), kv_cache_gb(**QWEN3_8B, ctx=32768))
print(kv_cache_gb(**QWEN3_8B, ctx=32768, bytes_per_value=1.0), kv_cache_gb(**LLAMA_70B, ctx=8192))
```

- **1.208 GB at 8K and 4.832 GB at 32K for Qwen3 8B.** Quadrupling the context quadruples the cache.
- **An 8-bit cache halves it, to 2.416 GB.**
- **The 70B model's cache at 8K is 2.684 GB,** bigger per token because it has more layers.

Next, the GPU budget and placement.

```python
def gpu_budget(device):
    if device["kind"] == "apple":
        share = 0.67 if device["ram_gb"] <= 36 else 0.75
        return round(device["ram_gb"] * share, 2)
    return device.get("vram_gb", 0)

def placement(need_gb, device):
    gpu = gpu_budget(device)
    if need_gb <= gpu:
        return "GPU", 1.0
    total = gpu + (device["ram_gb"] - 4 if device["kind"] != "apple" else 0)
    if need_gb <= total and gpu > 0:
        return "split", round(gpu / need_gb, 2)
    if need_gb <= total:
        return "CPU", 0.0
    return "does not fit", 0.0

DEVICES = {
    "rtx4060ti": {"kind": "nvidia", "vram_gb": 16, "ram_gb": 32, "bw": 288},
    "rtx4090": {"kind": "nvidia", "vram_gb": 24, "ram_gb": 64, "bw": 1008},
    "macbook-m4pro-24": {"kind": "apple", "ram_gb": 24, "bw": 273},
    "mac-m4max-64": {"kind": "apple", "ram_gb": 64, "bw": 546},
    "laptop-cpu": {"kind": "cpu", "ram_gb": 32, "bw": 89.6},
}
NEED_8B = round(5.2 + kv_cache_gb(**QWEN3_8B, ctx=8192) + 0.8, 2)
NEED_70B = round(42 + kv_cache_gb(**LLAMA_70B, ctx=8192) + 0.8, 2)
for name, d in DEVICES.items():
    print(name, gpu_budget(d), placement(NEED_8B, d), placement(NEED_70B, d))
```

- **Needs: 7.21 GB for the 8B, 45.48 GB for the 70B.**
- **The 24 GB MacBook offers 16.08 GB to the GPU; the 64 GB Mac offers 48.**
- **Four GB of system RAM are reserved for the operating system** on non-Apple machines when computing what a split can use.
- **Only the 64 GB Mac runs the 70B fully on its GPU.** The RTX 4090 splits it, 53 per cent on the GPU; the 16 GB card and the laptop cannot fit it.

Then, decode speed.

```python
def decode_tps(read_gb, gpu_fraction, gpu_bw, cpu_bw, efficiency=0.6):
    seconds = read_gb * gpu_fraction / gpu_bw if gpu_fraction else 0.0
    if gpu_fraction < 1:
        seconds += read_gb * (1 - gpu_fraction) / cpu_bw
    return round(efficiency / seconds, 1)

print(decode_tps(5.2, 1.0, 1008, 89.6), decode_tps(5.2, 1.0, 288, 89.6), decode_tps(5.2, 0.0, 288, 89.6))
print(decode_tps(42, 0.53, 1008, 89.6), decode_tps(42, 1.0, 546, 89.6))
```

- **116.3, 33.2, and 10.3 tokens per second for the 8B** on the RTX 4090, the RTX 4060 Ti, and that machine's CPU.
- **2.5 tokens per second for the split 70B on the RTX 4090,** against 7.8 fully on the M4 Max's GPU. More capacity at lower bandwidth beats a faster card that cannot hold the model.
- **Reading speed above 5 tokens per second feels usable for chat;** above 20 feels fluid.

Then, mixture-of-experts sizing.

```python
def moe_profile(total_b, active_b, bpw):
    return round(total_b * bpw / 8, 2), round(active_b * bpw / 8, 2)

mem, read = moe_profile(30.5, 3.3, 5.0)
print(mem, read, decode_tps(read, 0.0, 1, 89.6), decode_tps(mem, 0.0, 1, 89.6))
```

- **19.06 GB to hold, 2.06 GB read per token.**
- **26.1 tokens per second on the CPU, against 2.8 for a dense model of the same file size.**
- **Memory still has to hold all of it.** A 16 GB GPU cannot hold this model fully even though it is fast to run.

Finally, choosing an upgrade.

```python
OPTIONS = [
    {"name": "RTX 4060 Ti 16 GB", "kind": "nvidia", "vram_gb": 16, "ram_gb": 32, "bw": 288, "price": 420},
    {"name": "RTX 4090 24 GB", "kind": "nvidia", "vram_gb": 24, "ram_gb": 64, "bw": 1008, "price": 1600},
    {"name": "RTX 5090 32 GB", "kind": "nvidia", "vram_gb": 32, "ram_gb": 64, "bw": 1792, "price": 2000},
    {"name": "Mac mini M4 Pro 64 GB", "kind": "apple", "ram_gb": 64, "bw": 273, "price": 1900},
    {"name": "Mac Studio M4 Max 128 GB", "kind": "apple", "ram_gb": 128, "bw": 546, "price": 3600},
]

def upgrade(options, need_gb, read_gb, target_tps):
    best = None
    for o in options:
        where, _ = placement(need_gb, o)
        if where != "GPU":
            continue
        tps = decode_tps(read_gb, 1.0, o["bw"], 1)
        if tps < target_tps:
            continue
        if best is None or o["price"] < best[1]:
            best = (o["name"], o["price"], tps)
    return best

print(upgrade(OPTIONS, NEED_8B, 5.2, 20))
print(upgrade(OPTIONS, 22.0, 20.0, 30))
print(upgrade(OPTIONS, NEED_70B, 42, 5), upgrade(OPTIONS, NEED_70B, 42, 3), upgrade(OPTIONS, NEED_70B, 42, 10))
```

- **Qwen3 8B at 20 tokens per second: the RTX 4060 Ti, GBP 420, at 33.2.**
- **A 20 GB model needing 22 GB at 30 tokens per second: the RTX 4090, at 30.2,** cheaper than the RTX 5090.
- **The 70B at 5 tokens per second: only the M4 Max qualifies, at 7.8.** At 3 tokens per second the cheaper M4 Pro Mac mini qualifies at 3.9; at 10, nothing does.
- **Prices are illustrative.** Use current prices; the method is the point.

**Complexity.** Constant per estimate; linear in options.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Sizing by the file alone.** The KV cache and overhead add gigabytes. Add them before buying.

**Raising the context and losing the GPU.** A bigger `num_ctx` can push the model into a split. Check `ollama ps` after changing it.

**Buying compute instead of memory.** Decode speed follows bandwidth and capacity. A faster GPU with too little memory loses to a slower one that fits.

**Tiny splits are expensive.** Even 10 per cent on the CPU slows decode noticeably. Aim for 100 per cent GPU.

**Expecting unified memory to be all GPU memory.** macOS reserves part of it. Budget about two thirds to three quarters.

**Swapping.** If the model does not fit in RAM either, the system swaps and slows to a crawl. Treat that as "does not fit".

**Multiple models loaded at once.** Each holds memory. Watch `ollama ps` and `OLLAMA_MAX_LOADED_MODELS`.

**Parallel requests.** Each parallel slot needs its own context. `OLLAMA_NUM_PARALLEL` multiplies cache memory.

**Laptop thermals and power modes.** Sustained speed on battery can be far below the plugged-in figure. Test in the real conditions.

**Ignoring prefill.** Long prompts take time before the first token, especially on CPU. Measure time to first token separately.

**Benchmarks from others' machines.** Drivers, quantization, and context differ. Run your own short timing test.

**MoE memory surprises.** Active parameters set speed, not memory. Budget memory by total parameters.

# ---------------------------------------------------------------- Step 1
def kv_cache_gb(layers, kv_heads, head_dim, ctx, bytes_per_value=2.0):
    """Keys and values for every layer, KV head, and token of context."""
    return round(2 * layers * kv_heads * head_dim * ctx * bytes_per_value / 1e9, 3)


# ---------------------------------------------------------------- Step 2
def gpu_budget(device):
    """Memory the GPU can use; on Apple silicon, a share of unified memory."""
    if device["kind"] == "apple":
        share = 0.67 if device["ram_gb"] <= 36 else 0.75
        return round(device["ram_gb"] * share, 2)
    return device.get("vram_gb", 0)


def placement(need_gb, device):
    """Fully on the GPU, split, CPU only, or not at all."""
    gpu = gpu_budget(device)
    if need_gb <= gpu:
        return "GPU", 1.0
    total = gpu + (device["ram_gb"] - 4 if device["kind"] != "apple" else 0)
    if need_gb <= total and gpu > 0:
        return "split", round(gpu / need_gb, 2)
    if need_gb <= total:
        return "CPU", 0.0
    return "does not fit", 0.0


# ---------------------------------------------------------------- Step 3
def decode_tps(read_gb, gpu_fraction, gpu_bw, cpu_bw, efficiency=0.6):
    """Decode is bandwidth-bound: the slow part of a split dominates."""
    seconds = read_gb * gpu_fraction / gpu_bw if gpu_fraction else 0.0
    if gpu_fraction < 1:
        seconds += read_gb * (1 - gpu_fraction) / cpu_bw
    return round(efficiency / seconds, 1)


# ---------------------------------------------------------------- Step 4
def moe_profile(total_b, active_b, bpw):
    """Memory follows total parameters; speed follows active parameters."""
    return round(total_b * bpw / 8, 2), round(active_b * bpw / 8, 2)


# ---------------------------------------------------------------- Step 5
def upgrade(options, need_gb, read_gb, target_tps):
    """Cheapest option that holds the model on the GPU and meets the speed target."""
    best = None
    for o in options:
        where, _ = placement(need_gb, o)
        if where != "GPU":
            continue
        tps = decode_tps(read_gb, 1.0, o["bw"], 1)
        if tps < target_tps:
            continue
        if best is None or o["price"] < best[1]:
            best = (o["name"], o["price"], tps)
    return best
