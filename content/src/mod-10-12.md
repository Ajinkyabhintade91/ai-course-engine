# Running Local AI Agents

An **agent** is a model in a loop: it decides on an action, a tool runs it, the result comes back, and the model decides again until the task is done, Modules 8.1 to 8.3. Running that loop on a **local** model is attractive: no per-call cost, no data leaving the machine, and no rate limits. It is also harder than with frontier hosted models, because smaller local models make more mistakes in exactly the places agents are fragile: formatting tool calls, choosing arguments, knowing when to stop, and staying consistent across many steps. This module builds a small local agent loop that expects those mistakes, measures reliability properly, and turns measurements into concrete mitigations.

Ollama features cited are from its documentation at the time of writing (November 2026). The lab uses a scripted stand-in for the model so that it runs offline and deterministically.

## 1. First-Principles Mental Model & Intuition

### A capable apprentice with a checklist and a supervisor

A local model running an agent is like a capable **apprentice** in the shop. Given clear instructions and the right tools, the apprentice gets most jobs done. But apprentices sometimes fill in a job card in the wrong format, write a quantity as words instead of a number, ask for a tool the shop does not have, or announce "I'll check the stock" and then not do it. A good workshop does not give up on apprentices; it puts a **checklist** at the counter that rejects badly filled-in cards and says why, a **supervisor** who signs off anything that costs money, and a **logbook** that shows how often each kind of job goes wrong, so training and procedures can improve.

```text
 task --> [ local model ] --> reply text
                ^                 |
                |          extract tool call (JSON in text, code fences, native tool_calls)
                |                 |---- none and no attempt --> final answer
                |                 |---- malformed --> "error: could not parse" -------------+
                |          validate (tool exists, required args, types, no extras)         |
                |                 |---- invalid --> "error: missing argument sku" ----------+
                |          execute tool (approval gate for actions)                        |
                +---------- tool result <---------------------------------------------------+
     limits: max steps, max repairs      metrics: steps, repairs, pass@1, pass^k
```

### The central idea

Treat every model output as **untrusted input**: parse it defensively, validate it strictly, feed errors back so the model can repair them, cap everything, and measure reliability over repeated runs rather than a single demo.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Tool calling with local models

With Ollama, a request lists tools and a capable model answers with structured `tool_calls`, Module 10.11. Native tool calling depends on the model having been trained for it and on the chat template translating between the model's own tool format and the API's. When either is weak, the model may write the call as **text**: JSON in the message, often wrapped in a code fence or preceded by chatter. A robust agent handles both: it uses native tool calls when present and otherwise extracts a JSON object with a `name` and an `arguments` object from the text.

Extracting JSON from text needs care. Searching for the first `{` and the last `}` fails when the text contains two objects or braces inside strings. A **brace-matching scan** that tracks whether it is inside a string, and skips escaped quotes, finds each complete object; the first that parses and has the right shape is the call.

### Validation

A parsed call must be checked before anything runs: the tool must exist, every required argument must be present with the right type, and unexpected arguments should be rejected rather than silently ignored, because they often reveal that the model misunderstood the tool. Python's `bool` is a subclass of `int`, so a check for integers must exclude booleans explicitly. Validation errors become **feedback**: a message such as "error: qty must be int" appended to the history lets the model repair its call on the next step, which smaller models do surprisingly well when told exactly what was wrong.

### The loop and its limits

The loop, following the ReAct pattern of reasoning and acting in turns, runs until the model answers without a tool call, with two limits:

- **Maximum steps**, so a model that keeps calling tools, or keeps repeating the same call, cannot run forever.
- **Repairs** counted separately from successful tool calls, because a high repair rate is a symptom of the model, the prompt, or the tool design.

Detecting the **final answer** is itself fragile: a reply such as "Calling stock now." contains no call and looks final, though the model intended to act. Mitigations include requiring a specific final-answer format, or checking that the reply actually answers the task.

### Measuring reliability

A single successful run proves little. Run each task $k$ times and record success. Two summary numbers, from the tau-bench paper and Module 8.12, capture different things:

$$\text{pass@1} = \frac{1}{T}\sum_{t=1}^{T} \frac{s_t}{k}, \qquad \text{pass}^k = \frac{1}{T}\sum_{t=1}^{T} \mathbb{1}[s_t = k]$$

where $s_t$ is the number of successful runs of task $t$. pass@1 is the average success rate; pass^k is the share of tasks that succeed **every** time. For an agent customers rely on, pass^k matters more: a task that works four times in five fails one customer in five. Tasks with some successes and some failures are **flaky**, and flaky tasks are where prompt and tool improvements pay off most.

If each step succeeds independently with probability $p$, a task needing $n$ steps succeeds with probability $p^n$: at $p = 0.95$, a 5-step task succeeds about 77 per cent of the time and a 10-step task about 60 per cent. Shorter tasks and fewer tools are the strongest levers.

### Mitigations

| Symptom | Mitigation |
|---|---|
| Malformed tool calls | Constrain output with a JSON schema, Ollama's `format`; use a model with native tool calling; simplify tool schemas |
| Many steps per task | Narrow the task; fewer, clearer tools; combine common sequences into one tool |
| Low pass^k | Add a verification step; require human approval for actions that change things, Module 8.11 |
| Context overflows | Summarise history; raise `num_ctx`, Module 10.10 |
| Wrong tool chosen | Better tool descriptions; route simpler tasks to a workflow instead of an agent, Module 8.10 |

Benchmarks such as the Berkeley Function Calling Leaderboard compare models' tool-calling accuracy and are a useful first filter for which local models to try.

### Using existing agents with local models

Ollama's integrations let established agents, such as Claude Code or OpenCode, run against local models through its compatible APIs, Module 10.11. The same reliability issues apply: an agent designed around a frontier model may expect more consistent tool use than a small local model provides, so measure before relying on it.

### Complexity

Extracting a call scans the text, $O(L^2)$ in the worst case for repeated starts but linear in practice; validation is linear in arguments; the loop is bounded by its step limit; reliability metrics are linear in runs.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, extracting a tool call from text.

```python
import json

def extract_call(text):
    start = text.find("{")
    while start != -1:
        depth, in_str, esc = 0, False, False
        for i in range(start, len(text)):
            c = text[i]
            if in_str:
                if esc:
                    esc = False
                elif c == "\\":
                    esc = True
                elif c == '"':
                    in_str = False
                continue
            if c == '"':
                in_str = True
            elif c == "{":
                depth += 1
            elif c == "}":
                depth -= 1
                if depth == 0:
                    try:
                        obj = json.loads(text[start:i + 1])
                    except json.JSONDecodeError:
                        break
                    if isinstance(obj, dict) and "name" in obj and isinstance(obj.get("arguments"), dict):
                        return obj
                    break
        start = text.find("{", start + 1)
    return None

print(extract_call('Sure! ```json\n{"name": "stock", "arguments": {"sku": "SAW-3"}}\n```'))
print(extract_call('{"note": "x"} then {"name":"stock","arguments":{"sku":"A}B"}}'))
print(extract_call("No tools needed."), extract_call('{"name": "stock", "arguments": {"sku": "SAW-3"'))
```

- **Code fences and chatter are ignored.** The scan finds the object inside.
- **An earlier unrelated object is skipped,** and a brace inside a string does not end the object.
- **No call and a truncated call both return None.** The loop decides what that means.

Next, validating arguments.

```python
SCHEMAS = {"stock": {"required": {"sku": str}}, "reserve": {"required": {"sku": str, "qty": int}}}

def validate_call(call, schemas):
    if call["name"] not in schemas:
        return [f"unknown tool {call['name']}"]
    errs = []
    for arg, typ in schemas[call["name"]]["required"].items():
        if arg not in call["arguments"]:
            errs.append(f"missing argument {arg}")
        elif not isinstance(call["arguments"][arg], typ) or isinstance(call["arguments"][arg], bool):
            errs.append(f"{arg} must be {typ.__name__}")
    extra = sorted(set(call["arguments"]) - set(schemas[call["name"]]["required"]))
    errs += [f"unexpected argument {a}" for a in extra]
    return errs

print(validate_call({"name": "reserve", "arguments": {"sku": "SAW-3", "qty": "2"}}, SCHEMAS))
print(validate_call({"name": "stock", "arguments": {"sku": "SAW-3", "colour": "red"}}, SCHEMAS))
```

- **A quantity written as the string "2" is rejected.** Small models often do this.
- **Unexpected arguments are reported,** not silently dropped.
- **Booleans are not integers here,** even though Python treats them as such.

Then, a loop that repairs.

```python
def agent_loop(model, task, tools, schemas, max_steps=6):
    history = [("user", task)]
    stats = {"steps": 0, "tool_calls": 0, "repairs": 0}
    for _ in range(max_steps):
        stats["steps"] += 1
        reply = model(history)
        history.append(("assistant", reply))
        call = extract_call(reply)
        if call is None:
            if "{" in reply and '"name"' in reply:
                stats["repairs"] += 1
                history.append(("tool", "error: could not parse tool call; reply with one JSON object"))
                continue
            return reply.strip(), stats
        errs = validate_call(call, schemas)
        if errs:
            stats["repairs"] += 1
            history.append(("tool", "error: " + "; ".join(errs)))
            continue
        stats["tool_calls"] += 1
        history.append(("tool", str(tools[call["name"]](**call["arguments"]))))
    return None, stats

def scripted(replies):
    it = iter(replies)
    return lambda history: next(it)

STOCK = {"SAW-3": 4}
TOOLS = {"stock": lambda sku: STOCK.get(sku, 0), "reserve": lambda sku, qty: f"reserved {qty} x {sku}"}
model = scripted(['{"name": "stock", "arguments": {"sku": "SAW-3"}}',
                  '{"name": "reserve", "arguments": {"sku": "SAW-3", "qty": "2"}}',
                  '{"name": "reserve", "arguments": {"sku": "SAW-3", "qty": 2}}',
                  "Reserved 2 of the 4 SAW-3 in stock."])
print(agent_loop(model, "Reserve 2 SAW-3 if in stock", TOOLS, SCHEMAS))
```

- **Four steps: a stock check, a rejected reservation, the repaired reservation, and the answer.** One repair, two tool calls.
- **A broken-looking attempt is distinguished from a final answer** by the presence of a JSON-like fragment naming a tool.
- **A reply with no call ends the loop,** which is how "Calling stock now." would wrongly end it; the reliability measurement is what catches such runs.

Then, measuring reliability across repeated runs.

```python
def reliability(results):
    tasks = sorted(results)
    pass1 = sum(sum(r) / len(r) for r in results.values()) / len(tasks)
    passk = sum(all(r) for r in results.values()) / len(tasks)
    flaky = [t for t in tasks if 0 < sum(results[t]) < len(results[t])]
    return round(pass1, 3), round(passk, 3), flaky

RUNS = {"stock check": [True] * 5, "reserve": [True, True, False, True, True],
        "refund policy": [True, False, True, False, True], "price total": [False] * 5}
print(reliability(RUNS))
```

- **pass@1 is 0.6 but pass^5 is only 0.25.** Only the stock check works every time.
- **Two tasks are flaky:** reserve and refund policy. They are where to focus.
- **"Price total" always fails.** That is a capability gap, not flakiness: a different tool or model is needed.

Finally, turning measurements into mitigations.

```python
def mitigations(m):
    out = []
    if m["parse_failure_rate"] > 0.05:
        out.append("constrain output with a JSON schema or use a model with native tool calling")
    if m["avg_steps"] > 4:
        out.append("narrow the task or reduce the number of tools")
    if m["pass_k"] < 0.9:
        out.append("add a verification step and human approval for actions")
    if m["context_overflows"] > 0:
        out.append("summarise history or raise num_ctx")
    return out or ["no change needed"]

print(mitigations({"parse_failure_rate": 0.12, "avg_steps": 5.5, "pass_k": 0.25, "context_overflows": 2}))
```

- **Each rule maps one measured symptom to one standard fix.**
- **Thresholds are the shop's choices.** A customer-facing agent needs stricter ones than an internal helper.
- **A clean run returns "no change needed",** which is also worth recording.

**Complexity.** Linear in text, arguments, and runs; the loop is bounded.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Demo success.** One good run is anecdote. Measure pass^k.

**Tool calls as text.** Common with small models and imperfect templates. Extract robustly.

**Naive JSON extraction.** First `{` to last `}` breaks on two objects. Match braces.

**Strings for numbers.** "2" instead of 2. Validate types and feed back errors.

**Announcing instead of acting.** "I'll check that now" with no call. Require a final-answer format.

**Repeating the same call.** Loops burn steps. Cap steps and detect repeats.

**Too many tools.** Small models choose badly among many. Offer only what the task needs.

**Long histories.** Tool results fill the context. Summarise or trim, Module 10.10.

**Thinking models in loops.** Thinking adds tokens each step. Turn it off for simple tool steps.

**Actions without approval.** Reservations, refunds, emails. Gate them, Module 8.11.

**Trusting tool results blindly.** Tools can return errors or injected text. Treat results as data, Module 8.14.

**Expecting frontier behaviour.** Agents designed for large hosted models may struggle locally. Measure on your model.

**Question 1.** The shop's local agent works in a demo, but staff report it sometimes says "I'll reserve that now" and then does nothing. Using `agent_loop` and `reliability`, explain what is happening and how you would catch and reduce it.

<details>
<summary>View Answer</summary>

`agent_loop` ends the loop whenever a reply contains no tool call and no sign of an attempted one, treating it as the final answer. "I'll reserve that now" fits that description, so the loop returns it as the answer and the reservation never happens: the model announced an action instead of taking it, a common failure for smaller models. A single demo run hides this, because it happens only some of the time. Running each task several times and computing `reliability` exposes it: the reserve task shows up as flaky, with pass@1 below 1 and pass^k well below pass@1. To reduce it: require a final-answer format that must state the outcome, such as the SKU and quantity reserved, and treat a reply that lacks it as incomplete, prompting the model to act; check task-specific conditions, such as whether `reserve` was actually called for a reservation task; use schema-constrained output or a model with stronger native tool calling; and keep a human approval step on reservations, so a missed action is noticed before a customer relies on it.

</details>

**Question 2.** A colleague's agent parses tool calls by taking the text from the first `{` to the last `}`. It fails on the reply `Checked {"note": "ok"}, now {"name": "stock", "arguments": {"sku": "A}B"}}`. Using `extract_call`, explain why and what the robust approach does.

<details>
<summary>View Answer</summary>

Taking the first `{` to the last `}` captures `{"note": "ok"}, now {"name": "stock", "arguments": {"sku": "A}B"}}`, which is not one JSON object, so parsing fails and the call is lost. `extract_call` instead scans from each opening brace, counting depth while tracking whether it is inside a string and skipping escaped quotes, so the brace inside the string "A}B" does not end the object. The first complete object, `{"note": "ok"}`, parses but lacks a name and arguments, so the scan moves on; the next complete object is the tool call, with the SKU "A}B" intact. Text such as code fences or chatter before and after the JSON is ignored. If no valid call is found, or the JSON is truncated, the function returns None and the loop decides whether that is a final answer or a broken attempt needing repair. Native tool calls from Ollama, when the model and template support them, avoid this parsing entirely and should be preferred.

**Question 3.** After a week of nightly tests, the shop's agent shows a parse failure rate of 12 per cent, an average of 5.5 steps per task, pass^5 of 0.25, and two context overflows. Using `mitigations` and the per-step success formula, prioritise the changes.

        elif not isinstance(call["arguments"][arg], typ) or isinstance(call["arguments"][arg], bool):
            errs.append(f"{arg} must be {typ.__name__}")
    extra = sorted(set(call["arguments"]) - set(schemas[call["name"]]["required"]))
    errs += [f"unexpected argument {a}" for a in extra]
    return errs


# ---------------------------------------------------------------- Step 3
def agent_loop(model, task, tools, schemas, max_steps=6):
    """An agent loop that feeds parse and validation errors back for repair, with a step limit."""
    history = [("user", task)]
    stats = {"steps": 0, "tool_calls": 0, "repairs": 0}
    for _ in range(max_steps):
        stats["steps"] += 1
        reply = model(history)
        history.append(("assistant", reply))
        call = extract_call(reply)
        if call is None:
            if "{" in reply and '"name"' in reply:
                stats["repairs"] += 1
                history.append(("tool", "error: could not parse tool call; reply with one JSON object"))
                continue
            return reply.strip(), stats
        errs = validate_call(call, schemas)
        if errs:
            stats["repairs"] += 1
            history.append(("tool", "error: " + "; ".join(errs)))
            continue
        stats["tool_calls"] += 1
        history.append(("tool", str(tools[call["name"]](**call["arguments"]))))
    return None, stats


# ---------------------------------------------------------------- Step 4
def reliability(results):
    """pass@1, pass^k, and the flaky tasks, from repeated runs."""
    tasks = sorted(results)
    pass1 = sum(sum(r) / len(r) for r in results.values()) / len(tasks)
    passk = sum(all(r) for r in results.values()) / len(tasks)
    flaky = [t for t in tasks if 0 < sum(results[t]) < len(results[t])]
    return round(pass1, 3), round(passk, 3), flaky


# ---------------------------------------------------------------- Step 5
def mitigations(m):
    """Map measured symptoms to standard fixes."""
    out = []
    if m["parse_failure_rate"] > 0.05:
        out.append("constrain output with a JSON schema or use a model with native tool calling")
    if m["avg_steps"] > 4:
        out.append("narrow the task or reduce the number of tools")
    if m["pass_k"] < 0.9:
        out.append("add a verification step and human approval for actions")
    if m["context_overflows"] > 0:
        out.append("summarise history or raise num_ctx")
    return out or ["no change needed"]
