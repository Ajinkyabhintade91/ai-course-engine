# Deployment

An agent that runs on a laptop answers one question at a time while you watch. In production it must answer hundreds of customers at once, survive a crash halfway through a refund, stay under the model provider's rate limits, never spend more than the budget, and change its prompt without breaking for everyone. **Deployment** is the engineering that makes that true. Most of it is ordinary backend engineering, queues, workers, limits, rollouts, with a few features specific to agents: tasks that run for minutes, costs that vary per request, and behaviour that changes when a prompt changes.

## 1. First-Principles Mental Model & Intuition

### A restaurant kitchen at service

A kitchen does not cook each order the moment it is shouted. Orders go onto a **rail**, a queue, and cooks take tickets as they are free. A ticket taken by a cook who then walks out is not lost: the head chef notices it has not been served and puts it back on the rail. The kitchen has a fixed number of burners, so orders beyond that wait, a rate limit. The manager watches food costs and stops comping desserts once the week's allowance is spent, a budget. And a new dish goes on the menu for one table first, a canary, before the whole restaurant.

```text
   customers / webhooks / schedules
          |
     [ API front door ]  --(fast ack: "we're on it", ticket id)
          |
     [ queue ]  <- messages hidden while being worked on; reappear if a worker dies
          |
     [ workers x N ] -- [ token bucket ] --> model API (rate limited)
          |        \--- [ budget guard ] --> refuse or degrade when spend hits limits
          |         \-- tools (orders DB, payments, email) with idempotency keys
          v
     [ state store: checkpoints, leases, results ]
          |
     [ traces, metrics, cost per task ] --> dashboards, alerts, canary decisions
```

### Why agents stress deployment

| Agent property | Deployment consequence |
|---|---|
| Tasks take seconds to minutes | HTTP requests time out; work must run in the background |
| Each task makes many model and tool calls | Rate limits and partial failures are routine |
| Cost varies per task by orders of magnitude | Budgets must be enforced, not just reported |
| Behaviour depends on prompt and model versions | Every change is a release that needs a rollout |
| Tasks have side effects | Retries and redelivery need idempotency, Module 8.5 |

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Deployment shapes

| Shape | Good for | Watch out for |
|---|---|---|
| Serverless functions | Short, bursty, event-triggered work; scale to zero | Hard execution time limits; cold starts; no local state |
| Containers (long-running services) | Steady traffic, streaming responses, warm caches | Paying for idle capacity; you manage scaling |
| Queue plus workers | Long tasks, bursts, retries, back-pressure | At-least-once delivery; more moving parts |
| Schedulers | Nightly reports, periodic syncs | Overlapping runs; missed runs after outages |
| Durable workflow engines | Multi-step tasks over hours or days, human waits | Learning curve; determinism rules |

Limits decide shapes. AWS Lambda, at the time of writing (November 2026), caps a function's timeout at 900 seconds, 15 minutes. An agent task whose 99th-percentile duration exceeds the limit cannot run there safely, however short its median, so it belongs on a queue worker or in a durable workflow. Durable execution engines such as Temporal persist each step of a workflow so it can resume after a crash or wait days for a person, Module 8.11, without holding a process.

### Capacity: Little's law

How many tasks run at once? **Little's law** states that, in a stable system, the average number of items in the system equals the arrival rate times the average time each spends there:

$$L = \lambda W$$

If tickets arrive at $\lambda = 12$ per minute and each takes $W = 2.5$ minutes, then on average $L = 30$ are in progress. Workers should not run at 100 percent, because queues grow sharply as utilisation approaches 1; at a target utilisation $u$,

$$\text{workers} = \left\lceil \frac{\lambda W}{u} \right\rceil$$

which at $u = 0.7$ gives 43 workers. A nightly batch of 0.5 tasks per minute at 40 minutes each also needs $L = 20$ concurrent tasks, 29 workers at 0.7, despite the low arrival rate: long tasks consume capacity as surely as many tasks do.

### Queues, visibility timeouts, and at-least-once delivery

When a worker receives a message from a queue such as Amazon SQS, the message is not deleted; it becomes **invisible** for a **visibility timeout**, 30 seconds by default in SQS. If the worker finishes, it deletes the message. If the worker crashes, or takes longer than the timeout, the message becomes visible again and another worker receives it. This is what makes queues robust, and it is also why the SQS documentation describes its standard queues as **at-least-once**: a message may be delivered more than once.

Two consequences follow. Set the visibility timeout above the task's realistic maximum duration, or extend it while working; a refund task that takes 45 seconds with a 30-second timeout will be picked up twice. And make every side effect **idempotent**, keyed by the task, as Modules 8.5 and 8.11 did: redelivery must not mean a second refund. Messages that fail repeatedly should move to a **dead-letter queue** after a maximum number of receives, so one poisonous ticket does not loop forever.

### State and concurrency

Workers should be **stateless**: anything that must survive belongs in a store, a database or the durable engine's history. Agent state, the conversation, tool results, the checkpoint of Module 8.2, is loaded at the start of a task and saved at each step. Two workers must not process the same conversation at once, or they will interleave replies: a **lease**, a lock with an expiry, ensures one owner at a time and is released automatically if the owner dies.

### Rate limits: the token bucket

Model providers limit requests and tokens per minute. The Claude API's documentation states that it uses the **token bucket** algorithm: capacity refills continuously up to a maximum rather than resetting at fixed intervals. Your own deployment should rate-limit itself the same way, so it degrades gracefully instead of hammering the provider into 429 errors, Module 7.10. A bucket with capacity $C$ and refill rate $r$ per second holds

$$\text{tokens}(t) = \min\big(C,\ \text{tokens}(t_0) + r\,(t - t_0)\big)$$

and a request costing $c$ is allowed when at least $c$ tokens are available, which are then removed. The capacity allows **bursts**; the rate enforces the **average**. A shared bucket, in a store like Redis, is needed when many workers share one provider limit.

### Cost control

Agent cost per task varies widely, and a bug, a loop, or an abusive user can multiply it overnight. Reporting cost is not enough; it must be **enforced** before each expensive step:

| Control | Example |
|---|---|
| Global daily budget | Stop non-essential agent work above GBP 50 per day |
| Per-user or per-tenant budget | One customer cannot consume the day's budget |
| Per-task caps | Maximum steps and tokens per task, Module 8.2 |
| Model routing | Cheap model for easy routes, Module 8.10 |
| Caching | Prompt caching and response caching for repeated work |
| Alerts | Spend rate far above normal triggers a page |

When a budget is reached, **degrade** rather than fail silently: hand over to a person, answer from a cheaper path, or queue the work for later, and tell the customer.

### Observability

Every task should produce a **trace**: spans for each model call, tool call, and queue wait, with tokens, cost, latency, and outcome. OpenTelemetry's semantic conventions for generative AI give standard names for these attributes. From traces come the metrics to watch: task success rate, p50 and p95 latency, cost per task, queue depth and age of the oldest message, rate-limit rejections, and escalation rate. Queue age is the early warning: when the oldest message is getting older, capacity is short.

### Rollouts: canaries

A new prompt, model, or tool is a release. Module 8.12's evals catch much before release, but production traffic is different, so roll out gradually. A **canary** sends a small share of traffic to the new version, compares its metrics with the stable version's over enough requests, and then either promotes it or rolls it back. Google's Site Reliability Workbook describes canarying as exactly this: a partial, time-limited deployment evaluated against the control before proceeding.

Assignment should be **sticky**: hash the user identifier, as in Module 8.11's sampling, so each user stays on one version and the comparison is not muddled by users switching. With a hash modulo 100 compared to the percentage, raising the canary from 10 to 25 percent keeps every user already on the canary there, which keeps experiences consistent. The decision needs a **minimum sample**: with 120 canary requests, a difference of one error is noise. And the comparison must include **cost** as well as errors: a prompt that is as accurate but twice as expensive should not be promoted by accident.

### Complexity

Capacity is constant. Queue receive scans messages, linear in queue size here, constant with a real queue service. A token bucket check is constant. Budget checks are linear in tracked users for a global sum, constant with a running total. Sticky assignment is one hash; canary evaluation is constant.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, capacity and shape.

```python
import hashlib
import math

def capacity(arrivals_per_min, minutes_per_task, utilisation=0.7):
    concurrent = arrivals_per_min * minutes_per_task
    return round(concurrent, 2), math.ceil(concurrent / utilisation)

def shape(job, timeout_s=900):
    if job["trigger"] == "schedule":
        return "scheduler", "runs on a timetable"
    if job["p99_seconds"] > timeout_s:
        return "queue_worker", f"p99 {job['p99_seconds']}s exceeds the {timeout_s}s function timeout"
    if job["trigger"] == "http" and job["steady"]:
        return "container", "steady traffic keeps a service busy"
    return "serverless", "short, bursty work"

print(capacity(12, 2.5), capacity(0.5, 40))
print(shape({"trigger": "event", "p99_seconds": 1500, "steady": False}))
print(shape({"trigger": "http", "p99_seconds": 20, "steady": False}))
```

- **Little's law gives 30 concurrent tasks; at 70 percent utilisation, 43 workers.**
- **The nightly batch needs 20 concurrent tasks and 29 workers.** Long tasks fill capacity.
- **Shape follows the tail, not the median.** A task whose p99 is 1,500 seconds cannot live under a 900-second timeout.
- **Short, bursty HTTP work suits serverless.** It scales to zero between bursts.

Next, a queue with visibility timeouts.

```python
class Queue:
    def __init__(self, visibility=30):
        self.visibility, self.messages, self.next_id = visibility, {}, 1

    def send(self, body):
        mid = f"m{self.next_id}"
        self.next_id += 1
        self.messages[mid] = {"body": body, "visible_at": 0, "receives": 0}
        return mid

    def receive(self, now):
        for mid in sorted(self.messages, key=lambda m: int(m[1:])):
            message = self.messages[mid]
            if message["visible_at"] <= now:
                message["visible_at"] = now + self.visibility
                message["receives"] += 1
                return mid, message["body"], message["receives"]
        return None

    def delete(self, mid):
        return self.messages.pop(mid, None) is not None

queue = Queue(visibility=30)
queue.send("refund A-1")
queue.send("refund A-2")
print(queue.receive(0), queue.receive(0), queue.receive(10))
print(queue.receive(31), queue.delete("m1"), queue.receive(40), queue.receive(61))
```

- **Receiving hides a message for 30 seconds and counts the receive.** Two workers at time 0 get different messages.
- **At time 10, nothing is visible.** Both are being worked on.
- **At time 31, m1 is delivered again, its second receive.** Its worker did not delete it in time: crashed, or just slow.
- **After m1 is deleted, m2 is also redelivered at time 40.** Both refunds were delivered twice; without idempotency keys, both customers would be refunded twice.
- **At time 61, m2 is hidden again until 70.** The receive count is what a dead-letter policy would check.

Then, a token bucket.

```python
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity, self.tokens, self.last = rate, capacity, capacity, 0.0

    def allow(self, now, cost=1):
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True, round(self.tokens, 2)
        return False, round(self.tokens, 2)

bucket = TokenBucket(rate=2, capacity=5)
print([bucket.allow(0) for _ in range(6)])
print(bucket.allow(1), bucket.allow(1), bucket.allow(1), bucket.allow(10, cost=4))
```

- **Refill first, capped at capacity, then spend.**
- **A burst of five requests at time 0 is allowed; the sixth is refused.** Capacity sets the burst.
- **One second later, two tokens have refilled: two requests pass, the third does not.** Rate sets the average.
- **After nine idle seconds the bucket is full again, not over-full.** A cost-4 request leaves 1 token.

Then, a budget guard.

```python
def budget_guard(spend, user, cost, daily_limit, user_limit):
    if sum(spend.values()) + cost > daily_limit:
        return False, "daily budget reached"
    if spend.get(user, 0) + cost > user_limit:
        return False, "user budget reached"
    spend[user] = round(spend.get(user, 0) + cost, 4)
    return True, "ok"

SPEND = {"u1": 4.9, "u2": 40}
print(budget_guard(SPEND, "u1", 0.2, 50, 5), budget_guard(SPEND, "u3", 0.2, 50, 5), budget_guard(SPEND, "u3", 9.8, 50, 5))
```

- **The check happens before the spend, and spending is recorded only when allowed.**
- **u1 at 4.9 cannot spend another 0.2 under a limit of 5.**
- **u3's first 0.2 is fine.** The total is now 45.1.
- **A 9.8 request would take the day to 54.9, so the global limit refuses it first.** In production, the refusal triggers a degraded path, not a silent failure.

Finally, sticky canary assignment and the rollout decision.

```python
def variant(user_id, percent):
    return "canary" if int(hashlib.sha256(user_id.encode()).hexdigest(), 16) % 100 < percent else "stable"

def canary(stable, candidate, min_requests=200, max_error_delta=0.01, max_cost_ratio=1.2):
    if candidate["requests"] < min_requests:
        return "wait", f"{candidate['requests']} of {min_requests} requests"
    stable_errors = stable["errors"] / stable["requests"]
    cand_errors = candidate["errors"] / candidate["requests"]
    if cand_errors - stable_errors > max_error_delta:
        return "rollback", f"error rate {cand_errors:.3f} vs {stable_errors:.3f}"
    stable_cost = stable["cost"] / stable["requests"]
    cand_cost = candidate["cost"] / candidate["requests"]
    if cand_cost > stable_cost * max_cost_ratio:
        return "rollback", f"cost per request {cand_cost:.4f} vs {stable_cost:.4f}"
    return "promote", "within error and cost limits"

USERS = [f"user-{i}" for i in range(1, 21)]
print([u for u in USERS if variant(u, 10) == "canary"], [u for u in USERS if variant(u, 25) == "canary"])
STABLE = {"requests": 5000, "errors": 40, "cost": 100.0}
print(canary(STABLE, {"requests": 120, "errors": 0, "cost": 2.4}))
print(canary(STABLE, {"requests": 400, "errors": 9, "cost": 8.0}))
print(canary(STABLE, {"requests": 400, "errors": 3, "cost": 10.0}))
print(canary(STABLE, {"requests": 400, "errors": 4, "cost": 8.8}))
```

- **At 10 percent, users 3, 6, and 10 are on the canary; at 25 percent, user 9 joins them.** Everyone already on the canary stays there.
- **120 requests is too few to decide: wait.**
- **An error rate of 0.022 against 0.008 rolls back.** More than one point worse.
- **Equal accuracy at 0.025 per request against 0.020 also rolls back.** 25 percent dearer than the 20 percent allowance.
- **An error rate of 0.010 against 0.008, within the one-point tolerance, and 10 percent dearer: promote.**

**Complexity.** `capacity` and `shape` are constant. `Queue.receive` scans the messages here; managed queues do this in constant time. `TokenBucket.allow` is constant. `budget_guard` sums the spend dictionary; production keeps a running total. `variant` is one hash; `canary` is constant.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Running agents inside the HTTP request.** Minute-long tasks hit gateway timeouts. Acknowledge fast and work from a queue.

**Visibility timeout shorter than the task.** Slow tasks are redelivered mid-flight. Set it above the p99 or extend it while working.

**Assuming exactly-once.** Queues redeliver. Make side effects idempotent.

**No dead-letter queue.** One malformed ticket retries forever. Move it aside after a few receives.

**Sizing by arrival rate alone.** Long tasks need many concurrent workers. Use Little's law.

**Workers at 100 percent utilisation.** Queues explode near full load. Target 60 to 80 percent.

**Per-worker rate limiters.** Ten workers each allowed the full provider limit exceed it tenfold. Share the bucket.

**Budgets as dashboards.** A report next morning does not stop last night's loop. Enforce before spending.

**One customer eats the budget.** Without per-user limits, abuse or a stuck integration starves everyone. Cap per user or tenant.

**Big-bang prompt changes.** A new prompt to 100 percent of traffic turns a subtle regression into an outage. Canary it.

**Non-sticky canaries.** Users bouncing between versions see inconsistent behaviour, and the metrics blur. Hash the user.

**Watching only errors.** A canary can be as accurate and far more expensive. Compare cost too.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Deploying an agent means choosing shapes by trigger and tail duration: serverless for short bursty work within hard time limits such as Lambda's 900 seconds, containers for steady traffic, queues and workers for long tasks and bursts, schedulers for timetabled jobs, and durable workflow engines for multi-step tasks that wait. Little's law, concurrency equals arrival rate times duration, sizes the worker pool, with headroom below full utilisation. Queues hide received messages for a visibility timeout and redeliver them if not deleted, giving at-least-once delivery, so timeouts must exceed task durations, side effects must be idempotent, and repeated failures go to a dead-letter queue. Workers stay stateless, with state in stores and leases preventing concurrent processing of one conversation. Token buckets, which the Claude API itself uses, allow bursts up to capacity while enforcing an average rate, and must be shared across workers. Budgets are enforced before spending, globally and per user, with graceful degradation. Traces and metrics, including queue age and cost per task, make the system visible. Releases roll out as sticky canaries that are promoted only after enough requests show errors and cost within limits.

**Question 1.** Customers occasionally receive two refunds. The refund agent runs as a queue worker with a 30-second visibility timeout; the median refund task takes 12 seconds and the p99 takes 48 seconds. Explain the cause using the lab's `Queue`, and give two fixes that should both be applied.

<details>
<summary>View Answer</summary>

When a worker receives a refund message, the queue hides it for 30 seconds. Most tasks finish in about 12 seconds and delete the message in time, but the slowest few percent take longer than 30 seconds; for those, the message becomes visible again while the first worker is still running, a second worker receives it, and both complete the refund. The lab shows the mechanism: `receive(31)` delivers m1 a second time, with a receive count of 2, because it was not deleted within the timeout. This is the at-least-once delivery the SQS documentation describes, not a bug in the queue. The first fix is to set the visibility timeout well above the task's realistic maximum, for example 300 seconds against a 48-second p99, or to have the worker extend the timeout periodically while it works, so slow tasks are not redelivered. The second fix, needed regardless, is idempotency: the refund call carries a key derived from the ticket, such as the ticket identifier plus "refund", and the payment step, or the payment provider's own idempotency support, refuses to execute a key it has already completed. The timeout fix makes duplicates rare; idempotency makes them harmless, which matters because crashes and network failures cause redelivery too.

</details>

**Question 2.** A team plans capacity for a nightly job that researches 300 suppliers, each task taking about 40 minutes, to be finished within a 4-hour window. Using Little's law, how many tasks must run at once, how many workers do they need at 70 percent utilisation, and what else must they check before launching?

<details>
<summary>View Answer</summary>

To finish 300 tasks in 240 minutes, the arrival rate through the system must average 300 divided by 240, 1.25 tasks per minute. Each takes 40 minutes, so by Little's law the average number in progress is 1.25 times 40, 50 concurrent tasks. At 70 percent target utilisation, the lab's `capacity(1.25, 40)` gives 50 concurrent and 72 workers, the ceiling of 50 divided by 0.7. More importantly, 50 concurrent agent tasks each making model calls must fit within the provider's rate limits: if each task averages, say, 2,000 tokens per minute, 50 tasks need about 100,000 tokens per minute, so the team must check its tier's limits and set a shared token bucket below them; otherwise the workers will spend the night retrying 429 errors and miss the window. They should also check the budget, 300 tasks times the cost per task against the daily limit, with a per-run cap; the shape, since 40-minute tasks exceed a 15-minute serverless timeout and belong on queue workers or a durable workflow; the visibility timeout, well above 40 minutes or extended while working; and observability, queue age and completion rate during the run, with an alert if the projected finish time passes the window.

The 10 percent cost increase is acceptable under the rule, but it should be a conscious decision: across all traffic it adds 10 percent to the support agent's bill.

"""
Lab solution: Capacity and Shape, Queue Redelivery, Token Buckets, Budget Guards, Canary Rollouts
Standard library only. No network calls or models.

import hashlib
import math

USERS = [f"user-{i}" for i in range(1, 21)]
STABLE = {"requests": 5000, "errors": 40, "cost": 100.0}


# ---------------------------------------------------------------- Step 1
def capacity(arrivals_per_min, minutes_per_task, utilisation=0.7):
    """L = lambda * W, with headroom below full utilisation."""
    concurrent = arrivals_per_min * minutes_per_task
    return round(concurrent, 2), math.ceil(concurrent / utilisation)


def shape(job, timeout_s=900):
    """Shape follows the trigger and the tail duration."""
    if job["trigger"] == "schedule":
        return "scheduler", "runs on a timetable"
    if job["p99_seconds"] > timeout_s:
        return "queue_worker", f"p99 {job['p99_seconds']}s exceeds the {timeout_s}s function timeout"
    if job["trigger"] == "http" and job["steady"]:
        return "container", "steady traffic keeps a service busy"
    return "serverless", "short, bursty work"


# ---------------------------------------------------------------- Step 2
class Queue:
    """Visibility timeouts: robust to crashes, and therefore at-least-once."""

    def __init__(self, visibility=30):
        self.visibility, self.messages, self.next_id = visibility, {}, 1

    def send(self, body):
        mid = f"m{self.next_id}"
        self.next_id += 1
        self.messages[mid] = {"body": body, "visible_at": 0, "receives": 0}
        return mid

    def receive(self, now):
        for mid in sorted(self.messages, key=lambda m: int(m[1:])):
            message = self.messages[mid]
            if message["visible_at"] <= now:
                message["visible_at"] = now + self.visibility
                message["receives"] += 1
                return mid, message["body"], message["receives"]
        return None

    def delete(self, mid):
        return self.messages.pop(mid, None) is not None


# ---------------------------------------------------------------- Step 3
class TokenBucket:
    """Capacity sets the burst; rate sets the average."""

    def __init__(self, rate, capacity):
        self.rate, self.capacity, self.tokens, self.last = rate, capacity, capacity, 0.0

    def allow(self, now, cost=1):
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True, round(self.tokens, 2)
        return False, round(self.tokens, 2)


# ---------------------------------------------------------------- Step 4
def budget_guard(spend, user, cost, daily_limit, user_limit):
    """Enforce before spending, globally and per user."""
    if sum(spend.values()) + cost > daily_limit:
        return False, "daily budget reached"
    if spend.get(user, 0) + cost > user_limit:
        return False, "user budget reached"
    spend[user] = round(spend.get(user, 0) + cost, 4)
    return True, "ok"


# ---------------------------------------------------------------- Step 5
def variant(user_id, percent):
    """Sticky and nested: raising the percentage keeps existing canary users."""
    return "canary" if int(hashlib.sha256(user_id.encode()).hexdigest(), 16) % 100 < percent else "stable"


def canary(stable, candidate, min_requests=200, max_error_delta=0.01, max_cost_ratio=1.2):
    """Promote on evidence: enough requests, errors and cost within limits."""
    if candidate["requests"] < min_requests:
        return "wait", f"{candidate['requests']} of {min_requests} requests"
    stable_errors = stable["errors"] / stable["requests"]
    cand_errors = candidate["errors"] / candidate["requests"]
    if cand_errors - stable_errors > max_error_delta:
        return "rollback", f"error rate {cand_errors:.3f} vs {stable_errors:.3f}"
    stable_cost = stable["cost"] / stable["requests"]
    cand_cost = candidate["cost"] / candidate["requests"]
    if cand_cost > stable_cost * max_cost_ratio:
        return "rollback", f"cost per request {cand_cost:.4f} vs {stable_cost:.4f}"
    return "promote", "within error and cost limits"
