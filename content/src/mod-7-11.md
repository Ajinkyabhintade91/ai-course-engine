# Gmail Automation

Email is where a great deal of business work arrives: orders, questions, complaints, invoices, introductions. That makes the inbox one of the most valuable places to automate, and one of the most dangerous. An automation that reads mail can read everything. One that sends mail can embarrass a company in front of a customer in seconds, or send the same wrong message to a thousand people.

This chapter covers automating Gmail properly. It explains the triggers and actions available, read, label, draft, and send; how an AI triage step classifies, summarises, and drafts; the permissions, called OAuth scopes, that an automation asks for; the quotas that limit how fast it can work; and how to design sending so that mistakes stay in the drafts folder. The lab builds the pieces underneath: quota budgeting, scope selection, message parsing, threaded replies, and a send gate.

## 1. First-Principles Mental Model & Intuition

### A new assistant with a key to the post room

Imagine hiring an assistant to handle the company's post. On day one, you would not hand over the keys and say "deal with it". You would let them open and sort the post, put each letter in the right tray, and draft replies for you to sign. Only after weeks of good work would you let them send routine replies, the "thanks, received" kind, on their own. Anything about money, legal matters, or an angry customer would still come to you.

An email automation deserves the same treatment.

```text
   NEW EMAIL ARRIVES
        |
        v
   READ        fetch headers first, the body only if needed
        |
        v
   CLASSIFY    AI step: category, urgency, confidence      (Unit 5 prompts, Module 7.10 call)
        |
        v
   LABEL       apply a Gmail label: Support/Delivery, Billing, Spam-ish
        |
        v
   DRAFT       AI step writes a reply, saved as a Gmail draft in the same thread
        |
        v
   GATE        routine + confident + safe?  --yes-->  SEND
                         |
                         no
                         v
               leave the draft for a person, notify them
```

The stages are ordered by risk. Reading and labelling are reversible and invisible to customers. Drafting is invisible until someone presses send. Sending is irreversible and public. Most of an inbox assistant's value comes from the first three stages, which carry little risk; the last stage should be earned.

### What can be automated

| Stage | Gmail action | Typical use |
|---|---|---|
| Trigger | New email, new labelled email, new email matching a search | Start the workflow |
| Read | Get message metadata or full content | Feed the classifier |
| Label | Add or remove labels, archive, mark as read | Sort the inbox |
| Draft | Create a draft, optionally in a thread | Prepare replies for review |
| Send | Send a message or a draft | Routine replies, notifications |

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Triggers: polling and push

Workflow tools usually offer a Gmail trigger that polls: it asks Gmail every few minutes for messages newer than the last one seen, with the deduplication by ID from Module 7.6. Underneath, the Gmail API also supports **push notifications**: a `watch` call asks Gmail to publish a notification to a Google Cloud Pub/Sub topic whenever the mailbox changes, and the automation then asks for the history of changes since the last `historyId`. Google's documentation is specific about one maintenance task: you must call `watch` at least once every 7 days or notifications stop, and it recommends calling it once a day. A push-based integration that works perfectly for a week and then goes silent is usually missing that renewal.

A Gmail trigger can also be narrowed with Gmail's own search syntax, such as `to:support@ is:unread -category:promotions`, so that only relevant mail starts a run. Like a filter placed straight after the trigger in Module 7.9, this is the cheapest filter available.

### Messages are MIME documents

An email is not a simple record. It is a **MIME** document: headers such as `From`, `To`, `Subject`, `Date`, and `Message-ID`, followed by a body that is often several parts at once, a plain-text version and an HTML version of the same content, plus attachments, all nested inside one another.

```text
   From: Priya Shah <priya@example.com>
   Subject: Where is my order A1234?
   Message-ID: <CAB123@mail.example.com>
   Content-Type: multipart/alternative
     +-- part 1: text/plain   "Hi, my order A1234 has not arrived yet."   plus the quoted earlier reply
     +-- part 2: text/html    the same message with formatting
```

A classifier needs the plain text of the new message, without the HTML, without the quoted history of earlier replies, and without the signature. Feeding it the whole thread wastes tokens and confuses it with text the customer did not write today. Parsing an email properly, choosing the plain-text part, decoding it, and cutting off the quoted history, is the first job of any inbox automation, and Python's standard `email` package does the hard part.

When the Gmail API returns or accepts a whole message, it uses the `raw` field: the complete MIME message encoded as **base64url**, a variant of base64 that is safe in URLs.

### Threads

Gmail groups a conversation into a **thread**. A reply that lands outside the thread looks to the customer like an unrelated new email, and to the support team like a lost conversation. Google's threading guide lists the conditions for a message to join a thread:

1. The request includes the thread's `threadId`.
2. The `In-Reply-To` and `References` headers are set to the original message's `Message-ID`, as the email standard describes.
3. The `Subject` matches.

By convention a reply's subject is the original's with "Re: " in front, added once: a subject that already starts with "Re:" must not become "Re: Re:". Changing the words of the subject is what breaks a thread.

### OAuth scopes

A Gmail automation signs in with OAuth, Module 7.15's subject, and asks for **scopes**, named permissions. Google classifies Gmail's scopes by risk:

| Scope | Allows | Google's classification |
|---|---|---|
| `gmail.labels` | Create and edit labels | Non-sensitive |
| `gmail.send` | Send email, nothing else | Sensitive |
| `gmail.readonly` | Read all email and settings | Restricted |
| `gmail.metadata` | Read headers and labels, not bodies | Restricted |
| `gmail.compose` | Manage drafts and send | Restricted |
| `gmail.modify` | Read, compose, send, and change labels; no permanent deletion | Restricted |
| `mail.google.com` | Everything, including permanent deletion | Restricted |

Two principles follow. First, ask for the **narrowest** set of scopes that covers what the automation does: an automation that only sends notifications needs `gmail.send`, not `gmail.modify`. Second, know that restricted scopes carry obligations: an app that requests them from users outside your own organisation goes through Google's verification, including a security assessment, before it can be used widely. For a company's internal automation on its own Workspace accounts, the obligation is lighter, but the principle of least privilege still applies: if the automation's credentials leak, the scopes decide what an attacker can do.

Some scopes cover others. `gmail.modify` includes reading, composing, and sending, so an automation that labels messages, which needs `gmail.modify`, does not also need `gmail.readonly`. `gmail.compose` includes sending. A scope chooser should drop scopes covered by another it already has.

### Quotas

The Gmail API meters use in **quota units**. Google's published limits, at the time of writing (November 2026), are 1,200,000 units per minute per project and 6,000 units per minute **per user** per project, and each method has a cost:

| Method | Units |
|---|---|
| `messages.list` | 5 |
| `messages.get` | 20, or 60 when the format is full, raw, or html |
| `messages.modify` (change labels) | 5 |
| `drafts.create` | 10 |
| `messages.send` | 100 |
| `history.list` | 2 |
| `watch` | 100 |

For one inbox, the per-user limit is the one that bites. Fetching full content costs three times as much as fetching metadata, so an efficient triage reads headers first and fetches the body only for messages that need it. Sending is the most expensive call: 6,000 units allow at most 60 sends a minute from one user. There is also a limit of 500 recipients per message through the API.

Sending limits exist outside the API too. Google Apps Script, often used for simple Gmail automations, limits email recipients per day to 100 for consumer accounts and 1,500 for Workspace accounts at the time of writing. A daily cap in the automation itself, well below any platform limit, protects against a loop that sends the same message repeatedly.

### AI triage

The AI part of an inbox assistant usually does three jobs, each a model call of the kind Module 7.10 described:

| Job | Output | Model size |
|---|---|---|
| Classify | A category, an urgency, a confidence | Small model is usually enough |
| Summarise | One or two lines for a dashboard or chat message | Small or mid-sized |
| Draft | A reply in the company's voice | Mid-sized or larger |

The classification prompt should return structured output, a JSON object with a fixed set of categories, as Module 5.10 recommended, and the workflow should check it before acting. Model "confidence" scores deserve caution: a model's stated confidence is not a calibrated probability, so a threshold such as 0.9 is a useful filter only after testing it against a labelled sample of real emails, the evaluation method of Module 5.9.

### The safe-send design

The safest inbox assistants never send by themselves. The next safest send only when every one of several conditions holds:

| Condition | Why |
|---|---|
| The category is not on the blocked list, and is a routine type | Billing, legal, and complaints always need a person |
| The confidence is above a tested threshold | Low-confidence answers are where mistakes concentrate |
| There is exactly one recipient, the original sender | No accidental broadcasts |
| The reply was generated completely | A `max_tokens` stop means a truncated email, as Module 7.10 warned |
| The daily send count is under a cap | Stops runaway loops |

Everything that fails a condition stays a draft in the thread, labelled for review, and a person is notified. A dry-run period, in which the gate decides but sends nothing, logging what it would have sent, is the best way to tune the conditions before switching sending on.

### Complexity

Quota use is a sum over calls of their unit costs. Parsing a message is linear in its size. Building a reply is linear in its text. The send gate checks a fixed number of conditions.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, budgeting quota.

```python
UNITS = {"messages.list": 5, "messages.get": 20, "messages.get.full": 60, "messages.modify": 5,
         "drafts.create": 10, "messages.send": 100, "history.list": 2, "watch": 100}
PER_USER_PER_MINUTE = 6000

def quota(calls):
    total = sum(UNITS[method] * count for method, count in calls.items())
    return total, total <= PER_USER_PER_MINUTE

print(quota({"messages.list": 1, "messages.get": 50, "messages.get.full": 50, "messages.modify": 50, "drafts.create": 10}))
print(quota({"messages.list": 1, "messages.get.full": 100}))
print(quota({"messages.list": 1, "messages.get": 100, "messages.get.full": 20, "messages.modify": 100}))
print(quota({"messages.send": 61}))
```

- **Each method's cost comes from Google's table.** `messages.get.full` stands for a get in full format, which costs 60 instead of 20.
- **Triaging 50 emails, reading metadata and then full bodies for all of them, labelling all, and drafting 10, costs 4,355 units.** It fits in a minute.
- **Fetching 100 full messages at once costs 6,005 and does not fit.** The calls would start failing with rate-limit errors.
- **Reading metadata for 100, full bodies for only 20, and labelling 100 costs 3,705.** Headers alone are often enough to classify newsletters and notifications, so fetching bodies selectively cuts the cost by more than a third.
- **61 sends in a minute exceed the limit.** Sending is the most expensive operation by far.

Next, choosing scopes.

```python
SCOPE_FOR = {"read": "gmail.readonly", "apply_label": "gmail.modify", "create_label": "gmail.labels",
             "draft": "gmail.compose", "send": "gmail.send"}
COVERS = {"gmail.modify": {"gmail.readonly", "gmail.compose", "gmail.send"}, "gmail.compose": {"gmail.send"}}
RESTRICTED = {"gmail.readonly", "gmail.modify", "gmail.compose"}
SENSITIVE = {"gmail.send"}

def least_scopes(actions):
    needed = {SCOPE_FOR[action] for action in actions}
    for scope in list(needed):
        needed -= COVERS.get(scope, set())
    level = "restricted" if needed & RESTRICTED else "sensitive" if needed & SENSITIVE else "non-sensitive"
    return sorted(needed), level

print(least_scopes(["send"]))
print(least_scopes(["read", "draft"]))
print(least_scopes(["read", "apply_label", "draft", "create_label"]))
print(least_scopes(["create_label"]))
```

- **Each action maps to the narrowest scope that allows it.** Reading needs `gmail.readonly`, applying labels to messages needs `gmail.modify`, creating labels needs only `gmail.labels`, drafting needs `gmail.compose`, sending needs `gmail.send`.
- **Scopes covered by another are dropped.** With `gmail.modify` in the set, `gmail.readonly` and `gmail.compose` are redundant.
- **A send-only notifier needs one sensitive scope.** Not a restricted one.
- **Reading and drafting need two restricted scopes.** A full triage assistant needs `gmail.labels` and `gmail.modify`.
- **The level is the most serious classification in the set.** It tells you what review and protection the credentials deserve.

Then, parsing a message.

```python
import email
from email import policy

RAW = b"""From: Priya Shah <priya@example.com>
To: support@toolshop.example
Subject: Where is my order A1234?
Message-ID: <CAB123@mail.example.com>
Date: Mon, 16 Nov 2026 09:12:00 +0000
Content-Type: multipart/alternative; boundary="b1"

--b1
Content-Type: text/plain; charset="utf-8"

Hi, my order A1234 has not arrived yet.
Can you check?

Thanks,
Priya

> On Fri, Support wrote:
> Your order has been dispatched.
--b1
Content-Type: text/html; charset="utf-8"

<p>Hi, my order A1234 has not arrived yet.</p>
--b1--
"""

def parse_email(raw):
    message = email.message_from_bytes(raw, policy=policy.default)
    part = message.get_body(preferencelist=("plain",))
    body = part.get_content() if part else ""
    kept = []
    for line in body.splitlines():
        if line.startswith(">") or line.strip() == "--":
            break
        kept.append(line)
    sender = message["From"].addresses[0]
    return {"from": sender.addr_spec, "name": sender.display_name, "subject": str(message["Subject"]),
            "message_id": str(message["Message-ID"]), "body": "\n".join(kept).strip()}

print(parse_email(RAW))
```

- **`policy.default` gives the modern email API.** Headers are parsed into objects, so the `From` header's address and display name can be read separately.
- **`get_body` with a preference for plain text picks the text part.** The HTML part is ignored. If there were no plain part, `part` would be None and the body empty, a case the workflow should route to a person.
- **Reading stops at the first quoted line or signature marker.** The customer's earlier exchange, "Your order has been dispatched", is not part of today's message.
- **The result is a small, clean record.** Sender address, name, subject, the `Message-ID` needed for threading, and the new text only.

Then, a threaded reply.

```python
import base64
from email.message import EmailMessage

def build_reply(original, sender, text):
    reply = EmailMessage()
    subject = original["subject"]
    reply["Subject"] = subject if subject.lower().startswith("re:") else "Re: " + subject
    reply["From"] = sender
    reply["To"] = original["from"]
    reply["In-Reply-To"] = original["message_id"]
    reply["References"] = original["message_id"]
    reply.set_content(text)
    return base64.urlsafe_b64encode(reply.as_bytes()).decode("ascii"), reply

parsed = parse_email(RAW)
raw, reply = build_reply(parsed, "support@toolshop.example", "Hi Priya, we are checking with the courier and will update you today.")
print(reply["Subject"], reply["In-Reply-To"])
print(email.message_from_bytes(base64.urlsafe_b64decode(raw), policy=policy.default)["To"])
```

- **The subject gets "Re: " once.** A subject that already begins with "Re:" in any capitalisation is kept as it is.
- **The reply goes to the original sender only.** One recipient, chosen by the code, not by the model.
- **`In-Reply-To` and `References` carry the original `Message-ID`.** Together with the `threadId` in the API request, they keep the reply in the customer's thread.
- **`set_content` builds a correct plain-text MIME body.** No hand-built headers or encodings.
- **The message is encoded as base64url for the API's `raw` field.** Decoding it again shows the recipient is intact.
- **The same message can be sent or saved as a draft.** `drafts.create` with this raw message and the `threadId` puts it in the thread for review.

Finally, the send gate.

```python
def send_gate(draft, sent_today, daily_cap=100, threshold=0.9, blocked=("billing", "legal", "complaint")):
    reasons = []
    if draft["category"] in blocked:
        reasons.append("category:" + draft["category"])
    if draft["confidence"] < threshold:
        reasons.append("confidence")
    if len(draft["to"]) != 1:
        reasons.append("recipients")
    if sent_today >= daily_cap:
        reasons.append("daily_cap")
    if not draft["complete"]:
        reasons.append("incomplete")
    return ("send" if not reasons else "draft"), reasons

print(send_gate({"category": "delivery", "confidence": 0.95, "to": ["priya@example.com"], "complete": True}, 12))
print(send_gate({"category": "billing", "confidence": 0.97, "to": ["a@b.c"], "complete": True}, 12))
print(send_gate({"category": "delivery", "confidence": 0.7, "to": ["a@b.c", "d@e.f"], "complete": False}, 100))
```

- **Every condition from Section 2 is checked, and every failure is recorded.** The reasons explain to the reviewer why the draft was held.
- **A confident, routine, single-recipient, complete reply is sent.** The first draft passes everything.
- **A billing reply is held however confident it is.** Blocked categories always go to a person.
- **The third draft fails four ways.** The reasons list all of them, which helps tune the gate during the dry run.
- **The decision is "send" or "draft", never "discard".** A held reply is still useful work for the person who reviews it.

**Complexity.** `quota` is linear in the methods listed, `least_scopes` in the actions, `parse_email` in the message size, `build_reply` in the reply text, and `send_gate` is constant.

### An inbox assistant plan

```text
MAILBOX          support@  (Workspace account, internal use)
TRIGGER          Gmail search: to:support@ is:unread -category:promotions; push via watch, renewed daily
SCOPES           gmail.modify + gmail.labels   (no mail.google.com)
READ             metadata first; full body only for categories that need drafting
CLASSIFY         small model, JSON: {category, urgency, confidence}; checked against the category list
LABEL            Triage/[category]; Urgent if urgency is high
DRAFT            mid-sized model, company voice, saved as draft in the thread
GATE             allow-list: delivery-status, opening-hours; threshold tested on 200 labelled emails
                 single recipient; complete; daily cap 50
DRY RUN          two weeks: gate decides, logs, sends nothing
ALERTS           held drafts posted to the support channel with a link
```

### Which stage to automate first

| Stage | Risk | Value | Automate when |
|---|---|---|---|
| Label | Low | Medium | Immediately |
| Summarise to chat | Low | Medium | Immediately |
| Draft for review | Low | High | After testing the prompt on real emails |
| Send routine replies | High | Medium | After a dry run and a tested threshold |
| Send anything else | Very high | Low | Not at all |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Auto-send on day one.** The fastest way to lose trust in an automation is a wrong email to a customer. Start with labels and drafts.

**Replies outside the thread.** Missing `threadId`, `In-Reply-To`, or `References`, or a reworded subject, scatter conversations. Set all of them.

**"Re: Re: Re:".** Prefixing every time a reply is built makes subjects grow. Add the prefix only if it is absent.

**Classifying the whole thread.** Quoted history and signatures confuse the classifier and cost tokens. Parse out the new text first.

**HTML-only messages.** Some senders send no plain-text part. Have a fallback, such as stripping tags, or route them to a person.

**Broad scopes for convenience.** `mail.google.com` allows permanent deletion. Ask for the narrowest scopes that work.

**Push that stops after a week.** `watch` expires. Renew it daily.

**Fetching full bodies for everything.** It triples quota use. Read metadata first.

**Loops between two automations.** An auto-reply to an auto-reply can bounce forever. Never reply to messages with auto-reply headers, and cap daily sends.

**Trusting model confidence.** Stated confidence is not calibrated. Test the threshold against labelled emails.

**Personal data sent to models.** Emails contain names, addresses, and sometimes worse. Send only what the task needs, and check the model provider's data terms, as Module 7.10 warned.

**No dry run.** Switching sending on without a period of logged, unsent decisions means learning the gate's mistakes from customers.

**Question 2.** An automation replies to customers through the Gmail API, but customers report that replies arrive as separate emails, and some subjects read "Re: Re: Re: Order question". Explain both problems and the exact fixes, including what the reply's headers should contain when the original `Message-ID` is `<X9@mail.example.com>` and the subject is "Order question".

<details>
<summary>View Answer</summary>

Replies arrive outside the conversation because they do not meet Gmail's threading conditions: the send request must include the thread's `threadId`, the reply must carry `In-Reply-To` and `References` headers referring to the original message's `Message-ID`, and the subject must match. The automation is probably omitting the headers or the `threadId`, so Gmail treats each reply as a new conversation. The growing subject comes from adding "Re: " every time a reply is built, including when replying to a message whose subject already starts with "Re:". # ---------------------------------------------------------------- Step 1
def quota(calls):
    """Full-format reads cost three times metadata reads; a send costs 100."""
    total = sum(UNITS[method] * count for method, count in calls.items())
    return total, total <= PER_USER_PER_MINUTE


# ---------------------------------------------------------------- Step 2
def least_scopes(actions):
    """The narrowest scopes that cover the actions, with redundant ones dropped, and the most
    serious of Google's classifications among them."""
    needed = {SCOPE_FOR[action] for action in actions}
    for scope in list(needed):
        needed -= COVERS.get(scope, set())
    level = "restricted" if needed & RESTRICTED else "sensitive" if needed & SENSITIVE else "non-sensitive"
    return sorted(needed), level


# ---------------------------------------------------------------- Step 3
def parse_email(raw):
    """Plain text only, today's message only: no HTML part, no quoted history, no signature."""
    message = email.message_from_bytes(raw, policy=policy.default)
    part = message.get_body(preferencelist=("plain",))
    body = part.get_content() if part else ""
    kept = []
    for line in body.splitlines():
        if line.startswith(">") or line.strip() == "--":
            break
        kept.append(line)
    sender = message["From"].addresses[0]
    return {"from": sender.addr_spec, "name": sender.display_name, "subject": str(message["Subject"]),
            "message_id": str(message["Message-ID"]), "body": "\n".join(kept).strip()}


# ---------------------------------------------------------------- Step 4
def build_reply(original, sender, text):
    """Threading needs In-Reply-To, References, and a matching subject (plus threadId in the
    API request). The recipient is chosen by code, never by the model."""
    reply = EmailMessage()
    subject = original["subject"]
    reply["Subject"] = subject if subject.lower().startswith("re:") else "Re: " + subject
    reply["From"] = sender
    reply["To"] = original["from"]
    reply["In-Reply-To"] = original["message_id"]
    reply["References"] = original["message_id"]
    reply.set_content(text)
    return base64.urlsafe_b64encode(reply.as_bytes()).decode("ascii"), reply


# ---------------------------------------------------------------- Step 5
def send_gate(draft, sent_today, daily_cap=100, threshold=0.9, blocked=("billing", "legal", "complaint")):
    """Send only when every condition holds; otherwise keep the draft and say why."""
    reasons = []
    if draft["category"] in blocked:
        reasons.append("category:" + draft["category"])
    if draft["confidence"] < threshold:
        reasons.append("confidence")
    if len(draft["to"]) != 1:
        reasons.append("recipients")
    if sent_today >= daily_cap:
        reasons.append("daily_cap")
    if not draft["complete"]:
        reasons.append("incomplete")
    return ("send" if not reasons else "draft"), reasons
