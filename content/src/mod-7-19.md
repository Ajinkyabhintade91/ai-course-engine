# Project 4: Automated Reporting

Every business has reports that someone assembles by hand: the Monday sales summary, the month-end figures, the weekly marketing numbers. Someone downloads data, pastes it into a spreadsheet, works out the totals and the changes, writes a few sentences, and emails it. An automated report does all of that on a schedule, and a language model can write the sentences. That last part is where reporting automation goes wrong most often, because a model writing about numbers will sometimes write different numbers.

This project builds a report that people can trust. Its central rule is simple: **code computes every number; the model only writes words around them, and code checks that it did.** Around that rule sit a scheduled collection step, safe comparisons, alert thresholds, delivery, and checks that stop a report built on missing data.

## 1. First-Principles Mental Model & Intuition

### An accountant and a writer

Imagine a report produced by two people. An accountant works through the ledger and prepares a sheet of figures: totals, averages, changes, anything unusual. A writer then turns the sheet into a short, readable paragraph. The writer may choose which figures to mention and how to phrase them, but may not change a figure or add one. Before the report goes out, the accountant reads the paragraph and checks every number in it against the sheet.

The automated report divides the work in exactly this way, with code as the accountant and the model as the writer.

```text
   SCHEDULE         Monday 07:00 (cron, Module 7.6)
       |
       v
   COLLECT          pull last week's orders and the week before (API, sheet, or database)
       |
       v
   CHECK DATA       any rows? enough rows? data fresh?  -- no --> send "report not produced" alert
       |
       v
   COMPUTE          totals, averages, by channel, change against last week, anomalies     (code)
       |
       v
   FACTS            a small JSON object of computed figures
       |
       v
   WRITE            model writes 3 sentences using only the facts                          (model)
       |
       v
   VERIFY           every number in the text must be in the facts  -- fails --> send figures without commentary
       |
       v
   DELIVER          email, chat message, or dashboard; alerts only for anomalies
```

### Why the model must not calculate

Language models generate text one token at a time, predicting what is likely to come next. They are not calculators. Asked to add a column of figures, a model often gets it right, sometimes gets it slightly wrong, and gives no sign of which. A report with a wrong total is worse than no report, because people act on it. The figures must come from code, which is boringly, reliably correct.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Collecting on a schedule

A schedule trigger, written as cron as Module 7.6 explained, starts the report. Two schedule details matter for reports specifically. The **reporting period** must be defined precisely, for example Monday 00:00 to Sunday 23:59 in the business's time zone, not "the last seven days from whenever the job runs", or a delayed run silently covers a different week. And the job should run late enough that the period's data has arrived: an order system that syncs overnight needs the report to run in the morning, not at midnight.

### Computing the summary

The core figures for a sales report are simple aggregations:

| Figure | Formula |
|---|---|
| Orders | Count of orders in the period |
| Revenue | Sum of order totals |
| Average order value | Revenue divided by orders, if there are any |
| By channel | Revenue grouped by sales channel |

Every figure is computed from the raw rows, in code, and rounded to two places by code, never by the model.

### Comparing periods

Week-on-week change is

$$\text{change}\% = 100 \times \frac{\text{current} - \text{previous}}{\text{previous}}$$

with one essential guard: when the previous value is zero, the percentage is undefined, not infinite and not zero. A new product line that sold nothing last week and ten items this week has no meaningful percentage change; the report should say "new this week". A fall to zero is minus 100 percent, which is defined and important.

### Alert thresholds and anomalies

A report can also notice things: a day with far fewer orders than usual, a spike in refunds. The simplest test compares a value with recent history using a **z-score**: how many standard deviations the value lies from the mean of the history.

$$z = \frac{x - \bar{x}}{s}$$

where $\bar{x}$ is the mean of the recent history and $s$ its sample standard deviation. A common rule flags values with $|z| \ge 3$. For daily revenue of 1,180, 1,240, 1,205, 1,190, 1,260, 1,225, and 1,210 over the past week, a day of 640 has a z-score of about minus 20.5, clearly unusual; a day of 1,230 has about 0.5, perfectly normal.

The NIST/SEMATECH e-Handbook of Statistical Methods adds two cautions. Z-scores can mislead for small samples, and outliers in the history inflate the standard deviation and hide later outliers; it describes the **modified z-score**, which uses the median and the median absolute deviation instead, with values beyond 3.5 flagged as potential outliers, as Iglewicz and Hoaglin recommend. For business reports, simple alternatives also work well: a percentage deviation from the same weekday's average over several weeks, which respects weekly patterns, or fixed limits agreed with the business, "alert if daily orders fall below 20".

Whatever the test, the threshold is set in code, deliberately, and is never left to the model's judgement. A model asked "is anything unusual?" will often find something, because the question invites it.

### Facts in, words out

The model receives a small, explicit object of computed facts:

```text
   {"orders": 14, "revenue": 757.0, "previous_revenue": 690.0, "change_percent": 9.7,
    "top_channel": "web", "top_channel_revenue": 483.0, "anomalies": []}
```

and a prompt along the lines of: "Write three sentences for a shop owner summarising this week. Use only these figures. Do not calculate new numbers. Do not speculate about causes." Anthropic's guidance on building effective workflows describes exactly this shape, a chain of steps with programmatic checks, or gates, between them.

### Verifying the words

The final check extracts every number from the model's text and confirms each appears among the facts, after normalising formats, so "757.00", "757", and "GBP 757.00" all match 757.0, and "9.7%" matches 9.7. A sentence such as "Revenue rose 12 percent across 15 orders" fails twice: neither 12 nor 15 is in the facts.

When verification fails, the report should not be held back entirely. The safe fallback is to send the figures as a plain table without the commentary, and log the failure so the prompt can be improved. The numbers are what people rely on; the prose is a convenience.

Two details keep the check meaningful. Dates and labels in the report's title should be assembled by code, not written by the model, so that numbers in dates are never mistaken for claims. And rounding must be consistent: if the facts hold 54.07 and the model writes "about 54", the check fails, which is right, since the model was told not to alter numbers.

### Checking the data first

The most dangerous failure in reporting is silent: the schedule runs, the data source returns nothing, perhaps because an export failed or a token expired, and the report confidently announces "no sales this week, down 100 percent". Before computing anything, the report checks:

| Check | Catches |
|---|---|
| Any rows at all | Failed export, broken connection |
| At least a minimum number of rows | Partial data |
| The newest record is recent enough | A source that stopped updating |

If any check fails, the report is not produced; instead, an alert says what is wrong. This is the data-failure class from Module 7.14, caught before it reaches a reader.

### Delivery

| Channel | Good for |
|---|---|
| Email | Weekly and monthly summaries, read at leisure |
| Chat message | Short daily figures and alerts |
| Dashboard | Always-available detail, trends, drill-down |
| Spreadsheet row | A history of every report's figures, for later analysis |

Alerts and reports are different things. A report arrives on schedule whether or not anything happened. An alert arrives only when a threshold is crossed, and should follow Module 7.14's rules about deduplication and cooldowns. Google's SRE book makes the general point about monitoring: every alert should be actionable, because alerts that require no action train people to ignore alerts.

### Complexity

Summaries are linear in the rows. A change is constant time. A z-score is linear in the history length. Verifying numbers is linear in the text and the size of the facts.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, the weekly summary.

```python
from datetime import date, datetime, timedelta

SALES = [("web", 84.0), ("web", 22.5), ("shop", 40.0), ("web", 120.0), ("marketplace", 35.0), ("web", 64.5), ("shop", 18.0),
         ("web", 95.0), ("marketplace", 44.0), ("web", 30.0), ("shop", 76.0), ("web", 52.0), ("web", 15.0), ("marketplace", 61.0)]
ORDERS = [{"day": date(2026, 11, 9) + timedelta(days=i % 7), "channel": channel, "total": total}
          for i, (channel, total) in enumerate(SALES)]

def summarise(orders, start, end):
    rows = [order for order in orders if start <= order["day"] <= end]
    revenue = round(sum(order["total"] for order in rows), 2)
    by_channel = {}
    for order in rows:
        by_channel[order["channel"]] = round(by_channel.get(order["channel"], 0) + order["total"], 2)
    return {"orders": len(rows), "revenue": revenue,
            "average_order": round(revenue / len(rows), 2) if rows else 0.0,
            "by_channel": dict(sorted(by_channel.items()))}

print(summarise(ORDERS, date(2026, 11, 9), date(2026, 11, 15)))
print(summarise(ORDERS, date(2026, 11, 16), date(2026, 11, 22)))
```

- **The period is given as explicit start and end dates.** Monday 9 to Sunday 15 November, inclusive, regardless of when the job runs.
- **Fourteen orders total GBP 757.00.** The average order is 54.07.
- **By channel: web 483.00, shop 134.00, marketplace 140.00.** Sorted by name, so the output is the same every run.
- **An empty period gives zero orders and an average of 0.0, not a crash.** But a real report should not reach this point with no data, which is what the data checks prevent.

Next, safe comparisons and anomalies.

```python
import statistics

def change(current, previous):
    if previous == 0:
        return None
    return round(100 * (current - previous) / previous, 1)

def is_anomaly(history, value, threshold=3.0):
    if len(history) < 2:
        return False, None
    mean, spread = statistics.mean(history), statistics.stdev(history)
    if spread == 0:
        return value != mean, None
    z = (value - mean) / spread
    return abs(z) >= threshold, round(z, 2)

print(change(757.0, 690.0), change(10, 0), change(0, 50))
HISTORY = [1180, 1240, 1205, 1190, 1260, 1225, 1210]
print(is_anomaly(HISTORY, 1230), is_anomaly(HISTORY, 640), is_anomaly(HISTORY, 1310))
print(is_anomaly([500, 500, 500], 500), is_anomaly([500, 500, 500], 510))
```

- **Revenue rose 9.7 percent, from 690 to 757.** Rounded to one decimal place.
- **A change from zero is None, meaning undefined.** The report should say "new this week". A fall to zero is minus 100.0, which is real and important.
- **`is_anomaly` needs at least two history values for a standard deviation.**
- **1,230 has a z-score of 0.51, normal. 640 has minus 20.52, an anomaly.** That is a day to investigate: an outage, a failed payment provider, or missing data.
- **1,310 has a z-score of 3.36, also flagged.** A good day is worth knowing about too.
- **A perfectly flat history has no spread.** Any different value is flagged, and the z-score is None because it would be a division by zero.

Then, verifying the model's numbers.

```python
import re

NUMBER = re.compile(r"-?\d[\d,]*(?:\.\d+)?")

def numbers_in(text):
    return [float(match.replace(",", "")) for match in NUMBER.findall(text)]

def unsupported_numbers(summary, facts):
    allowed = set()
    def collect(value):
        if isinstance(value, bool):
            return
        if isinstance(value, (int, float)):
            allowed.add(round(float(value), 2))
        elif isinstance(value, dict):
            for inner in value.values():
                collect(inner)
        elif isinstance(value, list):
            for inner in value:
                collect(inner)
    collect(facts)
    return [number for number in numbers_in(summary) if round(number, 2) not in allowed]

FACTS = {"orders": 14, "revenue": 757.0, "previous_revenue": 690.0, "change_percent": 9.7,
         "top_channel": "web", "top_channel_revenue": 483.0, "anomalies": []}
good = "Revenue rose 9.7% to GBP 757.00 across 14 orders, led by web sales of GBP 483.00."
bad = "Revenue rose 12% to GBP 757.00 across 15 orders, the best week this year."
print(unsupported_numbers(good, FACTS), unsupported_numbers(bad, FACTS))
print(numbers_in("GBP 1,240.50 on 3 days"))
```

- **Numbers are extracted with thousands separators removed.** "1,240.50" becomes 1240.5.
- **Every number anywhere in the facts is allowed, rounded to two places.** Strings, such as the channel name, contribute nothing, and booleans are skipped because in Python they would otherwise count as 1 and 0.
- **The good summary passes.** 9.7, 757.00, 14, and 483.00 are all facts.
- **The bad summary fails on 12 and 15.** The model changed the percentage and the order count. "The best week this year" is a claim the facts cannot support either; a number check cannot catch it, which is why the prompt must forbid comparisons beyond the facts given.

Finally, checking the data before anything else.

```python
def data_checks(rows, now, latest, min_rows=5, max_age=timedelta(hours=26)):
    issues = []
    if not rows:
        issues.append("no_data")
    elif len(rows) < min_rows:
        issues.append("too_few_rows")
    if latest is None or now - latest > max_age:
        issues.append("stale")
    return issues

NOW = datetime(2026, 11, 16, 7, 0)
print(data_checks(ORDERS, NOW, datetime(2026, 11, 15, 23, 40)))
print(data_checks([], NOW, None))
print(data_checks(ORDERS[:3], NOW, datetime(2026, 11, 14, 22, 0)))
```

- **Monday's data passes.** Fourteen rows, the newest from Sunday at 23:40, under 26 hours before the run.
- **No rows and no timestamp give two issues.** The report is not produced; an alert says the source returned nothing.
- **Three rows with the newest from Saturday night give two issues.** Too few rows and stale data: the sync stopped on Saturday, and a report built on this would understate the week.
- **The age limit is 26 hours, not 24.** A little slack avoids false alarms when a nightly sync runs late.

**Complexity.** `summarise` is linear in the orders. `change` is constant. `is_anomaly` is linear in the history. `unsupported_numbers` is linear in the text plus the facts. `data_checks` is constant.

### What happens when something fails

| Failure | Report behaviour |
|---|---|
| No data, too few rows, stale data | No report; alert naming the problem |
| Model call fails | Send figures without commentary; retry next run |
| Commentary contains unsupported numbers | Send figures without commentary; log for review |
| Anomaly detected | Report includes it; separate alert if it needs action today |
| Delivery fails | Retry with backoff; alert after repeated failure (Module 7.14) |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Asking the model to do the maths.** It will be right most of the time, and you will not know when it is not. Compute in code.

**Unverified commentary.** "The model was told to use the figures" is not a check. Extract the numbers and compare.

**Reports on empty data.** "Revenue down 100 percent" from a broken export causes panic and erodes trust. Check the data first.

**Rolling windows that drift.** "Last seven days" from a job that ran late covers different days. Define periods by calendar dates.

**Time zones.** A UTC midnight cut-off puts late-evening orders in the wrong day. Use the business's time zone.

**Percentage change from zero.** Division by zero, or a misleading "infinite growth". Return undefined and say "new".

**Too many alerts.** A z-score threshold of 2 on a noisy series flags something every week. Alerts that need no action train people to ignore them.

**Ignoring weekly patterns.** Comparing Sunday with Saturday flags every quiet Sunday. Compare with the same weekday.

**Outliers distorting the baseline.** One huge Black Friday inflates the standard deviation for weeks. Consider the median-based modified z-score.

**The model inventing causes.** "Sales rose because of the warm weather" sounds insightful and is a guess. Forbid speculation.

**Long reports nobody reads.** Three sentences and a small table beat three pages. Put detail in a dashboard.

**No record of past reports.** Without a history of the figures, nobody can check last month's claims. Append each report's facts to a sheet.

**Question 2.** A Monday report runs at 07:00 and computes "last 7 days" from the moment it runs. One week the scheduler is delayed and the job runs on Tuesday at 10:00. Another week the order database's nightly sync fails on Saturday. Describe what each report would show, and how the design in this chapter prevents both problems.

<details>
<summary>View Answer</summary>

With a rolling window, the delayed Tuesday run covers Wednesday 10:00 to Tuesday 10:00 instead of Monday to Sunday: it includes Monday and part of Tuesday of the new week and omits Monday to Wednesday morning of the reporting week, so the figures describe a different period while carrying the same title, and the comparison with the previous week compares mismatched windows. The design prevents this by defining the period by calendar dates, Monday 00:00 to Sunday 23:59 in the business's time zone, computed from the report's intended week, so a late run reports the same week, just later. When the sync fails on Saturday, the database holds no orders after Friday night, so a naive report shows a fall in revenue, perhaps 30 percent, and might even flag Saturday and Sunday as anomalies, prompting the owner to worry about a problem that does not exist. **Question 3.** Daily order counts for the last two weeks are 52, 48, 50, 55, 49, 51, 20, 53, 47, 50, 54, 52, 49, 21, where the 20 and 21 are Sundays, when the shop is closed in the afternoon. Explain why a z-score test against the previous seven days either flags normal Sundays or misses real drops, and propose a better test for this report.

<details>
<summary>View Answer</summary>

A week such as 48, 50, 55, 49, 51, 20, 53 has a mean of 46.6 and, because of the one low Sunday, a standard deviation of about 12.0. A new Sunday value of 21 then has a z-score of about minus 2.14, so with a threshold of 3 it is not flagged at all: the earlier Sunday inflates the spread and would also hide a real drop on a weekday. Lower the threshold to 2 and it would be flagged, along with many ordinary days. By contrast, with a Sunday-free history, such as the six weekdays 53, 47, 50, 54, 52, 49, mean 50.8 and standard deviation about 2.6, the same 21 has a z-score of about minus 11.3 and is flagged. More generally, mixing a predictable weekly pattern into the history both inflates the spread, hiding real problems on weekdays, and makes normal Sundays look unusual, so the test is unreliable in both directions. A better test compares each day with the same weekday in recent weeks: Sunday with previous Sundays, Monday with previous Mondays, using for example a percentage deviation from the average of the last four or six of that weekday, with a threshold agreed with the owner, such as a fall of more than 40 percent. With enough history, the median-based modified z-score per weekday is more robust to occasional extreme days. The point is that the baseline must reflect what normal looks like for that day, and the threshold must be one the owner would act on.

</details>

SALES = [("web", 84.0), ("web", 22.5), ("shop", 40.0), ("web", 120.0), ("marketplace", 35.0), ("web", 64.5), ("shop", 18.0),
         ("web", 95.0), ("marketplace", 44.0), ("web", 30.0), ("shop", 76.0), ("web", 52.0), ("web", 15.0), ("marketplace", 61.0)]
ORDERS = [{"day": date(2026, 11, 9) + timedelta(days=i % 7), "channel": channel, "total": total}
          for i, (channel, total) in enumerate(SALES)]
NUMBER = re.compile(r"-?\d[\d,]*(?:\.\d+)?")


# ---------------------------------------------------------------- Step 1
def summarise(orders, start, end):
    """Code computes every figure, over an explicit calendar period."""
    rows = [order for order in orders if start <= order["day"] <= end]
    revenue = round(sum(order["total"] for order in rows), 2)
    by_channel = {}
    for order in rows:
        by_channel[order["channel"]] = round(by_channel.get(order["channel"], 0) + order["total"], 2)
    return {"orders": len(rows), "revenue": revenue,
            "average_order": round(revenue / len(rows), 2) if rows else 0.0,
            "by_channel": dict(sorted(by_channel.items()))}


# ---------------------------------------------------------------- Step 2
def change(current, previous):
    """A change from zero is undefined, not infinite and not zero."""
    if previous == 0:
        return None
    return round(100 * (current - previous) / previous, 1)


# ---------------------------------------------------------------- Step 3
def is_anomaly(history, value, threshold=3.0):
    """The threshold is chosen deliberately, in code, never left to the model."""
    if len(history) < 2:
        return False, None
    mean, spread = statistics.mean(history), statistics.stdev(history)
    if spread == 0:
        return value != mean, None
    z = (value - mean) / spread
    return abs(z) >= threshold, round(z, 2)


# ---------------------------------------------------------------- Step 4
def numbers_in(text):
    """Thousands separators removed, so 12,450 and 12450 compare equal."""
    return [float(match.replace(",", "")) for match in NUMBER.findall(text)]


def unsupported_numbers(summary, facts):
    """The model may only repeat numbers that code computed."""
    allowed = set()

    def collect(value):
        if isinstance(value, bool):
            return
        if isinstance(value, (int, float)):
            allowed.add(round(float(value), 2))
        elif isinstance(value, dict):
            for inner in value.values():
                collect(inner)
        elif isinstance(value, list):
            for inner in value:
                collect(inner)

    collect(facts)
    return [number for number in numbers_in(summary) if round(number, 2) not in allowed]


# ---------------------------------------------------------------- Step 5
def data_checks(rows, now, latest, min_rows=5, max_age=timedelta(hours=26)):
    """No report on missing, partial, or stale data: alert instead."""
    issues = []
    if not rows:
        issues.append("no_data")
    elif len(rows) < min_rows:
        issues.append("too_few_rows")
    if latest is None or now - latest > max_age:
        issues.append("stale")
    return issues
