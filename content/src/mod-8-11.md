# Human-in-the-Loop

An agent that can act can also act wrongly. **Human-in-the-loop**, HITL, design decides where people take part in an automated process: approving actions before they happen, reviewing them afterwards, or taking over a conversation the agent should not continue. Done badly, HITL is either absent, so an agent refunds the wrong customer GBP 2,000, or everywhere, so a person clicks "approve" four hundred times a day without reading. Done well, people are involved exactly where their judgement changes outcomes.

Earlier modules touched pieces of this: Module 1.6 added an approval gate to an agent loop, Module 7.16 measured human review of a classifier, and Module 8.2 checkpointed agent state. This chapter brings them together into a design discipline: which actions need which kind of oversight, how to pause and resume a run safely, when to escalate, and how to move the line as trust is earned.

## 1. First-Principles Mental Model & Intuition

### A new employee

A sensible manager does not give a new employee either no authority or all of it. On day one they can answer questions freely, issue small refunds and mention them in a daily summary, need a sign-off for anything over a limit, and are never allowed to change a supplier's bank details. If a customer becomes abusive or asks for a manager, they hand over. As months pass without mistakes, the limit rises. If they make a costly error, it falls.

Every part of that maps onto agent design:

| Employee practice | Agent design |
|---|---|
| Answers freely | Automatic actions |
| Small refunds, mentioned in a summary | Act, then notify; sampled review afterwards |
| Sign-off above a limit | Approval before the action |
| Never changes bank details | Blocked actions |
| Hands over angry customers | Escalation triggers |
| Limit rises with a good record | Autonomy adjusted from decision data |

```text
   agent proposes action
          |
   [ oversight policy ] --block-----------------------------> refuse, explain
          |  \--approve--> [ interrupt: save state, ask person ] --approve/edit--> execute --> log
          |                        |                \--reject/expire--> feedback to agent
          |--notify--> execute --> tell a person
          \--auto----> execute --> log --> [ sampled review ] --> decisions --> [ adjust limits ]
```

### Two failure modes

Too little oversight lets irreversible mistakes reach customers. Too much oversight creates **approval fatigue**: reviewers facing hundreds of identical requests stop reading them, and the approval step becomes a rubber stamp that gives false assurance. The EU AI Act's article on human oversight names the underlying tendency, **automation bias**, the habit of over-relying on a system's output, and asks that people overseeing high-risk systems remain aware of it. HITL design is about placing a limited supply of real attention where it matters.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Where humans belong: oversight tiers

Classify each action an agent can take by its consequences:

| Tier | When | Mechanism |
|---|---|---|
| Block | Never acceptable for the agent | Tool not offered, or refused by policy |
| Approve before | Irreversible, high value, or low confidence | Interrupt and wait for a decision |
| Notify after | Reversible but visible outside the company | Act, then tell a person |
| Automatic | Reversible, internal, low value | Act and log; sample for review |

The questions that decide the tier are **reversibility**, can it be undone and at what cost; **magnitude**, money, data, number of people affected; **visibility**, does it reach customers or the public; and **confidence**, how sure the agent is, from a classifier score or from the agent's own uncertainty signals. Expected cost gives a way to set limits: if an automatic action is wrong with probability $p$ and a wrong action costs $c$, while a human review costs $h$ in time, then review pays off when

$$p \cdot c > h$$

A GBP 40 refund that is wrong 2 percent of the time costs GBP 0.80 in expected error, less than a minute of a reviewer's time; a GBP 2,000 refund at the same error rate costs GBP 40, well worth a review. That is why limits are usually set by amount.

Agent frameworks implement this directly. The OpenAI Agents SDK lets a tool be marked as needing approval, always or by a function deciding per call, and the run then stops with **interruptions** to be approved or rejected. Claude Code's permission modes decide which tool uses need confirmation. The design question is the same in every tool: which calls, under which conditions.

### Approval decisions

An approval request carries the proposed action, enough context to judge it, and an expiry. A person can respond in four ways:

| Decision | Effect |
|---|---|
| Approve | Execute the action as proposed |
| Edit | Execute a corrected version, for example a smaller refund |
| Reject | Do not execute; return the reason to the agent as feedback, so it can try another approach or tell the customer |
| Expire | No answer in time; treat as rejection, never as approval |

Three rules make this safe. **Fail closed**: silence means no. **Decide once**: a request already decided cannot be decided again, which blocks double execution from two reviewers clicking at once. **Constrain edits**: an edit may change the fields of the proposed action, not add new ones the reviewer did not see validated.

### Interrupts, checkpoints, and resumable state

A run waiting for a person may wait minutes or days, so it cannot hold a process open. It must be **interrupted**: its state saved to durable storage with an identifier, and resumed later from that state with the decision. LangGraph's documentation describes exactly this: calling `interrupt()` inside a node saves the graph state through a checkpointer, keyed by a thread identifier, and the run waits indefinitely until it is resumed with a command whose value becomes the interrupt's return value. The OpenAI Agents SDK serialises a paused run as a `RunState` that can be resumed after decisions are made.

One subtlety catches many teams. In LangGraph, when a run resumes, **the node restarts from its beginning**, so any code before the `interrupt()` call runs again, and the documentation states that side effects before an interrupt must be idempotent. If that code sent an email, the customer gets two. The fixes are to place side effects after the interrupt, or in a separate node, or to make them idempotent with a key, as Module 8.5 did for tool calls: record that "run-7 draft email" was done and skip it on replay.

### Escalation

Escalation hands a conversation, not a single action, to a person. Common triggers:

| Trigger | Signal |
|---|---|
| Explicit request | The customer asks for a person or a manager |
| Frustration | Negative language in consecutive messages |
| Low confidence | The agent's classifier or retrieval scores are weak, Module 8.7 |
| Looping | The customer repeats the same question |
| Too long | More turns than the problem should need |
| Sensitive topics | Legal threats, safety issues, vulnerable customers |

An explicit request for a person should always be honoured; trapping customers with an agent that refuses to hand over is both bad service and, in some jurisdictions and sectors, a compliance problem. The handover should carry a summary so the customer does not repeat themselves, the pattern of Module 7.18.

### Review after the fact: sampling

Automatic actions still need **sampled review**, both to catch errors and to produce the data that justifies the agent's autonomy. Two rules: sample a fixed fraction **deterministically**, for example by hashing the action's identifier, so the sample is reproducible and cannot be gamed; and **always** review certain cases, such as the largest amounts or new action types, regardless of the sample. With a sampling rate $r$ over $N$ actions, the expected review load is $rN$ plus the always-review cases, and an error rate $e$ is estimated from about $rNe$ observed errors, so small rates need large volumes before the estimate is reliable.

### Balancing autonomy against risk

Autonomy should be adjusted from evidence. Track each reviewed decision as approved unchanged, edited, or rejected. If almost all approvals pass unchanged over a meaningful number of decisions, the approval limit is costing attention without adding value and can be raised. If rejections exceed a tolerance, it should be lowered. Two cautions. First, a 100 percent approval rate with very fast decisions may mean the reviewers are not reviewing; measure decision time and occasionally insert a known-bad test case. Second, never adjust from too few decisions: 10 approvals in a row say little.

Frameworks such as NIST's AI Risk Management Framework, and for high-risk systems in the EU the AI Act's human oversight requirements, which call for oversight measures commensurate with the risks, level of autonomy, and context of use, make the same point formally: oversight must be designed in proportion to risk and must be effective, not nominal.

### Complexity

Tiering is constant per action. Approval decisions are constant. Resume cost is reloading the checkpoint. Escalation checks are linear in the conversation. Sampling is linear in actions, with one hash each. Limit adjustment is linear in recorded decisions.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, oversight tiers.

```python
import hashlib
import re

BLOCKED = {"delete_customer", "change_bank_details"}

def oversight(action, limit=100):
    if action["name"] in BLOCKED:
        return "block", ["action is never automated"]
    reasons = []
    if not action["reversible"]:
        reasons.append("cannot be undone")
    if action["amount"] > limit:
        reasons.append(f"amount {action['amount']} over {limit}")
    if action["confidence"] < 0.6:
        reasons.append("low confidence")
    if reasons:
        return "approve", reasons
    if action["external"]:
        return "notify", ["visible outside the company"]
    return "auto", []

REFUND = {"name": "refund", "amount": 40, "reversible": True, "external": True, "confidence": 0.9}
print(oversight(REFUND))
print(oversight({**REFUND, "amount": 250}))
print(oversight({**REFUND, "reversible": False, "confidence": 0.5}))
print(oversight({**REFUND, "external": False}))
```

- **Blocked actions are checked first.** No amount of confidence makes them automatic.
- **Every reason for approval is collected, not just the first.** The reviewer sees "cannot be undone" and "low confidence" together.
- **A GBP 40 refund the customer will see is `notify`.** Act, then tell a person.
- **Over the limit of 100, it needs approval.**
- **An internal, reversible, confident action is automatic.** It is still logged and may be sampled.

Next, approval requests and decisions.

```python
def request_approval(run_id, action, now, ttl=3600):
    return {"id": f"{run_id}:{action['name']}", "action": dict(action), "expires": now + ttl, "status": "pending"}

def decide(request, decision, now, edits=None, reason=""):
    if request["status"] != "pending":
        raise ValueError(f"already {request['status']}")
    if now > request["expires"]:
        request["status"] = "expired"
        return {"execute": False, "feedback": "approval expired; action not taken"}
    if decision == "approve":
        request["status"] = "approved"
        return {"execute": True, "action": request["action"]}
    if decision == "edit":
        unknown = set(edits or {}) - set(request["action"])
        if unknown:
            raise ValueError(f"unknown fields {sorted(unknown)}")
        request["status"] = "edited"
        return {"execute": True, "action": {**request["action"], **edits}}
    if decision == "reject":
        request["status"] = "rejected"
        return {"execute": False, "feedback": f"rejected: {reason}"}
    raise ValueError(f"unknown decision {decision}")

request = request_approval("run-7", {"name": "refund", "amount": 250, "order": "A-1"}, now=1000)
print(decide(request, "edit", now=2000, edits={"amount": 200}), request["status"])
late = request_approval("run-8", {"name": "refund", "amount": 250}, now=1000)
print(decide(late, "approve", now=5000))
```

- **The request copies the action.** Later changes to the agent's state cannot alter what the reviewer approved.
- **A decided request cannot be decided again.** The status check raises, preventing double execution.
- **Expiry fails closed.** Approving at time 5000 a request that expired at 4600 does nothing.
- **An edit may only change existing fields.** The reviewer cut the refund to 200; adding a field nobody validated would raise.
- **A rejection returns its reason to the agent.** It can then explain to the customer or try a different approach.

Then, a node that is safe to resume.

```python
def node(state, log, resume=None, idempotent=True):
    key = f"{state['run']}:draft-email"
    if idempotent:
        if key not in {k for k, _ in log}:
            log.append((key, "draft email saved"))
    else:
        log.append((key, "draft email saved"))
    if resume is None:
        return "interrupted", {"question": "Send the refund email?", "draft": state["draft"]}
    return "done", "sent" if resume == "approve" else "discarded"

for idempotent in (False, True):
    log, state = [], {"run": "run-7", "draft": "Your refund of GBP 40 is on its way."}
    print(node(state, log, None, idempotent), node(state, log, "approve", idempotent), len(log))
```

- **The node saves a draft, then interrupts with a question.** On resume, it runs again from the top, as LangGraph's interrupts do.
- **The non-idempotent version saves the draft twice.** Two log entries; with a real email, two emails.
- **The idempotent version records a key and skips the side effect on replay.** One entry, however many times the node resumes.

Then, escalation triggers.

```python
HUMAN = re.compile(r"\b(human|person|agent|manager|someone real)\b", re.I)
NEGATIVE = {"angry", "useless", "ridiculous", "terrible", "worst", "unacceptable"}

def should_escalate(user_messages, confidence, max_turns=6):
    reasons = []
    if user_messages and HUMAN.search(user_messages[-1]):
        reasons.append("asked for a person")
    negative = [bool(NEGATIVE & set(re.findall(r"[a-z]+", m.lower()))) for m in user_messages]
    if len(negative) >= 2 and negative[-1] and negative[-2]:
        reasons.append("frustrated twice in a row")
    if confidence < 0.5:
        reasons.append("low confidence")
    if len(user_messages) > max_turns:
        reasons.append("too many turns")
    if len(user_messages) >= 2 and user_messages[-1].strip().lower() == user_messages[-2].strip().lower():
        reasons.append("repeated question")
    return reasons

print(should_escalate(["Where is my order?", "This is useless", "Absolutely ridiculous, let me talk to a human"], 0.9))
print(should_escalate(["Where is my order?", "where is my order?"], 0.4))
```

- **An explicit request for a person is checked on the latest message.**
- **Frustration needs two negative messages in a row.** One complaint is normal; two is a trend.
- **Low confidence, too many turns, and a repeated question are each enough.** The second conversation escalates for low confidence and repetition.
- **The function returns reasons, not a yes or no.** The handover summary includes them.

Finally, sampled review and limit adjustment.

```python
def sample(items, rate, always=lambda item: False):
    return [item["id"] for item in items
            if always(item) or int(hashlib.sha256(item["id"].encode()).hexdigest(), 16) % 1000 < rate * 1000]

def adjust_limit(decisions, limit, min_n=50, step=1.5):
    n = len(decisions)
    if n < min_n:
        return limit, "not enough decisions"
    if decisions.count("rejected") / n > 0.05:
        return round(limit / step, 2), "rejections above 5%"
    if decisions.count("approved") / n >= 0.98:
        return round(limit * step, 2), "98% approved unchanged"
    return limit, "keep"

ACTIONS = [{"id": f"act-{n}", "amount": n * 7 % 120} for n in range(1, 21)]
print(sample(ACTIONS, 0.1), sample(ACTIONS, 0.1, always=lambda a: a["amount"] > 100))
print(adjust_limit(["approved"] * 60, 100), adjust_limit(["approved"] * 50 + ["rejected"] * 4, 100))
```

- **The hash of the identifier decides sampling.** The same action is always in or out, so the sample is reproducible.
- **At a 10 percent rate, 3 of these 20 actions are sampled.** Small samples vary around the rate.
- **Always-review cases are added.** Actions over 100, act-15, act-16, and act-17, are reviewed regardless.
- **Sixty unchanged approvals raise the limit to 150.** Approval was costing attention without catching anything.
- **Four rejections in 54, 7.4 percent, lower it to 66.67.**
- **Fewer than 50 decisions change nothing.** Ten approvals in a row are not evidence.

**Complexity.** `oversight` and `decide` are constant. `node` scans the log for its key, linear in the log. `should_escalate` is linear in the messages. `sample` hashes each action once. `adjust_limit` counts the decisions, linear.

### An oversight policy

```text
ACTION              TIER                     LIMIT / RULE                       ON TIMEOUT
answer question     auto                     sampled 2% for QA review           n/a
refund              notify <= GBP 100        approve above GBP 100              reject after 4 hours, tell customer
send email          notify                   approve if confidence < 0.6        reject after 1 hour
cancel order        approve                  always (irreversible once shipped)  reject after 4 hours
change bank details block                    staff only, two-person rule        n/a
ESCALATE            asks for a person; 2 negative messages; confidence < 0.5; > 6 turns; repeated question
REVIEW              monthly: approval rates, edits, rejections, median decision time; adjust limits (min 50 decisions)
```

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Approving everything.** Hundreds of identical approvals train reviewers to click without reading. Raise limits where approvals never change anything.

**Approving nothing.** Agents with unchecked irreversible actions eventually make an expensive mistake. Tier by reversibility and magnitude.

**Silence treated as consent.** Auto-approving on timeout defeats the purpose. Fail closed.

**Approval screens without context.** "Approve refund?" with no order history invites guessing. Show what the reviewer needs to decide.

**Double approval.** Two reviewers approving the same request executes it twice. Decide once, atomically.

**Side effects before the interrupt.** Resumed nodes re-run their code. Put side effects after the interrupt or make them idempotent.

**Holding a process open while waiting.** Approvals can take days. Persist state and resume from a checkpoint.

**Trapping customers with the bot.** Refusing to hand over angers customers and can breach sector rules. Always honour an explicit request.

**Escalating without a summary.** Customers forced to repeat themselves are angrier than before. Hand over the conversation and the reasons.

**Rejections the agent never hears about.** Without the reason, the agent repeats the same proposal. Return rejection feedback into the run.

**Random sampling that cannot be reproduced.** Auditors need to see why an item was reviewed. Sample by a hash of the identifier.

**Measuring approval rates but not decision time.** Two-second approvals at 100 percent are a rubber stamp. Track time and test with known-bad cases.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Human-in-the-loop design places people where their judgement changes outcomes. Actions are tiered by reversibility, magnitude, visibility, and confidence into blocked, approve-before, notify-after, and automatic, and review pays off when the expected cost of an error, probability times cost, exceeds the cost of the review. Approval requests carry the action, context, and an expiry; decisions are approve, edit within the existing fields, reject with feedback to the agent, or expire, which fails closed, and each request is decided once. Waiting runs are interrupted, their state checkpointed and resumed later; because frameworks such as LangGraph re-run a node from its start on resume, side effects before an interrupt must be idempotent or moved after it. Escalation hands a conversation to a person on explicit requests, repeated frustration, low confidence, looping, or excessive length, with a summary. Automatic actions are sampled for review deterministically, with always-review cases added, and autonomy limits are raised or lowered from enough recorded decisions, watching for automation bias and rubber-stamping, in line with the proportionate, effective oversight that frameworks such as NIST's and the EU AI Act describe.

**Question 1.** An agent's refund approvals over the last quarter: 1,840 requests, 1,838 approved unchanged, 2 edited, median decision time 3 seconds, and one approved refund later found to be fraudulent. The team proposes removing approval entirely. Analyse the data and recommend a policy.

<details>
<summary>View Answer</summary>

The approval rate is 1,838 of 1,840, about 99.9 percent unchanged, which by the lab's `adjust_limit` rule, at least 50 decisions with 98 percent or more approved unchanged, justifies raising the limit. But two other facts matter. A median decision time of 3 seconds is too short to read an order history, so the approvals were probably rubber stamps: automation bias in action. And the fraudulent refund was approved, which shows the step did not catch the case it existed for. So the data does not show that approval is unnecessary; it shows that this approval step is not working. Removing it entirely would also remove the one point where a better check could catch fraud. A better policy: raise the approval limit, for example by the lab's factor of 1.5, so reviewers see fewer, larger refunds; make the approval screen show the evidence that distinguishes fraud, such as account age, refund history, and delivery confirmation; add automated fraud signals that route suspicious refunds to approval regardless of amount; track decision time and insert occasional known-bad test cases to measure whether reviewers catch them; and sample automatic refunds below the limit for after-the-fact review. Then re-measure next quarter.

</details>

**Question 2.** A LangGraph node generates a refund confirmation, charges a GBP 5 restocking fee through the payment API, then calls `interrupt()` to ask a person whether to send the confirmation. Customers report being charged the fee twice. Explain the cause using this chapter and the lab, and give two fixes.

<details>
<summary>View Answer</summary>

When a LangGraph run is resumed after an interrupt, the node restarts from its beginning, so all code before the `interrupt()` call runs again. The first execution charged the fee and paused; when the reviewer answered, the node re-ran, charged the fee a second time, reached the interrupt, and this time received the resume value and continued. The lab's `node` function shows the same effect: the non-idempotent version saves the draft twice across one interrupt and one resume, while the idempotent version saves it once. The first fix is to move the side effect after the interrupt, or into a separate node that runs only after the decision, which also makes more sense for the business: the fee should be charged only if the refund is approved. The second fix, needed anyway for any side effect that might be retried, is to make the charge idempotent with a key, such as the run identifier plus "restocking-fee", either by recording completed keys in the run's state and skipping on replay, or by passing an idempotency key to the payment API so it refuses duplicates, the pattern of Module 8.5. The documentation's rule, side effects before an interrupt must be idempotent, is the general lesson.

</details>

**Question 3.** Using the lab's `should_escalate`, a customer writes "Where is my order?", then "This is useless", then "Absolutely ridiculous, let me talk to a human", and the agent's confidence is 0.9. A product manager argues the agent was confident, so it should keep trying. Respond, and say what the handover should contain.

<details>
<summary>View Answer</summary>

`should_escalate` returns two reasons: "asked for a person", because the latest message contains "human", and "frustrated twice in a row", because "useless" and "ridiculous" both appear in the last two messages. Confidence of 0.9 does not trigger anything, but it does not cancel the other triggers either: confidence measures how sure the agent is about its answer, not whether the customer is willing to keep talking to it. An explicit request for a person should always be honoured; continuing to push automated answers to a customer who has asked for a human damages trust, and in some sectors and jurisdictions refusing to provide access to a person is itself a compliance problem. Moreover, the agent's high confidence combined with growing frustration suggests the agent may be confidently answering the wrong question, which is exactly when a person helps most. The handover should include a short summary of the issue, the order number and its current status as the agent found it, what the agent has already told the customer, and the escalation reasons, so the person can start where the agent stopped and the customer does not have to repeat themselves, as in Module 7.18's handoff.

"""
Lab solution: Oversight Tiers, Approval Decisions, Idempotent Resume, Escalation, Review Sampling
Standard library only. No network calls or models.

import hashlib
import re

BLOCKED = {"delete_customer", "change_bank_details"}
REFUND = {"name": "refund", "amount": 40, "reversible": True, "external": True, "confidence": 0.9}
HUMAN = re.compile(r"\b(human|person|agent|manager|someone real)\b", re.I)
NEGATIVE = {"angry", "useless", "ridiculous", "terrible", "worst", "unacceptable"}
ACTIONS = [{"id": f"act-{n}", "amount": n * 7 % 120} for n in range(1, 21)]


# ---------------------------------------------------------------- Step 1
def oversight(action, limit=100):
    """Tier by reversibility, magnitude, confidence, and visibility; blocked actions first."""
    if action["name"] in BLOCKED:
        return "block", ["action is never automated"]
    reasons = []
    if not action["reversible"]:
        reasons.append("cannot be undone")
    if action["amount"] > limit:
        reasons.append(f"amount {action['amount']} over {limit}")
    if action["confidence"] < 0.6:
        reasons.append("low confidence")
    if reasons:
        return "approve", reasons
    if action["external"]:
        return "notify", ["visible outside the company"]
    return "auto", []


# ---------------------------------------------------------------- Step 2
def request_approval(run_id, action, now, ttl=3600):
    """Copy the action so the reviewer approves exactly what they saw."""
    return {"id": f"{run_id}:{action['name']}", "action": dict(action), "expires": now + ttl, "status": "pending"}


def decide(request, decision, now, edits=None, reason=""):
    """Fail closed, decide once, constrain edits, feed rejections back."""
    if request["status"] != "pending":
        raise ValueError(f"already {request['status']}")
    if now > request["expires"]:
        request["status"] = "expired"
        return {"execute": False, "feedback": "approval expired; action not taken"}
    if decision == "approve":
        request["status"] = "approved"
        return {"execute": True, "action": request["action"]}
    if decision == "edit":
        unknown = set(edits or {}) - set(request["action"])
        if unknown:
            raise ValueError(f"unknown fields {sorted(unknown)}")
        request["status"] = "edited"
        return {"execute": True, "action": {**request["action"], **edits}}
    if decision == "reject":
        request["status"] = "rejected"
        return {"execute": False, "feedback": f"rejected: {reason}"}
    raise ValueError(f"unknown decision {decision}")


# ---------------------------------------------------------------- Step 3
def node(state, log, resume=None, idempotent=True):
    """Resumed nodes re-run from the top: side effects before the interrupt must be idempotent."""
    key = f"{state['run']}:draft-email"
    if idempotent:
        if key not in {k for k, _ in log}:
            log.append((key, "draft email saved"))
    else:
        log.append((key, "draft email saved"))
    if resume is None:
        return "interrupted", {"question": "Send the refund email?", "draft": state["draft"]}
    return "done", "sent" if resume == "approve" else "discarded"


# ---------------------------------------------------------------- Step 4
def should_escalate(user_messages, confidence, max_turns=6):
    """Reasons, not a yes or no: they go into the handover summary."""
    reasons = []
    if user_messages and HUMAN.search(user_messages[-1]):
        reasons.append("asked for a person")
    negative = [bool(NEGATIVE & set(re.findall(r"[a-z]+", m.lower()))) for m in user_messages]
    if len(negative) >= 2 and negative[-1] and negative[-2]:
        reasons.append("frustrated twice in a row")
    if confidence < 0.5:
        reasons.append("low confidence")
    if len(user_messages) > max_turns:
        reasons.append("too many turns")
    if len(user_messages) >= 2 and user_messages[-1].strip().lower() == user_messages[-2].strip().lower():
        reasons.append("repeated question")
    return reasons


# ---------------------------------------------------------------- Step 5
def sample(items, rate, always=lambda item: False):
    """Deterministic, reproducible sampling plus always-review cases."""
    return [item["id"] for item in items
            if always(item) or int(hashlib.sha256(item["id"].encode()).hexdigest(), 16) % 1000 < rate * 1000]


def adjust_limit(decisions, limit, min_n=50, step=1.5):
    """Move the line from evidence, and only with enough of it."""
    n = len(decisions)
    if n < min_n:
        return limit, "not enough decisions"
    if decisions.count("rejected") / n > 0.05:
        return round(limit / step, 2), "rejections above 5%"
    if decisions.count("approved") / n >= 0.98:
        return round(limit * step, 2), "98% approved unchanged"
    return limit, "keep"
