# Working with JSON

Whenever a model's output is read by a program, and whenever a program hands data to a model, the data usually travels as JSON. Tool calls are JSON. Structured outputs are JSON. The request your code sends to a model's API is JSON, and so is the response.

Module 5.5 covered how to make a model produce structured output and how enforcement works. This chapter is about the format itself and about handling it well: what is and is not JSON, how it maps to the values in a program, the few schema keywords that matter, how to parse a model's JSON without being fooled, and how to put JSON into a prompt without wasting tokens or confusing the model.

## 1. First-Principles Mental Model & Intuition

### The customs form

A parcel crossing a border carries a customs form. The form has labelled boxes: sender, contents, value, weight. A clerk anywhere in the world can process it without reading the sender's language, because the boxes are the same everywhere.

A letter describing the same parcel would contain the same facts. Nobody could process a million of them.

JSON is the customs form of software. It carries data as labelled values in a layout so simple that every programming language can read and write it. A model writing prose is writing letters. A model writing JSON is filling in the form, and a program can act on it.

### Where JSON sits

```text
   PROGRAM VALUES                 TEXT                      PROGRAM VALUES
   (your code)                    (what the model           (your code)
                                   reads and writes)

   dict, list, str,   serialise   {"order_id": "A1234",   parse    dict, list, str,
   int, float,       ---------->   "items": ["HAM"],     ------->  int, float,
   True, None                      "paid": true}                   True, None

                  json.dumps                             json.loads
```

A model only ever sees and produces the middle column: characters. Two crossings happen on either side of it. When your code turns values into text, that is **serialising**. When it turns text back into values, that is **parsing**. Nearly every JSON problem in practice occurs at one of the two crossings, and the lab builds a guard for each.

### Three rules to carry through the chapter

**JSON is stricter than it looks.** It resembles the way dictionaries are written in Python and objects in JavaScript, and it is neither. A single quote, a trailing comma, or a comment makes a document invalid.

**Parsing successfully is not the same as parsing correctly.** A standard parser will accept things that quietly lose information, such as a repeated field name.

**JSON is costly as prompt input.** Every field name is repeated in every record. For a long list, the names can be half the text.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### The whole of JSON

JSON has six kinds of value.

| Kind | Example | In Python |
|---|---|---|
| String | `"claw hammer"` | `str` |
| Number | `42`, `-3.5`, `1.2e6` | `int` or `float` |
| Boolean | `true`, `false` | `True`, `False` |
| Null | `null` | `None` |
| Array | `[1, "two", null]` | `list` |
| Object | `{"sku": "HAM-1", "qty": 2}` | `dict` |

Arrays and objects can contain any values, including other arrays and objects, to any depth. A complete JSON document is one value, usually an object or an array.

The rules that catch people out:

| Not JSON | Why | Correct form |
|---|---|---|
| `{'sku': 'HAM-1'}` | Strings and names need double quotes | `{"sku": "HAM-1"}` |
| `{sku: "HAM-1"}` | Names must be quoted | `{"sku": "HAM-1"}` |
| `{"qty": 2,}` | No comma after the last item | `{"qty": 2}` |
| `{"qty": 2} // two left` | No comments | Put the note in a field |
| `{"paid": True}` | The words are lowercase | `{"paid": true}` |
| `{"note": None}` | The empty value is `null` | `{"note": null}` |
| `{"qty": 02}` | No leading zeros | `{"qty": 2}` |
| `{"score": NaN}` | No not-a-number and no infinity | `{"score": null}` |
| A string containing a real line break | Control characters must be escaped | `"line one\nline two"` |

Inside a string, a double quote is written `\"`, a backslash `\\`, a line break `\n`, and any character at all can be written as `\u` followed by four hexadecimal digits. When a model writes JSON containing code, file paths, or quoted speech, these escapes are where it most often slips.

The standard that defines the format, RFC 8259, makes two further points that matter in practice. The names in an object should be unique, and what a parser does with a repeated name is not defined. And although the grammar allows numbers of any size, programs commonly store them as 64-bit floating point, so integers beyond about nine quadrillion are not safe to exchange as numbers.

### Crossing in and out of Python

Python's `json` module does both crossings. `json.loads` parses text into values, and `json.dumps` serialises values into text. The mapping is the table above, with four things to know.

**The round trip is not exact.** A tuple becomes an array and comes back as a list. A dictionary key that is a number becomes a string and stays one.

**`json.loads` is lenient in ways the standard is not.** By default it accepts `NaN` and `Infinity`, which are not JSON. When a name is repeated, it keeps the last value and discards the others without a word. Both behaviours can be turned off, and the lab does so.

**Errors carry a position.** A failed parse raises `json.JSONDecodeError`, which records the line and column where parsing stopped. That position is the most useful thing to send back to a model when asking it to correct its output.

**`json.dumps` has options that matter for prompts.**

| Option | Effect | Use |
|---|---|---|
| `indent=2` | Line breaks and indentation | For people to read |
| `separators=(",", ":")` | No spaces at all | Smallest valid JSON |
| `ensure_ascii=False` | Writes accented and non-Latin characters as themselves | Almost always, for text a model will read |
| `sort_keys=True` | Fields in alphabetical order | Stable output, for caching and for comparing |

By default `json.dumps` writes "José" as `"Jos\u00e9"`. That is valid, costs more tokens, and is harder for a model to read. Pass `ensure_ascii=False`.

### Numbers: the two traps

**Large integers.** A 64-bit floating-point number holds integers exactly only up to $2^{53}$, which is 9,007,199,254,740,992. Python's own integers have no such limit, so Python parses a larger identifier exactly. JavaScript, and many other tools in a pipeline, do not: the identifier 9007199254740993 arrives as 9007199254740992, a different record. The rule is that identifiers are strings, even when they consist of digits.

**Decimal fractions.** Most decimal fractions cannot be stored exactly in binary floating point. In Python, `0.1 + 0.2` is `0.30000000000000004`. For money, carry an integer number of the smallest unit, such as pence, or a string, and never a floating-point number.

### The JSON Schema keywords that matter

A schema is a JSON document that describes what another JSON document must look like. Module 5.5 used schemas to validate and to enforce. These keywords cover most real use.

| Keyword | Says |
|---|---|
| `type` | Which kind of value: string, number, integer, boolean, null, array, object |
| `properties` | For an object, the schema of each named field |
| `required` | The fields that must be present |
| `additionalProperties` | Set to false, forbids fields that are not listed |
| `items` | For an array, the schema every element must satisfy |
| `enum` | The value must be one of a fixed list |
| `minimum`, `maximum` | Bounds on a number |
| `minLength`, `pattern` | Constraints on a string |
| `description` | A note on what the field means |

```json
{
  "type": "object",
  "properties": {
    "order_id": {"type": "string", "description": "The order number, such as A1234"},
    "status": {"type": "string", "enum": ["PAID", "SHIPPED", "DELIVERED", "RETURNED"]},
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {"sku": {"type": "string"}, "qty": {"type": "integer", "minimum": 1}},
        "required": ["sku", "qty"],
        "additionalProperties": false
      }
    }
  },
  "required": ["order_id", "status", "items"],
  "additionalProperties": false
}
```

Three points for prompt writers. The `description` is read by the model: when a schema is given to a model as a tool or an output format, each description is a small prompt, and a good one improves the values. An `enum` is the most valuable constraint, because it turns free text into a choice. And the enforcement features of Module 5.5 support only part of JSON Schema, so check the provider's list before using an unusual keyword.

A practical way to write a schema is to write one good example of the data, derive a schema from it mechanically, and then tighten the result by hand, adding enums, bounds, and descriptions. The lab builds the deriving step.

### Parsing a model's JSON safely

Module 5.5 dealt with finding the JSON inside a chatty reply and with repair loops. Once you have the text, parse it defensively.

1. **Never evaluate it as code.** Functions that run a string as a program will run whatever the model, or someone who influenced the model, wrote. Use a JSON parser.
2. **Parse strictly.** Reject repeated names and non-finite numbers instead of accepting them silently.
3. **Check that the output was complete.** A reply that hit the output limit is cut off mid-document. The API reports why generation stopped. If the reason is the length limit, the JSON is incomplete, and no repair is trustworthy.
4. **Validate against the schema.** A document can be valid JSON and have the wrong fields.
5. **Check the values against the world.** An order number of the right shape may not exist.

On the third point, a cut-off document has a recognisable state: brackets that were opened and never closed, and sometimes a string still open. It is tempting to close them and carry on. The result parses, and it is missing whatever came after the cut, which may have been half the items in the order. Detect truncation, and ask again with a larger limit or a smaller request.

### Putting JSON into a prompt

Data given to a model is paid for in tokens and has to be understood. JSON is good at being unambiguous and poor at being compact.

Consider a list of $n$ records, each with the same $k$ fields, whose names average $L$ characters. In JSON with no spaces, every name appears in every record with two quotes and a colon, so the names alone cost about

$$
n \times k \times (L + 3) \text{ characters}
$$

A table with a header row states each name once:

$$
k \times (L + 1) \text{ characters}
$$

For 2,000 records with six fields of nine characters, the first figure is 144,000 characters, roughly 36,000 tokens at the four characters per token of Module 3.2. The second is 60 characters.

| Encoding | Field names | Best for |
|---|---|---|
| Indented JSON | Repeated, plus whitespace | People reading it |
| JSON with no spaces | Repeated | Nested or irregular data sent to a model |
| Header and rows | Once | Long lists of records with the same fields |
| One JSON object per line | Repeated | Streams and logs, processed a line at a time |

Newer compact notations make the same trade as the table: they declare the field names once and list the rows beneath. The authors of one, TOON, report token savings of around 40 percent against indented JSON on uniform data. The saving is real for lists of similar records and disappears for deeply nested or irregular data, where JSON's explicitness is worth its cost.

Format affects accuracy as well as cost. A 2023 study, "Table Meets LLM", gave models the same tables in different text formats and found that their accuracy on questions about the tables changed with the format. No single format is best for every model, which is a reason to test the choice on your own task as Module 5.9 described.

### Nested data pitfalls

**Depth.** Each level of nesting is another thing for the model to keep track of. Data five levels deep is answered less reliably than the same data in two. Flatten what you can before sending it.

**Position in long arrays.** A model cannot reliably find "the 37th item". Give each record an identifier and refer to records by it.

**Missing, null, and empty.** A field that is absent, a field that is `null`, and a field that is an empty string mean three different things to a program, and a model will often treat them as one. Decide which you mean and say so in the schema's description.

**Data used as names.** An object whose names are identifiers, such as one field per customer number, has no fixed schema and cannot be validated field by field. A list of records, each with an `id`, can.

**JSON inside a string.** A field whose value is a string containing more JSON has to be escaped once and parsed twice. Models get the escaping wrong. Nest the object directly.

**Sending everything.** An API response of 200 fields, passed whole to a model that needs four of them, costs tokens and dilutes attention, as Module 5.3 explained. Select the fields first.

### Complexity

Parsing and serialising are linear in the length of the text. The truncation check is one pass over the characters. Deriving a schema and flattening are linear in the number of values. The cost that matters is in tokens: field names repeated per record, which a table encoding removes.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, a parser that refuses what the standard parser lets through, and reports what went wrong.

```python
import json

class DuplicateKey(Exception):
    pass

class NonFinite(Exception):
    pass

def parse_strict(text):
    def pairs(items):
        result = {}
        for key, value in items:
            if key in result:
                raise DuplicateKey(key)
            result[key] = value
        return result

    def constant(name):
        raise NonFinite(name)

    try:
        return {"ok": True, "value": json.loads(text, object_pairs_hook=pairs, parse_constant=constant)}
    except json.JSONDecodeError as error:
        return {"ok": False, "kind": "syntax", "line": error.lineno, "column": error.colno}
    except DuplicateKey as error:
        return {"ok": False, "kind": "duplicate-key", "key": str(error)}
    except NonFinite as error:
        return {"ok": False, "kind": "non-finite", "name": str(error)}

print(parse_strict('{"id": 7, "tags": ["a", "b"], "paid": true, "note": null}'))
print(parse_strict("{'id': 7}"))
print(parse_strict('{\n  "id": 7,\n  "total": 12.5,\n  "paid": tru\n}')["line"])
print(parse_strict('{"id": 7, "id": 8}'), json.loads('{"id": 7, "id": 8}'))
print(parse_strict('{"score": NaN}'), json.loads('{"score": NaN}'))

big = '{"order_id": 9007199254740993}'
print(json.loads(big), json.loads(big, parse_int=float))
print(0.1 + 0.2, json.dumps({"name": "José"}), json.dumps({"name": "José"}, ensure_ascii=False))
print(json.loads(json.dumps({"when": (1, 2), 3: "x"})))
```

- **`object_pairs_hook` receives each object's fields as a list of pairs.** The standard parser would build a dictionary from them, and the last of any repeated name would win. The hook builds the dictionary itself and raises an error the moment a name repeats.
- **`parse_constant` is called for `NaN`, `Infinity`, and `-Infinity`.** These are not JSON. The standard parser accepts them. This one refuses.
- **The result is always a dictionary with an `ok` field.** The caller never has to catch an exception, and a failure says what kind it was: a syntax error with its line and column, a repeated name, or a non-finite number.
- **The first document parses.** Its `true` and `null` arrive as Python's `True` and `None`.
- **Single quotes are a syntax error at line 1, column 2.** The parser stopped at the first quote mark.
- **The five-line document fails on line 4.** The word `tru` is not a value. The line number is what you would send back to a model in a request to correct its output.
- **The repeated name is reported, where the standard parser returns 8.** Half of the document's information was thrown away with no error. In a model's output, a repeated field usually means the model changed its mind partway, and you want to know.
- **`NaN` is reported, where the standard parser returns a not-a-number value.** That value would have travelled into later arithmetic and corrupted it.
- **The large identifier survives as an integer and is wrong as a float.** Python parses 9007199254740993 exactly. Parsed the way JavaScript would, it becomes 9007199254740992.0. Identifiers belong in strings.
- **The last two lines show three serialising facts.** The sum of 0.1 and 0.2 is not 0.3. An accented letter is written as an escape unless `ensure_ascii=False` is passed. And a tuple and a numeric key come back from a round trip as a list and a string.

Next, detecting output that was cut off.

```python
def truncation_state(text):
    stack, in_string, escaped = [], False, False
    for character in text:
        if in_string:
            if escaped:
                escaped = False
            elif character == "\\":
                escaped = True
            elif character == '"':
                in_string = False
        elif character == '"':
            in_string = True
        elif character in "{[":
            stack.append(character)
        elif character in "}]" and stack:
            stack.pop()
    return {"in_string": in_string, "open": "".join(stack)}

print(truncation_state('{"a": [1, 2, {"b": "x"}]}'))
print(truncation_state('{"items": [{"sku": "A1", "note": "left at the'))
print(truncation_state('{"a": "brace } and bracket ] inside"'))
print(truncation_state('{"a": "quote \\" inside", "b": [1, 2'))
```

- **The function walks the text once, tracking two things.** Whether it is inside a string, and which brackets have been opened and not yet closed.
- **Inside a string, brackets are ordinary characters.** The third example has a closing brace and a closing bracket within a string. They are ignored, and the one opening brace is correctly reported as still open.
- **A backslash protects the next character.** In the fourth example, the escaped quote does not end the string. Without the `escaped` flag, the function would lose track of where strings begin and end.
- **A complete document has nothing open.** The first example returns an empty stack and is not inside a string.
- **The second example is the signature of truncation.** It is inside a string, with a brace, a bracket, and another brace open. The model ran out of output while writing a note.
- **The state says what was cut, not what was lost.** Appending a quote and the three closers would make the text parse. It would also present a partial order as a whole one. The right response is to request the output again.

Then, deriving a schema from an example.

```python
def schema_of(value):
    if value is None:
        return {"type": "null"}
    if isinstance(value, bool):
        return {"type": "boolean"}
    if isinstance(value, int):
        return {"type": "integer"}
    if isinstance(value, float):
        return {"type": "number"}
    if isinstance(value, str):
        return {"type": "string"}
    if isinstance(value, list):
        return {"type": "array", "items": schema_of(value[0]) if value else {}}
    if isinstance(value, dict):
        return {"type": "object", "properties": {name: schema_of(item) for name, item in value.items()},
                "required": list(value), "additionalProperties": False}
    raise TypeError("not a JSON value: " + type(value).__name__)

ORDER = {"order_id": "A1234", "paid": True, "total": 42.5,
         "items": [{"sku": "HAM-1", "qty": 2}, {"sku": "SAW-3", "qty": 1}], "coupon": None}
print(json.dumps(schema_of(ORDER)))
```

- **The function mirrors the six kinds of value.** Each kind of Python value maps to a `type`, and the two containers recurse into what they hold.
- **The check for a boolean comes before the check for an integer.** In Python, `True` is also an integer, so the tests in the other order would describe every boolean field as an integer. This is a classic bug in code that handles JSON.
- **An array's schema comes from its first element.** The function assumes the elements are alike. An empty array gives an empty schema for its items, which allows anything.
- **Every field of an object is marked required, and unlisted fields are forbidden.** That is the strictest reading of the example, and the right starting point: loosen deliberately, not by default.
- **The output is a draft.** The example's `coupon` was null, so the schema says the coupon is always null, which is wrong. A person now edits the draft: the coupon becomes a string or null, the `qty` gets a minimum of 1, a status gets an enum, and each field gets a description.

Finally, flattening nested data and encoding a list compactly.

```python
def flatten(value, prefix=""):
    if isinstance(value, dict) and value:
        flat = {}
        for name, item in value.items():
            flat.update(flatten(item, prefix + "." + name if prefix else name))
        return flat
    if isinstance(value, list) and value:
        flat = {}
        for index, item in enumerate(value):
            flat.update(flatten(item, f"{prefix}[{index}]"))
        return flat
    return {prefix: value}

def to_table(records):
    if not records:
        return ""
    columns = list(records[0])
    for record in records:
        if list(record) != columns:
            raise ValueError("records do not share the same fields")
    lines = [",".join(columns)]
    lines += [",".join(json.dumps(record[column], ensure_ascii=False) for column in columns) for record in records]
    return "\n".join(lines)

print(flatten(ORDER))

STOCK = [("Claw hammer", 12, 14.5, True), ("Tenon saw", 3, 22.0, True), ("Spirit level", 0, 9.75, False),
         ("Tape measure", 40, 6.2, True), ("Wood chisel", 7, 11.0, True), ("Hand plane", 2, 48.0, True),
         ("Mallet", 0, 13.25, False), ("Try square", 15, 8.4, True)]
RECORDS = [{"sku": f"SKU-{number:03d}", "name": name, "qty": qty, "price": price, "in_stock": in_stock}
           for number, (name, qty, price, in_stock) in enumerate(STOCK, start=1)]

pretty = json.dumps(RECORDS, indent=2)
minified = json.dumps(RECORDS, separators=(",", ":"))
table = to_table(RECORDS)
print(len(pretty), len(minified), len(table))
print(round(1 - len(minified) / len(pretty), 3), round(1 - len(table) / len(pretty), 3), round(1 - len(table) / len(minified), 3))
print(table.split("\n")[0])
print(table.split("\n")[1])
```

- **`flatten` turns a nested value into one level of path and value pairs.** A field inside an object gets a dot and its name. An element of an array gets its index in square brackets. The order becomes eight lines such as `items[1].sku` with the value `SAW-3`.
- **Empty containers are kept as values.** An empty list or object has no children to descend into, so it appears as a leaf. Dropping it would lose the fact that the field was present.
- **A flat list is easier for a model to answer questions about, and easy to compare.** Two versions of an order can be compared path by path. It is also what you want when only a few leaf values need to go into a prompt.
- **`to_table` writes the field names once, then one line per record.** Each cell is written with `json.dumps`, so strings keep their quotes, and a comma or quote mark inside a string cannot be mistaken for a separator.
- **It refuses records that do not share the same fields.** A table has no way to show a field that only some rows have. Irregular data should stay as JSON.
- **The eight stock records take 895 characters indented, 606 with no spaces, and 312 as a table.** Removing whitespace saves 32.3 percent. The table saves 65.1 percent against the indented form and 48.5 percent against the compact one.
- **About half of the compact JSON is field names.** The five names cost 38 characters per record with their quotes and colons, 304 characters over eight records, out of 606. The table's header states them in 27.
- **The saving grows with the list.** The header is paid once, so for hundreds of records the table approaches a third of the size of indented JSON.

**Complexity.** `parse_strict` is linear in the text. `truncation_state` is one pass over the characters. `schema_of` and `flatten` visit each value once. `to_table` is linear in the number of cells.

### A checklist for JSON coming out of a model

```text
[ ] Did generation stop normally, and not at the output limit?
[ ] Is there exactly one JSON value, with nothing after it?
[ ] Does it parse with a strict parser: no repeated names, no NaN?
[ ] Does it satisfy the schema: required fields, types, enums?
[ ] Are identifiers strings, and money an integer or a string?
[ ] Do the values exist in the real system?
[ ] On failure: was the line and column sent back, at most a fixed number of times?
```

### A checklist for JSON going into a prompt

```text
[ ] Only the fields the task needs
[ ] No indentation
[ ] ensure_ascii=False, so that text is readable
[ ] A table, when it is a long list of records with the same fields
[ ] An id on every record, so that nothing is referred to by position
[ ] As little nesting as the data allows
[ ] Stable field order, so that a repeated prefix can be cached
[ ] Clearly marked as data, separate from the instructions
```

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Python syntax mistaken for JSON.** Printing a Python dictionary gives single quotes, `True`, and `None`. Pasting that into a prompt as "the JSON" teaches the model the wrong format, and it will write the same back. Always serialise with `json.dumps`.

**Evaluating the model's output.** Running a model's reply through a function that executes code, because "it looks like a dictionary", hands control of the program to whatever the model wrote. Use `json.loads`.

**The last duplicate wins.** A model that revises a field partway through an answer can emit the same name twice. The standard parser keeps the second and hides the first. A strict parser turns a silent loss into a visible error.

**Truncated output repaired by closing brackets.** Libraries exist that complete broken JSON. Used on output that hit the length limit, they produce a valid document with the end missing. Check why generation stopped before repairing anything.

**Identifiers as numbers.** A 19-digit order number sent as a JSON number is rounded by the first JavaScript program that touches it. It then matches a different order, or none. Make identifiers strings in the schema.

**Money as a float.** A total of 0.30000000000000004 fails an equality check against 0.3, and rounding errors accumulate across a ledger. Use integers of the smallest unit.

**Dates in any format.** "03/04/2026" is March or April depending on the reader. Ask for ISO 8601, the form 2026-04-03, in the field's description, and validate it with a pattern.

**Null, missing, and empty treated alike.** A model asked for "the customer's phone number, if any" may omit the field, write null, or write an empty string, differently on different runs. Make the field required and allow null, so that there is exactly one way to say "none".

**Escaping inside strings.** JSON containing code, regular expressions, or Windows paths needs every backslash doubled and every quote escaped. Models miss some. Where a field holds a large block of text or code, consider returning it outside the JSON, with the JSON carrying only the metadata.

**Indented JSON in a prompt.** Indentation is for people. A model does not need it, and it can be a third of the characters. Serialise without spaces for the model, and indent only what a person will read.

**Thousands of records in one prompt.** Even as a table, a very large list dilutes attention, and a model cannot be relied on to count or sum it. Filter and aggregate in code, and send the model the rows that matter.

**A schema with no descriptions.** Field names such as `d1` and `flag` tell a model nothing. The description on each field is where you say what belongs in it, in what unit and form. It is the cheapest improvement to a structured output.

**Trusting that valid means correct.** A response that parses and matches the schema can still name a product that does not exist. Validation proves the shape. Module 5.5 made the same point, and it bears repeating wherever JSON feeds an action.

## 5. Active Recall Check & Synthesis Summary

**Summary.** JSON is a strict text format with six kinds of value: strings in double quotes, numbers, true and false, null, arrays, and objects. It allows no single quotes, trailing commas, comments, or non-finite numbers. A model reads and writes only the text. Programs cross between text and values by parsing and serialising, and most problems occur at those crossings. Python's standard parser is more lenient than the format: it keeps the last of a repeated name and accepts NaN, so a strict parser that reports the kind and position of a fault is the safer tool. Large identifiers belong in strings and money in integers, because floating point holds integers exactly only to $2^{53}$ and cannot hold most decimal fractions. A schema describes the expected shape with a few keywords, of which enums and descriptions do the most for a model's output, and a good one can be drafted from an example and tightened by hand. Output cut off at the length limit must be detected and requested again, not repaired. As prompt input, JSON repeats every field name in every record, at a cost of about $n \times k \times (L + 3)$ characters, so data should be trimmed to the needed fields, written without indentation, flattened where possible, and sent as a header and rows when it is a long uniform list.

**Question 1.** For each of these four texts, say what Python's `json.loads` does with it and what a strict parser should do, and explain the risk in each case: `{"id": 7, "id": 8}`, `{"score": NaN}`, `{'id': 7}`, and `{"order_id": 9007199254740993}`.

<details>
<summary>View Answer</summary>

For the first text, `json.loads` returns an object whose id is 8. It keeps the last value of a repeated name and discards the earlier one with no error. A strict parser should reject the document and report the repeated name. The risk is silent loss: in a model's output, a repeated field usually means the model wrote one value and then another, and the program acts on one of them without anyone knowing there was a conflict. For the second, `json.loads` accepts the text and returns a floating-point not-a-number, although NaN is not part of JSON. A strict parser should reject it. The risk is that the value flows into later arithmetic, where every sum or comparison involving it gives a meaningless result, far from where the fault entered. For the fourth, `json.loads` in Python returns the integer exactly, since Python integers have no size limit, and a strict parser accepts it too, because it is valid JSON. The remedy is in the schema and not the parser: identifiers should be strings.

**Question 2.** A prompt includes a list of 2,000 product records as JSON with no spaces. Each record has six fields whose names average nine characters. Estimate how many characters, and how many tokens at four characters per token, are spent on field names alone. At USD 2 per million input tokens and 10,000 requests a month, what do the field names cost? What would a header-and-rows table spend on names, and when would you keep JSON anyway?

<details>
<summary>View Answer</summary>

In JSON with no spaces, each field name appears in every record with two quote marks and a colon, so it costs its length plus three characters: nine plus three is twelve. With six fields that is 72 characters of names per record, and over 2,000 records it is 144,000 characters. At four characters per token that is about 36,000 tokens, spent on text that carries no information after the first record. At USD 2 per million input tokens, 36,000 tokens cost USD 0.072 per request, and over 10,000 requests a month that is USD 720, for the field names alone. A header-and-rows table states each name once, with a separator: six names of nine characters plus one each is 60 characters, about 15 tokens. The saving is essentially the whole 36,000 tokens per request, though prompt caching would recover much of the cost if the list is identical between requests and comes first. JSON should be kept in three situations. When the records are irregular, with fields that only some of them have, a table cannot represent them without inventing empty cells. When the data is nested, with objects and arrays inside each record, a table has nowhere to put the inner structure. And when the model must write the data back in JSON, showing it JSON keeps the input and output forms the same. It is also worth asking whether 2,000 records should be in the prompt at all: filtering in code to the rows the question concerns usually saves more than any change of format, and gives better answers.

**Question 3.** A model is asked for an order as JSON. The reply ends: `{"order_id": "A1234", "items": [{"sku": "HAM-1", "qty": 2}, {"sku": "SAW-3", "note": "customer asked for gift wr`. <details>
<summary>View Answer</summary>

Walking the text, the check finds an opening brace for the order, then an opening bracket for the items array. The first item's brace is opened and closed. The second item's brace is opened and never closed, and inside it the note's string is opened and never closed. So the check reports that the text ends inside a string, with a brace, a bracket, and a brace still open, in that order. That is the signature of output cut off at the length limit and not of a model that made a syntax error. Appending a quote mark, a brace, a bracket, and a brace does make the text parse. What it produces is an order with two items, the second of which has a note reading "customer asked for gift wr" and no quantity. Everything that would have followed is gone, and nothing in the repaired document says so: the remainder of the note, the second item's quantity, any further items, and any fields after the array, such as the total or the delivery address. A program acting on it would process a partial order as if it were complete. A schema check would catch the missing quantity here, by luck. Check the reason the API gives for stopping, which will be the length limit. Then request the output again with a larger limit, or change the request so that the output is smaller, for example by asking for the items in batches, or by leaving out free-text notes. # ---------------------------------------------------------------- Step 1
def parse_strict(text):
    """The standard parser keeps the last of a repeated name and accepts NaN. Both are silent
    losses. This one reports the kind of fault and, for syntax, where it is."""
    def pairs(items):
        result = {}
        for key, value in items:
            if key in result:
                raise DuplicateKey(key)
            result[key] = value
        return result

    def constant(name):
        raise NonFinite(name)

    try:
        return {"ok": True, "value": json.loads(text, object_pairs_hook=pairs, parse_constant=constant)}
    except json.JSONDecodeError as error:
        return {"ok": False, "kind": "syntax", "line": error.lineno, "column": error.colno}
    except DuplicateKey as error:
        return {"ok": False, "kind": "duplicate-key", "key": str(error)}
    except NonFinite as error:
        return {"ok": False, "kind": "non-finite", "name": str(error)}


# ---------------------------------------------------------------- Step 2
def truncation_state(text):
    """Open brackets or an open string at the end mean the output was cut off. The state
    says what was cut, not what was lost: request the output again, do not close it by hand."""
    stack, in_string, escaped = [], False, False
    for character in text:
        if in_string:
            if escaped:
                escaped = False
            elif character == "\\":
                escaped = True
            elif character == '"':
                in_string = False
        elif character == '"':
            in_string = True
        elif character in "{[":
            stack.append(character)
        elif character in "}]" and stack:
            stack.pop()
    return {"in_string": in_string, "open": "".join(stack)}


# ---------------------------------------------------------------- Step 3
def schema_of(value):
    """A draft, to be tightened by hand with enums, bounds, and descriptions. The boolean
    test comes first because True is also an integer in Python."""
    if value is None:
        return {"type": "null"}
    if isinstance(value, bool):
        return {"type": "boolean"}
    if isinstance(value, int):
        return {"type": "integer"}
    if isinstance(value, float):
        return {"type": "number"}
    if isinstance(value, str):
        return {"type": "string"}
    if isinstance(value, list):
        return {"type": "array", "items": schema_of(value[0]) if value else {}}
    if isinstance(value, dict):
        return {"type": "object", "properties": {name: schema_of(item) for name, item in value.items()},
                "required": list(value), "additionalProperties": False}
    raise TypeError("not a JSON value: " + type(value).__name__)


# ---------------------------------------------------------------- Step 4
def flatten(value, prefix=""):
    """One level of path and value pairs is easier for a model to answer questions about,
    and can be compared path by path. Empty containers are kept, so presence is not lost."""
    if isinstance(value, dict) and value:
        flat = {}
        for name, item in value.items():
            flat.update(flatten(item, prefix + "." + name if prefix else name))
        return flat
    if isinstance(value, list) and value:
        flat = {}
        for index, item in enumerate(value):
            flat.update(flatten(item, f"{prefix}[{index}]"))
        return flat
    return {prefix: value}

    quote inside a string cannot be mistaken for a separator."""

    lines = [",".join(columns)]
    lines += [",".join(json.dumps(record[column], ensure_ascii=False) for column in columns) for record in records]
    return "\n".join(lines)
