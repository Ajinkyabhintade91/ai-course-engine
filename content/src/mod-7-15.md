# Authentication and API Keys

Every API call in this unit has carried a credential: an API key in a header, a bearer token, an OAuth connection to Gmail. Credentials are what let an automation act on someone's behalf, and that makes them the most valuable thing an automation holds. A leaked key can read a company's email, empty its cloud budget, or send messages in its name. GitGuardian's State of Secrets Sprawl 2026 report counted 28,649,024 new secrets detected in public GitHub commits in 2025, a figure that says how often this goes wrong.

This chapter covers the main ways APIs authenticate callers, API keys, bearer tokens, basic authentication, and OAuth 2.0; where secrets should live in an automation; and the operational habits that limit the damage when one leaks: least privilege, rotation, redaction, and a rehearsed response. Module 7.7 introduced credential stores and Module 7.11 OAuth scopes; this chapter explains what is underneath both.

## 1. First-Principles Mental Model & Intuition

### Keys, wristbands, and valet keys

Think of three ways to get into a building.

A **key** opens the door for whoever holds it. It does not know who you are; possessing it is enough. An API key works like this: anyone who has it can use it, which is why it must be kept secret.

A **festival wristband** is issued after you show your ticket at the gate, lets you in for a limited time, and is useless after the festival ends. A bearer token works like this: you obtain it, often by exchanging something else, and present it with each request until it expires.

A **valet key** opens the car door and starts the engine, but not the boot or the glove box, and the owner hands it over without giving away their own key. OAuth works like this: a user lets an application act on their account with limited permissions, without ever giving the application their password, and can take that permission back.

```text
   API KEY                  BEARER TOKEN                  OAUTH 2.0
   one long secret          short-lived, obtained         user approves limited access
   sent on every call       from a login or exchange      app receives tokens, never the password
   valid until revoked      expires (minutes to hours)    access token + refresh token
   x-api-key: sk-SECRET     Authorization: Bearer TOKEN   scopes decide what it can do
```

### Authentication and authorisation

Two words are often confused. **Authentication** answers "who is calling?". **Authorisation** answers "what may they do?". An API key usually does both at once: it identifies an account and carries that account's permissions. OAuth separates them more carefully: the access token identifies the application and the user who approved it, and its **scopes** limit what it may do, as Gmail's scopes did in Module 7.11.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### API keys

An API key is a long random string issued by the service, sent with each request. Services choose where it goes:

| Placement | Example | Verdict |
|---|---|---|
| A custom header | `x-api-key: SECRET` | Good |
| The Authorization header | `Authorization: Bearer SECRET` | Good |
| A query parameter | `https://api.example.com/v1/orders?api_key=SECRET` | Avoid: URLs are logged by servers, proxies, browsers, and workflow tools |

Keys are simple and suit server-to-server automation. Their weakness is that they rarely expire: a key copied into a document three years ago still works today unless someone revoked it. Good services let you give each key a name, limited permissions, and an expiry, and show when it was last used.

### Bearer tokens

RFC 6750 defines **bearer token** usage for OAuth: any party in possession of the token can use it, so it must be protected in storage and in transit, always sent over HTTPS, and preferably short-lived. It is sent as `Authorization: Bearer <token>`. Many tokens are **JWTs**, JSON Web Tokens, three base64url parts separated by dots, a header, a payload of claims such as the expiry time, and a signature. A JWT's payload is encoded, not encrypted: anyone holding the token can read it, so it must not contain secrets.

### Basic authentication

HTTP **Basic** authentication sends a username and password joined by a colon, encoded in base64, in the Authorization header. Base64 is an encoding, not encryption: `c2hvcDpzM2NyZXQ=` decodes instantly to `shop:s3cret`. Basic authentication is acceptable only over HTTPS, and many services now issue an application-specific password or token for it rather than the account password.

### OAuth 2.0 and the authorization code flow

OAuth 2.0, defined in RFC 6749, lets a user grant an application limited access to their account at another service. The most important flow for automation tools is the **authorization code** flow, which is what happens when you click "Connect your Google account" in n8n, Make, or Zapier:

```text
   1  App sends user to the provider:  /authorize with client_id, redirect_uri, scope, state,
                                        code_challenge, and code_challenge_method=S256
   2  User signs in AT THE PROVIDER and approves the scopes
   3  Provider redirects back:          /callback?code=ONE_TIME_CODE&state=SAME_STATE
   4  App checks state matches, then exchanges the code (plus code_verifier) at /token
   5  Provider returns:                 access_token (short-lived), refresh_token (long-lived), expires_in
   6  App calls the API with:           Authorization: Bearer access_token
   7  When the access token expires:    POST /token with the refresh_token for a new access token
```

Each piece has a purpose:

| Piece | Purpose |
|---|---|
| `client_id` | Identifies the application to the provider |
| `redirect_uri` | Where the provider sends the user back; must match a registered value exactly |
| `scope` | The permissions requested; the user sees and approves them |
| `state` | A random value the app checks on return, defending against forged callbacks (cross-site request forgery) |
| Authorization code | One-time, short-lived; useless without the next step |
| Access token | Used on API calls; expires, often within an hour |
| Refresh token | Used to get new access tokens without asking the user again; must be guarded like a password |

The user's password never reaches the application. The user can revoke the application's access at the provider at any time, and the scopes limit what a stolen token can do.

### PKCE

An authorization code travels through the user's browser, where it could be intercepted. **PKCE**, Proof Key for Code Exchange, defined in RFC 7636, closes that gap. Before step 1, the app creates a random secret, the **code verifier**, a string of 43 to 128 characters from letters, digits, and `-._~`. It sends only a derived value, the **code challenge**, in step 1:

$$\text{code\_challenge} = \text{BASE64URL}\big(\text{SHA256}(\text{code\_verifier})\big)$$

with base64url padding removed, and `code_challenge_method=S256`. In step 4 it sends the verifier itself. The provider hashes the verifier and checks it matches the challenge it received earlier. An attacker who steals the code but not the verifier cannot redeem it, and cannot work the verifier out from the challenge because SHA-256 cannot be reversed.

RFC 7636 includes a worked example: the verifier `dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk` gives the challenge `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`. The lab reproduces it. RFC 9700, the IETF's 2025 Best Current Practice for OAuth 2.0 Security, recommends PKCE for all clients using the authorization code flow, not only mobile and browser apps.

### Token lifetimes and refresh

Access tokens expire so that a stolen one is useful only briefly. An automation must therefore track each token's expiry and refresh it before it lapses. Two details matter:

1. **Refresh a little early.** A token that expires during a request causes a 401 mid-workflow. Treat a token as expired a minute or so before its stated time, a margin called clock skew allowance.
2. **Plan for refresh failure.** Refresh tokens can be revoked by the user, expire after a period of disuse, or be invalidated when a password changes. When refresh fails, the only fix is for the user to authorise again, and the automation must say so clearly instead of failing silently, which is the expired-credential incident from Module 7.14.

Some providers also rotate refresh tokens: each refresh returns a new refresh token and invalidates the old one, so the automation must save the new one every time.

### Where secrets live

| Place | Verdict |
|---|---|
| Typed into a workflow step's field | No: travels with exports and screenshots, as Module 7.7 showed |
| In source code or a committed config file | No: version history keeps it forever, even after deletion |
| Environment variables on a server | Acceptable for small deployments; visible to anything running as that user |
| The workflow tool's credential store | Good: encrypted, referenced by name, kept out of exports |
| A secrets manager (cloud key vaults, HashiCorp Vault) | Best for teams: central, audited, supports rotation |

OWASP's Secrets Management Cheat Sheet adds principles that apply to any of them: centralise secrets, give each one an owner, grant least privilege, rotate regularly and automatically where possible, log access, and prepare for leaks before they happen.

### Least privilege and rotation

**Least privilege** means each credential can do only what its automation needs. A key that syncs orders needs read access to orders, not administrator rights. Separate keys for separate automations mean one leak does not compromise everything, and a key can be revoked without breaking unrelated workflows.

**Rotation** means replacing keys on a schedule, so that a key leaked without anyone noticing stops working eventually. A safe rotation overlaps: create the new key, update the automations to use it, confirm they work, then revoke the old one. Keys that have not been used for weeks are candidates for revocation, since a forgotten key is an unmonitored door.

### Leak response

When a secret leaks, the order of actions matters:

| Step | Why |
|---|---|
| 1. Revoke or rotate the secret immediately | Deleting it from a repository or message does not help: copies exist |
| 2. Check the provider's logs for misuse | Find out whether it was used and for what |
| 3. Update the automations with the new secret | Restore service |
| 4. Find and fix how it leaked | Hard-coded value, log line, export, screenshot |
| 5. Add detection | Secret scanning on repositories, redaction in logs |

### Complexity

Building headers and checking token expiry are constant time. Hashing for PKCE is linear in the verifier's length. Redacting a log is linear in its length times the number of patterns. Auditing keys is linear in the number of keys.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, building headers and catching secrets in URLs.

```python
import base64
from urllib.parse import parse_qs, urlparse

def auth_headers(kind, credential, header_name="x-api-key"):
    if kind == "api_key":
        return {header_name: credential}
    if kind == "bearer":
        return {"Authorization": "Bearer " + credential}
    if kind == "basic":
        user, password = credential
        return {"Authorization": "Basic " + base64.b64encode(f"{user}:{password}".encode("utf-8")).decode("ascii")}
    raise ValueError("unknown kind: " + kind)

SECRET_PARAMS = {"api_key", "apikey", "key", "token", "access_token", "secret", "password"}

def secrets_in_url(url):
    return sorted(name for name in parse_qs(urlparse(url).query) if name.lower() in SECRET_PARAMS)

print(auth_headers("api_key", "test-key-123"), auth_headers("bearer", "tok"), auth_headers("basic", ("shop", "s3cret")))
print(base64.b64decode("c2hvcDpzM2NyZXQ=").decode())
print(secrets_in_url("https://api.example.com/v1/orders?status=paid&api_key=abc"), secrets_in_url("https://api.example.com/v1/orders?page=2"))
```

- **Each kind of credential goes in its conventional header.** API keys in a named header, bearer tokens and Basic credentials in `Authorization`.
- **Basic credentials are only encoded.** Decoding `c2hvcDpzM2NyZXQ=` gives `shop:s3cret` immediately, which is why Basic authentication needs HTTPS.
- **An unknown kind is an error.** Silently sending no credential would produce confusing 401s.
- **`secrets_in_url` flags query parameters that look like credentials.** A key in a URL ends up in server logs and workflow histories, so a pre-flight check should refuse it.

Next, redacting secrets from logs.

```python
import re

PATTERNS = [("anthropic", re.compile(r"sk-ant-[A-Za-z0-9_-]{20,}")),
            ("aws_access_key", re.compile(r"AKIA[0-9A-Z]{16}")),
            ("github_token", re.compile(r"gh[pousr]_[A-Za-z0-9]{36}")),
            ("slack_token", re.compile(r"xox[baprs]-[A-Za-z0-9-]{10,}")),
            ("bearer", re.compile(r"(?i)(?<=bearer )[A-Za-z0-9._~+/-]{20,}=*"))]

def mask(value):
    return value[:4] + "*" * max(4, len(value) - 8) + value[-4:] if len(value) > 8 else "*" * len(value)

def redact(text):
    found = []
    for name, pattern in PATTERNS:
        def replace(match, name=name):
            found.append(name)
            return mask(match.group(0))
        text = pattern.sub(replace, text)
    return text, found

LOG = ("calling api with key sk-ant-api03-AbCdEfGhIjKlMnOpQrStUvWx and AKIAIOSFODNN7EXAMPLE; "
       "header Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.payload.sig123")
print(redact(LOG))
print(mask("sk-live-4f9a8b7c6d5e"), mask("short"))
```

- **Each pattern matches one well-known secret format.** Anthropic keys, AWS access key IDs, GitHub tokens, Slack tokens, and anything following "Bearer ".
- **The bearer pattern matches only the token, not the word "Bearer".** A lookbehind keeps the label readable in the log.
- **`mask` keeps the first and last four characters.** Enough to tell which key appeared, useless to an attacker. Short values are masked entirely.
- **The example log contains three secrets, and all are masked.** `AKIAIOSFODNN7EXAMPLE` is the example key from AWS's own documentation.
- **Redaction is a safety net, not a plan.** It catches known formats. The real fix is never to log credentials, and a scanner on repositories and logs catches what slips through.

Then, PKCE and the authorization URL.

```python
import hashlib
from urllib.parse import urlencode

def pkce_challenge(verifier):
    if not 43 <= len(verifier) <= 128 or not re.fullmatch(r"[A-Za-z0-9\-._~]+", verifier):
        raise ValueError("a code verifier is 43 to 128 characters from A-Z, a-z, 0-9, and -._~")
    digest = hashlib.sha256(verifier.encode("ascii")).digest()
    return base64.urlsafe_b64encode(digest).decode("ascii").rstrip("=")

def authorize_url(endpoint, client_id, redirect_uri, scopes, state, verifier):
    params = {"response_type": "code", "client_id": client_id, "redirect_uri": redirect_uri,
              "scope": " ".join(scopes), "state": state,
              "code_challenge": pkce_challenge(verifier), "code_challenge_method": "S256"}
    return endpoint + "?" + urlencode(params)

VERIFIER = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
print(pkce_challenge(VERIFIER))
print(authorize_url("https://auth.example.com/authorize", "shop-app", "https://shop.example.com/callback",
                    ["orders.read", "invoices.write"], "x7Kq2", VERIFIER))
```

- **The verifier is checked against RFC 7636's rules.** Length 43 to 128, unreserved characters only.
- **The challenge is the SHA-256 digest, base64url-encoded, without padding.** For the RFC's example verifier it is `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`, exactly as the RFC states.
- **The authorization URL carries everything the provider needs.** Client ID, redirect URI, scopes separated by spaces, the state value, and the challenge with method S256.
- **`urlencode` escapes the redirect URI.** The colon and slashes become `%3A` and `%2F`, so the URL stays valid.
- **In real use, the verifier and state are random.** `secrets.token_urlsafe(32)` produces a suitable 43-character verifier; the fixed example exists so the result can be checked.

Finally, token state and a key audit.

```python
from datetime import date, datetime, timedelta

def token_state(token, now, skew=timedelta(seconds=60)):
    if token is None:
        return "authorize"
    if now < token["expires_at"] - skew:
        return "valid"
    if token.get("refresh_token"):
        return "refresh"
    return "authorize"

TOKEN = {"access_token": "a", "refresh_token": "r", "expires_at": datetime(2026, 11, 16, 10, 0)}
print(token_state(TOKEN, datetime(2026, 11, 16, 9, 58)), token_state(TOKEN, datetime(2026, 11, 16, 9, 59, 30)),
      token_state({**TOKEN, "refresh_token": None}, datetime(2026, 11, 16, 10, 5)), token_state(None, datetime(2026, 11, 16)))

def audit_keys(keys, today, max_age=90, unused_days=30):
    report = []
    for key in keys:
        issues = []
        if (today - key["created"]).days > max_age:
            issues.append("rotate")
        if key["last_used"] is None or (today - key["last_used"]).days > unused_days:
            issues.append("unused")
        if any(scope in ("*", "admin") or scope.endswith(":*") for scope in key["scopes"]):
            issues.append("broad_scope")
        if key.get("shared"):
            issues.append("shared")
        report.append((key["name"], issues))
    return report

KEYS = [{"name": "orders-sync", "created": date(2026, 10, 1), "last_used": date(2026, 11, 15), "scopes": ["orders:read"]},
        {"name": "old-zapier", "created": date(2026, 3, 2), "last_used": date(2026, 6, 1), "scopes": ["*"]},
        {"name": "billing-bot", "created": date(2026, 7, 1), "last_used": date(2026, 11, 16), "scopes": ["invoices:write", "customers:*"], "shared": True}]
print(audit_keys(KEYS, date(2026, 11, 16)))
```

- **A token is valid until a minute before its expiry.** At 09:58 it is valid; at 09:59:30, inside the skew margin, it should be refreshed now.
- **Without a refresh token, an expired token means asking the user again.** "authorize" is the state that must produce a clear alert, not a stream of 401s.
- **No token at all also means authorise.** The connection was never made, or was removed.
- **`audit_keys` checks each key against four rules.** Older than 90 days, unused for over 30 days, scopes that grant everything, and keys shared between automations.
- **orders-sync is clean.** Recent, in use, and limited to reading orders.
- **old-zapier fails three ways.** Created in March, unused since June, and allowed to do anything: revoke it.
- **billing-bot is in use but needs work.** It is 138 days old, has a wildcard scope over customers, and is shared, so it should be split into separate, narrower keys and rotated.

**Complexity.** `auth_headers` and `token_state` are constant. `secrets_in_url` is linear in the URL. `redact` is linear in the text for each pattern. `pkce_challenge` is linear in the verifier. `audit_keys` is linear in the keys.

### Choosing an authentication method

| Situation | Method |
|---|---|
| Your server calls a service with its own account | API key or client credentials, stored in the credential store |
| Acting on a user's account at another service | OAuth authorization code with PKCE |
| A legacy service with username and password | Basic authentication over HTTPS, with an app-specific password |
| Short-lived access from a login | Bearer tokens, refreshed before expiry |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Keys committed to a repository.** Deleting the file leaves the key in history. Revoke the key; cleaning history is secondary.

**Keys in URLs.** Query strings appear in access logs and browser history. Use headers.

**Logging full requests.** Debug logs that print headers leak tokens. Redact before writing.

**One key for everything.** A single admin key shared by every automation makes every leak total. Use one narrow key per automation.

**Keys that never expire.** A key from a former employee's experiment still works years later. Set expiries and audit.

**Refresh tokens not saved after rotation.** Providers that rotate refresh tokens invalidate the old one. Save the new token every time.

**Silent OAuth expiry.** A revoked connection produces failures until someone notices. Treat "re-authorisation needed" as an alert.

**Skipping the state check.** Without it, a forged callback can attach an attacker's account. Generate and verify `state`.

**Secrets in screenshots and tutorials.** Screens shared for help often show keys. Mask them, or rotate after sharing.

**Pasting keys into AI chats.** Text sent to a chat assistant leaves your control. Never paste live secrets into prompts.

**Rotation that breaks production.** Revoking the old key before switching automations causes an outage. Overlap: add, switch, verify, revoke.

**Trusting base64.** Encoded is not encrypted. Basic credentials and JWT payloads are readable by anyone who sees them.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Credentials let automations act on someone's behalf, and leaks are common: GitGuardian counted 28,649,024 new secrets in public GitHub commits in 2025. API keys are long-lived secrets sent in a header, never a URL; bearer tokens are short-lived credentials that work for whoever holds them, often JWTs whose payload is readable; Basic authentication only encodes a username and password and needs HTTPS. OAuth 2.0's authorization code flow lets a user grant an application scoped access without sharing their password: the app redirects the user to the provider with its client ID, redirect URI, scopes, a random `state`, and a PKCE challenge, the base64url SHA-256 of a secret verifier; the provider returns a one-time code, which the app exchanges with the verifier for an access token and a refresh token. RFC 9700 recommends PKCE for all authorization code clients. Access tokens expire and are refreshed slightly early; when refresh fails, the user must authorise again, which should trigger an alert. Secrets belong in a credential store or secrets manager, not in step fields, code, or logs, and each should have an owner, least privilege, a rotation date, and a rehearsed leak response that starts with revoking the secret.

**Question 1.** A developer accidentally commits a file containing a live API key to a public repository, notices an hour later, deletes the file in a new commit, and moves on. What is wrong with this response, and what should the full response be, in order?

<details>
<summary>View Answer</summary>

Deleting the file in a new commit does not remove the key: the earlier commit still contains it, and anyone can read the history. Public repositories are scanned by automated tools within minutes, so after an hour it is safest to assume the key has been copied, and possibly already used. The deletion gives a false sense of safety while the key keeps working. The correct response, in order: first, revoke or rotate the key immediately at the provider, which is the only action that actually stops misuse; second, check the provider's usage and access logs for the period since the commit, for unexpected calls, costs, or data access, and contain any damage found; third, create a new key with the narrowest permissions the automation needs, store it in the credential store or secrets manager, and update the automations, confirming they work; fourth, find out how the key reached the file, a hard-coded value or a config file that should have been excluded, and fix that, for example by loading secrets from the credential store and adding the file to the ignore list; fifth, add detection, such as secret scanning on the repository and pre-commit checks, so the next mistake is caught before it is pushed. Rewriting the repository's history to remove the key is worth doing for tidiness, but only after the key is revoked, since copies may already exist elsewhere.

**Question 2.** Walk through what happens when a user clicks "Connect Google account" in a workflow tool, naming each parameter's role, and explain what an attacker could and could not do if they intercepted (a) the authorization code, (b) the access token, (c) the refresh token.

<details>
<summary>View Answer</summary>

The tool creates a random `state` value and a random code verifier, computes the code challenge as the base64url SHA-256 of the verifier, and redirects the user's browser to Google's authorization endpoint with its `client_id`, its registered `redirect_uri`, the `scope` it needs, the `state`, the `code_challenge`, and `code_challenge_method=S256`. The user signs in at Google, not in the tool, and sees and approves the requested scopes. Google redirects the browser to the redirect URI with a one-time authorization code and the same `state`. The tool checks that `state` matches what it generated, then sends the code and the original verifier to Google's token endpoint; Google hashes the verifier, checks it against the challenge, and returns an access token, a refresh token, and an expiry. The tool stores the tokens encrypted in its credential store and uses the access token on API calls, refreshing it before it expires. (a) An intercepted authorization code is useless on its own: it expires quickly, can be used once, and redeeming it requires the verifier, which never left the tool and cannot be derived from the challenge. (b) An intercepted access token can be used, by whoever holds it, to call the API within its scopes until it expires, typically within an hour, which is why scopes should be narrow and tokens short-lived. (c) An intercepted refresh token is the most dangerous: it can mint new access tokens repeatedly, within the same scopes, until it is revoked, so it must be guarded like a password, and the user or administrator should revoke the application's access at Google if it is suspected to have leaked.

# ---------------------------------------------------------------- Step 1
def auth_headers(kind, credential, header_name="x-api-key"):
    """Credentials go in headers. Basic is only base64 encoding, so it needs HTTPS."""
    if kind == "api_key":
        return {header_name: credential}
    if kind == "bearer":
        return {"Authorization": "Bearer " + credential}
    if kind == "basic":
        user, password = credential
        return {"Authorization": "Basic " + base64.b64encode(f"{user}:{password}".encode("utf-8")).decode("ascii")}
    raise ValueError("unknown kind: " + kind)


def secrets_in_url(url):
    """Query strings are logged everywhere; credentials must not be in them."""
    return sorted(name for name in parse_qs(urlparse(url).query) if name.lower() in SECRET_PARAMS)


# ---------------------------------------------------------------- Step 2
def mask(value):
    """Enough to recognise which key it was, useless to an attacker."""
    return value[:4] + "*" * max(4, len(value) - 8) + value[-4:] if len(value) > 8 else "*" * len(value)


def redact(text):
    """A safety net for logs: known secret formats are masked before anything is written."""
    found = []
    for name, pattern in PATTERNS:
        def replace(match, name=name):
            found.append(name)
            return mask(match.group(0))
        text = pattern.sub(replace, text)
    return text, found


# ---------------------------------------------------------------- Step 3
def pkce_challenge(verifier):
    """RFC 7636 S256: BASE64URL(SHA256(verifier)) without padding."""
    if not 43 <= len(verifier) <= 128 or not re.fullmatch(r"[A-Za-z0-9\-._~]+", verifier):
        raise ValueError("a code verifier is 43 to 128 characters from A-Z, a-z, 0-9, and -._~")
    digest = hashlib.sha256(verifier.encode("ascii")).digest()
    return base64.urlsafe_b64encode(digest).decode("ascii").rstrip("=")


def authorize_url(endpoint, client_id, redirect_uri, scopes, state, verifier):
    """Only the challenge travels through the browser; the verifier stays with the app."""
    params = {"response_type": "code", "client_id": client_id, "redirect_uri": redirect_uri,
              "scope": " ".join(scopes), "state": state,
              "code_challenge": pkce_challenge(verifier), "code_challenge_method": "S256"}
    return endpoint + "?" + urlencode(params)


# ---------------------------------------------------------------- Step 4
def token_state(token, now, skew=timedelta(seconds=60)):
    """Refresh a little early; when refresh is impossible, the user must authorise again."""
    if token is None:
        return "authorize"
    if now < token["expires_at"] - skew:
        return "valid"
    if token.get("refresh_token"):
        return "refresh"
    return "authorize"


# ---------------------------------------------------------------- Step 5
def audit_keys(keys, today, max_age=90, unused_days=30):
    """Old, unused, over-powerful, and shared keys are the ones that turn a leak into a disaster."""
    report = []
    for key in keys:
        issues = []
        if (today - key["created"]).days > max_age:
            issues.append("rotate")
        if key["last_used"] is None or (today - key["last_used"]).days > unused_days:
            issues.append("unused")
        if any(scope in ("*", "admin") or scope.endswith(":*") for scope in key["scopes"]):
            issues.append("broad_scope")
        if key.get("shared"):
            issues.append("shared")
        report.append((key["name"], issues))
    return report
