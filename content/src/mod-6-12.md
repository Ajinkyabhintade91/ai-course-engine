# Automated Content Pipelines

Every chapter of this unit has described a step done by a person with an AI tool: drafting a script, generating an image, cutting a Reel, building a carousel. This chapter connects the steps into a pipeline that runs on its own. A video is published, and within the hour there are drafts of a newsletter item, a carousel, a LinkedIn post, and a short post, each waiting for someone to read and approve them.

That last clause is the whole design. A pipeline that publishes without a person is a machine for producing the generic, repetitive content that Module 6.1 warned audiences scroll past and platforms penalise. A pipeline that drafts, checks, and queues for approval saves most of the time and keeps the judgement. This chapter covers how to build the second kind: the repurposing logic, the orchestration tools, the gates, and the engineering that stops a pipeline posting the same thing twice.

## 1. First-Principles Mental Model & Intuition

### A kitchen during service

A restaurant kitchen turns raw ingredients into many dishes quickly. It is organised into stations, each doing one job. Tickets move between them. And at the pass, before any plate goes out, the head chef looks at it.

A content pipeline is that kitchen. The ingredient is one piece of long content you made: a video, an article, a podcast. The stations are transcription, splitting, drafting for each format, and checking. The tickets are jobs, one per format. The pass is the approval queue, where a person decides what goes out.

Remove the pass and the kitchen still produces plates, faster. Some of them will be wrong, and they will be served.

### The shape

```text
   SOURCE                 PREPARE             FAN OUT               CHECK            PASS            OUT
   one long piece   ->    transcribe   ->     one job per     ->    rules per   ->   a person   ->   schedule
   you made               split into          format: draft         format:          approves,       and
   (video, article)       chunks              with an LLM           length, words    edits, or       publish,
                                                                     banned phrases   rejects         once
                                                                         |                 |
                                                                         +-- failed -------+-- rejected: back to draft
```

### Why one source, many outputs

The value of repurposing is that the expensive part, having something to say and saying it well, has already been done once. A video that took a day to make contains material for a week of posts. Each derived post costs minutes, not hours.

It also keeps the content original. Every output is built from your own material, which is what the platforms' policies on recycled content reward, and what an audience following you across platforms recognises.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### The stages

| Stage | What happens | Tools |
|---|---|---|
| **Trigger** | A new source appears: a video is published, an article goes live | A webhook or a scheduled check, covered in Unit 7 |
| **Transcribe** | Speech becomes text | Speech-to-text services and models |
| **Chunk** | The text is split into pieces a model can handle | Code |
| **Draft** | A model writes each output in its format and your voice | An LLM API, with the voice guide of Module 6.1 |
| **Check** | Each draft is tested against its format's rules | Code |
| **Approve** | A person reads, edits, approves, or rejects | A queue: a spreadsheet, a chat message, a review tool |
| **Schedule and publish** | Approved items are posted at chosen times | Scheduling tools or platform APIs |
| **Measure** | Results feed back into what is made next | Analytics, as in Modules 6.8 and 6.10 |

### Chunking

A long transcript may be more than a model should be given at once, and a summary of each part is usually better than a summary of the whole. The transcript is split into chunks of a fixed number of words, with a small **overlap** between neighbours so that a sentence cut at a boundary appears whole in one of them.

With a chunk size of $s$ words and an overlap of $o$, each new chunk starts $s - o$ words after the last. A text of $n$ words needs about

$$
\left\lceil \frac{n - o}{s - o} \right\rceil \text{ chunks}
$$

Module 3.2 introduced chunking for retrieval. Here its purpose is drafting: each chunk can become a candidate post, and the most useful ones are chosen.

### Fan-out and the job key

From one source, the pipeline creates one job per output format. Each job needs a **key**, an identifier that is the same every time the pipeline sees the same source and format, and different otherwise. A simple way to make one is to hash the source's identifier, the format, and the source's text together.

The key solves a problem that every automation meets, and that Unit 7 returns to in detail: **running twice**. Triggers fire more than once, workflows are retried after errors, and someone presses "run" again. Without a key, each run creates new jobs and, eventually, publishes the same post twice. With one, the pipeline can ask "have I already made or published this?" and do nothing if the answer is yes. An operation that has the same effect however many times it is repeated is called **idempotent**. Payment systems use the same idea: Stripe's API accepts an idempotency key so that a retried request does not charge a customer twice.

### Checks per format

Each format has rules a draft must meet before a person spends time on it.

| Format | Typical checks |
|---|---|
| Short text post | A character limit |
| Professional network post | A longer character limit, no hashtag walls |
| Newsletter item | A word limit, a link to the source |
| Carousel slide | A word limit per slide, as in Module 6.9 |
| Any | No banned phrases from the voice guide, no unsourced numbers, a disclosure if sponsored |

Checks in code are cheap and catch the mechanical failures: too long, wrong words, a missing link. They do not catch a dull post or a wrong claim, which is what the approval step is for.

### The approval gate as a state machine

A job moves through statuses, and the allowed moves are fixed in advance.

```text
   draft --> checked --> approved --> scheduled --> published
                  \
                   +--> rejected --> draft  (revised and checked again)
```

The rules that matter are two. A job cannot reach "published" without passing through "approved". And only a person can approve. If the automation itself is allowed to set "approved", the gate is decorative. Writing the transitions down as data, and refusing any that are not listed, makes the gate impossible to skip by accident.

Workflow tools support this directly. n8n, for example, can pause a workflow until a person approves a step, and offers the approval request through chat, email, and other channels. The same pattern can be built with a shared spreadsheet that has an approval column, which is how many small pipelines start.

### Publishing and its limits

Approved items are published through scheduling tools or through the platforms' own interfaces for programs. Each has rules that a pipeline must respect.

| Platform | Constraint for automated publishing |
|---|---|
| Instagram | The content publishing interface limits how many posts an account can publish through it in a rolling 24-hour window, and offers a way to check current usage |
| TikTok | Content posted by an application that has not passed the platform's audit is restricted to private viewing |
| YouTube | Uploads through the programming interface draw on a daily quota. Mass-produced, repetitive content is not eligible for monetisation |
| All | Spam and automation policies forbid flooding, duplicate posting, and fake engagement |

Two consequences follow for design. A pipeline must handle being told no, an error, a rate limit, a quota, without losing the job or retrying forever. And it must never post the same item twice, which is what the job key prevents.

### Disclosure in an automated pipeline

The rules of Module 6.1 do not relax because a pipeline is doing the posting. A sponsored mention must carry its disclosure in every derived post, not only in the original video: the Federal Trade Commission's guidance says disclosure must be clear and conspicuous in the content itself. A realistic synthetic image or voice in a derived post needs its label. Building these into the checks, for example by requiring a disclosure phrase whenever the source is marked as sponsored, is more reliable than remembering.

### Cost

A pipeline's money cost is mostly model calls, and its time cost is mostly review. For $S$ sources a week, $F$ formats, a rejection rate $r$ that sends drafts back for another attempt, input and output token counts $t_{\text{in}}$ and $t_{\text{out}}$, prices $P_{\text{in}}$ and $P_{\text{out}}$ per million tokens, and $m$ minutes to review each draft:

$$
\text{drafts attempted} = S F (1 + r)
$$

$$
\text{model cost} = S F (1 + r) \times \frac{t_{\text{in}} P_{\text{in}} + t_{\text{out}} P_{\text{out}}}{10^{6}} \qquad \text{review time} = S F (1 + r) \times m
$$

Three sources a week in four formats, at a quarter rejected, with 4,000 tokens in and 600 out at USD 2 and USD 10 per million, costs about 21 US cents a week in model calls and, at three minutes a draft, 45 minutes of review. The model calls are negligible. The review time is the real cost, and it is the cost that buys the quality. Lowering the rejection rate, through a better voice guide and better source material, saves more than any cheaper model. Prompt caching and batch processing, from Modules 5.9 and 3.1, cut the model bill further where it matters, at higher volume.

### Start small

The commonest failure of content automation is building too much at once. The advice that runs through practitioner writing on the subject is to begin with one source type and two outputs, run them for a few weeks with every draft reviewed, and add a format only when the first two are reliably approved without heavy edits.

### Complexity

Chunking is linear in the transcript. Fan-out is linear in the formats. Checks are linear in each draft's length. The pipeline's throughput is set, as Module 6.1 showed for any pipeline, by its slowest stage, which here is the person at the pass.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, splitting a transcript.

```python
import hashlib

TRANSCRIPT = ("A blunt chisel tears the wood. Most people blame the chisel. The problem is the edge. "
              "Flatten the back first, twenty strokes on the coarse stone. Hold the bevel at twenty-five degrees. "
              "Do not rock the blade, because rocking rounds the edge. Take off the burr with two light strokes. "
              "Finish with ten pulls on a leather belt. Test on end grain. If it shaves, you are done.")

def chunk_words(text, size, overlap=0):
    if size <= 0 or overlap < 0 or overlap >= size:
        raise ValueError("need size > overlap >= 0")
    words, step = text.split(), size - overlap
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return chunks

chunks = chunk_words(TRANSCRIPT, 25, overlap=5)
print(len(TRANSCRIPT.split()), len(chunks), [len(chunk.split()) for chunk in chunks])
print(chunk_words("a b c d e f g", 3, overlap=1))
```

- **Each chunk is a run of words, and each new chunk starts `size - overlap` words after the last.** With a size of 25 and an overlap of 5, chunks start every 20 words.
- **The 68-word transcript gives four chunks of 25, 25, 25, and 8 words.** By the formula of Section 2, 68 minus 5 is 63, over 20 is 3.15, rounded up to 4.
- **The overlap repeats the last few words of each chunk at the start of the next.** In the small example, "c" and "e" appear twice. A sentence cut by one boundary survives whole in a neighbour.
- **The loop stops once a chunk reaches the end.** Without that, a final chunk made only of overlap would be repeated.
- **Impossible settings are refused.** An overlap as large as the chunk would never move forward.

Next, the jobs, with stable keys.

```python
FORMATS = {"x_post": {"max_chars": 280}, "linkedin": {"max_chars": 3000},
           "newsletter": {"max_words": 150}, "carousel_slide": {"max_words": 40}}

def fan_out_jobs(source_id, source_text, formats):
    jobs = []
    for name in sorted(formats):
        key = hashlib.sha256(f"{source_id}:{name}:{source_text}".encode("utf-8")).hexdigest()[:12]
        jobs.append({"key": key, "format": name, "source": source_id, "status": "draft"})
    return jobs

first_run = fan_out_jobs("vid-0042", TRANSCRIPT, FORMATS)
second_run = fan_out_jobs("vid-0042", TRANSCRIPT, FORMATS)
edited = fan_out_jobs("vid-0042", TRANSCRIPT + " Thanks for watching.", FORMATS)
print([job["format"] for job in first_run])
print(all(a["key"] == b["key"] for a, b in zip(first_run, second_run)), first_run[0]["key"] != edited[0]["key"])
```

- **One job per format, in alphabetical order.** Each starts in the "draft" status.
- **The key is a hash of the source, the format, and the text.** Twelve hexadecimal characters is plenty to tell jobs apart in a pipeline of this size.
- **Running twice gives identical keys.** The second run can check the keys against a list of jobs already created or published and do nothing. That is what makes the pipeline idempotent.
- **A changed source gives new keys.** If the transcript is corrected, the derived posts are new work, and the keys say so.
- **The key is the defence against double posting.** Before publishing, the publisher checks whether the key is already in its record of published items, and records it after. Retries, double triggers, and manual reruns then cannot post twice.

Then, the checks.

```python
def check_draft(text, rules):
    problems = []
    if "max_chars" in rules and len(text) > rules["max_chars"]:
        problems.append(f"over-{rules['max_chars']}-chars")
    if "max_words" in rules and len(text.split()) > rules["max_words"]:
        problems.append(f"over-{rules['max_words']}-words")
    problems += ["banned:" + phrase for phrase in rules.get("banned", []) if phrase.lower() in text.lower()]
    if rules.get("needs") and rules["needs"].lower() not in text.lower():
        problems.append("missing:" + rules["needs"])
    return problems

print(check_draft("x" * 281, FORMATS["x_post"]))
print(check_draft("w " * 41, FORMATS["carousel_slide"]))
print(check_draft("Unlock razor edges with our sponsor's stones!", {"max_chars": 280, "banned": ["unlock"], "needs": "#ad"}))
print(check_draft("Flatten the back first. Full video: link #ad", {"max_chars": 280, "banned": ["unlock"], "needs": "#ad"}))
```

- **Each format's rules are data.** A character limit, a word limit, banned phrases from the voice guide, and a phrase the draft must contain.
- **The 281-character post fails the 280 limit, and the 41-word slide fails the 40.**
- **The sponsored draft fails twice.** It uses a banned word, and it lacks the disclosure tag that the rules require because the source was sponsored.
- **The revised draft passes.** It is short, plain, and carries the disclosure.
- **A draft that fails is revised before a person sees it.** A person's attention is spent only on drafts that are at least mechanically sound.

Finally, the gate and the cost.

```python
ALLOWED = {("draft", "checked"), ("checked", "approved"), ("checked", "rejected"),
           ("approved", "scheduled"), ("scheduled", "published"), ("rejected", "draft")}

def advance(job, new_status, actor):
    if (job["status"], new_status) not in ALLOWED:
        raise ValueError(f"cannot go from {job['status']} to {new_status}")
    if new_status in ("approved", "rejected") and actor == "automation":
        raise ValueError("only a person can approve or reject")
    return dict(job, status=new_status, history=job.get("history", []) + [(new_status, actor)])

def pipeline_cost(sources_per_week, formats, input_tokens, output_tokens, price_in, price_out, review_minutes, rejection_rate):
    drafts = sources_per_week * formats
    attempts = drafts * (1 + rejection_rate)
    return {"drafts": drafts,
            "llm_cost": round(attempts * (input_tokens * price_in + output_tokens * price_out) / 1e6, 3),
            "review_hours": round(attempts * review_minutes / 60, 2)}

job = advance(first_run[0], "checked", "automation")
for attempt in (("published", "automation"), ("approved", "automation")):
    try:
        advance(job, *attempt)
    except ValueError as error:
        print("refused:", error)
job = advance(advance(advance(job, "approved", "sam"), "scheduled", "automation"), "published", "automation")
print(job["status"], job["history"])
print(pipeline_cost(3, 4, 4000, 600, 2, 10, 3, 0.25))
print(pipeline_cost(10, 6, 4000, 600, 2, 10, 4, 0.5))
```

- **`ALLOWED` lists every legal move.** Anything else is refused, so there is no path from "checked" to "published" that skips approval.
- **Approval and rejection need a person.** The automation can check, schedule, and publish. It cannot decide. An attempt to approve as "automation" is refused.
- **Each move is recorded with who made it.** The history shows that "sam" approved this post. When something goes wrong, the record says what happened and who decided.
- **`advance` returns a new job and leaves the old one unchanged.** That makes it safe to retry: a failed move has not half-changed anything.
- **Three videos a week in four formats cost 21 US cents in model calls and 45 minutes of review.** Twelve drafts, a quarter of them redone.
- **Ten videos in six formats, half of them redone, cost USD 1.26 and six hours.** The money is still trivial. The review time has become a part-time job. That, and not the model bill, is what limits how far a pipeline can grow, and it is why a better voice guide, which lowers the rejection rate, is the best investment.

**Complexity.** Every function is linear in its input, and `advance` is constant time.

### A pipeline specification

```text
SOURCE:      [new video on channel X]            TRIGGER: [webhook / check every hour]
TRANSCRIPT:  [service]                            CHUNKS:  [size] words, overlap [o]
FORMATS:     [x_post: 280 chars] [newsletter: 150 words] [carousel: 40 words a slide]
DRAFTING:    model [name], voice guide [link], 2 sample posts per format
CHECKS:      limits per format, banned phrases, numbers traced to the source,
             "#ad" required when the source is sponsored
APPROVAL:    [who], via [sheet / chat], within [24 h]; only people may approve or reject
PUBLISH:     scheduled at [times]; record each key; never publish a key twice
ERRORS:      retry [3] times with growing waits, then alert [who]; never drop a job silently
REVIEW:      weekly: rejection rate, edits per draft, results per format
```

### When to add, change, or stop

| Signal | Action |
|---|---|
| A format is approved without edits most weeks | Add another format |
| A format is rejected or heavily edited most weeks | Fix its prompt and samples, or drop it |
| Review takes longer than writing would | The pipeline is not saving time. Simplify |
| A post went out twice | Find where the key check was bypassed, before anything else |
| Results for derived posts are poor | Better source material, not more posts |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Publishing without review.** The pipeline that posts whatever the model writes is the one that eventually posts something wrong, embarrassing, or against a platform's rules, and nobody notices until a follower does. Keep a person at the pass.

**Automation that only multiplies.** Five posts a day generated from trending topics, with nothing of yours in them, is the pattern that audiences ignore and platform policies on inauthentic and repetitive content target. Start from your own material.

**Building everything at once.** Six platforms, image generation, scheduling, and analytics in the first week means nothing works well and nobody knows why. One source, two outputs, then grow.

**No idempotency.** A webhook that fires twice, a workflow retried after a timeout, or a manual rerun creates duplicates. Give every job a key, record what has been published, and check before publishing.

**Retrying forever.** A rate limit or a quota is answered with retries, each of which uses more quota. Back off, cap the attempts, and alert a person.

**Dropping jobs silently.** An error that ends a run without a record means a post that was supposed to go out never did. Every failure should leave a trace and, past a threshold, a notification.

**The disclosure lost in translation.** A sponsored video turned into five posts, four of which omit the sponsorship. Make the disclosure a check that blocks the draft, not a line in the prompt.

**Generic outputs from a good source.** A strong video turned into bland posts usually means the prompt had no voice guide and no samples. Give each format two examples of posts you liked.

**Approving without reading.** A queue of thirty drafts at the end of the day gets approved in bulk. The gate only works if the person looks. Keep the queue small enough to read.

**API limits discovered in production.** A platform's publishing limits and audit requirements are found when posts stop going out. Read them before building, and design for the limits.

**No record of who approved what.** When something goes wrong, the first question is how it was published. Log every status change with its actor and, in a real system, a timestamp.

**Measuring output instead of outcome.** A pipeline producing forty posts a week is not a success if none is saved, shared, or clicked. Feed each format's results back, as Modules 6.8 and 6.10 described, and cut what does not work.

## 5. Active Recall Check & Synthesis Summary

**Summary.** An automated content pipeline turns one piece of long content you made into drafts for several formats, and it is worth building only with a person at the pass who approves what goes out. Its stages are trigger, transcribe, chunk, draft, check, approve, schedule and publish, and measure. Chunking splits a transcript into pieces of $s$ words with an overlap $o$, about $\lceil (n - o)/(s - o) \rceil$ of them. Fan-out creates one job per format, each with a key derived from the source, the format, and the text, so that a pipeline run twice does nothing new and never publishes the same item twice, the property called idempotency. Each draft is checked in code against its format's limits, banned phrases, and required disclosures before a person sees it. The approval gate is a state machine whose allowed transitions are listed in advance, in which only a person can approve or reject and nothing reaches publication without approval. Platforms limit automated publishing, require audits, and penalise repetitive content, so pipelines must handle refusals and respect quotas. Model calls cost little, about $SF(1 + r)$ drafts at a cent or two each, while review time, $SF(1 + r)m$, is the real cost, and lowering the rejection rate is the best way to reduce it.

**Question 1.** A transcript has 1,800 words. It is split into chunks of 300 words with an overlap of 50. How many chunks are there, and how many words does the last one have? Why use an overlap at all, and what would happen if the overlap were set to 300?

<details>
<summary>View Answer</summary>

Each new chunk starts 300 minus 50, which is 250 words after the last. Chunks start at words 0, 250, 500, 750, 1,000, 1,250, and 1,500. The chunk starting at 1,500 runs to word 1,800, the end of the text, so it is the last. That is seven chunks, matching the formula: 1,800 minus 50 is 1,750, divided by 250 is exactly 7. The first six have 300 words each, and the last has 1,800 minus 1,500, which is 300 words as well, because the text happens to end exactly at a chunk boundary. The overlap exists because a fixed-size split cuts wherever the word count falls, often in the middle of a sentence or a point. Repeating the last fifty words of each chunk at the start of the next means any sentence cut at a boundary appears whole in one of the two chunks, so a model drafting from either has the complete thought. It costs a little extra text, about a sixth more here. An overlap of 300 would equal the chunk size, so each new chunk would start zero words after the last and the split would never move forward. The function in this chapter refuses that setting, because a loop with no progress would either run forever or produce endless copies of the first chunk.

</details>

**Question 2.** A pipeline's webhook fires twice for the same new video, a few seconds apart, and both runs complete. Describe what happens with and without job keys, and say where in the pipeline the key must be checked to prevent a duplicate post.

<details>
<summary>View Answer</summary>

Without keys, each run treats the video as new. Each creates its own set of jobs, one per format, so there are two drafts of every post. If both sets are checked and approved, which is likely when a reviewer approves a queue quickly, both are scheduled and both are published, and followers see every post twice. A platform may also treat the repeat as spam, and on some the duplicate counts against a daily publishing limit. With keys, both runs compute the same key for each format, because the key is derived from the same source identifier, format, and text. The second run, on creating jobs, finds that jobs with those keys already exist and does nothing, so there is one draft per format. The key must be checked in two places. The first is at job creation, so that duplicates never reach the review queue and waste a person's time. The second, which is essential, is immediately before publishing: the publisher looks up the key in its record of what has been published, publishes only if it is absent, and records it immediately after. That second check protects against every other way a duplicate can arise, such as a retried publishing step after a timeout where the first attempt actually succeeded. Where several runs might publish at the same moment, the record must be updated atomically, so that two runs cannot both see the key as absent.

</details>

**Question 3.** A creator's pipeline turns 5 videos a week into 5 formats. Each draft takes 4 minutes to review, and 40 percent of drafts are rejected and redrafted. Model calls cost about 1.5 US cents per draft. Compute the weekly model cost and review time. import hashlib

TRANSCRIPT = ("A blunt chisel tears the wood. Most people blame the chisel. The problem is the edge. "
              "Flatten the back first, twenty strokes on the coarse stone. Hold the bevel at twenty-five degrees. "
              "Do not rock the blade, because rocking rounds the edge. Take off the burr with two light strokes. "
              "Finish with ten pulls on a leather belt. Test on end grain. If it shaves, you are done.")

FORMATS = {"x_post": {"max_chars": 280}, "linkedin": {"max_chars": 3000},
           "newsletter": {"max_words": 150}, "carousel_slide": {"max_words": 40}}

ALLOWED = {("draft", "checked"), ("checked", "approved"), ("checked", "rejected"),
           ("approved", "scheduled"), ("scheduled", "published"), ("rejected", "draft")}


# ---------------------------------------------------------------- Step 1
def chunk_words(text, size, overlap=0):
    """The overlap repeats the end of each chunk at the start of the next, so a sentence cut
    at one boundary survives whole in a neighbour."""
    if size <= 0 or overlap < 0 or overlap >= size:
        raise ValueError("need size > overlap >= 0")
    words, step = text.split(), size - overlap
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return chunks


# ---------------------------------------------------------------- Step 2
def fan_out_jobs(source_id, source_text, formats):
    """The key is the same every time the same source and format are seen, which is what lets
    a pipeline run twice and do nothing new: idempotency."""
    jobs = []
    for name in sorted(formats):
        key = hashlib.sha256(f"{source_id}:{name}:{source_text}".encode("utf-8")).hexdigest()[:12]
        jobs.append({"key": key, "format": name, "source": source_id, "status": "draft"})
    return jobs


# ---------------------------------------------------------------- Step 3
def check_draft(text, rules):
    """Cheap mechanical checks, so that a person's attention is spent only on drafts that are
    at least sound. They cannot tell a dull post or a wrong claim."""
    problems = []
    if "max_chars" in rules and len(text) > rules["max_chars"]:
        problems.append(f"over-{rules['max_chars']}-chars")
    if "max_words" in rules and len(text.split()) > rules["max_words"]:
        problems.append(f"over-{rules['max_words']}-words")
    problems += ["banned:" + phrase for phrase in rules.get("banned", []) if phrase.lower() in text.lower()]
    if rules.get("needs") and rules["needs"].lower() not in text.lower():
        problems.append("missing:" + rules["needs"])
    return problems


# ---------------------------------------------------------------- Step 4
def advance(job, new_status, actor):
    """Every legal move is listed in advance, and only a person may approve or reject. If the
    automation could approve, the gate would be decorative."""
    if (job["status"], new_status) not in ALLOWED:
        raise ValueError(f"cannot go from {job['status']} to {new_status}")
    if new_status in ("approved", "rejected") and actor == "automation":
        raise ValueError("only a person can approve or reject")
    return dict(job, status=new_status, history=job.get("history", []) + [(new_status, actor)])


# ---------------------------------------------------------------- Step 5
def pipeline_cost(sources_per_week, formats, input_tokens, output_tokens, price_in, price_out, review_minutes, rejection_rate):
    """The model bill is small. Review time is the real cost, and every point of rejection
    adds to it, which is why a better voice guide beats a cheaper model."""
    drafts = sources_per_week * formats
    attempts = drafts * (1 + rejection_rate)
    return {"drafts": drafts,
            "llm_cost": round(attempts * (input_tokens * price_in + output_tokens * price_out) / 1e6, 3),
            "review_hours": round(attempts * review_minutes / 60, 2)}
