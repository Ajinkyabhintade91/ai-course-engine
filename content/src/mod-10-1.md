# What are Local LLMs?

Every earlier unit used models running in someone else's data centre: you send text over the internet, a provider runs the model, and text comes back. A **local LLM** runs on hardware you control: your laptop, a desktop with a graphics card, or a server in your office. Unit 10 is about running models this way, with **Ollama** as the main tool, and this first module explains what makes it possible, what it is good for, and what it costs.

Local models are not a replacement for the largest cloud models. They are a different tool, with a different set of trade-offs: privacy, offline use, and predictable cost on one side; smaller models, your own hardware, and your own maintenance on the other.

## 1. First-Principles Mental Model & Intuition

### A home kitchen versus a restaurant

Ordering from a restaurant gets you a meal cooked by a professional kitchen with equipment you could never afford, but your order leaves the house, you pay per meal, and you cannot eat when the restaurant is closed or the road is blocked. Cooking at home, your ingredients never leave the house, a meal costs only the groceries once the kitchen is equipped, and you can cook any time, but your kitchen is smaller, the most elaborate dishes are out of reach, and you do the washing up.

Cloud models are the restaurant; local models are the home kitchen. Which is better depends on the meal.

```text
   CLOUD MODEL                                     LOCAL MODEL
   your app --internet--> provider's GPUs          your app --localhost--> your GPU / CPU / Apple Silicon
   + largest, newest models                        + data never leaves the machine
   + no hardware to buy or maintain                + works offline; no per-token bill
   - data leaves your network                      - smaller models (memory-limited)
   - per-token cost; rate limits; outages          - hardware cost, setup, updates
                                                   
   WHAT MAKES LOCAL POSSIBLE
   open-weight models (downloadable)  ->  quantization (fewer bits per weight)  ->  GGUF file
        ->  runtime: llama.cpp (engine) | Ollama (CLI + registry + API) | LM Studio (desktop app) | vLLM (serving)
```

### Why now

Two developments made local models practical. **Open-weight models**: model makers such as Alibaba, Meta, Google, Mistral AI, and DeepSeek publish the trained weights of some of their models for anyone to download, under licences that vary from permissive to restrictive, which later modules examine. And **quantization**: storing each weight in 4 to 8 bits instead of 16 shrinks a model by two to four times with a modest quality loss, so models that once needed data-centre GPUs now fit in a laptop's memory.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Why and why not

| Reasons to run locally | Reasons not to |
|---|---|
| Sensitive data must not leave the machine or network | You need the strongest available model quality |
| Must work offline: on site, in transit, air-gapped | You have no suitable hardware |
| High, steady volume where per-token fees add up | Low or bursty volume, where cloud costs little |
| Predictable latency without rate limits | You do not want to maintain models and runtimes |
| Experimenting freely, learning how models work | Features such as very long context or large multimodal models |

Many organisations end up **hybrid**: local models for sensitive or high-volume routine work, cloud models where quality matters most, Module 10.13 returns to the privacy side.

### Open weights and licences

An open-weight model is a set of numbers, the weights, that you can download and run. **Open weights** is not the same as **open source**: the training data and code may not be published, and the licence may restrict use, for example by company size or purpose. Always read the licence of a specific model before commercial use; Modules 10.5 to 10.9 cover the major families.

### Memory: parameters times bits

A model's weights take, approximately,

$$\text{weights (GB)} \approx \frac{P \times b}{8}$$

where $P$ is the number of parameters in billions and $b$ the **bits per weight**. At 16 bits, the format models are usually published in, an 8-billion-parameter model needs about 16 GB; at about 4.5 bits, 4.5 GB. On top of the weights, running a model needs memory for the **KV cache**, which stores attention state for the conversation so far and grows with context length, and for the runtime's own working memory. A practical estimate adds both:

$$\text{memory needed} \approx \text{weights} + \text{KV cache} + \text{overhead}$$

Module 10.10 develops this into hardware sizing; for now, the rule of thumb is that the model must fit in GPU memory, or in the unified memory of Apple Silicon, to run fast.

### Quantization and GGUF

**Quantization** stores weights with fewer bits. Hugging Face's documentation of the **GGUF** format, the file format used by llama.cpp and Ollama, lists the quantization types with their effective bits per weight, which include the scales stored alongside each block of weights:

| Type | Bits per weight | Notes |
|---|---|---|
| F16 / BF16 | 16 | Unquantized half precision |
| Q8_0 | 8.5 | 8-bit, 32-weight blocks plus a scale |
| Q6_K | 6.5625 | K-quant |
| Q5_K | 5.5 | K-quant |
| Q4_K | 4.5 | K-quant; Q4_K_M is a popular default |
| Q3_K | 3.4375 | K-quant |
| Q2_K | 2.625 | K-quant; noticeable quality loss |

The "K" types group weights into super-blocks with their own scales; suffixes `_S`, `_M`, and `_L` mix types across layers, so real file sizes differ slightly from the base figure. Lower bits mean smaller files and faster generation but more quality loss; 4 to 5 bits is the common sweet spot, and below 4 bits quality drops more steeply, especially for small models.

A GGUF file bundles the weights with metadata such as the architecture, tokenizer, and prompt template, so one file is enough to run the model. File names usually encode the family, size, variant, and quantization: `Qwen3-8B-Instruct-Q4_K_M.gguf` is a Qwen3 model with 8 billion parameters, instruction-tuned, at Q4_K_M.

### The runtime landscape

| Runtime | What it is | Best for |
|---|---|---|
| **llama.cpp** | The C/C++ inference engine that runs GGUF models on CPUs and GPUs | Maximum control, embedding in other software |
| **Ollama** | A model runner with a command line, a model registry, and a local HTTP API | Simple setup and use from applications; this unit's main tool |
| **LM Studio** | A desktop application to find, download, chat with, and serve models | People who prefer a graphical interface |
| **vLLM** | A high-throughput serving engine for GPUs | Serving many users at once in production |

Ollama and LM Studio build on llama.cpp-style engines for most models; vLLM is aimed at data-centre GPUs and batches many requests efficiently. Module 10.2 looks at Ollama's architecture.

### Cost: when does local pay off?

Cloud cost scales with tokens; local cost is mostly up-front hardware plus electricity. With monthly volume $V$ million tokens at cloud price $c$ per million, hardware cost $H$, power draw $w$ watts for $h$ hours a month at electricity price $e$ per kilowatt-hour:

$$\text{months to break even} = \frac{H}{V c - \frac{w}{1000} h e}$$

when the cloud bill exceeds the power bill; otherwise local never pays off on cost alone. At 200 million tokens a month and an illustrative 2 per million, the cloud bill is 400 a month; a 2,000 machine drawing 350 watts for 160 hours at 0.30 per kilowatt-hour costs about 16.80 in power, so it pays for itself in about 5 months. At 5 million tokens a month, the cloud bill of 10 is less than the power bill, and local never pays on cost. The comparison ignores quality differences, maintenance time, and hardware resale, which often decide the question.

### Complexity

All the lab's calculations are constant time per decision, file name, or estimate.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, local, cloud, or hybrid.

```python
import re

def where_to_run(needs):
    local, cloud = [], []
    if needs["sensitive_data"]:
        local.append("data must not leave the machine")
    if needs["offline"]:
        local.append("must work offline")
    if needs["monthly_tokens_m"] >= 500:
        local.append("high volume makes local hardware pay off")
    if needs["needs_frontier_quality"]:
        cloud.append("needs frontier-model quality")
    if needs["no_hardware"]:
        cloud.append("no suitable hardware")
    if local and cloud:
        return "hybrid", local + cloud
    if local:
        return "local", local
    return "cloud", cloud or ["no reason to run locally"]

BASE = {"sensitive_data": False, "offline": False, "monthly_tokens_m": 5, "needs_frontier_quality": False, "no_hardware": False}
print(where_to_run(BASE))
print(where_to_run({**BASE, "sensitive_data": True}))
print(where_to_run({**BASE, "sensitive_data": True, "needs_frontier_quality": True}))
```

- **With no reason to go local, the default is cloud.**
- **Customer order data that must stay in the office points to local.**
- **Sensitive data plus a need for the best quality points to hybrid.** Route each task to the right place.

Next, reading GGUF file names.

```python
BPW = {"F16": 16.0, "BF16": 16.0, "Q8_0": 8.5, "Q6_K": 6.5625, "Q5_K": 5.5, "Q4_K": 4.5, "Q4_0": 4.5, "Q3_K": 3.4375, "Q2_K": 2.625}
NAME = re.compile(r"^(?P<family>.+?)-(?P<size>\d+(?:\.\d+)?)B(?:-(?P<variant>[A-Za-z]+))?-(?P<quant>Q\d_K(?:_[SML])?|Q8_0|Q4_0|BF16|F16)\.gguf$", re.I)

def parse_gguf(filename):
    m = NAME.match(filename)
    if not m:
        return None
    quant = m.group("quant").upper()
    return {"family": m.group("family"), "params_b": float(m.group("size")), "variant": m.group("variant") or "",
            "quant": quant, "bpw": BPW[re.sub(r"_[SML]$", "", quant)]}

for name in ["Qwen3-8B-Instruct-Q4_K_M.gguf", "gemma-3-4b-it-Q8_0.gguf", "Mistral-7B-F16.gguf", "model.bin"]:
    print(name, parse_gguf(name))
```

- **The family can contain hyphens and dots; the size is the number before "B".**
- **`Q4_K_M` maps to the Q4_K figure of 4.5 bits per weight.** The `_M` mix varies slightly in practice.
- **Names that do not follow the convention return None.** Check the model card instead.

Then, estimating memory.

```python
def weights_gb(params_b, bpw):
    return round(params_b * bpw / 8, 2)

def fits(params_b, bpw, memory_gb, kv_gb=1.0, overhead_gb=1.0):
    need = round(weights_gb(params_b, bpw) + kv_gb + overhead_gb, 2)
    return need <= memory_gb, need

print(weights_gb(8, 4.5), weights_gb(8, 16), weights_gb(70, 4.5))
print(fits(8, 4.5, 8), fits(8, 8.5, 8), fits(70, 4.5, 24), fits(70, 4.5, 64, kv_gb=4))
```

- **An 8B model is 16 GB at 16 bits but 4.5 GB at Q4_K.**
- **With 1 GB each for the KV cache and overhead, 8B at Q4_K needs 6.5 GB: it fits in 8 GB.** At Q8_0 it needs 10.5 GB and does not.
- **A 70B model at Q4_K needs about 41 GB: not in a 24 GB card, but in 64 GB of unified memory even with a larger cache.**

Then, choosing a runtime.

```python
def runtime(needs):
    if needs["serve_many_users"]:
        return "vLLM", "high-throughput serving with batching on GPUs"
    if needs["wants_gui"]:
        return "LM Studio", "desktop app to browse, download, and chat"
    if needs["embed_in_app"] or needs["max_control"]:
        return "llama.cpp", "the underlying engine, maximum control"
    return "Ollama", "simple CLI, model registry, and local API"

NEEDS = {"serve_many_users": False, "wants_gui": False, "embed_in_app": False, "max_control": False}
print(runtime(NEEDS), runtime({**NEEDS, "wants_gui": True}), runtime({**NEEDS, "serve_many_users": True}))
```

- **The default for building applications on one machine is Ollama.**
- **A graphical app suits people who do not live in a terminal.**
- **Many concurrent users call for a serving engine such as vLLM.**

Finally, the break-even point.

```python
def break_even(monthly_tokens_m, cloud_price_per_m, hardware_cost, power_watts, hours_per_month, price_per_kwh):
    cloud = round(monthly_tokens_m * cloud_price_per_m, 2)
    power = round(power_watts / 1000 * hours_per_month * price_per_kwh, 2)
    saving = cloud - power
    return cloud, power, (round(hardware_cost / saving, 1) if saving > 0 else None)

print(break_even(200, 2.0, 2000, 350, 160, 0.3))
print(break_even(5, 2.0, 2000, 350, 160, 0.3))
```

- **At 200 million tokens a month, the cloud bill of 400 against 16.80 of power pays back 2,000 in about 5.2 months.**
- **At 5 million tokens, the cloud costs 10 a month, less than the power: local never pays on cost.** Privacy or offline needs could still justify it.

**Complexity.** Every function here is constant time.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Expecting frontier quality.** An 8B model on a laptop is not the largest cloud model. Match the task to the model.

**Ignoring the licence.** Open weights come with terms. Read them before commercial use.

**Counting only the weights.** Context and runtime need memory too. Leave headroom.

**Too few bits.** Two-bit quantizations of small models degrade badly. Start at 4 to 5 bits.

**Assuming local is cheaper.** At low volume, cloud costs less than electricity. Do the arithmetic.

**Forgetting maintenance.** Models, runtimes, and drivers need updates. Budget the time.

**Downloading models from anywhere.** Weights and runtime files can be tampered with. Use reputable sources.

**Treating local as automatically private.** Plugins, telemetry, and integrations can send data out. Check, Module 10.13.

**CPU-only expectations.** Large models on a CPU are slow. Fit the model in GPU or unified memory.

**Using a base model for chat.** Base models continue text; instruction-tuned variants follow requests. Pick the right variant.

**Wrong prompt template.** Each model expects its own chat format. Runtimes usually handle it; custom setups must too.

**One model for everything.** Different tasks suit different models. Keep a small set, Module 10.15.

**Question 2.** A colleague downloads `Llama-3.3-70B-Instruct-Q4_K_M.gguf` to run on a laptop with 16 GB of memory and a 24 GB graphics card. Use `parse_gguf` and `fits` to explain what will happen and suggest alternatives.

<details>
<summary>View Answer</summary>

`parse_gguf` reads a 70-billion-parameter instruction-tuned model at Q4_K_M, 4.5 bits per weight, so the weights alone are about 70 times 4.5 divided by 8, 39.4 GB, and `fits` estimates about 41.4 GB with a gigabyte each for the KV cache and overhead. That exceeds the 24 GB graphics card and the 16 GB of system memory, so the model either fails to load or runs with most layers on the CPU, splitting between devices, so slowly that it is impractical. Alternatives: choose a smaller model, such as one in the 7 to 14 billion parameter range at Q4_K_M, which needs roughly 6 to 10 GB and fits comfortably in the 24 GB card with room for longer context; or a mid-sized model around 24 to 32 billion parameters at Q4, about 14 to 20 GB, which fits the card with modest context; or, if a 70B model is truly needed, use hardware with more memory, such as a machine with 64 GB or more of unified memory, or run it in the cloud. Dropping to Q2_K, about 23 GB of weights (about 25 GB with cache and overhead), would still just miss a 24 GB card and would cost noticeable quality.

**Question 3.** Explain to a manager why "the model is only 4.5 GB" does not mean it will run well on any computer with 8 GB of RAM.

<details>
<summary>View Answer</summary>

The 4.5 GB is just the quantized weights of an 8-billion-parameter model at about 4.5 bits per weight. Running it also needs memory for the KV cache, which holds the attention state of the conversation and grows with the length of the context, and for the runtime itself; the lab's estimate adds a gigabyte for each, giving about 6.5 GB, and longer documents need more. The computer's operating system and other applications also use memory, so 8 GB of system RAM is tight. Just as important is where the memory is: a model runs fast when it fits in a graphics card's memory or in Apple Silicon's unified memory, where the processor can read weights at high bandwidth; on a computer with 8 GB of ordinary RAM and no suitable GPU, the model runs on the CPU, which works but generates text slowly, perhaps a few words a second, Module 10.10. So the right question is not "is the file smaller than my RAM" but "does the model, plus its working memory, fit in fast memory with room to spare", and the answer depends on the hardware, the quantization, and the context length.

</details>

    """Parameters times bits per weight, in gigabytes."""
    return round(params_b * bpw / 8, 2)


def fits(params_b, bpw, memory_gb, kv_gb=1.0, overhead_gb=1.0):
    """Weights plus KV cache plus overhead must fit."""
    need = round(weights_gb(params_b, bpw) + kv_gb + overhead_gb, 2)
    return need <= memory_gb, need

def break_even(monthly_tokens_m, cloud_price_per_m, hardware_cost, power_watts, hours_per_month, price_per_kwh):
    """Months for avoided cloud spend, net of power, to repay the hardware."""
    cloud = round(monthly_tokens_m * cloud_price_per_m, 2)
    power = round(power_watts / 1000 * hours_per_month * price_per_kwh, 2)
    saving = cloud - power
    return cloud, power, (round(hardware_cost / saving, 1) if saving > 0 else None)
