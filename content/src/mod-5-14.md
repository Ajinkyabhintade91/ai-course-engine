# 100 Ready-to-Use Prompts

This chapter contains a hundred prompts. They are organised into ten kinds of work, written to the standards of this unit, and ready to be used today.

It also contains a warning about lists of prompts, including this one. A prompt copied from a list is a starting point with holes in it. The holes are where your situation goes: your audience, your text, your constraints. A prompt with nothing of yours in it produces an answer for nobody in particular. So the chapter has three jobs. It gives the library. It shows how to turn any prompt into a template with named variables. And it shows how to keep a library of your own in working order, so that it does not decay into a file of things that used to work.

## 1. First-Principles Mental Model & Intuition

### A recipe box, not a recipe book

A published recipe book has a thousand recipes. Most households cook the same fifteen meals.

A recipe box is different. It holds the cards somebody actually cooks from, with the quantities altered in pencil, a note that the oven runs hot, and a card removed when nobody liked the dish. It is small, it is used, and it gets better.

A prompt library should be a recipe box. The hundred prompts in Section 3 are the book: a broad collection to choose from. Your library is the dozen or two you adapt, test on your own work, and keep.

### A template is a prompt with labelled holes

```text
   A PROMPT (used once)

   "Summarise this refund policy for new staff in at most 60 words.
    Lead with the main conclusion."

   A TEMPLATE (used many times)

   "Summarise the text below for {{audience}} in at most {{words}} words.
    Lead with the main conclusion.

    {{text}}"
          |                 |                  |
          v                 v                  v
      who reads it      how long         what to summarise
```

Everything that stays the same between uses is the template. Everything that changes is a variable. Writing a template is deciding which is which.

That decision has a useful side effect. The variables are a checklist of what the model needs to be told. A person about to use the template can see that it wants an audience and a length, and cannot forget to supply them.

### Why prompt lists disappoint

People who collect long lists of prompts often report that the prompts work less well than promised. There are three reasons, each of which this chapter addresses.

| Reason | Remedy |
|---|---|
| The prompt has no context of yours | Variables that force you to supply it |
| It was written for a different model, or an older one | Tests that you re-run when the model changes |
| Nobody checked that it works | A test case stored beside every template |

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### What makes a prompt reusable

Look at any template in Section 3 and you will find components adapted from those of Module 5.1, with the variable parts cut out.

| Component | In a template |
|---|---|
| Task | Fixed text. It is what the template is for |
| Context | A variable: the audience, the situation, the facts |
| Material | A variable: the text, the notes, the code |
| Constraints | Fixed where they always apply, a variable where they change, such as length |
| Output format | Fixed. A template that returns a different shape each time cannot be built on |

A template should fix as much as it can. Each variable is a decision the user has to make and a place to make a mistake. Three or four variables is typical. More than seven usually means two templates have been merged.

### The arithmetic of reuse

A template with $k$ variables, where variable $i$ can take $m_{i}$ different values, stands for

$$
\prod_{i=1}^{k} m_{i}
$$

distinct prompts. Three variables with five values each is 125 prompts written once.

Whether a template earns its place is also arithmetic. Suppose writing the prompt from scratch takes $t_{w}$ minutes, filling in the template takes $t_{f}$, the template is used $n$ times a year, and keeping it tested and current costs $t_{m}$ minutes a year. The time saved is

$$
n \, (t_{w} - t_{f}) - t_{m}
$$

and the template pays for itself only if it is used more than

$$
n^{*} = \frac{t_{m}}{t_{w} - t_{f}}
$$

times. With four minutes to write, half a minute to fill, and thirty minutes a year of upkeep, the break-even is about nine uses. A template used forty times saves 110 minutes. A template used three times costs more than it saves. That is the case for a small library.

### Variable syntax

A variable needs a marker that cannot be confused with ordinary text.

| Convention | Looks like | Used by |
|---|---|---|
| Double braces | `{{audience}}` | Anthropic's console and many prompt tools |
| Single braces | `{audience}` | Python's `str.format` and f-strings |
| Dollar names | A dollar sign followed by the name | Python's `string.Template` and shell scripts |
| Square brackets | `[AUDIENCE]` | People typing by hand |

This chapter uses double braces. The reason is practical. Prompts often contain JSON, and JSON is full of single braces. Python's `str.format` treats every single brace as the start of a variable, so a template containing an example such as `{"name": "Ana"}` raises an error. Double braces with a plain name inside do not collide with JSON, code, or mathematics.

Whatever the syntax, a filler must handle three situations, and the careless ones handle none.

| Situation | Careless filler | Strict filler |
|---|---|---|
| A variable has no value | Sends the literal marker to the model | Refuses, and names the variable |
| A value is supplied that the template does not use | Ignores it | Refuses: it is probably a misspelt name |
| A value is blank | Sends an empty slot | Refuses |

The first row is the commonest fault in automated prompts: a model receives "Summarise this for `{{audience}}`" and does its best. Nothing fails. The output is merely worse, and nobody knows why.

### Adapting a template

A template from this chapter, or from anywhere, should be adapted before it joins your library. Five adjustments cover most cases.

| Adjustment | Example |
|---|---|
| **Fix what never changes for you** | If the audience is always "our retail customers", write it in and remove the variable |
| **Add your constraints** | House style, a word you never use, a legal disclaimer |
| **Add an example of good output** | One real result you were pleased with, as Module 5.4 showed |
| **Tighten the format** | The exact headings, or a schema, if a program reads the result |
| **Add the fallback** | What to do when information is missing: ask, or say so |

Then run it on three real inputs. Published libraries are explicit that their prompts are starting points. The library of teaching prompts kept by Ethan and Lilach Mollick, for instance, releases its prompts for anyone to adapt and remix. Anthropic's public prompt library is organised by task and likewise presents each prompt as something to adapt.

### Templates are sensitive to their wording

A 2023 study, "Quantifying Language Models' Sensitivity to Spurious Features in Prompt Design", took prompts for the same tasks and changed only their formatting: separators, spacing, capitalisation of labels. Nothing about the meaning changed. Accuracy moved by as much as 76 percentage points for one model, and the sensitivity persisted in larger models and with more examples.

Two lessons follow for a library. A template that works was found to work in exactly its present form, so casual edits are not safe. And a template tested on one model has not been tested on another. Both are reasons to store a test with every entry.

### The shape of a library entry

| Field | Purpose |
|---|---|
| `id` | A stable name to refer to, such as `sum-21` |
| `category` | Where to find it |
| `title` | What it does, in a few words |
| `template` | The text, with its variables |
| `variables` | The declared list, which must match the template |
| `tests` | At least one set of values with what the output must satisfy |
| Version and model | Which version this is, and the model it was last tested on, as in Module 5.7 |

The `variables` field looks redundant, since the names can be read from the template. Its value is as a cross-check. When someone edits the template and renames a variable, the two disagree, and a linter catches it before a user does.

### Maintaining a library

A library decays in three ways, and each has a routine that prevents it.

**Entries stop working.** A model update, or an edit to the template, changes the output. Run every entry's tests when the model changes and when a template is edited. Module 5.9 covered the method.

**Entries drift out of step.** The template says one thing and its description, variables, or tests say another. Lint the library: every variable declared, every declared variable used, every entry tested.

**Entries pile up.** Each addition seemed useful at the time. Log which entries are used, and remove the ones that are not. An unused entry still costs attention every time someone scans the list, and upkeep if it is tested.

### Complexity

Finding and filling variables is linear in the length of the template. Linting is linear in the size of the library. Testing costs one model call per test, per entry, each time the suite runs, which is the reason to keep both the library and each entry's tests small.

### The tools

A library needs four small tools. First, finding and filling variables.

```python
import re
from collections import Counter

VARIABLE = re.compile(r"\{\{([a-z_]+)\}\}")

def find_variables(template):
    names = []
    for name in VARIABLE.findall(template):
        if name not in names:
            names.append(name)
    return names

def fill(template, values):
    names = set(VARIABLE.findall(template))
    missing = sorted(name for name in names if not str(values.get(name, "")).strip())
    if missing:
        raise ValueError("missing: " + ", ".join(missing))
    unused = sorted(key for key in values if key not in names)
    if unused:
        raise ValueError("unused: " + ", ".join(unused))
    return VARIABLE.sub(lambda match: str(values[match.group(1)]), template)

SUMMARY_TEMPLATE = "Summarise the text below for {{audience}} in at most {{words}} words. Lead with the main conclusion.\n\n{{text}}"
print(find_variables(SUMMARY_TEMPLATE))
print(find_variables('Return JSON like {"name": "Ana"} for {{person}} and again for {{person}}.'))
print(fill("Write to {{person}} about {{topic}}.", {"person": "Ana", "topic": "the invoice"}))
for values in ({"person": "Ana"}, {"person": "Ana", "topic": "x", "tone": "warm"}):
    try:
        fill("Write to {{person}} about {{topic}}.", values)
    except ValueError as error:
        print(error)
print(fill('Return {"name": "{{person}}"} only.', {"person": "Ana"}))
try:
    'Return {"name": "{person}"} only.'.format(person="Ana")
except KeyError as error:
    print("str.format fails with KeyError:", error)
```

- **A variable is a lowercase name between double braces.** The pattern matches letters and underscores only, so braces around anything else are left alone.
- **`find_variables` returns each name once, in order of first appearance.** The summary template has three. In the second example the JSON's braces are ignored and `person`, used twice, is listed once.
- **`fill` checks before it substitutes.** A variable with no value, or a blank one, raises an error naming it. So does a value the template does not use.
- **The first failure is a missing topic.** Without the check, the model would have been sent the literal text of the marker.
- **The second failure is an unused value.** Someone supplied a tone to a template with no tone variable. Either the template lost a variable in an edit, or the name is misspelt. Both are worth stopping for.
- **JSON in a template is safe.** The next example fills a variable inside a JSON example and leaves the surrounding braces as they are.
- **`str.format` cannot do this.** The same template in single-brace form fails, because Python reads the JSON's opening brace as the start of a variable named `"name"`.

Next, the entries, a linter, and a test runner.

```python
POLICY = ("Refunds are accepted within 30 days of delivery. Items must be unused and in their original packaging. "

     "variables": ["words", "text", "tone"],

     "variables": ["expected", "actual", "error", "code"], "tests": []},

def lint_entry(entry):
    problems = ["missing-field:" + key for key in ("id", "category", "title", "template") if not entry.get(key)]
    used = set(VARIABLE.findall(entry.get("template", "")))
    declared = set(entry.get("variables", []))
    if not used:
        problems.append("no-variables")
    problems += ["undeclared:" + name for name in sorted(used - declared)]
    problems += ["unused-declared:" + name for name in sorted(declared - used)]
    if not entry.get("tests"):
        problems.append("no-tests")
    return problems

def render(template, values):
    return VARIABLE.sub(lambda match: str(values.get(match.group(1), match.group(0))), template)

def stub_model(prompt):
    limit = re.search(r"at most (\d+) words", prompt)
    body = prompt.split("\n\n")[-1]
    return " ".join(body.split()[:int(limit.group(1))]) if limit else body

def run_tests(entry, model):
    results = []
    for test in entry.get("tests", []):
        prompt = render(entry["template"], test["values"])
        if "{{" in prompt:
            results.append(False)
            continue
        output = model(prompt)
        passed = all(phrase.lower() in output.lower() for phrase in test.get("contains", []))
        if test.get("max_words") is not None and len(output.split()) > test["max_words"]:
            passed = False
        results.append(passed)
    return results

for entry in LIBRARY:
    print(entry["id"], lint_entry(entry), run_tests(entry, stub_model))

drifted = dict(LIBRARY[0], template=SUMMARY_TEMPLATE.replace("at most", "about"))
print(lint_entry(drifted), run_tests(drifted, stub_model))
```

- **Each entry carries its template, its declared variables, and its tests.** A test is a set of values, phrases the output must contain, and an optional limit on its length.
- **`lint_entry` checks the entry against itself.** Required fields present, at least one variable, the declared variables equal to those in the template, and at least one test.
- **Two entries have findings.** `wri-02` declares a `tone` variable that its template no longer uses: someone removed it from the text and not from the list. `cod-73` has no tests, so nothing would notice if it stopped working.
- **`stub_model` stands in for a model.** It obeys one instruction: if the prompt says "at most N words", it returns the first N words of the material. It is a toy, and it is enough to show a template's test passing and failing.
- **`run_tests` fills each test's values and checks the output.** A prompt that still contains a marker fails at once. Otherwise every required phrase must appear and the length limit must hold.
- **The three tested entries pass.** The fourth returns an empty list: no tests, no results.
- **The drifted entry shows what tests are for.** Someone softened "at most" to "about" in the summary template. The linter finds nothing wrong, since the variables still match. The test fails, because the stand-in model no longer sees a limit and returns all 48 words. A small rewording changed the behaviour, and only the test noticed.

Finally, deciding what to remove.

```python
def prune_candidates(library, usage_log, min_uses=2):
    counts = Counter(usage_log)
    return sorted(entry["id"] for entry in library if counts[entry["id"]] < min_uses)

USAGE_LOG = ["sum-21"] * 9 + ["eml-11"] * 4 + ["cod-73"] + ["old-99"] * 3
print(prune_candidates(LIBRARY, USAGE_LOG))
print(prune_candidates(LIBRARY, USAGE_LOG, min_uses=5))
print(5 ** 3, 40 * (4 - 0.5) - 30, round(30 / (4 - 0.5), 1))
```

- **The usage log is a list of entry identifiers, one per use.** Counting it gives the number of times each entry was used.
- **Entries used fewer than the minimum are candidates for removal.** With a minimum of two, they are `cod-73`, used once, and `wri-02`, never used. Identifiers in the log that are not in the library, such as an entry already deleted, are ignored.
- **The threshold is a judgement.** Raising it to five adds `eml-11`, used four times. Section 2's break-even figure of about nine uses a year suggests the stricter line is closer to right.
- **A candidate is a question, not a verdict.** A template for the annual report is used once a year and worth keeping. The list is for a person to read.
- **The last line checks Section 2's arithmetic.** Three variables with five values each stand for 125 prompts. Forty uses save 110 minutes, and the break-even is 8.6, so nine uses.

**Complexity.** `find_variables` and `fill` are linear in the template. `lint_entry` is linear in the entry. `run_tests` makes one model call per test. `prune_candidates` is linear in the log plus the library.

### A routine for keeping a library healthy

| When | Do |
|---|---|
| Adding an entry | Adapt it, give it a test from a real input, and lint it |
| Editing a template | Re-run its tests, and record why it changed |
| The model changes | Re-run every test before trusting the library again |
| Every few months | Read the usage counts, remove what nobody uses, and merge near-duplicates |
| An entry disappoints someone | Add the input that disappointed as a new test, then fix the template |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Pasting a prompt with its holes unfilled.** A template sent with "{{audience}}" still in it gets a generic answer and no error. Use a filler that refuses, or at the least search the text for braces before sending.

**Collecting and not using.** A file of five hundred prompts saved from articles is a reading list. The value is in the handful that have been adapted to your work and tried on it.

**The mega-prompt.** Templates of a thousand words that cover every eventuality are popular and brittle. Nobody knows which sentences matter, so nobody dares edit them, and the model follows the middle of them least. Prefer a short template with a clear job.

**No example of good output.** A template says what to do and an example shows it. Keeping one output you were pleased with beside each template is the fastest way to get the next output to resemble it.

**Too many variables.** A template with nine holes takes as long to fill as writing the prompt. If several variables always take the same values for you, write them in.

**Vague variable names.** A hole labelled `{{input}}` or `{{details}}` does not say what belongs in it. Names such as `{{customer_email}}` and `{{refund_policy}}` are instructions to the person filling them.

**Editing a template that works.** Rewording for style feels harmless. The research in Section 2 found large changes in accuracy from formatting alone. Edit, then re-run the tests.

**Stale after a model update.** Phrases that compensated for an older model's weaknesses, such as heavy emphasis or elaborate role-play, can make a newer model worse. A library needs retesting when the model changes, and some entries will need simplifying.

**Secrets in templates.** A shared library spreads. Customer names, internal figures, and credentials written into a template travel with it. Keep such things in variables, filled at the time of use.

**One library for everyone.** A template tuned to the legal team's needs serves marketing badly. Shared libraries work when entries say who they are for and each team adapts its own copies.

**No owner.** A shared file that everyone can edit and nobody is responsible for accumulates duplicates and broken entries. Give the library an owner, or at least a rule that every entry names who last tested it.

**Trusting the output because the prompt is "from the library".** A tested template lowers the chance of a bad answer. It does not check the facts in this particular answer. The verification habits of Module 2.12 still apply.

## 5. Active Recall Check & Synthesis Summary

**Summary.** A prompt becomes reusable when the parts that change are replaced with named variables and the parts that do not are fixed. The variables are also a checklist of what the model must be told. A template with variables taking $m_{1}, m_{2}, \dots$ values stands for their product in distinct prompts, and it pays for itself only if used more than $t_{m} / (t_{w} - t_{f})$ times, which argues for a small library of adapted templates over a large collection of copied ones. Double-brace variables avoid collisions with JSON, and a strict filler refuses a missing, blank, or unused value instead of sending a broken prompt silently. Templates are sensitive to wording and to the model, so each library entry carries its declared variables, at least one test, and a record of the model it was tested on. A library is kept healthy by linting entries against themselves, re-running tests on every edit and every model change, and pruning what the usage log shows nobody uses. The hundred templates in this chapter are a book to choose from. The library is what you build from it.

The template stands for 5 times 4 times 3, which is 60 distinct prompts. Each use saves 4 minus 0.5, which is 3.5 minutes. The upkeep of 30 minutes is recovered after 30 divided by 3.5 uses, which is about 8.6, so the template pays for itself from the ninth use in a year. At 40 uses it saves 40 times 3.5, which is 140 minutes, less the 30 of upkeep: 110 minutes. At 3 uses it saves 10.5 minutes against 30 of upkeep, a net loss of 19.5 minutes. Every entry carries a fixed cost, in testing when the model changes, in being read past when someone scans the list, and in the risk that it has quietly stopped working. Entries used a few times a year do not repay that cost and are better deleted, with the prompt written fresh on the rare occasion it is needed. There are two exceptions worth keeping. One is the template for a rare task that is hard to get right, where the saving per use is much larger than a few minutes. **Question 2.** A colleague found prompt 22 from this chapter, "Key points with quotes", and complains that it "doesn't work": the points are generic and some quotes are not in the document. <summary>View Answer</summary>

Several things may be at fault, and the first is to find out which. Generic points usually mean the template has none of the colleague's context: it does not say who the points are for or what they will be used to decide, so the model picks what any reader might find important. **Question 3.** A script fills a template and sends it to a model every night. Last week someone edited the template and renamed the variable `{{audience}}` to `{{reader}}`. Which library routines would have caught the problem before the nightly run?

<details>
<summary>View Answer</summary>

With the careless filler, the template's `{{reader}}` has no matching value, so it is left in the text, and the supplied `audience` matches nothing and is dropped. The prompt goes to the model reading, for example, "Summarise the text below for {{reader}} in at most 60 words". Nothing raises an error. def render(template, values):
    """Provided helper: a CARELESS filler. It substitutes the values it has and leaves any
    other marker in place. Used by the test runner, which then checks for leftover markers."""
    return VARIABLE.sub(lambda match: str(values.get(match.group(1), match.group(0))), template)


def stub_model(prompt):
    """Provided stand-in for a model. If the prompt says "at most N words", it returns the
    first N words of the material after the last blank line. Otherwise it returns all of it."""
    limit = re.search(r"at most (\d+) words", prompt)
    body = prompt.split("\n\n")[-1]
    return " ".join(body.split()[:int(limit.group(1))]) if limit else body


# ---------------------------------------------------------------- Step 1
def find_variables(template):
    """The variables are the template's checklist of what the model must be told."""
    names = []
    for name in VARIABLE.findall(template):
        if name not in names:
            names.append(name)
    return names


# ---------------------------------------------------------------- Step 2
def fill(template, values):
    """Refuses where a careless filler would send a broken prompt in silence. A failure
    that names the variable is noticed and fixed. A slightly worse answer is not."""
    names = set(VARIABLE.findall(template))
    missing = sorted(name for name in names if not str(values.get(name, "")).strip())
    if missing:
        raise ValueError("missing: " + ", ".join(missing))
    unused = sorted(key for key in values if key not in names)
    if unused:
        raise ValueError("unused: " + ", ".join(unused))
    return VARIABLE.sub(lambda match: str(values[match.group(1)]), template)


# ---------------------------------------------------------------- Step 3
def lint_entry(entry):
    """Checks an entry against itself. The declared variables look redundant and are the
    cross-check that catches a template edited without its entry."""
    problems = ["missing-field:" + key for key in ("id", "category", "title", "template") if not entry.get(key)]
    used = set(VARIABLE.findall(entry.get("template", "")))
    declared = set(entry.get("variables", []))
    if not used:
        problems.append("no-variables")
    problems += ["undeclared:" + name for name in sorted(used - declared)]
    problems += ["unused-declared:" + name for name in sorted(declared - used)]
    if not entry.get("tests"):
        problems.append("no-tests")
    return problems


# ---------------------------------------------------------------- Step 4
def run_tests(entry, model):
    """Run on every edit and every change of model. A reworded template can pass the
    linter and fail here, which is the only place the change in behaviour shows."""
    results = []
    for test in entry.get("tests", []):
        prompt = render(entry["template"], test["values"])
        if "{{" in prompt:
            results.append(False)
            continue
        output = model(prompt)
        passed = all(phrase.lower() in output.lower() for phrase in test.get("contains", []))
        if test.get("max_words") is not None and len(output.split()) > test["max_words"]:
            passed = False
        results.append(passed)
    return results


# ---------------------------------------------------------------- Step 5
def prune_candidates(library, usage_log, min_uses=2):
    """Every entry has an upkeep cost. The list is a question for a person, not a verdict:
    a template used once a year for the annual report may be worth keeping."""
    counts = Counter(usage_log)
    return sorted(entry["id"] for entry in library if counts[entry["id"]] < min_uses)
