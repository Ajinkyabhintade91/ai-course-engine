# Privacy and Offline Usage

"It runs locally, so it's private" is the most common reason people give for local AI, and it is mostly true. But "mostly" hides the details that matter when personal data is involved: model downloads and updates still go over the internet; cloud-tagged models and web search send content to a service; front ends and plug-ins may call out on their own; a server exposed to the network can be used by anyone who reaches it; and the logs, documents, and conversation histories a local system keeps are personal data stored on a disk. This module maps what stays on your machine and what does not, shows how to build a fully offline setup, and lists the compliance work that remains even when nothing leaves the building.

Ollama behaviour is from its documentation at the time of writing (November 2026). Legal references are to the GDPR and UK guidance as general orientation; this module is not legal advice.

## 1. First-Principles Mental Model & Intuition

### A workshop with a locked door and a filing cabinet

Running AI locally is like moving a job from an outside contractor into your own **workshop**. The customer's drawings no longer leave the building, which is the main win. But a workshop still has **deliveries** coming in, timber and tools, which reveal what you are working on even if they carry no drawings: model downloads and updates. It may have a **phone line** to suppliers that someone could use to read out a drawing: cloud models and web search. Its **door** may be locked or open to the street: the server's bind address. And it has a **filing cabinet** full of old drawings and notes: logs and histories, which need a lock, a clear-out schedule, and no unnecessary copies.

```text
                         YOUR MACHINE / BUILDING
   +-------------------------------------------------------------------+
   |  Ollama server (127.0.0.1:11434)    models on disk    front end    |
   |  logs, chat history, uploaded documents  <- personal data at rest  |
   +---------^----------------------^-------------------^---------------+
             | model pulls          | app updates        | cloud models, web search,
             | (no prompts)         | (no prompts)       | remote embeddings, plug-ins
   registry.ollama.ai / hf.co    ollama.com             PROMPT CONTENT LEAVES
   offline: carry models in on media, verify sha256; OLLAMA_NO_CLOUD=1; bind to localhost
```

### Two separate questions

Privacy for a local system means answering two questions separately. **Does content leave?** Map every flow. **Is the content that stays protected?** Access, logs, retention, encryption. A setup can pass the first and fail the second.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### What stays and what leaves

Ollama's FAQ says that when you run locally, Ollama does not see your prompts or data. Several things still involve the network:

| Flow | Destination | Contains prompts? |
|---|---|---|
| Pulling models | `registry.ollama.ai`, or `hf.co` for Hugging Face models | No, but reveals which models you use |
| App updates on macOS and Windows | ollama.com | No |
| Cloud models, such as `:cloud` tags | Ollama's cloud | **Yes**: prompts and responses are processed there |
| Web search API | ollama.com | **Yes**: search queries |
| Remote embedding or plug-in services in front ends | Their providers | **Yes**, often document text |
| Server bound to `0.0.0.0` | Anyone on the network | Anyone can send and read |

For cloud models, Ollama's cloud FAQ describes a zero data retention policy: prompts and responses are processed transiently, not stored or logged, and not used for training. That is a policy of the provider, not a technical guarantee you can verify, and for a requirement that "nothing leaves the building" it does not suffice.

### Turning cloud features off

The FAQ describes disabling cloud features by setting `OLLAMA_NO_CLOUD=1`, or `disable_ollama_cloud` in `~/.ollama/server.json`, and restarting; the logs then show cloud disabled. With cloud features off, cloud models and web search are unavailable, so a misconfigured application fails loudly instead of quietly sending content out.

### Fully offline setups

An **air-gapped** machine has no network connection at all. Ollama can run this way because inference needs no network. The procedure:

1. On a connected machine, install the same Ollama version and `ollama pull` the needed models with pinned tags, Module 10.4.
2. Copy the installer, or on Linux the manual-install package, Module 10.3, and the model directory: `manifests` and `blobs`.
3. Carry them in on approved media, install Ollama, and place the models in `OLLAMA_MODELS`.
4. **Verify the files.** Each blob is named `sha256-` followed by the SHA-256 digest of its content, so recomputing the digest detects corruption or tampering in transit:

$$\text{valid} \iff \operatorname{SHA256}(\text{file bytes}) = \text{name without the } \texttt{sha256-} \text{ prefix}$$

5. Set `OLLAMA_NO_CLOUD=1`, keep the server on `127.0.0.1`, and confirm with `ollama ls` and a test prompt.

Updates follow the same path: download, verify, carry in, test.

### Personal data at rest

Local systems create stores of personal data: server and application logs, conversation histories in front ends, uploaded documents, and vector indexes of documents for retrieval, Module 8.7. The GDPR's principles in Article 5 include **data minimisation**, collecting only what is needed, and **storage limitation**, keeping it no longer than necessary, plus security. In practice:

- **Redact** personal data from logs before writing them: email addresses, phone numbers, card numbers. Card numbers can be recognised with the **Luhn checksum**, which double every second digit from the right, subtract 9 from results above 9, and require the total to be divisible by 10; this distinguishes real card numbers from order numbers of similar length.
- **Retain** logs for a fixed period, then delete them.
- **Encrypt** disks that hold logs, histories, and documents.
- **Restrict access**: the server on localhost, or behind an authenticating proxy if it must be shared.

### Compliance use cases and remaining risks

Local deployment helps with use cases where data must not reach third parties: legal and medical drafting, HR documents, customer correspondence, and regulated or confidential engineering data. It does not remove obligations. Under the GDPR, processing that is likely to result in high risk to individuals requires a **data protection impact assessment**, Article 35. The UK Information Commissioner's Office publishes guidance on AI and data protection covering fairness, transparency, and accuracy, which apply whether the model is local or hosted.

Remaining risks also include the model itself: it may produce inaccurate statements about people, and it is vulnerable to **prompt injection** through documents it reads, as the OWASP Top 10 for LLM applications describes. Local models also need patching: the Ollama server is software with its own security updates.

### Complexity

Mapping flows is linear in the setup's components; verifying blobs is linear in their total size; redaction is linear in text length; retention is linear in log entries.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, mapping external flows.

```python
CONTENT = {"prompts and responses for cloud models", "search queries", "document text for embeddings"}

def external_flows(setup):
    flows, errors = [], []
    cloud_off = setup.get("no_cloud", False)
    if setup.get("pull_models"):
        flows.append(("registry.ollama.ai", "model downloads (no prompts)"))
    if setup.get("auto_update"):
        flows.append(("ollama.com", "app updates (no prompts)"))
    if setup.get("cloud_models"):
        if cloud_off:
            errors.append("cloud model requested but cloud features are disabled")
        else:
            flows.append(("ollama.com", "prompts and responses for cloud models"))
    if setup.get("web_search"):
        if cloud_off:
            errors.append("web search requested but cloud features are disabled")
        else:
            flows.append(("ollama.com", "search queries"))
    if setup.get("remote_embeddings"):
        flows.append((setup["remote_embeddings"], "document text for embeddings"))
    if setup.get("host", "127.0.0.1") not in ("127.0.0.1", "localhost", "::1"):
        flows.append(("local network", "API reachable by other machines"))
    return flows, errors

PROPOSED = {"pull_models": True, "auto_update": True, "cloud_models": True, "web_search": True,
            "remote_embeddings": "api.embed.example", "host": "0.0.0.0"}
for flow in external_flows(PROPOSED)[0]:
    print(flow)
print(external_flows({"no_cloud": True, "cloud_models": True}))
```

- **Six flows in the proposed setup; three carry content.** Cloud models, web search, and the remote embedding service.
- **Downloads and updates carry no prompts,** but they are still connections an air-gapped site must plan for.
- **With cloud features disabled, a request for a cloud model becomes an error,** which is what you want: failure rather than leakage.

Next, verifying model files carried in.

```python
import hashlib

def verify_blobs(blobs):
    bad = []
    for name, data in sorted(blobs.items()):
        if not name.startswith("sha256-") or hashlib.sha256(data).hexdigest() != name[7:]:
            bad.append(name)
    return bad

good = b"weights"
BLOBS = {"sha256-" + hashlib.sha256(good).hexdigest(): good, "sha256-" + "0" * 64: b"tampered", "notes.txt": b"x"}
print(verify_blobs(BLOBS))
```

- **A blob whose content matches its name passes.** The name is the digest.
- **A changed file fails,** whatever the cause: corruption, a bad copy, or tampering.
- **Unexpected files are flagged too.** The blobs folder should contain only digests.

Then, redacting logs.

```python
import re

def luhn_ok(digits):
    total = 0
    for i, d in enumerate(reversed(digits)):
        n = int(d)
        if i % 2:
            n = n * 2 - 9 if n * 2 > 9 else n * 2
        total += n
    return total % 10 == 0

def redact(text):
    text = re.sub(r"[\w.+-]+@[\w-]+\.[\w.-]+", "[EMAIL]", text)
    def card(m):
        digits = re.sub(r"[ -]", "", m.group(0))
        return "[CARD]" if 13 <= len(digits) <= 19 and luhn_ok(digits) else m.group(0)
    text = re.sub(r"\b\d(?:[ -]?\d){12,18}\b", card, text)
    text = re.sub(r"(?:\+44\s?7\d{3}|\b07\d{3})\s?\d{3}\s?\d{3}\b", "[PHONE]", text)
    return text

print(redact("Call Priya on 07700 900123 or priya@harperjoinery.co.uk; card 4111 1111 1111 1111, order 1234567890123."))
```

- **The email, phone number, and card number are replaced.** The test card number passes the Luhn check.
- **The 13-digit order number is kept** because it fails the Luhn check. Without the checksum, order numbers would be redacted too.
- **Cards are handled before phones,** so card digits are not mistaken for phone numbers. Patterns cover UK mobiles; other formats need their own.

Then, enforcing retention.

```python
from datetime import date

def retention_sweep(entries, today, days):
    t = date.fromisoformat(today)
    keep = [e for e in entries if (t - date.fromisoformat(e["date"])).days <= days]
    return keep, len(entries) - len(keep)

LOGS = [{"date": "2026-11-10", "msg": "a"}, {"date": "2026-08-01", "msg": "b"}, {"date": "2026-10-18", "msg": "c"}]
print(retention_sweep(LOGS, "2026-11-17", 30))
```

- **With 30-day retention, the August entry is deleted; two remain.**
- **An entry exactly 30 days old is kept.** Decide the boundary deliberately and document it.
- **Run the sweep on a schedule,** and include conversation histories and uploaded documents, not just logs.

Finally, the compliance gap list.

```python
def compliance_gaps(setup, use_case):
    gaps = []
    flows, errors = external_flows(setup)
    content = sorted({dest for dest, what in flows if what in CONTENT})
    if use_case.get("data_must_stay_local") and content:
        gaps.append("content leaves the machine: " + ", ".join(content))
    if any(dest == "local network" for dest, _ in flows) and not setup.get("auth_proxy"):
        gaps.append("API exposed without authentication")
    if use_case.get("personal_data"):
        if not setup.get("log_redaction"):
            gaps.append("redact personal data in logs")
        if not setup.get("retention_days"):
            gaps.append("set a log retention period")
        if not setup.get("disk_encryption"):
            gaps.append("encrypt the disk holding logs and documents")
    if use_case.get("high_risk") and not setup.get("dpia_done"):
        gaps.append("complete a data protection impact assessment")
    return gaps + errors

USE = {"data_must_stay_local": True, "personal_data": True, "high_risk": True}
for gap in compliance_gaps(PROPOSED, USE):
    print(gap)
```

- **The proposed setup has six gaps,** starting with content leaving for two destinations.
- **The checklist separates "does content leave" from "is stored data protected",** the two questions from Section 1.
- **A clean result means the listed controls are in place,** not that the system is compliant; that judgement belongs to the organisation.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Assuming "local" means everything is local.** Cloud tags, web search, and plug-ins send content. Map the flows.

**Cloud tags in a privacy-sensitive app.** They run on a service. Disable cloud features.

**Front-end extras.** Web search, remote embeddings, and analytics in chat front ends. Turn them off or review them.

**Exposed server.** `0.0.0.0` without a firewall or proxy. Bind to localhost.

**Logs with personal data.** Prompts are logged by apps and proxies. Redact and retain briefly.

**Over-eager redaction.** Order numbers removed as card numbers. Use checksums.

**Unverified model files.** USB copies can corrupt. Verify digests.

**Stale offline systems.** Air-gapped machines miss security fixes. Schedule updates.

**Vector stores as copies.** Embedding indexes contain document text. Apply the same retention.

**Backups.** Logs and histories in backups outlive retention. Include backups in the plan.

**Prompt injection in documents.** Local does not prevent it. Treat document content as data.

**Treating a checklist as compliance.** Controls help; accountability stays with the organisation.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Running models locally keeps prompts on the machine, but model downloads, updates, cloud models, web search, remote embedding services, and exposed servers all involve the network, and several of them carry content. Disabling cloud features with `OLLAMA_NO_CLOUD` makes misconfiguration fail rather than leak, and fully offline setups carry installers and model files in, verifying each blob against its SHA-256 name. **Question 2.** The model files arrive on a USB stick, and one blob fails `verify_blobs`. Explain what the check does, what the failure could mean, and what to do.

<details>
<summary>View Answer</summary>

Ollama stores each layer of a model as a blob whose file name is `sha256-` followed by the SHA-256 digest of its content. `verify_blobs` recomputes the digest of every file and compares it with the name; any difference, or any file not named that way, is reported. A failure means the bytes are not the ones that were downloaded: the copy may have been corrupted on the USB stick, interrupted, or deliberately altered. Whatever the cause, the file must not be used: a corrupted weights file can crash or misbehave, and a tampered one is a security risk. The fix is to discard it, recopy the blob from the staging machine, ideally verifying it there first so the source is known to be good, and verify again on arrival. Recording the digests of every blob in the transfer log also gives an audit trail of exactly which model versions entered the building.

</details>

**Question 3.** After the flows are fixed, the adviser says the system is now "GDPR compliant". Using `compliance_gaps`, `redact`, and `retention_sweep`, explain why that is premature.

<details>
<summary>View Answer</summary>

Fixing the flows answers only the first question, whether content leaves. `compliance_gaps` also checks how stored data is handled, because the system keeps personal data in logs, histories, and documents. For a use case with personal data it requires log redaction, a retention period, and disk encryption, and for high-risk processing a data protection impact assessment, as Article 35 requires. `redact` shows what log redaction does: it replaces email addresses, UK mobile numbers, and Luhn-valid card numbers, while keeping order numbers that merely look similar. `retention_sweep` enforces storage limitation by deleting entries older than the retention period. Even with all checks passing, compliance is a judgement the organisation must make and document: the model can still write inaccurate statements about people, documents can carry prompt injections, backups can hold old logs, and the offline system needs a schedule of security updates.     for i, d in enumerate(reversed(digits)):
        n = int(d)
        if i % 2:
            n = n * 2 - 9 if n * 2 > 9 else n * 2
        total += n
    return total % 10 == 0


def redact(text):
    """Remove emails, card numbers (Luhn-checked), and UK mobile numbers before logging."""
    text = re.sub(r"[\w.+-]+@[\w-]+\.[\w.-]+", "[EMAIL]", text)

    def card(m):
        digits = re.sub(r"[ -]", "", m.group(0))
        return "[CARD]" if 13 <= len(digits) <= 19 and luhn_ok(digits) else m.group(0)

    text = re.sub(r"\b\d(?:[ -]?\d){12,18}\b", card, text)
    text = re.sub(r"(?:\+44\s?7\d{3}|\b07\d{3})\s?\d{3}\s?\d{3}\b", "[PHONE]", text)
    return text


# ---------------------------------------------------------------- Step 4
def retention_sweep(entries, today, days):
    """Storage limitation: keep only entries within the retention period."""
    t = date.fromisoformat(today)
    keep = [e for e in entries if (t - date.fromisoformat(e["date"])).days <= days]
    return keep, len(entries) - len(keep)
