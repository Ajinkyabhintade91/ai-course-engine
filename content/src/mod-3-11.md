# Gemini Gems

A **Gem** is a saved, customised version of Gemini. You give it a name, write instructions describing what it should do and how, optionally attach reference files, and from then on you can start a chat with that Gem and skip the explanation. A Gem for editing your writing, a Gem that knows your company's products, a Gem that quizzes you on your course notes.

If that sounds familiar, it should. A Gem is Google's version of the idea you met as a custom GPT in Module 2.6 and, in a different shape, as a Claude Project in Module 3.2.

**An important note on timing.** As this chapter is written, in November 2026, Google is retiring Gems in favour of a newer feature called **skills**. According to Google's help pages, Gems on personal accounts become read-only on 17 November 2026 and are removed on 17 December 2026, having been converted to skills automatically. Business accounts keep Gems until March 2027 and education accounts until June 2027. This is the same shift that Module 2.6 described for custom GPTs and that Module 3.5 described from Claude's side.

So this chapter does two things. It teaches the durable craft, which is writing good instructions, choosing knowledge, and testing an assistant, using Gems as the example. And it explains what changes with skills and how to move across without losing what you built.

## 1. First-Principles Mental Model & Intuition

### A job description and a binder

Hiring an assistant for one kind of task, you would hand over two things: a **job description** ("you edit my newsletters; keep my voice; never lengthen a sentence") and a **binder** of reference material (the style guide, three past issues). Each morning they re-read both and start work.

A Gem is exactly that pair, saved.

```text
+---------------------- GEM: "Newsletter editor" ----------------------+
|                                                                      |
|  NAME          Newsletter editor                                     |
|                                                                      |
|  INSTRUCTIONS  (the job description)                                 |
|                Who you are, what you do, how to answer,              |
|                what to do when unsure                                |
|                                                                      |
|  KNOWLEDGE     (the binder)                                          |
|                style-guide.pdf   issue-41.docx   issue-42.docx       |
|                                                                      |
+----------------------------------------------------------------------+
            |                    |                    |
        chat today          chat tomorrow        chat next week
        (each one starts with the job description and the binder)
```

Two properties are worth noticing, because they are where Gems and their successors differ.

**A Gem is a place you go.** You open the Gem and chat inside it. The whole conversation is under its instructions.

**Each chat starts fresh.** The Gem carries its instructions and knowledge into every chat. It does not carry yesterday's conversation.

### The same idea, three vendors

| | Gem (Google) | Custom GPT (OpenAI) | Project (Claude) |
|---|---|---|---|
| Saved instructions | Yes | Yes | Yes |
| Reference files | Yes, including live files from Google Drive | Yes | Yes, with retrieval for large sets |
| Main intent | A personal or shared assistant for one job | A packaged tool to publish and reuse | A workspace for a continuing body of work |
| Status in late 2026 | Being replaced by skills | Being retired in favour of newer features | Current |

The details in this table are from each vendor's documentation as the earlier modules reported them, and they change. What matters is the bottom row. Two of the three vendors are retiring their "saved persona" feature in the same season, for the same successor.

### From a place you go to a procedure you call

A **skill** packages the same ingredients, instructions and files, in a different way. A skill is not a separate chat you enter. It is a procedure you can call into any conversation, and the assistant can also decide to apply it when a request matches.

```text
   GEM                                   SKILL

   open the Gem  -->  chat inside it     any chat  -->  "/newsletter-edit"  (or applied automatically)
   one Gem per conversation              several skills can be used in one conversation
   always fully loaded                   loaded when needed
```

Module 3.5 explained why this design wins: a procedure that is loaded only when relevant costs almost nothing when it is not, and several can be combined. Google's description of its skills follows the same lines. They are invoked with a slash in any chat, Gemini can apply one on its own initiative, more than one can be active in a conversation, and a skill written as a `SKILL.md` file can be imported. That last point means the format you studied in Module 3.5 is becoming common ground between vendors.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### What a Gem is made of

According to Google's help pages at the time of writing, creating a Gem involves:

| Part | What it is | Notes |
|---|---|---|
| **Name** | What you will see in the list | Make it say what the Gem does |
| **Instructions** | Free text describing the job | A button offers to have Gemini rewrite and expand what you typed |
| **Knowledge** | Optional reference files | Uploaded from your device, linked from Google Drive, or attached as a notebook from Google's notebook tool |
| **Preview** | A test chat beside the editor | Lets you try the Gem before saving |

Three details are worth knowing. Files linked from Google Drive are live: the Gem uses the latest version, so updating the document updates the Gem. Gems you create on the web also appear in the mobile app and in the side panel of Google's office applications. And Gems can be shared with other people in the same way as a document in Google Drive, with permission to view or to edit.

### Where the instructions sit

As with every saved-instruction feature in this course, the mechanism is the one from Module 1.4. The model is stateless. On every turn the application assembles an input and sends it.

```text
+--------------------------------------------------+
| Google's own system instructions                 |
| Your saved preferences                           |
| THE GEM'S INSTRUCTIONS                           |
| Relevant content from the Gem's knowledge        |
| The conversation so far                          |
| Your new message                                 |
+--------------------------------------------------+
                     |
                     v
                  MODEL
```

A Gem's instructions are a prompt that is sent every time. That explains both why Gems work and how they fail.

### Writing instructions: Persona, Task, Context, Format

Google's prompting guide for its workplace products recommends thinking about four elements. They suit a Gem's instructions well.

| Element | Question it answers | Example |
|---|---|---|
| **Persona** | Who is the assistant, and for whom? | "You are an editor for a weekly newsletter read by small-business owners." |
| **Task** | What does it do? Start with a verb | "Edit the draft I paste for clarity and length." |
| **Context** | What does it need to know? | "The house style is in style-guide.pdf. Sentences average 15 words. British spelling." |
| **Format** | What should the answer look like? | "Return the edited text, then a list of at most five changes with reasons." |

The guide notes that not every prompt needs all four, and that the task, stated with a clear verb, matters most. For a Gem, add a fifth line that the guide does not list and experience demands:

- **Fallback.** What to do when the request is outside the job or the knowledge does not cover it. "If the style guide does not address a point, say so and ask me."

Without a fallback, a Gem asked something its files do not cover will usually answer from the model's general knowledge, in the same confident voice.

### Why Gems drift in long chats

A common complaint is that a Gem "forgets" its instructions as a conversation grows. A simple model shows why. Suppose the instructions are $I$ tokens and each exchange adds $c$ tokens to the conversation. After $t$ exchanges, the instructions make up this share of what the model reads:

$$
\text{share}(t) = \frac{I}{I + c \cdot t}
$$

With $I = 400$ and $c = 500$:

| Exchanges $t$ | Share of the input that is instructions |
|---|---|
| 1 | 0.444 |
| 5 | 0.138 |
| 20 | 0.038 |
| 50 | 0.016 |

The instructions are still present at every turn. They are an ever smaller part of a growing input, competing with a long transcript in which the recent messages are closest to where the model starts writing. Module 1.9 described this weakening of attention over long inputs. The formula is an illustration and not a measurement of any product, but the remedy it suggests is the one that works: for each new piece of work, start a new chat.

### Knowledge: what goes in, and what does not survive the move

Knowledge files follow the principles of Module 3.2. Fewer, current, well-named files beat a large pile. Two questions decide whether a file belongs: would the assistant give a wrong answer without it, and is it the current version?

The move to skills adds a practical constraint, documented on Google's transition page.

- A skill's files may total **100 MB**. If a Gem's knowledge is larger, the largest files are dropped first when it is converted.
- Some file types are **not carried over**: audio, video, older office formats such as `.doc`, `.xls`, and `.ppt`, compressed archives, and files linked from code repositories.
- Several tools that a Gem could use are **not yet available** to skills at the time of writing, including the document canvas and deep research.
- **Sharing carries over**, but people you shared a Gem with must accept the converted skill before using it.

The size rule can be stated as an algorithm. Remove the unsupported types. Then, while the total exceeds the limit $L$, remove the largest remaining file:

$$
\text{while } \sum_{f \in K} \text{size}(f) > L: \quad K \leftarrow K \setminus \{\arg\max_{f \in K} \text{size}(f)\}
$$

"Largest first" has an unwelcome property. The largest file is often the most important one, the handbook or the full catalogue. An automatic conversion can therefore discard exactly the file the assistant depends on, and keep three small ones. The fix is to do the trimming yourself before the conversion does it for you.

### Testing an assistant

A Gem is software in the sense that matters: it has behaviour you rely on, and editing it can break that behaviour. The discipline from Module 2.5 applies. Keep a small set of test prompts, each with a check, and run them after every change.

$$
\text{pass rate} = \frac{\text{tests passed}}{\text{tests run}}
$$

Useful tests for a custom assistant fall into three kinds.

| Kind | Example prompt | What to check |
|---|---|---|
| **Does the job** | A typical request | The answer has the required format and uses the knowledge |
| **Stays in its lane** | A request outside the job | It declines or redirects, as the instructions say |
| **Admits gaps** | A question the files do not answer | It says so, and does not invent |

Comparing the pass rate before and after an edit is a **regression test**: it tells you whether the change that fixed one thing broke another. A migration from Gem to skill is a change like any other, and a reason to run the tests.

### Complexity

Building and checking instructions is linear in their length. Planning which files survive is quadratic in the number of files at worst, since each removal searches for the largest. Running a test set costs one model call per test.

## 3. Production-Grade Implementation & Annotated Walkthrough

The craft of this chapter can be made mechanical. First, building instructions from the four elements and checking them for common weaknesses.

```python
def build_instructions(persona, task, context="", fmt="", fallback=""):
    if not task.strip():
        raise ValueError("a task is required")
    sections = [("Persona", persona), ("Task", task), ("Context", context), ("Format", fmt), ("If unsure", fallback)]
    return "\n".join(f"{label}: {text.strip()}" for label, text in sections if text.strip())

VAGUE = ("be helpful", "do your best", "as appropriate", "and so on")
FORMAT_WORDS = ("format", "bullet", "table", "words", "sentences", "list")
FALLBACK_WORDS = ("if unsure", "if you are unsure", "do not guess", "say so", "ask me")

def lint_instructions(text):
    lowered = text.lower()
    warnings = []
    if len(text.split()) < 20:
        warnings.append("too-short")
    if any(phrase in lowered for phrase in VAGUE):
        warnings.append("vague")
    if not any(word in lowered for word in FORMAT_WORDS):
        warnings.append("no-format")
    if not any(phrase in lowered for phrase in FALLBACK_WORDS):
        warnings.append("no-fallback")
    return warnings

weak = "You are a support helper. Be helpful and answer questions."
strong = build_instructions(
    persona="You are a support agent for Acme Tools, writing to customers who are not technical.",
    task="Answer questions about orders, delivery, and refunds using the attached policy.",
    context="Refunds are handled under refund-policy.pdf. We never promise delivery dates.",
    fmt="Reply in at most 80 words, then a list of the next steps as three bullets.",
    fallback="If the policy does not cover the question, say so and ask me to escalate. Do not guess.",
)
print(lint_instructions(weak))
print(strong)
print(lint_instructions(strong))
```

- **The task is the one required element.** The function refuses to build instructions without it. Persona, context, format, and fallback are included when supplied and omitted when blank, which matches the guide's advice that not every prompt needs all four.
- **Each section is labelled.** Labels cost a few tokens and make the instructions easy for a person to review and edit later. They also make it obvious when a section is missing.
- **The linter looks for four known weaknesses.** Too few words to describe a job. Phrases that sound like instructions and constrain nothing. No statement of what the output should look like. No statement of what to do when the answer is not known.
- **The weak instructions trip all four.** Ten words, "be helpful", no format, no fallback. The strong version passes cleanly.
- **A clean result is a low bar.** The linter cannot tell whether the instructions are right. It finds the omissions that cause most of the complaints.

Next, predicting what survives the move to a skill, and writing the skill file.

```python
import re

BLOCKED = (".doc", ".xls", ".ppt", ".zip", ".mp3", ".wav", ".mp4", ".mov")

def carry_over(files, limit_mb=100, blocked=BLOCKED):
    kept = [(name, size) for name, size in files if not name.lower().endswith(blocked)]
    dropped = [name for name, size in files if name.lower().endswith(blocked)]
    while sum(size for _, size in kept) > limit_mb:
        largest = max(kept, key=lambda item: item[1])
        kept.remove(largest)
        dropped.append(largest[0])
    return [name for name, _ in kept], dropped

def to_skill_md(name, description, instructions):
    slug = re.sub(r"[^a-z0-9]+", "-", name.lower()).strip("-")
    summary = " ".join(description.split())
    return f"---\nname: {slug}\ndescription: {summary}\n---\n\n{instructions.strip()}\n"

FILES = [("handbook.pdf", 40), ("brand-guide.pdf", 35), ("old-deck.ppt", 20),
         ("training.mp4", 300), ("faq.docx", 30), ("prices.csv", 10)]
print(carry_over(FILES))
print(carry_over([file for file in FILES if file[0] != "brand-guide.pdf"]))
print(to_skill_md("Acme Support Helper!", "Answers customer questions about orders and refunds.\nUse when a customer asks about an order.", strong))
```

- **Unsupported types go first.** The old presentation format and the video are removed whatever their size. Note `.docx` is kept: only the older `.doc` is on the list, and `endswith` distinguishes them.
- **Then the largest file is removed until the rest fits.** The four supported files total 115 MB. The largest is the 40 MB handbook, so it is dropped, leaving 75 MB.
- **The result is the wrong outcome.** The handbook is the file the assistant most needs, and the automatic rule discards it. The second call shows the alternative: remove the brand guide yourself beforehand, and the handbook, FAQ, and price list all survive at 80 MB.
- **`to_skill_md` produces the format from Module 3.5.** The name becomes lowercase with hyphens, as that format requires. The description is collapsed to one line. The Gem's instructions become the body, unchanged.
- **The description needs rewriting for its new job.** A Gem's description was a label for a person browsing a list. A skill's description is how the assistant decides when to apply it, so it should say what the skill does and when to use it.

Finally, a regression test, with stand-ins for the assistant before and after an edit.

```python
def pass_rate(model, cases):
    if not cases:
        return 0.0
    passed = 0
    for prompt, check in cases:
        try:
            passed += 1 if check(model(prompt)) else 0
        except Exception:
            pass
    return passed / len(cases)

def gem_before(prompt):
    if "refund" in prompt.lower():
        return "Refunds take up to 14 days.\n- Check the order number\n- Confirm the return arrived\n- Reply to the customer"
    if "poem" in prompt.lower():
        return "I can only help with Acme orders, delivery, and refunds."
    return "The policy does not cover that. Please escalate."

def gem_after(prompt):                      # edited to sound friendlier; the bullet list was lost
    if "refund" in prompt.lower():
        return "Great question! Refunds take up to 14 days. Let me know if you need anything else."
    return gem_before(prompt)

CASES = [
    ("How long does a refund take?", lambda reply: reply.count("\n- ") == 3),
    ("How long does a refund take?", lambda reply: "14 days" in reply),
    ("Write me a poem about hammers.", lambda reply: "only help" in reply.lower()),
    ("Do you ship to Antarctica?", lambda reply: "does not cover" in reply.lower()),
]
print("before the edit:", pass_rate(gem_before, CASES))
print("after the edit :", pass_rate(gem_after, CASES))
print([round(400 / (400 + 500 * t), 3) for t in (1, 5, 20, 50)])
```

- **Each case pairs a prompt with a check.** The checks are simple functions: three bullets present, the right figure quoted, an out-of-scope request declined, a gap admitted. They cover the three kinds of test from Section 2.
- **A check that crashes counts as a failure.** As with the quality gate in Module 3.9, a test that cannot run must not be counted as passed.
- **The edit lowers the pass rate from 1.0 to 0.75.** The friendlier wording kept the fact and lost the three-bullet format. Without the test set, the first person to notice would be a customer.
- **No cases means nothing was verified.** The function returns zero for an empty test set. Returning a perfect score for no tests would be a comfortable lie.

**Complexity.** `build_instructions` and `lint_instructions` are linear in the text. `carry_over` is quadratic in the number of files at worst. `pass_rate` makes one model call per case.

### Patterns worth building

Whether you build them as Gems now or as skills later, the same handful of assistants repay the effort.

| Pattern | Instructions in one line | Knowledge |
|---|---|---|
| **Editor in your voice** | "Edit what I paste to match these samples. Never add content. List your changes." | Three or four pieces of your own writing |
| **Study partner** | "Quiz me on the attached notes one question at a time. Wait for my answer. Explain mistakes using the notes." | Course notes or a notebook |
| **Policy answerer** | "Answer only from the attached policy. Quote the section. If it is not covered, say so." | The current policy document, linked live |
| **Meeting preparer** | "Given an agenda, list the decisions needed, the questions I should ask, and the risks." | Team goals, last quarter's plan |
| **Brief writer** | "Turn my rough notes into a one-page brief in this template." | The template and two good examples |

Each of these is a procedure more than a persona, which is one more reason the skill form suits them.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

Reports on Gems come mostly from user forums and help communities. The same failure patterns recur.

**"My Gem stopped following its instructions."** Almost always in a long conversation. The instructions are a shrinking share of a growing input. Start a new chat for each task, and put the rules that matter most at the start of the instructions, stated plainly.

**"It is not reading my files."** Users report Gems answering from general knowledge when the answer was in an attached file, and linked files that stop being consulted. Tell the Gem in its instructions to use the files and to name the file it relied on. If a linked file has stopped working, removing and re-attaching it is the commonly reported fix.

**Instructions written once and never tested.** People write a paragraph, try one prompt, and share the Gem with the team. Three test prompts, one typical, one out of scope, one unanswerable, catch most problems in five minutes.

**The rewrite button makes instructions longer, not always better.** Letting Gemini expand your instructions produces fluent, comprehensive text that may include rules you did not intend. Read what it wrote and delete what you do not want.

**Spreadsheets and unusual files.** Users report errors with spreadsheet knowledge files and with scanned documents. As in Module 3.2, ask a question whose answer you know before trusting any file.

**Live files cut both ways.** A linked document that updates the Gem automatically is convenient until someone edits it carelessly. If several people can edit a file your assistant depends on, that file is now part of your assistant's behaviour.

**Shared Gems share their knowledge.** Anyone who can use a shared Gem can ask it about its files. Do not attach anything some of those people should not see.

**Waiting for the automatic conversion.** The conversion to skills drops the largest files first when the total is too big, does not carry over some file types, and loses access to tools that skills do not yet have. An assistant that depended on any of these will change behaviour without an error message. Convert the important ones by hand, early, and test them.

**Converted skills that never trigger.** A Gem did not need a good description, because you opened it deliberately. A skill that is meant to be applied automatically depends on its description, as Module 3.5 explained. Rewrite it: what the skill does, and when to use it.

**Rebuilding the same assistant on every platform.** With three vendors converging on similar skill formats, keep the master copy of your instructions and files somewhere neutral, such as a folder of plain files. Then a change of platform is an import and not a rewrite.

**One giant assistant.** A single Gem instructed to be an editor, a researcher, a coach, and a coder does all four poorly. One job per assistant. With skills, several small ones can be combined in a conversation, which removes the temptation.

**Availability differs by account.** Features arrive at different times for personal, business, and education accounts, and by region and language. If a tutorial shows something you do not have, check the account type before assuming you have done something wrong.

## 5. Active Recall Check & Synthesis Summary

**Summary.** A Gem is a saved, customised version of Gemini with a name, written instructions, and optional knowledge files. It is Google's form of the idea behind custom GPTs and Claude Projects. Its instructions are a prompt sent on every turn, best written with a persona, a task that begins with a verb, context, a format, and a fallback for what the knowledge does not cover. In long chats those instructions become a small share of the input, $I / (I + c \cdot t)$, which is why behaviour drifts and why a new chat restores it. Google is replacing Gems with skills, procedures that can be called into any chat, combined, and applied automatically, in a file format shared with other vendors. The conversion has rules that can change an assistant's behaviour: a size limit under which the largest files are dropped first, file types that do not carry over, and tools not yet available. The dependable approach is to trim and convert by hand, rewrite the description for automatic triggering, and run a small test set before and after.

def build_instructions(persona, task, context="", fmt="", fallback=""):
    """The task is the one required element. Labels make the result easy to review
    and make a missing section obvious."""
    if not task.strip():
        raise ValueError("a task is required")
    sections = [("Persona", persona), ("Task", task), ("Context", context), ("Format", fmt), ("If unsure", fallback)]
    return "\n".join(f"{label}: {text.strip()}" for label, text in sections if text.strip())


# ---------------------------------------------------------------- Step 2
def lint_instructions(text):
    """Four omissions behind most complaints. A clean result is a low bar: the linter
    cannot tell whether the instructions are right, only whether they are incomplete."""
    lowered = text.lower()
    warnings = []
    if len(text.split()) < 20:
        warnings.append("too-short")
    if any(phrase in lowered for phrase in VAGUE):
        warnings.append("vague")
    if not any(word in lowered for word in FORMAT_WORDS):
        warnings.append("no-format")
    if not any(phrase in lowered for phrase in FALLBACK_WORDS):
        warnings.append("no-fallback")
    return warnings


# ---------------------------------------------------------------- Step 3
def carry_over(files, limit_mb=100, blocked=BLOCKED):
    """'Largest first' often discards the most important file. Running this before the
    automatic conversion shows what to trim by hand."""
    kept = [(name, size) for name, size in files if not name.lower().endswith(blocked)]
    dropped = [name for name, size in files if name.lower().endswith(blocked)]
    while sum(size for _, size in kept) > limit_mb:
        largest = max(kept, key=lambda item: item[1])
        kept.remove(largest)
        dropped.append(largest[0])
    return [name for name, _ in kept], dropped


# ---------------------------------------------------------------- Step 4
def to_skill_md(name, description, instructions):
    """The Module 3.5 format: a lowercase hyphenated name, a one-line description, and
    the instructions as the body."""
    slug = re.sub(r"[^a-z0-9]+", "-", name.lower()).strip("-")
    summary = " ".join(description.split())
    return f"---\nname: {slug}\ndescription: {summary}\n---\n\n{instructions.strip()}\n"

def pass_rate(model, cases):
    """A test that cannot run is a failure, and no tests means nothing was verified."""
    if not cases:
        return 0.0
    passed = 0
    for prompt, check in cases:
        try:
            passed += 1 if check(model(prompt)) else 0
        except Exception:
            pass
    return passed / len(cases)
