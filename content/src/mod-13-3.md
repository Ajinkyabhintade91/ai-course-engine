# 100+ AI Terminology Glossary

This glossary collects the terms used throughout the course, grouped into three parts: **core machine learning and language model terms**, **agent, retrieval, and automation terms**, and **business and deployment terms**. Each entry gives a short, plain definition and, where useful, the module where the idea is covered in depth. Use it as a reference while working, as a revision aid, and as a source of plain-language explanations for clients, who will often ask what a word means before they ask what it costs.

Definitions are deliberately brief; the modules give the detail. Where a product or standard is named, the description reflects the time of writing (November 2026).

## 1. First-Principles Mental Model & Intuition

### A trade's own vocabulary

Every trade has its own words. A joiner speaks of tenons, rebates, and kerf; an apprentice who does not know them cannot follow instructions or read a drawing. Learning the vocabulary is not the craft, but the craft cannot be learned without it. AI has an unusually large and fast-changing vocabulary, much of it borrowed from mathematics, computing, and business, and some of it used loosely in marketing. A shared, precise vocabulary lets you read documentation, talk to other builders, and explain things to clients without hand-waving.

```text
 CORE (40)                          AGENTS, RAG, AUTOMATION (35)          BUSINESS AND DEPLOYMENT (30)
 how models are built and run       how models are used in systems        how systems are sold, run, governed
 token, transformer, embedding      prompt, tool calling, RAG, agent      API key, latency, open weights, DPIA
 training, fine-tuning, LoRA        vector database, evaluation set       retainer, scope creep, ROI
 temperature, quantization          prompt injection, workflow, MCP       ideal client profile, case study

 use it: look up a term -> follow its "see also" -> check related terms -> drill with flashcards
```

### Words with precise meanings

Several terms are used loosely in everyday talk but precisely here. An **agent** is not any AI product; it is a model choosing actions in a loop. **Open weights** is not the same as **open source**. A **hallucination** is fluent but unsupported output, not a random error. Getting these right avoids confusion with clients and colleagues.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Part 1: core machine learning and language model terms

- **Artificial intelligence (AI):** systems that perform tasks associated with human intelligence, such as understanding language. Unit 1.
- **Machine learning:** methods that learn patterns from data instead of following hand-written rules.
- **Deep learning:** machine learning with many-layered neural networks.
- **Neural network:** a function built from layers of weighted connections, trained by adjusting the weights.
- **Parameter:** a learned number inside a model; model size is counted in parameters, such as 8 billion.
- **Weight:** a parameter on a connection; "the weights" means the whole trained model.
- **Training:** adjusting weights to reduce error on data.
- **Inference:** using a trained model to produce outputs.
- **Supervised learning:** learning from examples with known answers.
- **Unsupervised learning:** finding structure in data without labels.
- **Reinforcement learning:** learning from rewards for actions.
- **RLHF:** reinforcement learning from human feedback, used to align models with human preferences.
- **Transformer:** the neural architecture behind modern language models, built on attention.
- **Attention:** a mechanism letting each token weigh information from other tokens.
- **Self-attention:** attention within one sequence, the core of the transformer.
- **Token:** a piece of text, often part of a word, that a model reads and writes.
- **Tokenizer:** the component that splits text into tokens and back.
- **Embedding:** a vector of numbers representing meaning, so similar texts have nearby vectors. Module 8.7.
- **Context window:** the maximum number of tokens a model can consider at once, also called context length; in Ollama, `num_ctx`. Module 10.2.
- **Large language model (LLM):** a large transformer trained to predict text.
- **Foundation model:** a large general model adapted to many tasks.
- **Pre-training:** the initial training on very large text collections.
- **Fine-tuning:** further training on examples to adapt behaviour.
- **Instruction tuning:** fine-tuning on instructions and good responses, so a model follows requests.
- **LoRA:** low-rank adaptation, fine-tuning small added matrices instead of all weights.
- **Distillation:** training a smaller model to imitate a larger one. Module 10.9.
- **Quantization:** storing weights with fewer bits to save memory and speed up inference. Module 10.1.
- **GGUF:** a file format for quantized models used by llama.cpp and Ollama.
- **KV cache:** stored keys and values for previous tokens, growing with context. Module 10.10.
- **Temperature:** a sampling setting; higher values make output more varied.
- **Top-p:** sampling from the smallest set of tokens whose probabilities add up to p, also called nucleus sampling.
- **Top-k:** sampling from the k most likely tokens.
- **Greedy decoding:** always choosing the most likely token, equivalent to temperature 0.
- **Hallucination:** fluent output that is false or unsupported by the input.
- **Multimodal:** handling more than one kind of input, such as text and images.
- **Mixture of experts (MoE):** a model with many expert layers, using only some for each token. Module 10.10.
- **Reasoning model:** a model trained to produce intermediate reasoning, sometimes called thinking, before answering.
- **Chain of thought:** step-by-step reasoning written out before an answer.
- **Benchmark:** a standard test for comparing models.
- **Overfitting:** learning the training data too closely and generalising poorly.

### Part 2: agent, retrieval, and automation terms

- **Prompt:** the input given to a model. Unit 5.
- **System prompt:** instructions that set a model's role and rules for a conversation.
- **Prompt engineering:** designing prompts for reliable results.
- **Zero-shot prompting:** asking without examples.
- **Few-shot prompting:** including examples of the desired input and output.
- **Structured output:** responses constrained to a format such as JSON. Module 8.5.
- **JSON Schema:** a standard way to describe the shape of JSON data.
- **Agent:** a model in a loop that chooses actions, uses tools, and observes results. Unit 8.
- **Tool calling:** a model requesting a function call with structured arguments, also called function calling.
- **Agent loop:** the cycle of model decision, tool execution, and result.
- **ReAct:** a pattern alternating reasoning and acting.
- **Orchestrator:** a component or model that plans and assigns subtasks.
- **Multi-agent system:** several agents working together. Module 8.9.
- **Memory:** information an agent keeps across steps or sessions.
- **RAG:** retrieval-augmented generation, fetching relevant documents to ground an answer. Module 8.7.
- **Retrieval:** finding the documents relevant to a query.
- **Chunking:** splitting documents into pieces for retrieval.
- **Vector database:** a store that finds items by embedding similarity, also called a vector store. Module 8.8.
- **Similarity search:** finding the nearest vectors to a query vector.
- **Cosine similarity:** a measure of how closely two vectors point in the same direction.
- **Reranking:** re-ordering retrieved results with a more precise model.
- **BM25:** a classic keyword-based relevance scoring method.
- **Hybrid search:** combining keyword and vector search.
- **Evaluation set:** fixed test cases used to measure quality over time. Module 8.12.
- **LLM-as-judge:** using a model to grade another model's outputs against a rubric.
- **pass^k:** the share of tasks that succeed on every one of k runs. Module 10.12.
- **Guardrail:** a check that blocks or corrects unsafe inputs or outputs.
- **Prompt injection:** untrusted text that tries to override a model's instructions. Module 8.14.
- **Human in the loop:** a person approving or correcting steps. Module 8.11.
- **Workflow:** a fixed sequence of steps, some of which may call a model. Unit 7.
- **Trigger:** the event that starts a workflow.
- **Webhook:** an HTTP request one system sends another when something happens.
- **API:** an application programming interface, how programs call a service.
- **MCP:** the Model Context Protocol, an open protocol for connecting AI applications to tools and data sources.
- **Context engineering:** deciding what information to put in the context window for a task.

### Part 3: business and deployment terms

- **API key:** a secret that identifies and authorises calls to a service; never share it in code or email.
- **Rate limit:** the maximum number of requests a service accepts in a period.
- **Latency:** the time to respond; time to first token matters for chat.
- **Throughput:** how many requests or tokens a system handles per second.
- **Token pricing:** charging per thousand or million input and output tokens.
- **Local model:** a model running on your own hardware. Unit 10.
- **Open weights:** a model whose weights are published, under some licence.
- **Open source:** software or models whose licence meets an open-source definition, allowing free use, study, change, and sharing; some open-weights licences do not qualify. Module 10.6.
- **Ollama:** a tool for running models locally with a server, CLI, and API. Module 10.2.
- **Cloud model:** a model running on a provider's servers.
- **Deployment:** making a system available for real use. Module 9.11.
- **Environment variable:** a setting passed to a program from its environment, often used for configuration and secrets.
- **Monitoring:** watching a system's health and quality over time.
- **Observability:** being able to understand a system's behaviour from its logs, metrics, and traces.
- **Model drift:** changes in quality as data, users, or the model change.
- **Personal data:** information relating to an identifiable person.
- **Data controller:** under the GDPR, the party deciding why and how personal data is processed.
- **Data processor:** under the GDPR, a party processing personal data on a controller's behalf. Module 11.10.
- **DPIA:** a data protection impact assessment, required for high-risk processing. Module 10.13.
- **Data retention:** how long data is kept before deletion.
- **Licence:** the terms under which software or model weights may be used, such as Apache 2.0 or MIT.
- **Productised service:** a service with fixed scope, deliverables, and price. Module 11.6.
- **Retainer:** a monthly fee for ongoing work or support. Module 11.12.
- **Scope creep:** gradual growth of work beyond what was agreed. Module 11.11.
- **Change request:** a written, priced request for out-of-scope work.
- **ROI:** return on investment, net gain divided by cost. Module 11.7.
- **Payback period:** how long savings take to repay the price.
- **Value-based pricing:** pricing by the value delivered to the client rather than by hours.
- **Ideal client profile:** a description of the clients you serve best. Module 11.4.
- **Case study:** a short account of a client's problem, your approach, and the measured result. Module 11.5.

### Using the glossary well

A glossary is most useful when its entries are **connected**: each term lists related terms to read next, and every cross-reference points to a real entry. **Aliases**, such as "function calling" for tool calling or "context length" for context window, let readers find a term under the name they know. Finding which definitions **mention** a term reveals the concepts that depend on it. And **retrieval practice**, Module 12.1, turns a reference into learning: drill definitions as flashcards, answering from memory before checking.

### Complexity

Looking up a term with aliases is linear in the glossary; grouping, cross-reference checks, and mention searches are linear in entries and definition length; drawing a quiz sample is linear in the number of cards.

def lookup(g, term):
    t = term.strip().lower()
    for k, v in g.items():

Next, grouping by category.

```python
def by_category(g):
    out = {}
    for k, v in g.items():
        out.setdefault(v["cat"], []).append(k)
    return {c: sorted(ts, key=str.lower) for c, ts in out.items()}

groups = by_category(GLOSSARY)
print({k: len(v) for k, v in groups.items()}, groups["agents"][:3])
```

- **Twelve core, nine agent, and seven business terms in the sample.**
- **Sorting ignores case,** so "agent" comes before "RAG".

Then, checking cross-references.

```python
def broken_links(g):
    return sorted({s for v in g.values() for s in v["see"] if s not in g})

print(broken_links(GLOSSARY))
print(broken_links({"a": {"cat": "x", "def": "d", "aliases": [], "see": ["b", "a"]}}))
```

- **The sample glossary has no broken links.**
- **A reference to a missing entry is reported,** so it can be added or removed.

Then, finding related terms.

```python
def mentions(g, term):
    pat = re.compile(r"\b" + re.escape(term.lower()) + r"s?\b")
    return sorted(k for k, v in g.items() if k != term and pat.search(v["def"].lower()))

print(mentions(GLOSSARY, "token"))
print(mentions(GLOSSARY, "workflow"))
```

- **Four definitions mention tokens:** KV cache, context window, mixture of experts, and top-p.
- **A plural "s" is allowed;** whole-word matching avoids false hits inside other words.

Finally, a reproducible flashcard quiz.

```python
def quiz(g, n, seed):
    rng = random.Random(seed)
    return [(g[t]["def"], t) for t in rng.sample(sorted(g), n)]

def grade(cards, answers):
    correct = sum(1 for (d, t), a in zip(cards, answers) if lookup(GLOSSARY, a) and lookup(GLOSSARY, a)[0] == t)
    return correct, round(correct / len(cards) * 100)

cards = quiz(GLOSSARY, 3, 7)
print([t for _, t in cards])
print(grade(cards, ["eval set", "nonsense", "HALLUCINATION"]))
```

- **The seed makes the quiz reproducible:** evaluation set, ROI, hallucination.
- **Answers are graded through lookup,** so an alias such as "eval set" or different capitalisation still counts.
- **Two of three correct, 67 per cent.**

**Complexity.** Linear in the glossary size.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Using terms loosely with clients.** "Agent" for any chatbot confuses expectations. Be precise.

**Jargon in proposals.** Translate terms into outcomes.

**Open weights versus open source.** Different things. Check the licence.

**"Hallucination" for every error.** Use it for unsupported content.

**Missing aliases.** Readers search for the name they know.

**Broken cross-references.** Check before publishing.

**Copying definitions from marketing pages.** They oversell. Use neutral wording.

**Outdated product terms.** Names change. Date your glossary.

**Memorising without using.** Practise recall and apply terms in projects.

**Too many terms for clients.** Give them the thirty they need.

**Inconsistent spelling.** Choose one, list the other as an alias.

**Assuming shared meaning.** Define terms at the start of a project.

## 5. Active Recall Check & Synthesis Summary

**Summary.** This glossary defines over one hundred terms in three parts: core machine learning and language model terms such as tokens, transformers, embeddings, fine-tuning, quantization, and sampling settings; agent, retrieval, and automation terms such as prompts, tool calling, RAG, vector databases, evaluation sets, prompt injection, workflows, and MCP; and business and deployment terms such as API keys, latency, open weights, data protection roles, DPIAs, retainers, scope creep, and ROI. **Question 1.** A client says they want "an agent" to send weekly sales summaries. Using the glossary's definitions of agent and workflow, explain what they probably need and why the distinction matters.

<details>
<summary>View Answer</summary>

The glossary defines an agent as a model in a loop that chooses actions, uses tools, and observes results, and a workflow as a fixed sequence of steps, some of which may call a model. A weekly sales summary has a fixed trigger, every Monday, and fixed steps: read the sales export, summarise it with a model, and email it, so it is a workflow, not an agent. The distinction matters for cost, reliability, and expectations: a workflow is predictable, cheaper to build and run, and easier to test, while an agent adds flexibility the task does not need and more ways to go wrong, Module 13.2. Explaining this in plain terms also sets the right expectations: the client gets a dependable report, not an autonomous assistant. If they later want something that decides what to investigate, an agent might then be appropriate.

</details>

**Question 2.** Using `lookup` and `broken_links`, explain why aliases and cross-reference checks make a glossary more useful.

<details>
<summary>View Answer</summary>

Readers search for the term they already know, which is often not the one the glossary uses. `lookup` finds "context window" when someone types "num_ctx", the Ollama parameter name, and "tool calling" when someone types "Function Calling", ignoring case, so readers are not told a term is missing when it is only named differently. Cross-references turn a list into a network: each entry points to related terms to read next, such as RAG to embedding and vector database. But a reference to an entry that does not exist is a dead end; `broken_links` lists every see-also target missing from the glossary, so it can be added or the reference removed before publishing. On the sample glossary it returns nothing; on a glossary referencing a missing "b", it reports "b".

</details>

**Question 3.** Sam wants to learn the glossary rather than just refer to it. Using `quiz` and `grade`, and Module 12.1, describe a routine.

<details>
<summary>View Answer</summary>

Module 12.1 explains that recall practice, answering from memory before checking, strengthens memory more than rereading, and that spacing practice over days beats cramming. `quiz` turns the glossary into flashcards: it shows definitions and asks for the term, and its seed makes each quiz reproducible, so Sam can seed it with the date and get a different but repeatable set each day. `grade` checks answers through `lookup`, so aliases such as "eval set" and differences of capitalisation still count, and reports a percentage. A routine of three cards a day in the ten-minute review block, with missed terms added to the next day's cards, covers the glossary in about five weeks and revisits weak terms more often. Using the terms in projects and client explanations completes the learning.

</details>

# ---------------------------------------------------------------- Step 1
def lookup(g, term):
    """Find a term by name or alias, ignoring case."""
    t = term.strip().lower()
    for k, v in g.items():
        if k.lower() == t or t in (a.lower() for a in v["aliases"]):
            return k, v["def"]
    return None


# ---------------------------------------------------------------- Step 2
def by_category(g):
    """Terms grouped by category, sorted ignoring case."""
    out = {}
    for k, v in g.items():
        out.setdefault(v["cat"], []).append(k)
    return {c: sorted(ts, key=str.lower) for c, ts in out.items()}


# ---------------------------------------------------------------- Step 3
def broken_links(g):
    """Cross-references that point to missing entries."""
    return sorted({s for v in g.values() for s in v["see"] if s not in g})


# ---------------------------------------------------------------- Step 4
def mentions(g, term):
    """Entries whose definitions mention a term."""
    pat = re.compile(r"\b" + re.escape(term.lower()) + r"s?\b")
    return sorted(k for k, v in g.items() if k != term and pat.search(v["def"].lower()))


# ---------------------------------------------------------------- Step 5
def quiz(g, n, seed):
    """A reproducible set of flashcards: definition then term."""
    rng = random.Random(seed)
    return [(g[t]["def"], t) for t in rng.sample(sorted(g), n)]


def grade(cards, answers):
    """Score answers, accepting aliases and any capitalisation."""
    correct = sum(1 for (d, t), a in zip(cards, answers) if lookup(GLOSSARY, a) and lookup(GLOSSARY, a)[0] == t)
    return correct, round(correct / len(cards) * 100)
