# Project 2: Full Web App, "Client Lead Tracker"

The second project builds the application specified in Module 9.8: a **Client Lead Tracker** where the tool shop's sales team records leads, moves them through a pipeline from new to won or lost, and sees totals and a forecast. It is a real web application: a database, validated create, read, update, and delete operations, user accounts with passwords, role-based access, a pipeline view, tests, and a deployment.

An AI app builder or coding agent can generate most of the code. The project's lessons are in what you must still decide and verify: requirements precise enough to test, validation that protects the data, authentication done correctly, numbers on the dashboard that mean what people think they mean, and evidence that the tests cover the requirements before anything is deployed.

## 1. First-Principles Mental Model & Intuition

### A builder, an inspector, and a building code

A house built by a fast, capable contractor still needs drawings agreed in advance, inspections at each stage, and a building code that some things must meet whatever the contractor prefers: fire exits, wiring standards, load-bearing walls. In this project, the **user stories with acceptance criteria** are the drawings, the **tests** are the inspections, and **security and data rules**, validation, password hashing, access control, are the building code. The AI is the contractor: fast, capable, and not the one who signs off.

```text
   REQUIREMENTS   user stories + Given/When/Then criteria  ------> test names (one per criterion)
        |
   DATA           leads(id, name, email unique, stage enum, value >= 0, owner, created_at, updated_at)
        |
   CRUD           create/update validate every field; duplicates rejected; timestamps maintained
        |
   AUTH           passwords: salted, slow hash (PBKDF2/Argon2id/scrypt); constant-time compare; sessions expire
   ACCESS         roles + ownership on every route (Module 9.8)
        |
   VIEWS          pipeline board by stage; totals; weighted forecast; win rate
        |
   TESTS          unit -> integration -> a few end-to-end; coverage of requirements, not just lines
        |
   DEPLOY         pipeline: build, test, staging, smoke test, production (Module 9.11)
```

### Done means verified

"The AI says it's done" is not done. Done is: every acceptance criterion has a passing test, every requirement is covered by at least one test, the security rules are checked, and a smoke test passes on the deployed app.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Requirements as user stories

A **user story** states who wants what and why: "As a salesperson, I want to add a lead, so that it is not lost in my inbox." On its own a story is vague; **acceptance criteria** make it testable. The widely used **Given/When/Then** form, described by Martin Fowler, splits each criterion into a starting state, an action, and an expected outcome: "Given I am signed in, when I submit a lead with a valid email, then it appears in New." Each criterion maps directly to one test, and a story with no criteria, or criteria not in this form, such as "export should be fast", cannot be tested until it is rewritten, for example "Given 1,000 leads, when I export, then the file downloads within 5 seconds".

### Validated CRUD

Every write to the database is validated on the server: required fields present, formats correct, values in range, and uniqueness rules respected. For the lead tracker: a name is required; the email must look like an email and be unique, compared without regard to case so `PRIYA@` and `priya@` are the same; the stage must be one of the defined stages; the value must not be negative. Validation returns **all** errors at once, so a user fixing a form sees every problem, and an invalid update leaves the stored record unchanged. Each record keeps `created_at` and `updated_at` timestamps for auditing.

### Authentication: storing passwords

Passwords are never stored in plain text, and never merely encrypted, since anything that can be decrypted can be leaked. They are **hashed** with a slow, salted function:

- A **salt**, random bytes unique to each password, means identical passwords produce different hashes, which defeats precomputed tables.
- A **slow** function with many iterations makes guessing expensive: if checking one guess costs $t$ seconds, an attacker testing $N$ guesses needs $N t$ seconds, so raising the cost per guess from microseconds to tens of milliseconds multiplies an offline attack's cost by tens of thousands.
- **Constant-time comparison**, such as Python's `hmac.compare_digest`, avoids leaking information through how long a comparison takes.

OWASP's Password Storage Cheat Sheet recommends Argon2id first, then scrypt, and, where FIPS-140 compliance is required, PBKDF2 with HMAC-SHA-256 and a work factor of 600,000 or more iterations. Python's standard library provides PBKDF2 as `hashlib.pbkdf2_hmac`, which the lab uses. The stored value records the algorithm, iteration count, salt, and digest together, so the work factor can be raised later and old hashes still verified. In practice, use a well-maintained authentication library or provider rather than writing your own, and use code like the lab's to understand what that library must do.

### Sessions

After login, the server issues a **session token**: long, random, unguessable, generated with a cryptographic random source such as Python's `secrets` module, sent in a cookie marked `Secure` and `HttpOnly`, and expiring after inactivity. OWASP's Session Management Cheat Sheet covers these properties. Logging out must invalidate the token on the server.

### The pipeline view and forecast

The pipeline board groups leads by stage with a count and total value per stage. A **weighted forecast** estimates expected revenue from open leads by multiplying each lead's value by the probability that its stage converts:

$$\text{forecast} = \sum_{\ell \in \text{open}} v_\ell \cdot P(\text{stage}_\ell)$$

With probabilities of 0.1 for new, 0.25 for contacted, and 0.5 for quoted, open leads worth 3,000 in new, 4,000 in contacted, and 4,800 in quoted forecast $300 + 1{,}000 + 2{,}400 = 3{,}700$. The **win rate** is won divided by closed, won plus lost, not won divided by all leads, since open leads have not been decided yet. The probabilities should come from the team's own history and be revisited; a forecast is only as good as its weights.

### Testing

The **test pyramid**, explained in Ham Vocke's article on martinfowler.com, recommends many fast **unit tests** of individual functions, such as validation and the forecast; fewer **integration tests** of components working together, such as an API route writing to a test database; and a few **end-to-end tests** of whole user journeys through the browser. AI agents write tests readily; check that they test behaviour from the acceptance criteria, not just the implementation as written.

**Coverage** is usually reported as lines of code executed by tests, but for a project like this a more useful measure is **requirement coverage**: the fraction of requirements with at least one test,

$$\text{coverage} = 1 - \frac{|\text{uncovered requirements}|}{|\text{requirements}|}$$

and the list of uncovered requirements is the to-do list. Security requirements, such as logout and role permissions, are the ones most often left uncovered.

### Deployment

Deploy through the pipeline of Module 9.11: tests on every push, a staging deployment, a smoke test that logs in, creates a lead, moves it, and deletes it, then production from main only. Database migrations follow Module 9.11's add-first discipline.

### Complexity

Story parsing is linear in criteria. Each CRUD validation scans the leads for duplicate emails, linear in leads, constant with a unique index in a real database. Password hashing costs the chosen number of iterations, deliberately. The pipeline view and forecast are linear in leads. Coverage is linear in tests and requirements.

First, turning stories into tests.

```python
import hashlib
import hmac
import re
import secrets

def stories_to_tests(stories):
    tests, gaps = [], []
    for story in stories:
        if not story["criteria"]:
            gaps.append(f"{story['id']}: no acceptance criteria")
        for i, criterion in enumerate(story["criteria"], 1):
            m = re.match(r"Given (.+?), when (.+?), then (.+)", criterion, re.I)
            if not m:
                gaps.append(f"{story['id']} criterion {i}: not in Given/When/Then form")
                continue
            slug = re.sub(r"[^a-z0-9]+", "_", m.group(3).lower()).strip("_")
            tests.append(f"test_{story['id'].lower()}_{slug}")
    return tests, gaps

STORIES = [{"id": "LT1", "story": "As a salesperson I want to add a lead",
            "criteria": ["Given I am signed in, when I submit a lead with a valid email, then it appears in New",
                         "Given I am signed in, when I submit a duplicate email, then I see an error"]},
           {"id": "LT2", "story": "As a viewer I want to see the pipeline", "criteria": []},
           {"id": "LT3", "story": "As an admin I want to export", "criteria": ["Export should be fast"]}]
print(stories_to_tests(STORIES))
```

- **Each Given/When/Then criterion becomes a test name from its outcome.** `test_lt1_it_appears_in_new`.
- **LT2 has no criteria; LT3's criterion is not testable as written.** Both are reported before any code is generated.

Next, validated CRUD.

```python
STAGES = ["new", "contacted", "quoted", "won", "lost"]
EMAIL = re.compile(r"^[^@\s]+@[^@\s]+\.[a-z]{2,}$", re.I)

class LeadStore:
    def __init__(self):
        self.rows, self.next_id = {}, 1

    def validate(self, data):
        errors = []
        if not data.get("name", "").strip():
            errors.append("name is required")
        if not EMAIL.match(data.get("email", "")):
            errors.append("email is invalid")
        elif any(r["email"].lower() == data["email"].lower() and r["id"] != data.get("id") for r in self.rows.values()):
            errors.append("email already exists")
        if data.get("stage", "new") not in STAGES:
            errors.append("unknown stage")
        if data.get("value", 0) < 0:
            errors.append("value must not be negative")
        return errors

    def create(self, data, now):
        errors = self.validate(data)
        if errors:
            return None, errors
        row = {"id": self.next_id, "stage": "new", "value": 0, **data, "created_at": now, "updated_at": now}
        self.rows[self.next_id] = row
        self.next_id += 1
        return row, []

    def update(self, lead_id, changes, now):
        if lead_id not in self.rows:
            return None, ["not found"]
        merged = {**self.rows[lead_id], **changes}
        errors = self.validate(merged)
        if errors:
            return None, errors
        merged["updated_at"] = now
        self.rows[lead_id] = merged
        return merged, []

    def delete(self, lead_id):
        return self.rows.pop(lead_id, None) is not None

store = LeadStore()
print(store.create({"name": "Harper Joinery", "email": "priya@harperjoinery.example", "value": 4800}, now=1))
print(store.create({"name": "", "email": "nope", "value": -5}, now=2))
print(store.create({"name": "Dup", "email": "PRIYA@harperjoinery.example"}, now=3))
print(store.update(1, {"stage": "maybe"}, now=6))
```

- **All errors are returned together.** The empty name, bad email, and negative value appear at once.
- **Duplicates are compared case-insensitively.** `PRIYA@` is the same customer.
- **An invalid update returns errors and leaves the stored lead unchanged.** The merged copy is validated before it replaces anything.
- **Defaults and timestamps are set on the server.** New leads start in `new`; updates bump `updated_at`.

Then, password hashing.

```python
def hash_password(password, salt=None, iterations=600_000):
    salt = salt or secrets.token_bytes(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, iterations)
    return f"pbkdf2_sha256:{iterations}:{salt.hex()}:{digest.hex()}"

def verify_password(password, stored):
    algorithm, iterations, salt_hex, digest_hex = stored.split(":")
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt_hex), int(iterations))
    return hmac.compare_digest(digest.hex(), digest_hex)

stored = hash_password("correct horse battery", iterations=1000)
print(stored.split(":")[:2], verify_password("correct horse battery", stored), verify_password("wrong", stored))
print(hash_password("same", iterations=1000) != hash_password("same", iterations=1000))
```

- **A fresh random 16-byte salt per password.** The same password hashed twice gives different stored values.
- **The stored string records algorithm, iterations, salt, and digest.** Verification reads the iteration count from it, so the default can rise later.
- **The default is 600,000 iterations, OWASP's figure for PBKDF2-HMAC-SHA256.** The example uses 1,000 only to run quickly.
- **`hmac.compare_digest` compares in constant time.**

Then, the pipeline view.

```python
PROBABILITY = {"new": 0.1, "contacted": 0.25, "quoted": 0.5, "won": 1.0, "lost": 0.0}

def pipeline(leads):
    view = {stage: {"count": 0, "value": 0} for stage in STAGES}
    for lead in leads:
        view[lead["stage"]]["count"] += 1
        view[lead["stage"]]["value"] += lead["value"]
    forecast = round(sum(l["value"] * PROBABILITY[l["stage"]] for l in leads if l["stage"] not in ("won", "lost")), 2)
    closed = view["won"]["count"] + view["lost"]["count"]
    win_rate = round(view["won"]["count"] / closed, 3) if closed else None
    return view, forecast, win_rate

LEADS = [{"stage": "new", "value": 1000}, {"stage": "new", "value": 2000}, {"stage": "contacted", "value": 4000},
         {"stage": "quoted", "value": 4800}, {"stage": "won", "value": 3000}, {"stage": "won", "value": 1500},
         {"stage": "lost", "value": 2500}]
print(pipeline(LEADS))
```

- **Every stage appears, even when empty, so the board has stable columns.**
- **The forecast covers open leads only: 300 plus 1,000 plus 2,400, 3,700.** Won revenue is already banked, not forecast.
- **The win rate is 2 won of 3 closed, 0.667.** Dividing by all seven leads would understate it.

Finally, requirement coverage.

```python
def coverage(requirements, tests):
    covered = {r for t in tests for r in t["covers"]}
    missing = [r for r in requirements if r not in covered]
    return (round(1 - len(missing) / len(requirements), 3) if requirements else 1.0), missing

REQUIREMENTS = ["create lead", "validate email", "reject duplicate", "move stage", "login", "logout", "role permissions", "pipeline totals"]
TESTS = [{"name": "test_create", "covers": ["create lead", "validate email"]}, {"name": "test_dup", "covers": ["reject duplicate"]},
         {"name": "test_login", "covers": ["login"]}, {"name": "test_pipeline", "covers": ["pipeline totals", "move stage"]}]
print(coverage(REQUIREMENTS, TESTS))
```

- **Six of eight requirements are covered: 0.75.**
- **Logout and role permissions have no tests.** Exactly the security requirements Module 9.8 warned about; write those tests before deploying.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Stories without criteria.** "Users can manage leads" cannot be tested. Write Given/When/Then.

**Untestable criteria.** "Fast" and "intuitive" are not checks. Add numbers and observable outcomes.

**Validation only in the browser.** Requests can bypass forms. Validate on the server.

**Case-sensitive uniqueness.** `Priya@` and `priya@` become two customers. Normalise before comparing.

**Partial validation errors.** Users fix one error, submit, and find the next. Return all errors.

**Hand-rolled authentication.** Subtle mistakes are common. Use a maintained library and understand what it does.

**Fast hashes for passwords.** Plain SHA-256 is fast, which is the problem. Use a slow, salted algorithm.

**Plain string comparison of secrets.** Timing differences leak. Use constant-time comparison.

**Win rate over all leads.** Open leads are undecided. Divide won by closed.

**Forecast weights from thin air.** Made-up probabilities make a precise-looking guess. Use your own history.

**Line coverage as the goal.** High line coverage can miss whole requirements. Measure requirement coverage.

**Tests written after the fact by the AI, from the code.** They test what the code does, not what it should do. Write tests from the criteria first.

**Question 1.** The AI-generated version of the tracker stores passwords as plain SHA-256 hashes and compares them with `==`. Explain both problems and what `hash_password` and `verify_password` do differently.

<details>
<summary>View Answer</summary>

Plain SHA-256 is designed to be fast, so an attacker who steals the database can test billions of guesses per second on ordinary hardware, and without a salt, identical passwords produce identical hashes, so one cracked hash reveals every account with that password and precomputed tables work against all of them. `hash_password` fixes both: it generates a random 16-byte salt per password with the `secrets` module, so the same password produces different stored values, and it uses PBKDF2-HMAC-SHA256 with 600,000 iterations by default, OWASP's figure for PBKDF2 where FIPS compliance is required, so each guess costs hundreds of thousands of hash computations instead of one. It also stores the algorithm, iteration count, salt, and digest together, so `verify_password` can recompute the hash with the same parameters and the iteration count can be raised later. Comparing with `==` can stop at the first differing character, so response times can leak how much of a value matched; `verify_password` uses `hmac.compare_digest`, which takes the same time regardless. OWASP prefers Argon2id where available. In production the team should use a maintained authentication library and treat this code as an explanation of what that library must do.

</details>

**Question 2.** The sales manager's dashboard shows a win rate of 28.6 percent and a forecast of 8,200 from the lab's leads. Use `pipeline` to find what was computed wrongly and give the correct figures.

<details>
<summary>View Answer</summary>

There are seven leads: two won, one lost, and four still open. A win rate of 28.6 percent is 2 divided by 7, won over all leads, which counts the four undecided leads as if they had been lost; `pipeline` divides won by closed, 2 out of 3, giving 0.667, or 66.7 percent. A forecast of 8,200 is 3,700 plus 4,500, which adds the value of the won leads, already banked revenue, to the expected value of the open ones; `pipeline` forecasts open leads only: new leads worth 3,000 at 0.1 give 300, contacted at 4,000 times 0.25 gives 1,000, and quoted at 4,800 times 0.5 gives 2,400, for 3,700. Won value should be shown separately as closed revenue, 4,500. Both errors make the dashboard misleading in opposite directions: the win rate looks worse than it is and the forecast looks better. The stage probabilities should come from the team's own history, for example the share of quoted leads that were eventually won, and be revisited quarterly, since a forecast is only as reliable as its weights.

</details>

**Question 3.** The AI reports 92 percent line coverage and says the tracker is ready to deploy. Use `stories_to_tests` and `coverage` to explain why that is not enough, and what to do before deploying.

<details>
<summary>View Answer</summary>

Line coverage measures which lines the tests executed, not whether the requirements are tested: the tests can run every line of the login code without ever checking that logout invalidates the session, or that a viewer is refused an update. `coverage` against the requirement list shows 0.75, with logout and role permissions untested, the security requirements whose failure would let the wrong people see or change data. `stories_to_tests` also shows gaps before coverage can even be measured: story LT2 has no acceptance criteria and LT3's criterion, "Export should be fast", is not testable as written, so some requirements cannot have meaningful tests yet. Before deploying: add Given/When/Then criteria for LT2, such as "Given I am a viewer, when I open the pipeline, then I see all stages with counts", and rewrite LT3 with a measurable threshold; write tests for logout and for every role and action, Module 9.8, ideally before asking the AI to change any code; bring requirement coverage to 100 percent; and run the staging smoke test through the deployment pipeline, Module 9.11. Line coverage can stay as a secondary signal for untested code paths.

# ---------------------------------------------------------------- Step 1
def stories_to_tests(stories):
    """One test per Given/When/Then criterion; everything else is a gap."""
    tests, gaps = [], []
    for story in stories:
        if not story["criteria"]:
            gaps.append(f"{story['id']}: no acceptance criteria")
        for i, criterion in enumerate(story["criteria"], 1):
            m = re.match(r"Given (.+?), when (.+?), then (.+)", criterion, re.I)
            if not m:
                gaps.append(f"{story['id']} criterion {i}: not in Given/When/Then form")
                continue
            slug = re.sub(r"[^a-z0-9]+", "_", m.group(3).lower()).strip("_")
            tests.append(f"test_{story['id'].lower()}_{slug}")
    return tests, gaps


# ---------------------------------------------------------------- Step 2
class LeadStore:
    """Validated create, update, delete with timestamps."""

    def __init__(self):
        self.rows, self.next_id = {}, 1

    def validate(self, data):
        errors = []
        if not data.get("name", "").strip():
            errors.append("name is required")
        if not EMAIL.match(data.get("email", "")):
            errors.append("email is invalid")
        elif any(r["email"].lower() == data["email"].lower() and r["id"] != data.get("id") for r in self.rows.values()):
            errors.append("email already exists")
        if data.get("stage", "new") not in STAGES:
            errors.append("unknown stage")
        if data.get("value", 0) < 0:
            errors.append("value must not be negative")
        return errors

    def create(self, data, now):
        errors = self.validate(data)
        if errors:
            return None, errors
        row = {"id": self.next_id, "stage": "new", "value": 0, **data, "created_at": now, "updated_at": now}
        self.rows[self.next_id] = row
        self.next_id += 1
        return row, []

    def update(self, lead_id, changes, now):
        if lead_id not in self.rows:
            return None, ["not found"]
        merged = {**self.rows[lead_id], **changes}
        errors = self.validate(merged)
        if errors:
            return None, errors
        merged["updated_at"] = now
        self.rows[lead_id] = merged
        return merged, []

    def delete(self, lead_id):
        return self.rows.pop(lead_id, None) is not None

def hash_password(password, salt=None, iterations=600_000):
    """Salted, slow, self-describing."""
    salt = salt or secrets.token_bytes(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, iterations)
    return f"pbkdf2_sha256:{iterations}:{salt.hex()}:{digest.hex()}"


def verify_password(password, stored):
    """Recompute with the stored parameters; compare in constant time."""
    algorithm, iterations, salt_hex, digest_hex = stored.split(":")
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), bytes.fromhex(salt_hex), int(iterations))
    return hmac.compare_digest(digest.hex(), digest_hex)


# ---------------------------------------------------------------- Step 4
def pipeline(leads):
    """Totals by stage, a forecast of open leads, a win rate over closed ones."""
    view = {stage: {"count": 0, "value": 0} for stage in STAGES}
    for lead in leads:
        view[lead["stage"]]["count"] += 1
        view[lead["stage"]]["value"] += lead["value"]
    forecast = round(sum(l["value"] * PROBABILITY[l["stage"]] for l in leads if l["stage"] not in ("won", "lost")), 2)
    closed = view["won"]["count"] + view["lost"]["count"]
    win_rate = round(view["won"]["count"] / closed, 3) if closed else None
    return view, forecast, win_rate

def coverage(requirements, tests):
    """Requirement coverage, and the to-do list it implies."""
    covered = {r for t in tests for r in t["covers"]}
    missing = [r for r in requirements if r not in covered]
    return (round(1 - len(missing) / len(requirements), 3) if requirements else 1.0), missing
