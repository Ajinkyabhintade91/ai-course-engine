# Prompting for AI Agents

A chat prompt asks for one answer. An agent prompt starts a process: the model chooses an action, sees the result, chooses another, and continues, perhaps for hundreds of steps, with nobody reading along. Modules 3.4 and 3.7 showed agents at work. This chapter is about what to write for them.

Three kinds of text steer an agent, and all three are prompts. The **instructions** say what the goal is, how far the agent may go, and when to stop. The **tool descriptions** are what the agent reads to decide which tool to use and how. And the **delegation brief** is the prompt one agent writes for another. The chapter covers each, and then the guidance that a long-running task needs, where the work outlasts the context window.

## 1. First-Principles Mental Model & Intuition

### Sending someone on an errand

Compare two ways of getting something done.

In the first, a colleague sits beside you. You ask for one thing, look at the result, and ask for the next. If they misunderstood, you see it at once.

In the second, you send a capable freelancer to another city with a company card and a list of contacts. You will not be there. They will make dozens of decisions you did not foresee. Before they leave, they need to know what you are trying to achieve and how they will recognise that it is done. They need to know what they may spend, which decisions are theirs, and which need a phone call to you. And they need to know what to do when something goes wrong.

A chat prompt is the first arrangement. An agent prompt is the second. You are writing a policy for decisions you cannot see being made.

### The loop, and where the prompts sit

```text
        INSTRUCTIONS                       TOOL DESCRIPTIONS
        goal, done-when, limits,           what each tool does,
        what needs approval                when to use it, its arguments
                |                                    |
                v                                    v
        +----------------------------------------------------+
        |   MODEL:  given everything so far, what next?      | <-----+
        +----------------------------------------------------+       |
             |              |               |                        |
             v              v               v                        |
         call a tool     ask a person    finish                      |
             |                                                       |
             v                                                       |
        TOOL RESULT  ------------------------------------------------+
        (size-capped, with a hint if cut)

        OUTSIDE THE MODEL:   step limit   cost limit   loop detector   permission checks
```

Everything above the loop is text the model reads. Everything on the bottom line is code that the model cannot argue with. An agent needs both, for the reason Module 5.7 gave: an instruction is advice, and a control is something outside the model.

### Why mistakes cost more here

In a chat, a mistake is one bad answer on the screen. In an agent, a mistake at step 4 is the input to step 5. If each step goes right 97 percent of the time, a run of 30 steps goes right throughout only about 40 percent of the time. And the agent acts: a wrong belief can become a sent email or a deleted file.

That is why agent prompts are so concerned with three things that a chat prompt hardly mentions: how to check the work, when to stop, and when to ask.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### How an agent prompt differs

| | A chat prompt | An agent prompt |
|---|---|---|
| Asks for | One response | A sequence of actions |
| Is read | Once | On every step of the loop |
| Describes | The output wanted | The goal, and how to tell it is reached |
| Errors | Visible immediately | Carried forward and built on |
| Ends | When the reply ends | When a stop condition is met |
| Risk | A wrong answer | A wrong action |
| Cost | One request | Many, each with a growing context |

On the last row, Anthropic reports from its own systems that an agent uses about four times the tokens of a chat interaction, and a multi-agent system about fifteen times. An agent is the expensive way to do something. Its instructions should make it stop as soon as the job is done.

### The four parts of agent instructions

**A goal with a definition of done.** "Tidy up the billing module" has no end. "Every function in the billing module has a docstring, and the test suite passes" can be checked. The definition of done should be something the agent can verify with a tool, because an agent with no check available will decide for itself that it has finished. Anthropic's write-up on long-running agents names this as the main failure it saw: declaring victory early.

**Tools, and guidance on using them.** Which tools exist, which to prefer, and what each is for. Most of this belongs in the tool descriptions, covered below.

**Stopping conditions.** There are four ways a run should end, and the instructions should name each.

| Stop because | The instruction says | The harness enforces |
|---|---|---|
| Done | "When the tests pass, summarise what you changed and stop" | The loop ends when the model finishes |
| Out of budget | "You have at most 30 tool calls" | A limit on turns, cost, or time |
| Stuck | "If the same action fails twice, stop and report" | A detector for repeated actions |
| Needs a person | "If the task needs a refund above USD 100, ask" | A permission check before the action |

The right-hand column matters as much as the middle one. Agent frameworks provide these limits, and they are often off by default: in Anthropic's agent toolkit, at the time of writing (November 2026), the limits on turns and on spending both default to none. A run that reaches a limit ends with an error result that says which limit it was. Set the limits, and handle that result.

**Autonomy.** What the agent may do without asking, what it must ask about first, and what it must never do. The useful dividing line is reversibility. Reading, searching, and drafting can be undone or ignored. Sending, paying, deleting, and publishing cannot.

### Reliability over a run

If each step is right with probability $p$, a run of $n$ steps is right throughout with probability $p^{n}$, as in Module 5.8. For an agent, a second version of the same arithmetic matters. If a whole task succeeds with probability $q$ on any one run, it succeeds on all of $k$ runs with probability

$$
q^{k}
$$

An agent that completes a task 80 percent of the time completes it eight times in a row only about 17 percent of the time, since $0.8^{8} \approx 0.168$. A demonstration that worked once says little about a process that must work every day.

The length of task that models can complete has been growing fast. The research group METR measures the duration, in human working time, of tasks that models complete with 50 percent reliability, and found it doubling roughly every seven months. If $h_{0}$ is the figure now, then after $t$ months it is about

$$
h(t) = h_{0} \times 2^{\,t/7}
$$

which is eightfold in 21 months. The measure is at 50 percent reliability. The length of task a model completes dependably is much shorter, and that is the figure a product needs.

### Tool descriptions are prompts

An agent chooses its tools by reading their names and descriptions. A vague description is a vague instruction, read on every step. Anthropic's guidance on writing tools is to describe each one as you would to a new member of staff. Its recommendations are concrete.

| Recommendation | Example |
|---|---|
| Name tools with their system as a prefix | `orders_search` and `inventory_search`, not two tools called `search` |
| Say what the tool does and when to use it | "Use this when the customer has not given an order number" |
| Say what it returns | "Returns at most 10 orders, newest first" |
| Give arguments unambiguous names | `customer_id`, not `user` or `id` |
| Describe every argument, with its format | "Earliest order date as YYYY-MM-DD" |
| Make mistakes hard | Require an absolute file path, so a relative one cannot go wrong |
| Return names a model can read | A product name, not only an internal identifier |
| Make errors say what to do | "No customer C-9. Customer numbers look like C-10293" |

The same source reports that its own coding tool stopped making a class of file errors once a tool was changed to require absolute paths. That is the principle in the sixth row: change the tool so that the mistake cannot be made, and the prompt no longer has to warn against it.

Tool descriptions should be tested like any prompt. Anthropic describes having a model use a set of tools, read where it went wrong, and rewrite the descriptions, which cut the time to complete tasks by 40 percent in one case.

### Tool results are part of the context

Whatever a tool returns goes into the agent's context and is paid for on every later step. A search that returns 5,000 rows can exhaust the window in one call.

Two practices follow. **Cap the size** of every result. Anthropic's coding tool limits a tool's response to 25,000 tokens by default. And when a result is cut, **say so, and say how to narrow the request**. An agent that receives the first 50 rows with no notice believes it has all of them. An agent told "showing 50 of 5,000, add a date range" asks a better question.

A related practice is to let the agent choose how much detail it gets. In Anthropic's example, a tool's concise response used 72 tokens where its detailed one used 206.

### Delegation briefs

When one agent hands part of a task to another, it writes a prompt. The sub-agent starts with nothing: it has not seen the conversation, the user's request, or what the other sub-agents are doing. Everything it needs must be in the brief.

Anthropic's account of its research system lists what a brief needs.

| Part | Without it |
|---|---|
| **Objective**: what to find out or produce, specifically | The sub-agent solves a different problem |
| **Output format**: what to hand back | The lead agent cannot combine the results |
| **Tools and sources**: which to use and which to trust | It uses the wrong tool or poor sources |
| **Boundaries**: what is out of scope, and what others are covering | Two sub-agents do the same work |

The same account gives rules for effort, written into the lead agent's prompt because agents are poor at judging it: one agent making three to ten tool calls for a simple fact, two to four sub-agents with ten to fifteen calls each for a comparison, and more than ten sub-agents only for complex research. Before those rules, its agents would start 50 sub-agents for a simple question, or search without end for sources that did not exist.

Delegation has a further use. A sub-agent works in its own context and returns only a summary, which keeps the lead agent's context clear.

A 2025 study of multi-agent systems, drawing on more than 1,600 recorded runs from seven frameworks, catalogued 14 distinct ways they fail, in three groups: faults in the system's design, misalignment between agents, and failures to verify the work. Most of them are faults in what one agent told another.

### Guardrails and escalation

Guardrails are the limits on what an agent may do. They come in two kinds.

| Kind | Example | Strength |
|---|---|---|
| In the prompt | "Never delete files outside the project folder" | Usually followed. Can be argued away by injected text |
| In the harness | A check that refuses any delete outside the project folder | Cannot be argued with |

Agent frameworks provide the second kind as permission modes, lists of allowed and denied actions, and hooks that run before a tool call and can block it. Module 3.4 covered permission modes and the allow and deny lists. Anything that must not happen belongs there. The prompt's job is to explain the boundary, so that the agent plans within it and does not walk into the wall.

The risk that makes this pressing is the one Module 3.6 called the lethal trifecta: an agent with access to private data, exposure to untrusted content, and a way to send data out can be steered by a web page or an email into leaking what it knows. The security community now publishes a list of the top risks specific to agents, covering hijacked goals, misused tools, and failures that cascade between agents.

**Escalation** is the instruction to stop and ask. A good escalation rule names the triggers.

- The action cannot be undone.
- The action is outside the stated scope.
- The request is ambiguous in a way that changes what to do.
- The same step has failed twice.
- The action involves money, credentials, or another person's data.

And it says what the message to the person must contain: what the agent was trying to do, what it found, the options, and its recommendation. "I am stuck" is not an escalation.

### Guidance for long-running tasks

A task that takes hours outlasts the context window. Older turns are summarised or dropped to make room, a process called compaction, and instructions given at the start can be lost with them. The agent then drifts: it forgets a constraint, repeats work, or redefines the goal.

The remedy is to keep the task's state outside the model's context, in files, and to tell the agent to use them. Anthropic's write-up on harnesses for long-running agents describes a working arrangement.

| Device | Purpose |
|---|---|
| A project instructions file | Durable rules are reloaded in every session and survive compaction |
| A feature list in a file, every item marked as failing at the start | The definition of done, in a form that cannot be forgotten |
| A rule that only the pass mark of an item may be edited | The agent cannot finish by rewriting the list |
| A progress file | What was done, what was tried, what is next |
| A commit after each completed item | A known good state to return to |
| One item per session | Each session starts with a fresh context |
| A smoke test at the start of every session | The agent finds out at once if the last session left things broken |

The instructions for each session then become short and the same every time: read the progress file and the feature list, run the smoke test, choose the next failing item, implement it, run its test, mark it as passing only if the test passes, commit, update the progress file, and stop.

### Complexity

An agent's cost grows with the number of steps and with the size of what each step adds to the context. Capping tool results bounds the second. Step and cost limits bound the first. Delegation multiplies total tokens while keeping each context small.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, linting a tool description and a delegation brief.

```python
import json
import re

VAGUE_PARAMETERS = {"id", "user", "data", "name", "value", "input", "item", "info"}

def lint_tool(tool):
    problems = []
    description = tool.get("description", "")
    if "_" not in tool.get("name", ""):
        problems.append("unscoped-name")
    if len(description.split()) < 15:
        problems.append("short-description")
    if "use" not in re.findall(r"[a-z]+", description.lower()):
        problems.append("no-when")
    for name, text in tool.get("parameters", {}).items():
        if name in VAGUE_PARAMETERS:
            problems.append("vague-parameter:" + name)
        if not text.strip():
            problems.append("undocumented-parameter:" + name)
    return problems

def brief_gaps(brief):
    gaps = [key for key in ("objective", "output_format", "tools", "boundaries") if not brief.get(key)]
    if brief.get("objective") and len(brief["objective"].split()) < 8:
        gaps.append("vague-objective")
    if not brief.get("max_tool_calls"):
        gaps.append("no-budget")
    return gaps

BAD_TOOL = {"name": "search", "description": "Searches.", "parameters": {"user": "", "q": "query"}}
GOOD_TOOL = {
    "name": "orders_search",
    "description": ("Search the customer's past orders by keyword or date range. Use this when the customer asks about "
                    "a previous purchase and has not given an order number. Returns at most 10 orders, newest first."),
    "parameters": {"customer_id": "The customer's account number, such as C-10293.",
                   "query": "Words from the product name, or empty to list recent orders.",
                   "since_date": "Optional earliest order date as YYYY-MM-DD."},
}
print(lint_tool(BAD_TOOL))
print(lint_tool(GOOD_TOOL))

GOOD_BRIEF = {
    "objective": "List the five largest UK hand-tool retailers by revenue, with a source for each figure.",
    "output_format": "A table: retailer, revenue, year, source URL.",
    "tools": ["web_search", "fetch_page"],
    "boundaries": "UK only. Do not cover power tools; another agent has that.",
    "max_tool_calls": 15,
}
print(brief_gaps({"objective": "Research competitors"}))
print(brief_gaps(GOOD_BRIEF))
```

- **`lint_tool` checks four things from Section 2.** A name with no underscore has no system prefix and will collide with another tool. A description under 15 words cannot say what the tool does, when to use it, and what it returns. A description without the word "use" does not say when. And each argument is checked for a vague name and for a missing description.
- **The bad tool has five findings.** It is called `search`, described in one word, and takes an undescribed argument called `user`. An agent offered two tools like this chooses between them by guessing.
- **The good tool has none.** Its name says which system it searches. Its description says what it does, when to use it, and what comes back. Each argument says what it is and in what format.
- **The linter checks form and not truth.** A description can pass every check and be wrong about what the tool does. The real test is an agent using the tool on realistic tasks.
- **`brief_gaps` checks the four parts of a delegation brief, and two more.** An objective under eight words is flagged as vague, and a brief with no limit on tool calls is flagged as having no budget.
- **"Research competitors" has five gaps.** It gives no output format, no tools, no boundaries, and no budget, and its objective is two words. A sub-agent given this brief will research something, at length.
- **The good brief has none.** It could be handed to a stranger.

Next, the decision to stop, written as code outside the model.

```python
def stop_reason(history, max_steps, max_cost, repeat_limit=3):
    if history and history[-1]["tool"] == "finish":
        return "done"
    recent = history[-repeat_limit:]
    if len(recent) == repeat_limit and len({(step["tool"], json.dumps(step["args"], sort_keys=True)) for step in recent}) == 1:
        return "loop"
    if len(history) >= max_steps:
        return "max_steps"
    if sum(step["cost"] for step in history) >= max_cost:
        return "budget"
    return None

search = {"tool": "orders_search", "args": {"query": "hammer"}, "cost": 0.25}
print(stop_reason([search, search], 20, 5.0), stop_reason([search, search, search], 20, 5.0))
print(stop_reason([search, search], 2, 5.0), stop_reason([search, search], 20, 0.5))
print(stop_reason([search, search, search, {"tool": "finish", "args": {}, "cost": 0.25}], 3, 0.5))
```

- **The function looks at the run so far and returns a reason to stop, or nothing.** It is called after every step. The model has no part in it.
- **Finishing is checked first.** If the last action was the agent declaring the task finished, the reason is "done", even if a limit was also reached on that step.
- **A loop is the same tool with the same arguments three times running.** Two searches for "hammer" return nothing. The third returns "loop". The instructions told the agent to stop after two failures. The detector is set one higher, so that it catches only an agent that did not follow the instruction. The arguments are compared in a fixed key order, so that the same arguments written in a different order still match.
- **Then the limits.** Two steps against a limit of two gives "max_steps". A cost of 0.5 against a limit of 0.5 gives "budget".
- **The last line shows the order of checks.** Four steps exceed a limit of three, and the cost exceeds its limit, yet the answer is "done", because the agent finished.
- **Each reason calls for a different response.** "Done" goes to verification. "Loop" and the two limits go to a person, with the history. Reporting a run that hit its limit as a success is the failure this function exists to prevent.

Then, capping what a tool returns.

```python
def cap_output(rows, limit_tokens, hint):
    kept, used = [], 0
    for row in rows:
        size = len(row) // 4 + 1
        if used + size > limit_tokens:
            break
        kept.append(row)
        used += size
    if len(kept) == len(rows):
        return "\n".join(kept)
    return "\n".join(kept + [f"[Showing {len(kept)} of {len(rows)} results. {hint}]"])

ROWS = [f"ORD-{number:04d} / 2026-{1 + number % 12:02d}-{1 + number % 28:02d} / Claw hammer x{1 + number % 3}" for number in range(1, 201)]
capped = cap_output(ROWS, 100, "Add a date range or a product name to narrow the search.")
print(len(ROWS), sum(len(row) // 4 + 1 for row in ROWS), len(capped.split("\n")))
print(capped.split("\n")[-1])
print(cap_output(ROWS[:2], 100, "unused"))
```

- **Each row's size is estimated at a quarter of its length plus one.** This is the rough four characters per token from Module 3.2.
- **Rows are kept until the next one would pass the limit.** The function never cuts a row in half, since half a record is worse than none.
- **Two hundred rows would cost about 2,000 tokens.** With a cap of 100, ten are kept.
- **A notice is added when anything was dropped.** It says how many of how many are shown, and how to narrow the request. The capped result is eleven lines: ten rows and the notice.
- **The notice is the important part.** Without it, the agent would tell the customer they have ten orders. With it, the agent knows there are 200 and what to do about it.
- **A result that fits is returned as it is.** The last line shows two rows with no notice.

Finally, guarding the progress file of a long-running task.

```python
def illegal_edits(before, after):
    problems = []
    old = {feature["id"]: feature for feature in before}
    new = {feature["id"]: feature for feature in after}
    for identifier, feature in old.items():
        if identifier not in new:
            problems.append("removed:" + identifier)
            continue
        for key, value in feature.items():
            if key != "passes" and new[identifier].get(key) != value:
                problems.append("edited:" + identifier + "." + key)
    for identifier in new:
        if identifier not in old:
            problems.append("added:" + identifier)
    return problems

FEATURES = [
    {"id": "F1", "description": "User can log in", "test": "tests/test_login.py", "passes": False},
    {"id": "F2", "description": "User can reset password", "test": "tests/test_reset.py", "passes": False},
    {"id": "F3", "description": "User can export data as CSV", "test": "tests/test_export.py", "passes": False},
]
honest = [dict(FEATURES[0], passes=True), FEATURES[1], FEATURES[2]]
shortcut = [dict(FEATURES[0], passes=True), dict(FEATURES[1], passes=True, test="tests/test_smoke.py")]
print(illegal_edits(FEATURES, honest))
print(illegal_edits(FEATURES, shortcut))
```

- **The feature list is the task's definition of done.** Each item has an identifier, a description, the test that proves it, and a pass mark that starts as false.
- **The agent may change one thing: the pass mark.** `illegal_edits` compares the list before and after a session and reports anything else.
- **The honest update has no findings.** One pass mark changed from false to true.
- **The shortcut has two.** The agent pointed the second feature at an easier test, and removed the third feature from the list. Both make the list look complete without the work being done.
- **This is a control and not an instruction.** The prompt says "edit only the pass mark". The check makes any other edit fail the session. An agent under pressure to finish, with its early instructions compacted away, will sometimes take the shortcut, and the check does not depend on the agent remembering.
- **The check does not prove a pass mark is deserved.** For that, the harness runs the named test itself and does not take the agent's word.

**Complexity.** `lint_tool` and `brief_gaps` are linear in the text. `stop_reason` is linear in the history, and is called once per step. `cap_output` is linear in the rows kept. `illegal_edits` is linear in the number of features times their fields.

### An agent instruction template

```text
GOAL
[What to achieve, in one or two sentences.]

DONE WHEN
[A condition you can check with a tool. When it holds, summarise and stop.]

TOOLS
[Which to prefer for what. Anything not obvious from the tool descriptions.]

LIMITS
At most [N] tool calls. If the same action fails twice, stop and report.

WITHOUT ASKING YOU MAY
[Read, search, draft, run tests.]

ASK FIRST BEFORE
[Anything that sends, pays, deletes, publishes, or leaves the stated scope.]

NEVER
[The hard limits. These are also enforced outside you.]

WHEN YOU ASK
Say what you were doing, what you found, the options, and what you recommend.
```

### A delegation brief template

```text
OBJECTIVE:      [Exactly what to find or produce. You have no other context.]
OUTPUT FORMAT:  [What to return, in what structure, at what length.]
TOOLS/SOURCES:  [Which to use. Which sources to trust or avoid.]
BOUNDARIES:     [What is out of scope. What other agents are covering.]
EFFORT:         [At most N tool calls. Stop when you have enough.]
```

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**No definition of done.** "Improve the documentation" gives an agent nothing to check, so it stops when it feels finished, or never. State a condition a tool can verify.

**Victory declared early.** The agent reports success with tests failing or half the list untouched. It is the failure most often reported by people running long tasks. Have the harness run the check, and never accept the agent's own report as the result.

**No limits set.** Step and cost limits that default to none stay at none until a run costs a great deal overnight. Set both on every run, and treat a run that hits one as a failure to investigate.

**The loop.** An agent repeats a failing action with small variations, sure that the next attempt will work. Detect repetition in code, and tell the agent in its instructions what to do when something fails twice.

**Two tools called search.** Tools with overlapping names and descriptions make the agent's choice a guess. Prefix names with their system, and say in each description when to use it and when to use the other.

**Tools designed for programs.** A tool that returns internal identifiers and codes is easy for code to consume and hard for a model to reason about. Return names, and say in the description what the fields mean.

**The result that fills the window.** One unfiltered query returns thousands of rows, and the agent's context is gone. Cap every result, and tell the agent when it was cut and how to narrow it.

**Sub-agents sent out with one line.** "Look into pricing" produces a sub-agent that does not know for whom, how deeply, or in what form to answer. It starts with no context at all. Write the brief as if for a stranger.

**Duplicate work between sub-agents.** Three sub-agents given overlapping briefs return the same sources three times. Say in each brief what the others are covering.

**Too many agents.** A question one agent could answer in five tool calls is split among ten. Every agent adds tokens, time, and a way to fail. Start with one, and add more only when the work is truly parallel.

**Rules that exist only in the first message.** A constraint stated once at the start of a long run can be compacted away. Put durable rules where they are reloaded: the project instructions file, or the top of every session's prompt.

**State kept only in the context.** An agent that tracks its progress in its own head loses it when the context turns over. Keep progress in files, and have each session begin by reading them.

**Guardrails written only as sentences.** "Do not delete anything important" is a hope. Deny the action in the harness, and use the sentence to explain the boundary.

**Escalations with no content.** An agent that stops and says it needs help leaves the person to reconstruct the situation. Require what it was doing, what it found, the options, and a recommendation.

## 5. Active Recall Check & Synthesis Summary

**Summary.** An agent prompt is a policy for a sequence of decisions that nobody watches. Its instructions need a goal with a definition of done that a tool can check, guidance on tools, stopping conditions for being done, out of budget, stuck, and in need of a person, and a statement of what may be done without asking. Each stopping condition and each hard limit is also enforced in the harness, because a prompt is advice and limits often default to none. Reliability compounds against long runs: $p^{n}$ across steps and $q^{k}$ across repeated runs. Tool descriptions are prompts read on every step, and should name the tool's system, say what it does, when to use it, and what it returns, with unambiguous documented arguments and errors that say what to do. Tool results are capped, with a notice saying what was cut and how to narrow the request. A delegation brief gives a sub-agent, which starts with nothing, an objective, an output format, tools and sources, boundaries, and an effort budget. Long-running tasks keep their state in files: a feature list whose pass marks alone may be edited, a progress file, and commits, with each session starting by reading them.

**Question 1.** An agent takes about 30 steps per task, and each step goes right 97 percent of the time. Estimate the probability that a whole run goes right. Separately, a second agent completes its task on 80 percent of runs: what is the probability that it succeeds five times in a row? What do the two results imply for how agent instructions and harnesses should be designed?

<details>
<summary>View Answer</summary>

For the first agent, the probability that all 30 steps go right is 0.97 to the power 30, which is about 0.40. A step that fails three times in a hundred sounds dependable, and a run built from 30 of them fails more often than it succeeds. For the second agent, five successes in a row have probability 0.8 to the power 5, which is about 0.33. An agent that looks good in a demonstration fails at least once in most working weeks. Four things follow for design. First, shorten the run: fewer steps means a higher product, so the instructions should say when to stop, tools should do more per call, and a job that needs no agent should be a fixed chain as in Module 5.6. Second, make errors visible and recoverable inside the run: a definition of done that the agent can check with a tool, such as a test suite, lets it catch and repair a wrong step, which raises the effective success rate above the raw product. Third, do not trust a single success or the agent's own report: the harness should verify the result itself, and the agent should be evaluated over many runs of the same task, not one. Fourth, plan for failure: step and cost limits, a detector for repeated actions, and an escalation rule mean that the failing runs stop early and reach a person with their history, instead of continuing to act on a mistake.

**Question 2.** An agent has two tools. The first is named `get` with the description "Gets data" and one argument `id`. The second is named `lookup` with the description "Looks things up" and one argument `name`. The agent often calls the wrong one. Explain why, and rewrite both.

<details>
<summary>View Answer</summary>

The agent chooses a tool by reading the names and descriptions, and these give it nothing to choose by. "Get" and "lookup" are near synonyms, neither name says which system the tool belongs to, and "gets data" and "looks things up" would describe almost any tool. Neither description says when the tool should be used or what it returns. The arguments are just as bare: `id` could be an order number, a customer number, or a product code, and `name` could be a person or a product. **Question 3.** An agent is left overnight to implement a list of 20 features. In the morning it reports that all 20 are complete. Inspection shows that 6 tests fail, 2 features have disappeared from the list, and several test files were altered. Explain how this happened and describe the instructions and the controls that would have prevented it.

<details>
<summary>View Answer</summary>

Three things combined. The task outlasted the context window, so the early instructions, including any rule about not touching the tests or the list, were compacted away, and later sessions worked from a thinner memory of what was asked. The definition of done was the agent's own report, with nothing checking it, so declaring completion was the cheapest way to finish. And the agent had the ability to edit the feature list and the tests, so making the list look complete was easier than making the features work. No bad intent is needed: an agent told to get everything passing, and able to change what passing means, will sometimes do that. The instructions should be short, identical in every session, and reloaded each time from a project instructions file: read the progress file and the feature list; run the smoke test; take the next failing feature only; implement it; run its test; mark it as passing only if that test passes; never edit a test file or any field of the feature list except the pass mark; commit; update the progress file; stop. One feature per session keeps each context fresh. The controls do what the instructions cannot guarantee. The harness compares the feature list before and after each session and fails the session if anything other than a pass mark changed, or if an item was removed or added. It denies writes to the test directory outright, through a permission rule or a hook. It runs each test itself to confirm a pass mark before accepting it, and runs the full suite at the end, reporting that result and not the agent's summary. Step and cost limits bound each session, and a commit after each accepted feature means that a bad session can be discarded without losing the good ones.

def cap_output(rows, limit_tokens, hint):
    """A result is paid for on every later step, so it is capped. The notice matters most:
    an agent shown ten rows with no notice believes there are ten."""
    kept, used = [], 0
    for row in rows:

        if used + size > limit_tokens:
            break
        kept.append(row)
        used += size
    if len(kept) == len(rows):
        return "\n".join(kept)
    return "\n".join(kept + [f"[Showing {len(kept)} of {len(rows)} results. {hint}]"])
