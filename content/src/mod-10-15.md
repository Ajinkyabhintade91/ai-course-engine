# Model Selection Guide

This unit has surveyed the main local model families, Qwen, Llama, Gemma, Mistral, and DeepSeek, along with the hardware, tooling, and licence questions around them. This final module turns all of that into a **repeatable selection process**: filter by task, hardware, and licence to get a shortlist; test the shortlist on a **personal benchmark** built from your own tasks; compare candidates in a way that respects how little a small test can prove; and record the outcome in a **decision table** you revisit when new models arrive, which, as this unit has shown, happens every few months.

Model names and sizes in the shortlist are from the earlier modules and Ollama's library at the time of writing (November 2026). The benchmark outputs in the lab are illustrative, labelled model A, B, and C, not results of real models.

## 1. First-Principles Mental Model & Intuition

### Choosing a new machine for the workshop

Choosing a model is like choosing a machine for a workshop. First the **hard constraints**: does it do the job at all, does it fit through the door, can you legally use it the way you intend? That gives a shortlist. Then a **trial**: run each candidate on your own typical jobs, not the manufacturer's showcase pieces, and inspect the results with the same checklist. Then a **decision** that can be justified and revisited: which machine for which job, and what would make you change your mind.

```text
 NEEDS                         CONSTRAINTS                      SHORTLIST (largest first)
 tasks -> capabilities   +     memory (x1.2 headroom)     ->   capable, fits, licensed
 (tools, vision, audio,        licence vs intended use         2 to 5 candidates
  thinking, context)
                                                                       |
 PERSONAL BENCHMARK (your cases, graded by rules)  <-------------------+
   per model: overall pass rate, per-task pass rate, latency
   paired comparison: wins / losses on the same cases, sign test p-value
                                                                       |
 DECISION TABLE: task -> model meeting pass-rate and latency bars; review on new releases
```

### Why your own benchmark

Public leaderboards measure general abilities on general tasks, under the vendors' or organisers' settings. Your tasks have their own vocabulary, formats, and failure modes. A model that tops a leaderboard can lose on your quote arithmetic or your JSON tags; a smaller model can win. Leaderboards are a good way to choose what to **test**, not what to **use**.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Selecting by task

Translate each task into required **capabilities**: tool calling for agents and lookups, vision for photos and scanned documents, audio for speech, thinking for multi-step arithmetic and planning, and a context length for long documents. Modules 10.5 to 10.9 listed which models have which.

### Selecting by hardware

Module 10.10's rule of thumb: a model fits fully on the GPU if its file size times about 1.2 fits in GPU memory, with more for long contexts. Mixture-of-experts models are much faster per token for their size but need memory for every expert.

### Selecting by licence

Apache 2.0 and MIT models can be used commercially with simple notice requirements; the Llama licence and some modified MIT licences add conditions, Modules 10.6 and 10.8; non-production licences such as Codestral's rule out commercial use. Filter out what the intended use does not permit, and flag what needs a closer read.

### A personal benchmark

A good personal benchmark has:

- **Cases from real work**, such as anonymised customer questions, real quote calculations, and real catalogue entries, 20 to 100 per task to start.
- **Rule-based grading** wherever possible: an expected phrase, a number within a tolerance, valid JSON with required keys, or the absence of forbidden content. Rules are cheap, repeatable, and transparent. Where rules cannot judge, use a model-based grader with a rubric and check it against human judgement, Module 8.12.
- **Normalisation in the rules** so formatting differences do not count as failures: "254mm" and "254 mm" are the same answer.
- **The same settings for every model:** each model's recommended sampling from its card, the same context, and the same prompts.
- **Latency measured alongside quality,** since a slightly better model that is three times slower may be the wrong choice.

### Comparing two models fairly

With a small benchmark, differences can be chance. Compare models **case by case**: count cases where A passes and B fails, $w$, and where B passes and A fails, $l$; ties tell you nothing about which is better. Under the null hypothesis that neither is better, each discordant case is a coin flip, so the **sign test** gives a two-sided p-value:

$$p = \min\left(1,\; 2 \sum_{i=0}^{\min(w, l)} \binom{n}{i} \left(\tfrac{1}{2}\right)^n\right), \quad n = w + l$$

With 3 wins and 0 losses, $p = 2 \times (1/8) = 0.25$: not convincing. With 10 wins and 2 losses, $p \approx 0.039$. A handful of cases cannot separate close models; grow the benchmark where decisions are close.

### A decision table

For each task, choose the model that meets a **minimum pass rate** and a **maximum latency**, preferring the higher pass rate and then the lower latency. Tasks for which no model qualifies are recorded as gaps: they need a better model, a different approach such as a workflow or retrieval, or human handling. The table lists the date and model versions, so it can be re-run when a new model appears.

### Complexity

Shortlisting is linear in the catalogue; grading is linear in cases and output lengths; the sign test is linear in discordant cases; the decision table is linear in tasks times models.

```python
def shortlist(catalogue, needs, mem_gb, commercial=True, headroom=1.2):
```

Next, grading individual cases.

```python
def score_case(output, case):
    kind = case["kind"]
    if kind == "contains":
        return case["expect"].lower().replace(" ", "") in output.lower().replace(" ", "")
    if kind == "number":
        nums = re.findall(r"-?\d+(?:\.\d+)?", output.replace(",", ""))
        return any(abs(float(n) - case["expect"]) <= case.get("tol", 0) for n in nums)
    if kind == "json_keys":
        try:
            data = json.loads(output)
        except json.JSONDecodeError:
            return False
        return isinstance(data, dict) and all(k in data for k in case["expect"])
    if kind == "refuse":
        return not any(w in output.lower() for w in case["forbidden"])
    raise ValueError(kind)

print(score_case("The 254mm blade fits.", {"kind": "contains", "expect": "254 mm"}))
print(score_case("About 43", {"kind": "number", "expect": 43.2, "tol": 0.01}))
```

- **"254mm" matches "254 mm" after removing spaces.** Formatting is not quality.
- **"About 43" fails a tolerance of 0.01 against 43.2.** For money, close is wrong.
- **JSON must parse and contain the keys;** forbidden phrases must be absent. Unknown kinds raise an error rather than passing silently.

Then, running the benchmark.

```python
    "model-c": ["Use a 254 mm blade.", "I cannot help with that.", "3 x 12 = 36", "43.2",
                '{"sku": "SAW-3"}', '{"sku": "BLADE-10", "category": "blades"}'],
}

def run_benchmark(outputs, cases):
    table = {}
    for model, outs in outputs.items():
        passed = [score_case(o, c) for o, c in zip(outs, cases)]
        by_task = {}
        for p, c in zip(passed, cases):
            by_task.setdefault(c["task"], []).append(p)
        table[model] = {"overall": round(sum(passed) / len(cases), 3),
                        "by_task": {t: round(sum(v) / len(v), 3) for t, v in by_task.items()},
                        "passed": passed}
    return table

TABLE = run_benchmark(OUTPUTS, CASES)
for model, row in TABLE.items():
    print(model, row["overall"], row["by_task"])
```

- **Model A passes all six; model B half; model C five of six,** failing one tagging case.
- **Per-task rates matter more than the overall figure:** model C is perfect on support and quotes.
- **These outputs are illustrative.** Real runs record each model's actual outputs with the same prompts and settings.

Then, a fair comparison.

```python
def sign_test(a, b):
    wins = sum(1 for x, y in zip(a, b) if x and not y)
    losses = sum(1 for x, y in zip(a, b) if y and not x)
    n = wins + losses
    if n == 0:
        return wins, losses, 1.0
    k = min(wins, losses)
    p = sum(math.comb(n, i) for i in range(k + 1)) / 2 ** n * 2
    return wins, losses, round(min(1.0, p), 4)

print(sign_test(TABLE["model-a"]["passed"], TABLE["model-b"]["passed"]))
print(sign_test([True] * 10 + [False] * 2, [False] * 10 + [True] * 2))
```

- **A beats B on three cases and never loses, yet p is 0.25.** Six cases cannot establish it.
- **Ten wins to two losses gives p of about 0.039,** reasonable evidence of a real difference.
- **Ties are ignored,** because cases both pass or both fail say nothing about which is better.

Finally, the decision table.

```python
LATENCY = {"model-a": 2.1, "model-b": 2.6, "model-c": 1.4}

def decision_table(table, latency, min_pass=0.75, max_latency=3.0):
    tasks = sorted({t for r in table.values() for t in r["by_task"]})
    rows = []
    for t in tasks:
        ok = [(m, r["by_task"][t]) for m, r in table.items() if r["by_task"][t] >= min_pass and latency[m] <= max_latency]
        if not ok:
            rows.append((t, None, 0.0))
            continue
        best = max(ok, key=lambda x: (x[1], -latency[x[0]]))
        rows.append((t, best[0], best[1]))
    return rows

print(decision_table(TABLE, LATENCY))
print(decision_table(TABLE, LATENCY, 1.0, 2.0))
```

- **Quotes and support go to model C,** tied with A on quality but faster; tagging goes to model A.
- **With stricter bars, a perfect pass rate within 2 seconds, tagging has no qualifying model:** a gap to fill.
- **Using two models is legitimate,** if the shop is willing to run both; otherwise model A covers all three tasks.

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Choosing from leaderboards.** They choose what to test, not what to use.

**Testing with vendor examples.** Use your own cases.

**Brittle grading.** "254mm" versus "254 mm". Normalise.

**Too few cases.** Close models need dozens of discordant cases. Grow the set.

**Different settings per model.** Unfair comparisons. Use each card's sampling, same prompts and context.

**Ignoring latency.** Users feel speed. Measure it.

**One model for everything.** Sometimes two small models beat one large one. Consider routing.

**Forgetting licences until launch.** Filter at the shortlist stage.

**Benchmark leakage.** Test cases copied into prompts or fine-tuning data. Keep a held-out set.

**Never revisiting.** New models arrive every few months. Re-run the benchmark.

**Over-fitting the benchmark.** Tuning prompts until one set passes. Keep a fresh validation set.

**Ignoring failure severity.** A wrong refund amount is worse than a clumsy sentence. Weight critical cases.

# ---------------------------------------------------------------- Step 1
def shortlist(catalogue, needs, mem_gb, commercial=True, headroom=1.2):
    """Capable, fits, and licensed for the use; largest first; licence conditions flagged."""
    out = []
    for m in sorted(catalogue, key=lambda m: -m["gb"]):
        if not set(needs) <= m["caps"]:
            continue
        if m["gb"] * headroom > mem_gb:
            continue
        if commercial and m["licence"] == "mnpl":
            continue
        out.append((m["name"], "" if m["licence"] in PERMISSIVE else "check licence conditions"))
    return out


# ---------------------------------------------------------------- Step 2
def score_case(output, case):
    """Rule-based grading with normalisation."""
    kind = case["kind"]
    if kind == "contains":
        return case["expect"].lower().replace(" ", "") in output.lower().replace(" ", "")
    if kind == "number":
        nums = re.findall(r"-?\d+(?:\.\d+)?", output.replace(",", ""))
        return any(abs(float(n) - case["expect"]) <= case.get("tol", 0) for n in nums)
    if kind == "json_keys":
        try:
            data = json.loads(output)
        except json.JSONDecodeError:
            return False
        return isinstance(data, dict) and all(k in data for k in case["expect"])
    if kind == "refuse":
        return not any(w in output.lower() for w in case["forbidden"])
    raise ValueError(kind)


# ---------------------------------------------------------------- Step 3
def run_benchmark(outputs, cases):
    """Overall and per-task pass rates for each model."""
    table = {}
    for model, outs in outputs.items():
        passed = [score_case(o, c) for o, c in zip(outs, cases)]
        by_task = {}
        for p, c in zip(passed, cases):
            by_task.setdefault(c["task"], []).append(p)
        table[model] = {"overall": round(sum(passed) / len(cases), 3),
                        "by_task": {t: round(sum(v) / len(v), 3) for t, v in by_task.items()},
                        "passed": passed}
    return table


# ---------------------------------------------------------------- Step 4
def sign_test(a, b):
    """Two-sided sign test on discordant cases."""
    wins = sum(1 for x, y in zip(a, b) if x and not y)
    losses = sum(1 for x, y in zip(a, b) if y and not x)
    n = wins + losses
    if n == 0:
        return wins, losses, 1.0
    k = min(wins, losses)
    p = sum(math.comb(n, i) for i in range(k + 1)) / 2 ** n * 2
    return wins, losses, round(min(1.0, p), 4)

def decision_table(table, latency, min_pass=0.75, max_latency=3.0):
    """Per task, the best model that meets the quality and latency bars, or a recorded gap."""
    tasks = sorted({t for r in table.values() for t in r["by_task"]})
    rows = []
    for t in tasks:
        ok = [(m, r["by_task"][t]) for m, r in table.items() if r["by_task"][t] >= min_pass and latency[m] <= max_latency]
        if not ok:
            rows.append((t, None, 0.0))
            continue
        best = max(ok, key=lambda x: (x[1], -latency[x[0]]))
        rows.append((t, best[0], best[1]))
    return rows
