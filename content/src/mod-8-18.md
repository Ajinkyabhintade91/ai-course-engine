# Agent Project 4: AI Content Creation Agent

A content agent researches a topic, plans an article, drafts it, edits it to the brand's voice, and hands it to an editor for review and publishing. Language models are very good at producing fluent text quickly, which is exactly why content agents need structure: fluent is not the same as accurate, on-brand, readable, or approved. Without checks, a content agent produces a steady stream of generic articles with invented facts, words the brand never uses, and sentences no customer wants to read.

Module 7.21 automated social posts with length and disclosure checks, Module 8.10 introduced chains and evaluator-optimizer loops, and Module 8.15 built the research discipline. This project combines them into a pipeline with a **memory of the brand's voice** that improves from the editor's own edits.

## 1. First-Principles Mental Model & Intuition

### A small editorial team

A good magazine produces an article in stages. A commissioning editor writes a **brief**: topic, audience, length, points to cover. A researcher gathers sources. A writer produces an **outline**, which the editor approves before drafting, because fixing structure in an outline costs minutes and in a draft costs hours. The writer drafts; a sub-editor checks it against the **style guide**; the editor reviews, makes changes, and approves **that version** for publication. Over time, the writer learns the editor's preferences from their corrections.

A content agent mirrors each role, and the system around it checks each handoff.

```text
   BRIEF (topic, audience, words, must-cover points)
     |
   [research]  sources with citations (Module 8.15)
     |
   [outline]  headings + word budget -> CHECK: covers brief, budget within 10%
     |
   [draft]  section by section, from research notes
     |
   [edit]  style lint (banned, preferred terms, sentence length) + voice memory rules
     |      + readability score; evaluator-optimizer loop (Module 8.10)
     |
   [review]  editor edits and approves version N -> edits feed the VOICE MEMORY
     |
   [publish gate]  0 style issues, readability >= target, 0 uncited claims, approved version == current
     |
   scheduled publish
```

### Why a voice memory

Style guides are never complete. An editor who changes "huge" to "wide" and "assist" to "help" every week is expressing rules nobody wrote down. If the agent learns nothing, the editor makes the same corrections forever, and soon stops reviewing carefully. A **voice memory** records repeated corrections and turns them into rules, Module 8.3's long-term memory applied to style.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### The pipeline

The stages form a chain with gates, Module 8.10, and the edit stage is an evaluator-optimizer loop: lint, revise, re-lint, within a round limit. Separating stages matters because each has different inputs and checks:

| Stage | Input | Output | Check |
|---|---|---|---|
| Research | Brief | Sourced notes | Citation discipline, Module 8.15 |
| Outline | Brief, notes | Headings with word budgets | Must-cover points present; budget near target |
| Draft | Outline, notes | Text per section | Every factual claim cited |
| Edit | Draft, style guide, voice memory | Revised text | Style lint clean; readability target met |
| Review | Edited draft | Approved version | Editor approval recorded with version |
| Publish | Approved version | Live page | Publish gate |

### Outline checks

An outline is checked against the brief before any drafting: every **must-cover** point appears in a heading, and the planned word counts add up to the target within a tolerance:

$$(1 - t) \cdot W \;\le\; \sum_i w_i \;\le\; (1 + t) \cdot W$$

for target $W$, section budgets $w_i$, and tolerance $t$, 10 percent in the lab. A 1,200-word brief allows 1,080 to 1,320 planned words. An outline that misses "safety" in a buying guide for power tools is cheaper to fix now than after 1,200 words are written.

### Style guides as code

Public style guides, such as GOV.UK's A to Z, Mailchimp's content style guide, and Google's developer documentation style guide, share a pattern: lists of words to prefer or avoid, rules on sentence length, punctuation, tone, and spelling. Many of these rules can be checked by code:

| Rule type | Example | Check |
|---|---|---|
| Banned phrases | "game-changer", "revolutionary" | Substring search |
| Preferred terms | "use" not "utilise", "buy" not "purchase" | Word-boundary replacement, preserving capitals |
| Spelling variant | "colour" not "color" for a UK brand | Replacement map |
| Sentence length | No more than 25 words | Count words per sentence |
| Punctuation | At most one exclamation mark | Count |

Code-checkable rules are applied deterministically, and some can be **auto-fixed**; rules that need judgement, such as tone, go to a model grader with examples, calibrated as in Module 8.12.

### Learning the voice from edits

Each review produces a pair: the agent's text before and the editor's text after. Aligning the two word sequences, with a standard diff algorithm such as Python's `difflib.SequenceMatcher`, reveals **substitutions**: a single word replaced by a single word. Counting substitutions across many reviews, and promoting those seen at least $k$ times to rules, turns an editor's habits into a style guide:

$$\text{rule}(a \to b) \iff \text{count}(a \to b) \ge k$$

A threshold of $k = 2$ or more prevents a one-off correction, made for a particular context, from becoming a global rule. Multi-word rewrites, such as "Get started today" to "Start today", are recorded but not auto-promoted: they need a person to generalise them.

### Readability

The **Flesch reading ease** score estimates how easy a text is to read from sentence and word length:

$$\text{FRE} = 206.835 - 1.015 \cdot \frac{\text{words}}{\text{sentences}} - 84.6 \cdot \frac{\text{syllables}}{\text{words}}$$

Higher is easier: scores around 60 to 70 are often described as plain English for general adult readers, and low or negative scores indicate dense, technical prose. Syllables are estimated by counting vowel groups, with a correction for a silent final "e"; the estimate is rough, but the score is only a signal. Short sentences of short words score high: "Charge the battery. Fit the blade. Cut the board." scores about 100. A single 12-word sentence of long words scores below zero. Readability targets catch drafts that have drifted into jargon, but they cannot tell whether the text is accurate or useful.

### Review, approval, and versions

The editor approves a **specific version**. If the agent, or anyone, changes the article after approval, the approval no longer covers what is about to be published. The publish gate therefore compares the approved version with the current one, and blocks if they differ. This is the content equivalent of Module 8.11's rule that an approval covers exactly what the reviewer saw.

### Publishing responsibly

Google's Search guidance on AI-generated content says its systems aim to reward original, high-quality content however it is produced, while using automation, including AI, to generate content with the primary purpose of manipulating search rankings violates its spam policies. The practical consequence for a content agent is to optimise for usefulness: sourced facts, real expertise, and editorial review, rather than volume. Disclosure of AI involvement, where required or expected, follows the rules of Module 7.21.

### Complexity

Outline checks are linear in headings and points. Style linting is linear in text length times rules. Learning from edits costs a sequence alignment per pair, roughly quadratic in the worst case but fast for sentences. Readability is linear in text length. The publish gate is constant.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, the outline check.

```python
import difflib
import re
from collections import Counter

def outline_check(outline, brief, tolerance=0.1):
    issues = []
    headings = " ".join(heading.lower() for heading, _ in outline)
    for point in brief["must_cover"]:
        if point not in headings:
            issues.append(f"missing: {point}")
    total = sum(words for _, words in outline)
    if not brief["words"] * (1 - tolerance) <= total <= brief["words"] * (1 + tolerance):
        issues.append(f"{total} words planned, target {brief['words']}")
    return not issues, issues

BRIEF = {"must_cover": ["runtime", "safety", "blades"], "words": 1200}
OUTLINE = [("Why cordless saws", 200), ("Runtime and batteries", 350), ("Choosing blades", 300),
           ("Safety checklist", 250), ("Verdict", 150)]
print(outline_check(OUTLINE, BRIEF))
print(outline_check(OUTLINE[:3], BRIEF))
```

- **Every must-cover point must appear in some heading.** "Blades" is found in "Choosing blades".
- **The full outline plans 1,250 words, inside 1,080 to 1,320.**
- **The first three sections miss safety and plan only 850 words.** Both problems are reported before drafting starts.

Next, the style lint with auto-fixes.

```python
GUIDE = {"banned": ["game-changer", "revolutionary", "best ever"],
         "prefer": {"utilise": "use", "purchase": "buy", "color": "colour"},
         "max_sentence_words": 25, "max_exclamations": 1}
WORDS = re.compile(r"[A-Za-z0-9'-]+")

def style_lint(text, guide):
    issues, fixed = [], text
    for wrong, right in guide["prefer"].items():
        pattern = re.compile(rf"\b{re.escape(wrong)}\b", re.I)
        if pattern.search(fixed):
            issues.append(f"prefer '{right}' to '{wrong}'")
            fixed = pattern.sub(lambda m: right.capitalize() if m.group(0)[0].isupper() else right, fixed)
    for phrase in guide["banned"]:
        if phrase in text.lower():
            issues.append(f"banned: {phrase}")
    for index, sentence in enumerate(re.split(r"(?<=[.!?])\s+", text.strip()), start=1):
        count = len(WORDS.findall(sentence))
        if count > guide["max_sentence_words"]:
            issues.append(f"sentence {index} has {count} words")
    if text.count("!") > guide["max_exclamations"]:
        issues.append(f"{text.count('!')} exclamation marks")
    return issues, fixed

DRAFT = ("This revolutionary saw is a game-changer! Utilise the quick-release clamp to swap blades in seconds, and purchase "
         "spare batteries if you plan to work on site all day without access to a charging point or a generator nearby. Choose a color!")
issues, fixed = style_lint(DRAFT, GUIDE)
print(issues)
print(fixed)
```

- **Preferred terms are replaced on word boundaries, keeping a capital at the start of a sentence.** "Utilise" becomes "Use".
- **Banned phrases are reported but not auto-removed.** Deleting "revolutionary" can leave a broken sentence; a reviser, model or person, rewrites it.
- **The second sentence has 32 words, over the limit of 25.**
- **Two exclamation marks against a limit of one.**
- **Seven issues from three sentences.** Typical of an unedited model draft, and the input to an evaluator-optimizer round.

Then, learning the voice from edits.

```python
def learn_voice(pairs, min_count=2):
    counts = Counter()
    for before, after in pairs:
        a, b = before.split(), after.split()
        for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(a=a, b=b).get_opcodes():
            if tag == "replace" and i2 - i1 == 1 and j2 - j1 == 1:
                counts[(a[i1].lower().strip(".,!"), b[j1].lower().strip(".,!"))] += 1
    return {wrong: right for (wrong, right), n in sorted(counts.items()) if n >= min_count}, counts

EDITS = [("We offer a huge range of saws.", "We offer a wide range of saws."),
         ("Our team will assist you.", "Our team will help you."),
         ("A huge choice of blades.", "A wide choice of blades."),
         ("Staff assist with fitting.", "Staff help with fitting."),
         ("Get started today.", "Start today.")]
print(learn_voice(EDITS))
```

- **The diff aligns before and after word by word.** Only one-for-one substitutions are counted.
- **"Huge" became "wide" twice, and "assist" became "help" twice.** Both become rules.
- **"Get started" to "Start" replaces two words with one.** It is not counted; a person decides whether it generalises.
- **The rules can be merged into the guide's preferred terms.** Next week's draft will not need those corrections.

Then, readability.

```python
def syllables(word):
    w = word.lower().strip(".,!?;:'\"")
    n = len(re.findall(r"[aeiouy]+", w))
    if w.endswith("e") and not w.endswith(("le", "ee")) and n > 1:
        n -= 1
    return max(1, n)

def flesch(text):
    sentences = [s for s in re.split(r"[.!?]+", text) if s.strip()]
    words = WORDS.findall(text)
    total_syllables = sum(syllables(w) for w in words)
    score = 206.835 - 1.015 * len(words) / len(sentences) - 84.6 * total_syllables / len(words)
    return round(score, 1), len(words), len(sentences), total_syllables

print([(w, syllables(w)) for w in ["saw", "battery", "blade", "simple", "generator"]])
print(flesch("Charge the battery. Fit the blade. Cut the board."))
print(flesch("Utilisation of the lithium-ion battery necessitates comprehensive consideration of environmental temperature conditions."))
```

- **Syllables are vowel groups, minus a silent final "e".** "Blade" has one; "simple" keeps two because of the "le" ending.
- **Nine short words in three sentences score 100.4.** Easier than the scale's nominal top; the formula is not bounded.
- **Twelve long words in one sentence score -87.3.** Forty syllables in twelve words.
- **The heuristic miscounts some words.** For a target such as 60, it is close enough.

Finally, the publish gate.

```python
def publish_gate(article, now):
    blockers = []
    if article["style_issues"]:
        blockers.append(f"{article['style_issues']} style issues")
    if article["readability"] < article["min_readability"]:
        blockers.append(f"readability {article['readability']} below {article['min_readability']}")
    if article["uncited_claims"]:
        blockers.append(f"{article['uncited_claims']} uncited claims")
    if not article["approved_by"]:
        blockers.append("no editor approval")
    elif article["approved_version"] != article["version"]:
        blockers.append(f"approved v{article['approved_version']}, current v{article['version']}")
    if article["publish_at"] < now:
        blockers.append("publish time in the past")
    return ("ready" if not blockers else "blocked"), blockers

ARTICLE = {"style_issues": 0, "readability": 64.2, "min_readability": 60, "uncited_claims": 0,
           "approved_by": "sam", "approved_version": 3, "version": 3, "publish_at": 200}
print(publish_gate(ARTICLE, now=100))
print(publish_gate({**ARTICLE, "version": 4}, now=100))
```

- **A clean, readable, cited article approved at its current version is ready.**
- **Version 4 was never approved.** A late "small fix" after Sam's approval blocks publishing until Sam approves again.
- **All blockers are listed at once, so one revision can fix them all.**

**Complexity.** `outline_check` is linear in headings and points. `style_lint` is linear in text times rules. `learn_voice` aligns each pair once. `flesch` is linear in text. `publish_gate` is constant.

### A content agent playbook

```text
BRIEF        topic, audience (trade buyers), 1,200 words +/- 10%, must cover: runtime, safety, blades

MEASURE      editor edits per article (should fall), time to approve, reader engagement, corrections issued
```

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Drafting before the outline is approved.** Structural problems found in a draft cost hours. Check the outline against the brief.

**Generic content at volume.** Search engines and readers reward usefulness, not quantity. Fewer, sourced, reviewed articles.

**Style guide in the prompt only.** Models drift from long lists of rules. Lint in code and feed back the specific issues.

**Auto-deleting banned phrases.** Removing a word can break a sentence. Flag it and let the reviser rewrite.

**Losing capitals in replacements.** "use the clamp" at the start of a sentence looks careless. Preserve case.

**Learning from one edit.** A single correction may be contextual. Require repeats before promoting a rule.

**Never reviewing learned rules.** A wrong rule spreads to every article. Show the voice memory to the editor monthly.

**Readability as quality.** A high score can still be wrong or useless. Use it as a signal, not a goal.

**Approval of the idea, not the version.** Changes after approval are unreviewed. Tie approval to a version number.

**Invented statistics.** Fluent drafts invent numbers. Every number must trace to a source, Module 7.18.

**Ignoring the editor's workload.** If edits per article do not fall, the agent is not learning. Track it.

**Publishing straight from the agent.** A person's approval is the last gate for anything public, Module 8.11.

**Question 1.** After a month, the editor still changes "huge" to "wide" in most articles. The voice memory shows the pair ("huge", "wide") with a count of 7 but no rule. What are the likely causes, and how would you investigate using the lab's `learn_voice`?

<summary>View Answer</summary>

With a count of 7 and a threshold of 2, `learn_voice` would return the rule, so the problem is in what happens after learning. Likely causes are, first, that the learned rules are never merged into the style guide's preferred terms, so the lint and the drafting prompt never see them; second, that the rules are merged but applied only by the lint, which runs after drafting, while the draft prompt still uses the old guide, so the word appears and is then fixed or missed depending on the order of steps; or third, that the replacement does not match because of case or punctuation, for example "Huge" at the start of a sentence, if the merge step lost the case-insensitive matching. To investigate, run `learn_voice` on the month's edit pairs and confirm the rule appears; then run `style_lint` with the guide the pipeline actually used and check whether "utilise"-style replacements include the new pair; then test a sentence beginning with "Huge" to check case handling. The fix is to make rule promotion update the guide used by both the drafting prompt and the lint, with the editor reviewing new rules monthly, and to track edits per article so the improvement is visible.

**Question 2.** A draft scores 41 on Flesch reading ease against a target of 60. The writer agent's revision splits every sentence in half, and the score rises to 61, but the editor says the text now reads like a list of fragments. Explain the score's behaviour and propose a better revision strategy.

<details>
<summary>View Answer</summary>

The score has two terms: 1.015 times words per sentence, and 84.6 times syllables per word. Splitting sentences halves the first term without touching the second, so the score rises mechanically, here, with sentences averaging about 40 words, from 41 to about 61, even if the result reads badly. The formula rewards short sentences and short words, but has no notion of flow, coherence, or whether a sentence is complete. The agent optimised the metric, not the reader's experience: a classic case of a proxy becoming a target. A better strategy uses the score to find problems and other means to fix them. Identify the specific sentences that are long and the words that are long and avoidable; the style guide's preferred terms already replace many, such as "use" for "utilise". Rewrite those sentences for clarity, combining short related ideas where needed, and keep technical terms that the trade audience expects. Then check with both the score and a model grader using a rubric for flow and clarity, calibrated against the editor's judgements, and let the editor's review remain the final test. A target range, for example 55 to 75, with a cap on the share of very short sentences, also discourages fragmenting.

Explain using `publish_gate`, and propose a policy.

<details>
<summary>View Answer</summary>

`publish_gate` compares the approved version with the current one: Sam approved version 3, the current version is 4, so it reports "approved v3, current v4" and blocks. The gate cannot tell a typo from a substantive change, and in this case the second change was substantive: a price is a factual claim customers rely on, and a wrong price can be a legal and reputational problem, so it is exactly the kind of change an editor should see. The general principle, from Module 8.11, is that an approval covers exactly what the reviewer saw; once the text changes, the approval no longer covers it. A practical policy keeps that guarantee while reducing friction. Show the editor a diff between the approved and current versions, so re-approval of a typo fix takes seconds; classify changes, so that pure spelling and formatting changes detected by code, with no numbers, names, or claims touched, can be auto-approved with a record, while any change to a number, price, claim, or citation requires re-approval; and schedule publication only after the final approval, with the agent's corrections made before review where possible.

import re
from collections import Counter

         "prefer": {"utilise": "use", "purchase": "buy", "color": "colour"},
         "max_sentence_words": 25, "max_exclamations": 1}
WORDS = re.compile(r"[A-Za-z0-9'-]+")

def syllables(word):
    """Given: vowel groups, minus a silent final e (not -le or -ee), at least 1."""
    w = word.lower().strip(".,!?;:'\"")
    n = len(re.findall(r"[aeiouy]+", w))
    if w.endswith("e") and not w.endswith(("le", "ee")) and n > 1:
        n -= 1
    return max(1, n)


# ---------------------------------------------------------------- Step 1
def outline_check(outline, brief, tolerance=0.1):
    """Fix structure before drafting."""
    issues = []
    headings = " ".join(heading.lower() for heading, _ in outline)
    for point in brief["must_cover"]:
        if point not in headings:
            issues.append(f"missing: {point}")
    total = sum(words for _, words in outline)
    if not brief["words"] * (1 - tolerance) <= total <= brief["words"] * (1 + tolerance):
        issues.append(f"{total} words planned, target {brief['words']}")
    return not issues, issues


# ---------------------------------------------------------------- Step 2
def style_lint(text, guide):
    """Code-checkable rules, with safe auto-fixes for preferred terms only."""
    issues, fixed = [], text
    for wrong, right in guide["prefer"].items():
        pattern = re.compile(rf"\b{re.escape(wrong)}\b", re.I)
        if pattern.search(fixed):
            issues.append(f"prefer '{right}' to '{wrong}'")
            fixed = pattern.sub(lambda m: right.capitalize() if m.group(0)[0].isupper() else right, fixed)
    for phrase in guide["banned"]:
        if phrase in text.lower():
            issues.append(f"banned: {phrase}")
    for index, sentence in enumerate(re.split(r"(?<=[.!?])\s+", text.strip()), start=1):
        count = len(WORDS.findall(sentence))
        if count > guide["max_sentence_words"]:
            issues.append(f"sentence {index} has {count} words")
    if text.count("!") > guide["max_exclamations"]:
        issues.append(f"{text.count('!')} exclamation marks")
    return issues, fixed


# ---------------------------------------------------------------- Step 3
def learn_voice(pairs, min_count=2):
    """Repeated one-for-one substitutions in the editor's edits become rules."""
    counts = Counter()
    for before, after in pairs:
        a, b = before.split(), after.split()
        for tag, i1, i2, j1, j2 in difflib.SequenceMatcher(a=a, b=b).get_opcodes():
            if tag == "replace" and i2 - i1 == 1 and j2 - j1 == 1:
                counts[(a[i1].lower().strip(".,!"), b[j1].lower().strip(".,!"))] += 1
    return {wrong: right for (wrong, right), n in sorted(counts.items()) if n >= min_count}, counts


# ---------------------------------------------------------------- Step 4
def flesch(text):
    """A readability signal from sentence length and word length."""
    sentences = [s for s in re.split(r"[.!?]+", text) if s.strip()]
    words = WORDS.findall(text)
    total_syllables = sum(syllables(w) for w in words)
    score = 206.835 - 1.015 * len(words) / len(sentences) - 84.6 * total_syllables / len(words)
    return round(score, 1), len(words), len(sentences), total_syllables


# ---------------------------------------------------------------- Step 5
def publish_gate(article, now):
    """Approval covers one version; every blocker reported."""
    blockers = []
    if article["style_issues"]:
        blockers.append(f"{article['style_issues']} style issues")
    if article["readability"] < article["min_readability"]:
        blockers.append(f"readability {article['readability']} below {article['min_readability']}")
    if article["uncited_claims"]:
        blockers.append(f"{article['uncited_claims']} uncited claims")
    if not article["approved_by"]:
        blockers.append("no editor approval")
    elif article["approved_version"] != article["version"]:
        blockers.append(f"approved v{article['approved_version']}, current v{article['version']}")
    if article["publish_at"] < now:
        blockers.append("publish time in the past")
    return ("ready" if not blockers else "blocked"), blockers
