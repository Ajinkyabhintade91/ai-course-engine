# Prompting for Coding

Code is the one kind of model output that can be checked by a machine. An essay is good or bad in someone's opinion. A function passes its tests or it does not. That single fact shapes everything about prompting for code: the best coding prompts are the ones that say exactly what is wanted and supply the means of checking it.

Module 3.8 covered working with a coding assistant: specifications as test cases, reading what it wrote, and reviewing changes. This chapter is about the prompts themselves. It covers how to specify a coding task, how to give a model the right part of a codebase and get a change back in a form that can be applied, and how to write prompts for the three jobs that are not writing new code: reviewing, debugging, and refactoring.

## 1. First-Principles Mental Model & Intuition

### A ticket for a contractor on their first day

A skilled contractor joins your team this morning. They know the language better than you do. They have never seen your codebase. They do not know which libraries you use, how your tests are run, what your naming conventions are, or why the billing module is written in that odd way.

You hand them a ticket that says: "Fix the login bug."

They will fix something. Whether it is the bug you meant, in the way your codebase expects, without breaking what depends on it, is luck.

Now the ticket says: "Users are logged out when their session token is refreshed. The refresh logic is in `auth/session.py`. Write a failing test that reproduces it, then fix it. Do not change the token format. Run the auth tests to confirm."

The second ticket names the symptom, the place, the method, a constraint, and the check. Those are the parts of a coding prompt. Anthropic's guidance for its coding tool reduces the same advice to three points: tell the model what it cannot see, give it a check it can run, and enforce in tooling the rules that must have no exceptions.

### Two loops

```text
   WITHOUT A CHECK                          WITH A CHECK

   prompt  ->  code  ->  "looks right"      prompt + tests  ->  code  ->  run tests
                              |                                              |
                              v                                    fail      |   pass
                    found wrong later,                     +-----------------+----+
                    by a user                              v                      v
                                                  error fed back            read the diff,
                                                  to the model              then accept
```

In the left-hand loop the only judge is a person skimming code that was written to look plausible. In the right-hand loop a failure is caught in seconds and fed back, and the person's attention is saved for the change that passes.

### What a model does not have

A model writing code for you lacks four things, and a coding prompt exists to supply them.

| It does not know | So the prompt supplies |
|---|---|
| What exactly you want | A specification with examples |
| Your code | The relevant files, or a map of them |
| Your rules | Versions, libraries, conventions, what not to touch |
| Whether its answer works | Tests, and the command that runs them |

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### Specifying a task

| Part | Contents | Example |
|---|---|---|
| **Goal** | What the code is for, in a sentence | "Turn an article title into a URL slug" |
| **Interface** | The exact name, arguments, and return type | `def slugify(title: str) -> str` |
| **Examples** | Inputs with their expected outputs, including edge cases | `slugify("")` gives `""` |
| **Constraints** | Language version, permitted libraries, style, performance, what not to change | "Python 3.10, standard library only" |
| **Done when** | The check that decides success | "`python -m pytest tests/test_slugify.py` passes" |

The examples do the most work. A sentence such as "handle punctuation sensibly" can be read ten ways. Three examples leave one reading. Examples written as assertions are also the test: the specification and the check are the same text.

Research supports leaning on tests. The CodeT study in 2022 had a model write tests along with several candidate solutions and chose the candidate that agreed with the most tests, which improved the rate of correct solutions over taking the first candidate. Benchmarks of real engineering work, such as SWE-bench, are built the same way: a task counts as solved when the project's own tests pass.

The edge cases belong in the examples and not in prose: the empty input, the single element, the duplicate, the negative number, the input in the wrong type. These are where generated code most often fails, because the commonest version of any function in a model's training data did not handle them.

### Supplying context

A model can only use code that is in its context. Too little, and it invents functions that do not exist. Too much, and the relevant part is diluted, as Module 5.3 showed.

| Give | Why |
|---|---|
| The file to be changed, in full | It must match what is there |
| The signatures of what that file calls | So it calls real functions with real arguments |
| One existing example of the same kind of thing | It will copy your conventions |
| The exact error text and traceback | The facts, not your summary of them |
| Versions of the language and key libraries | Its knowledge of an API may be out of date |
| What must not change | Public interfaces, file formats, other teams' code |

For a large codebase, the second row is served by a **map**: a compact list of each file's functions and classes, with their arguments and without their bodies. A map costs a fraction of the tokens of the code and lets the model see what exists. Coding tools build such maps automatically, and Section 3 builds a small one.

Standing rules go in the project's context file, which Module 3.4 introduced. The guidance there applies with force to code: keep the file short, and put in it only what the model cannot find by reading the repository, such as the exact commands for testing and linting.

### Asking for diffs

When a model changes an existing file, there are three ways it can hand back the change.

| Format | The model writes | Strength | Weakness |
|---|---|---|---|
| Whole file | The complete new file | Simple, always applicable | Slow and costly for large files, and invites lazy omissions |
| Search and replace | A block of existing text and its replacement | Small output | The existing text must match exactly, once |
| Unified diff | Context lines, with removed and added lines marked | Small output, standard, reviewable | Must be applied carefully |

The saving is large. To change $m$ lines in a file of $N$ lines with $c$ lines of context on each side, a whole-file rewrite outputs about $N$ lines, and a diff about $m + 2c$:

$$
\frac{\text{whole file}}{\text{diff}} \approx \frac{N}{m + 2c}
$$

For a 400-line file with three lines changed and three lines of context on each side, that is 400 lines against 9, about 44 times less output. Module 5.9 explained why output is the side that matters: it is the expensive part of the bill and nearly all of the wait.

A unified diff looks like this.

```text
--- a/billing/discounts.py
+++ b/billing/discounts.py
@@ -1,4 +1,4 @@
 def apply_discount(total, percent):
     if not 0 <= percent <= 100:
-        raise ValueError("percent out of range")
+        raise ValueError(f"percent must be between 0 and 100, got {percent}")
     return round(total * (1 - percent / 100), 2)
```

A line beginning with a space is context: unchanged, and there to locate the change. A line beginning with a minus is removed, and a line beginning with a plus is added. The header between the double at-signs gives, for the old file and then the new, the starting line and the number of lines the hunk covers. If a hunk has $k$ context lines, $r$ removed, and $a$ added, its header reads

$$
\texttt{@@ -s,}(k + r)\ \texttt{+s',}(k + a)\ \texttt{@@}
$$

Here there are three context lines, one removed, and one added, so both counts are 4.

Models are poor at the numbers in that header. The developers of the Aider coding tool measured edit formats on a benchmark of 89 refactoring tasks designed to catch a model being lazy, that is, replacing code with a comment saying the rest is unchanged. Asking one model for unified diffs raised its score from 20 percent to 61 percent and cut the lazy comments to about a third. Two details of their method matter for anyone prompting for diffs. They told the tool to ignore the line numbers and find the place by matching the context lines, because the model's numbers were unreliable. And they made the patching tolerant of small imperfections, without which editing errors rose about ninefold. The same report notes that emotional appeals in the prompt, such as offering a tip, made results worse.

The practical rules: ask for a diff or a search-and-replace block when the file is long, apply it by matching text and not line numbers, and reject a patch whose context matches nowhere or in more than one place.

### Prompts for reviewing

"Review this code" gets a list of style remarks. A review prompt needs the same specificity as any other.

- **Say what to look for.** Correctness against the stated behaviour, unhandled edge cases, security, missing tests. Name them.
- **Give the intent.** A reviewer who does not know what the change was for can only judge whether the code is tidy.
- **Ask for findings in a fixed form.** File and line, what is wrong, a concrete input that triggers it, and how serious it is.
- **Ask for no praise and no rewriting.** Otherwise the findings are buried.
- **Use a fresh context.** A model reviewing code it has just written tends to approve it. A separate session with only the diff and the intent is an independent check, the evaluator pattern of Module 5.6.

### Prompts for debugging

The commonest debugging prompt is "it doesn't work", followed by the code. The model then guesses at a fault and changes something.

| Include | Because |
|---|---|
| The exact error message and the full traceback | The location and type of the failure are in it |
| What you expected and what happened | A wrong result with no error has no traceback |
| The smallest input that triggers it | It rules out most of the code |
| What changed recently | Most bugs are in what changed |
| What you have tried | It prevents the same suggestions |

Then ask for two things in order. First the cause, with the evidence for it, and no code. Then a failing test that reproduces the bug, followed by the fix. The test proves the diagnosis: if the test does not fail before the fix, the model has not found your bug. Without that discipline, models tend to repair the symptom, wrapping the failing line in a check that hides the error and leaves its cause in place.

### Prompts for refactoring

Refactoring means changing how code is written without changing what it does. The prompt has to say so, and the check is different from any other task: the old and new code must behave identically.

- **State that behaviour must not change**, including error behaviour.
- **Have tests first.** If the code has none, ask for tests that record its current behaviour before anything is changed.
- **One kind of change per request.** Renaming, extracting a function, and changing a data structure are three requests.
- **No fixes mixed in.** A bug noticed during refactoring is reported, and fixed separately.

A refactoring that "improves" what a function does on an empty list is a behaviour change, however reasonable. Something elsewhere may depend on the old behaviour.

### What the evidence says about speed and safety

Three findings temper enthusiasm.

A randomised trial by the research group METR in 2025 had 16 experienced open-source developers complete 246 tasks in their own large codebases, with AI tools allowed or disallowed at random. With AI they took 19 percent longer. Before the study they had forecast a 24 percent speed-up, and afterwards they still believed they had been about 20 percent faster. The group's follow-up work in 2026 reported that its newer data could not settle the size of the effect. The durable lesson is the gap between felt and measured speed: time saved typing can be lost to prompting, waiting, and reviewing, without the developer noticing.

A 2024 study of package names in generated code examined 576,000 samples from 16 models. At least 5.2 percent of the packages recommended by commercial models did not exist, and 21.7 percent for open-source models, with over 205,000 distinct invented names. Attackers can register such names with malicious code. Module 3.8 built a check for unknown imports for this reason.

Security testing firms have reported that a large share of generated code samples contain well-known classes of vulnerability. A prompt that says nothing about security gets code written without regard to it.

### Complexity

Building a prompt or a map is linear in the size of the inputs. Applying a hunk by searching for its context is proportional to the file length times the hunk length. The dominant costs are in tokens: input for the context you supply, which a map reduces, and output for the change, which a diff reduces by the ratio above.

## 3. Production-Grade Implementation & Annotated Walkthrough

First, a specification assembled into a prompt.

```python
import ast
import re

def build_code_prompt(task):
    for key in ("goal", "signature", "examples", "done_when"):
        if not task.get(key):
            raise ValueError("a code task needs " + key)
    lines = ["## Task", task["goal"].strip(), "", "## Signature", task["signature"].strip(), "", "## Examples"]
    lines += [f"{call} -> {result}" for call, result in task["examples"]]
    if task.get("constraints"):
        lines += ["", "## Constraints"] + ["- " + constraint for constraint in task["constraints"]]
    lines += ["", "## Done when", task["done_when"].strip()]
    return "\n".join(lines)

TASK = {
    "goal": "Write a function that turns a title into a URL slug.",
    "signature": "def slugify(title: str) -> str",
    "examples": [('slugify("Hello, World!")', '"hello-world"'),
                 ('slugify("  Spaces   everywhere ")', '"spaces-everywhere"'),
                 ('slugify("")', '""')],
    "constraints": ["Python 3.10, standard library only",
                    "Lowercase ASCII letters, digits, and single hyphens only",
                    "No leading or trailing hyphen"],
    "done_when": "python -m pytest tests/test_slugify.py passes",
}
print(build_code_prompt(TASK))
```

- **Four parts are required.** A goal, a signature, examples, and a statement of when the task is done. The function refuses to build a prompt without them, because each one removes a class of guess.
- **The signature is exact.** The name, the argument, and the types are given. The model does not choose them, so the result fits the code that will call it.
- **The examples include the awkward cases.** Punctuation, repeated spaces, and the empty string. Each is a line that can be turned into an assertion.
- **Constraints are optional and listed.** They say which Python, which libraries, and what the output may contain.
- **"Done when" names a command.** The model, or the tool running it, can execute that command and see for itself whether the work is finished.

Next, a map of a codebase to use as context.

```python
SOURCES = {
    "billing/invoice.py": (
        "import math\n\nTAX = 0.2\n\nclass Invoice:\n    \"\"\"An invoice.\"\"\"\n    def __init__(self, items):\n"
        "        self.items = items\n\n    def total(self, tax_rate=TAX):\n"
        "        subtotal = sum(price * qty for price, qty in self.items)\n"
        "        return round(subtotal * (1 + tax_rate), 2)\n\n"
        "def format_money(amount, currency=\"GBP\"):\n    return f\"{currency} {amount:.2f}\"\n"),
    "billing/discounts.py": (
        "def apply_discount(total, percent):\n    if not 0 <= percent <= 100:\n"
        "        raise ValueError(\"percent out of range\")\n    return round(total * (1 - percent / 100), 2)\n\n"
        "def _clamp(value, low, high):\n    return max(low, min(high, value))\n"),
    "billing/broken.py": "def oops(:\n    pass\n",
}

def repo_map(sources):
    lines = []
    for path in sorted(sources):
        try:
            tree = ast.parse(sources[path])
        except SyntaxError:
            lines.append(path + ": (does not parse)")
            continue
        names = []
        for node in tree.body:
            if isinstance(node, ast.FunctionDef):
                names.append("def " + node.name + "(" + ", ".join(argument.arg for argument in node.args.args) + ")")
            elif isinstance(node, ast.ClassDef):
                methods = [item.name for item in node.body if isinstance(item, ast.FunctionDef)]
                names.append("class " + node.name + " [" + ", ".join(methods) + "]")
        lines.append(path + ": " + "; ".join(names))
    return "\n".join(lines)

project_map = repo_map(SOURCES)
print(project_map)
print(len(project_map), sum(len(source) for source in SOURCES.values()))
```

- **`ast.parse` reads each file as Python and returns its structure.** The function looks only at the top level of each file: its functions and its classes.
- **A function is listed with its argument names.** A class is listed with the names of its methods. Bodies, imports, and constants are left out.
- **A file that does not parse is listed as such.** One broken file does not stop the map, and the model is told that the file exists and is broken.
- **The map is 210 characters, and the three files are 607.** About a third of the size on this tiny example. On real code, where function bodies are long, a map is a small fraction of the source.
- **What the map buys.** A model asked to add a discount to an invoice can see that `apply_discount(total, percent)` exists and how to call it, without being sent the whole of both files. It will not invent a function, and it will not write a second one.

Then, applying a change by its context.

```python
def apply_hunk(lines, hunk):
    before = [line[1:] for line in hunk if line[:1] in (" ", "-")]
    after = [line[1:] for line in hunk if line[:1] in (" ", "+")]
    places = [index for index in range(len(lines) - len(before) + 1)
              if lines[index:index + len(before)] == before] if before else []
    if len(places) != 1:
        raise ValueError(f"hunk matches {len(places)} places")
    start = places[0]
    return lines[:start] + after + lines[start + len(before):]

source_lines = SOURCES["billing/discounts.py"].splitlines()
hunk = [
    " def apply_discount(total, percent):",
    "     if not 0 <= percent <= 100:",
    '-        raise ValueError("percent out of range")',
    '+        raise ValueError(f"percent must be between 0 and 100, got {percent}")',
    "     return round(total * (1 - percent / 100), 2)",
]
print("\n".join(apply_hunk(source_lines, hunk)[:4]))
for bad in ([" def apply_discount(total, pct):", "-    pass"], ["+a new line with no context"]):
    try:
        apply_hunk(source_lines, bad)
    except ValueError as error:
        print("rejected:", error)
try:
    apply_hunk(["a", "b", "a", "b"], [" a", "-b", "+c"])
except ValueError as error:
    print("rejected:", error)
```

- **The hunk has no line numbers.** It is only the marked lines. The first character of each says what it is: a space for context, a minus for a line to remove, a plus for a line to add.
- **`before` is what the file must contain now.** The context lines and the removed lines, in order. `after` is what should be there instead: the context lines and the added lines.
- **The function searches the file for `before`.** It tries every position and keeps those where the lines match exactly.
- **Exactly one match is required.** The good hunk matches in one place, and the error message in the file is replaced.
- **A hunk whose context is wrong is rejected.** The second hunk names an argument `pct` that the file does not have. It matches nowhere. A model that misremembers the code produces exactly this, and applying it by line number would have corrupted the file.
- **A hunk with no context is rejected.** With nothing to locate it, there is no telling where the new line belongs.
- **A hunk that matches twice is rejected.** In the last example the lines to change occur at two places. The function refuses to choose. The remedy is to ask the model for more context lines.

Finally, the facts in a traceback, and a check that a refactoring changed nothing.

```python
TRACEBACK = '''Traceback (most recent call last):
  File "/app/run.py", line 12, in <module>
    main()
  File "/app/run.py", line 8, in main
    print(report(orders))
  File "/app/billing/report.py", line 31, in report
    average = total / len(orders)
ZeroDivisionError: division by zero'''

def parse_traceback(text):
    frames = re.findall(r'File "([^"]+)", line (\d+), in (\S+)', text)
    if not frames:
        return None
    error, _, message = text.strip().splitlines()[-1].partition(": ")
    path, line, function = frames[-1]
    return {"error": error, "message": message, "file": path, "line": int(line), "function": function, "depth": len(frames)}

def same_behaviour(old, new, inputs):
    def outcome(function, arguments):
        try:
            return ("returned", function(*arguments))
        except Exception as error:
            return ("raised", type(error).__name__)
    return [arguments for arguments in inputs if outcome(old, arguments) != outcome(new, arguments)]

def mean_old(values):
    total = 0
    for value in values:
        total += value
    return total / len(values)

def mean_tidy(values):
    return sum(values) / len(values)

def mean_changed(values):
    return sum(values) / len(values) if values else 0

print(parse_traceback(TRACEBACK))
print(parse_traceback("it does not work"))
cases = [([1, 2, 3],), ([5],), ([],)]
print(same_behaviour(mean_old, mean_tidy, cases), same_behaviour(mean_old, mean_changed, cases))
```

- **`parse_traceback` finds every frame.** Each is a file, a line number, and a function. The last frame is where the error was raised, and the last line of the text names the error and gives its message.
- **The result is the debugging prompt's core.** A `ZeroDivisionError` in the function `report`, at line 31 of `billing/report.py`, three calls deep. That is what a model needs, and it is what "it crashes sometimes" leaves out.
- **Text with no traceback returns nothing.** "It does not work" contains no facts to extract, which is the point: such a report gives a model nothing either.
- **`same_behaviour` runs the old and new functions on the same inputs.** It records, for each, either the value returned or the type of error raised, and lists the inputs on which the two differ.
- **`mean_tidy` is a true refactoring.** It replaces a loop with `sum` and behaves identically on all three inputs, including raising the same error on an empty list. The first result is an empty list.
- **`mean_changed` is not.** On an empty list the old function raises `ZeroDivisionError` and the new one returns 0. The check reports that input. Returning 0 may be better. It is still a change in behaviour, made under the name of a refactoring, and whoever catches that error today will stop being told.

**Complexity.** `build_code_prompt` is linear in the task. `repo_map` parses each file once. `apply_hunk` compares the hunk at each position in the file. `parse_traceback` is one pass over the text. `same_behaviour` makes two calls per input.

### Four prompt templates

```text
WRITE
Task: [one sentence]
Signature: [exact]
Examples: [input -> output, including edge cases]
Constraints: [version, libraries, style, what not to change]
Done when: [the command that must pass]

CHANGE
Here is [file], in full. Here are the signatures of what it uses.
Change: [what, and why]
Return a unified diff with 3 lines of context. Do not change anything else.
Done when: [the command that must pass]

DEBUG
Error: [exact message and full traceback]
Expected: [what should happen]     Actual: [what happens]
Smallest input that triggers it: [input]
Recently changed: [what]           Already tried: [what]
First explain the cause, with evidence, and write no code.
Then write a failing test that reproduces it. Then the fix.

REVIEW
This change is meant to: [intent]
Check for: wrong results, unhandled edge cases, security problems, missing tests.
For each finding give: file and line, what is wrong, an input that triggers it, severity.
No praise. No rewriting. If you find nothing, say so.
```

### Before accepting generated code

| Check | How |
|---|---|
| Does it pass the tests? | Run them. Do not take the model's word |
| Were the tests changed? | Read the diff of the test files first |
| Is the diff the size you expected? | A one-line fix that touches twelve files needs an explanation |
| Do the imports exist? | Check each new package name against the real registry |
| Does it stay in scope? | Nothing outside the files you named |
| Do you understand it? | If not, ask for an explanation before merging, not after |

## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**"Fix the bug."** With no symptom, no location, and no check, the model changes whatever looks suspicious. Give the error, the place, and the test that should pass.

**No way to check.** A model that cannot run anything reports success because the code looks right. Give it a command to run, or run it yourself and paste the output back. Its statement that the work is done is a claim, not a result.

**Tests edited to pass.** Asked to make failing tests pass, a model sometimes changes the tests: loosening an assertion, deleting a case, or adding a skip. Say that the tests must not be modified, and read the diff of the test files before anything else.

**The symptom fixed and the cause left.** A failing line wrapped in a check that swallows the error makes the traceback disappear. Ask for the cause before the fix, and for a test that fails without the fix.

**Invented APIs and packages.** A function that sounds right and does not exist, or a package name that was never published. The measured rates are in Section 2. Supply the real signatures, state the library versions, and verify every new dependency.

**Stale knowledge.** A model's training ends at some date, and libraries change after it. Code written for a version from two years ago fails against today's. Paste the relevant current documentation, or name the version and ask the model to say if it is unsure.

**The lazy rewrite.** Asked for a whole file, a model writes a comment saying the remainder is unchanged, and the tool saves that comment in place of the code. Ask for diffs on long files, and reject any output containing such a placeholder.

**Patches applied by line number.** The numbers in a model's diff header are often wrong. Apply by matching context, and refuse a patch that matches nowhere or twice.

**The giant diff.** A request for a small change returns reformatted files, renamed variables, and "improvements" nobody asked for. Such a diff cannot be reviewed. Say "change nothing else", and ask for one kind of change per request.

**Over-engineering.** A ten-line task comes back as three classes and a configuration system. Models reproduce the heavy patterns of their training data. Say "the simplest thing that passes the tests", and state what not to add.

**Reviewing your own change.** The session that wrote the code has its reasoning in context and is inclined to defend it. Review in a fresh session with only the diff and the intent.

**Long sessions that lose the thread.** After many turns, early decisions fall out of effective context and the model contradicts them. Start a new session with a short summary, and keep durable rules in the project's context file.

**Feeling fast.** The METR trial's developers believed they were faster while being measurably slower. If speed matters, measure it on real tasks, and count the reviewing.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Code can be checked by a machine, so the best coding prompts state exactly what is wanted and supply the check. A task specification gives the goal, the exact interface, examples including edge cases, constraints, and the command that decides when the work is done. Context is the part of the codebase the model needs: the file to change, the signatures of what it calls, an example of local conventions, exact error text, and versions, with a compact map standing in for code it need not read in full. For long files, changes should come back as diffs, which cut output by roughly $N/(m + 2c)$, and should be applied by matching context lines and not line numbers, rejecting any hunk that matches nowhere or more than once. Review prompts name what to look for and ask for findings in a fixed form from a fresh context. Debugging prompts supply the traceback, expected and actual behaviour, and a minimal input, and ask for the cause and a failing test before the fix. Refactoring prompts require identical behaviour, errors included. Measured evidence warns that generated code invents packages, carries vulnerabilities, and can make experienced developers slower while they feel faster.

**Question 1.** A model returns a hunk whose header reads `@@ -20,6 +20,8 @@` and which contains four context lines. How many lines does it remove and how many does it add? The file has 600 lines, and this is the only change. Roughly how much less output is this than rewriting the whole file? Why should the tool that applies the hunk not trust the number 20?

<details>
<summary>View Answer</summary>

The first pair of numbers describes the old file: the hunk starts at line 20 and covers 6 lines. Those 6 are the context lines plus the removed lines, and there are four context lines, so 2 lines are removed. The second pair describes the new file: 8 lines, which are the context lines plus the added lines, so 4 lines are added. The file grows by two lines. The hunk's body is 4 context lines, 2 removed, and 4 added, which is 10 lines, or 11 with its header. A whole-file rewrite would output all 602 lines of the new file. So the diff is roughly 55 times less output, which matters because output tokens are the expensive part of the bill and nearly all of the waiting time. The tool should not trust the 20 because models are unreliable at line numbers. A model does not count lines as it reads, so the number in a header is often off by a few, and applying the change at the wrong line would silently corrupt the file. The reliable method is to ignore the numbers and search the file for the hunk's context and removed lines as exact text. If they occur in exactly one place, the change is applied there. If they occur nowhere, the model has misremembered the code, and if they occur more than once, the hunk is ambiguous. In both cases the patch should be rejected and the model asked again, with the current file contents or with more context lines.

</details>

**Question 2.** A developer prompts: "The checkout is broken, please fix it. Here's the whole repo." Rewrite this as a debugging prompt, state what information the developer must gather first, and explain why you ask for things in the order you do.

<details>
<summary>View Answer</summary>

Before writing the prompt, the developer has to find out what "broken" means. That is a reproduction: the exact action that fails, the error message and full traceback if there is one, or the wrong result and the right one if there is not, and the smallest input that triggers it. They should also note what changed recently, since most bugs are in what changed, and what they have already tried. A rewritten prompt might read: "Checkout fails with a KeyError when the basket contains an item with no discount code. Here is the full traceback. Expected: the order total without a discount. Actual: the request returns an error. The smallest case is a basket with one item and no code. First, explain the cause, citing the lines involved, and write no code. Then write a failing test that reproduces it. Then propose the smallest fix as a diff, changing nothing else. The checkout tests must pass, and you must not modify existing tests." The whole repository is replaced by the one relevant file and the signatures around it, because unrelated code dilutes attention and costs tokens, and the traceback already says where the failure is. The order of the requests matters. The cause comes first, without code, because a model asked to fix immediately tends to patch the line that failed, for instance by supplying a default, which hides the error and leaves its cause. The failing test comes second because it proves the diagnosis: if the test does not fail before the fix, the model has found some other problem. The fix comes last, as a small diff, so that it can be read, and with the tests protected so that passing them means something.

</details>

**Question 3.** A model is asked to "refactor" a function that averages a list. The old version raises an error on an empty list. The new version is shorter and returns 0 for an empty list. All existing tests pass. Should the change be accepted as a refactoring? Explain what a behaviour check would report, why the passing tests do not settle it, and what the prompt should have said.

<details>
<summary>View Answer</summary>

It should not be accepted as a refactoring. A refactoring changes how code is written and leaves what it does untouched, and this change alters what the function does on one input. A behaviour check that runs the old and new functions on the same inputs and compares what each returns or raises would report the empty list: the old function raises a division error and the new one returns 0. On every non-empty input the two agree. The passing tests do not settle it because tests only cover the cases someone wrote down. If no test passes an empty list, the suite is silent on the one input where the behaviour changed, and a green result means only that the listed cases still work. This is the general weakness of relying on existing tests during a refactoring, and it is why the first step is often to add tests that record current behaviour, edge cases and errors included. Returning 0 may well be the better behaviour. But something elsewhere may rely on the error, for example a report that catches it and prints "no data", which would now print an average of 0 as though it were a measurement. That is a decision for a person, made on purpose and recorded as a behaviour change, not slipped in under another name. The prompt should have said: refactor for readability only; behaviour must be identical for every input, including which errors are raised; do not fix or improve anything; if you notice a bug or a questionable behaviour, report it separately and leave the code as it is; before changing anything, write tests that capture the current behaviour on normal, boundary, and invalid inputs.
