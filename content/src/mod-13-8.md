# AI Tool Selection Cheat Sheet

Every client conversation eventually reaches the question "which tool should we use?". The honest answer is "it depends on the task", and this bonus module makes that answer systematic: a **decision matrix** that scores tools against weighted criteria for each task, a **cost and capability quick reference** that turns usage into a monthly figure, and a list of **red flags** that rule a tool out regardless of its score. The output is a one-page cheat sheet, one line per task, that Sam can hand to a client and defend.

The tools here are **categories**, a frontier API model, a small API model, a local model, a free consumer chat app, and a no-code automation platform, rather than brands, because brands and prices change every few months while the categories and the method last. All prices are illustrative, in GBP per million tokens; check current pricing pages, such as Anthropic's, before quoting a client.

## 1. First-Principles Mental Model & Intuition

### The joiner's tool wall

A joiner does not ask "what is the best saw?". A panel saw, a tenon saw, a coping saw, and a track saw each win at different cuts, and the choice depends on the cut, the material, the budget, and safety. Some tools are never used, however cheap, because they are unsafe: a saw with a missing guard is not a bargain. Choosing AI tools works the same way: match the tool to the task, weigh what matters for this job, check the running cost, and refuse anything with a missing guard.

```text
 TASK            DECISION MATRIX                    COST CHECK                 RED FLAGS
  drafting  -->  score each tool on            -->  monthly = fixed fee   -->  trains on your data?   (critical)
  extraction     quality, privacy, cost, ease       + requests x tokens       no data processing      (critical)
  classif.       weighted by what matters           x price per million       agreement?
  automation     for this client                                               no export? no status page?
                                                                               (warnings)
                         \______________________ choose: best score, then lowest cost, then name ___/
                                                  cheat sheet: one line per task
```

### No single best tool

Clients often want one answer: "should we use the expensive one or the free one?". The decision matrix shows why the answer varies: a frontier model wins on quality for drafting proposals, a small cheap model is enough to classify emails, a local model wins when data must not leave the building, and a no-code platform is the right tool for wiring the steps together. A cheat sheet with one line per task captures this without forcing a single choice.

## 2. Core Theory, Mathematical Foundations & Architecture Internals

### The decision matrix

Each tool is scored from 1 to 5 on four criteria: **quality** of output for the task, **privacy**, how well client data is protected, **cost**, where 5 is cheapest, and **ease** of setup and use. The client sets weights reflecting what matters to them, and the weighted score is

$$S(t) = \frac{\sum_c w_c \, s_c(t)}{\sum_c w_c}$$

for weights $w_c$ and scores $s_c(t)$. With Sam's default weights, quality 4, privacy 3, cost 2, ease 1, summing to 10, the five categories score:

| Tool | Quality | Privacy | Cost | Ease | Weighted |
|---|---|---|---|---|---|
| Frontier API | 5 | 3 | 2 | 4 | 3.7 |
| Small API model | 3 | 3 | 5 | 4 | 3.5 |
| Local model | 3 | 5 | 4 | 2 | 3.7 |
| Free chat app | 4 | 1 | 5 | 5 | 3.4 |
| No-code automation platform | 3 | 3 | 3 | 5 | 3.2 |

The weights matter more than any single score. A clinic that weights privacy 5, quality 2, cost 2, and ease 1 sees the local model jump to 4.1 and the frontier API fall to 3.3. Agreeing the weights with the client before scoring is the most important step, because it makes the recommendation the client's own priorities applied consistently.

### The cost and capability quick reference

API models charge per token, separately for input and output; local models and platforms usually have a fixed monthly cost. For $r$ requests a month with $i$ input and $o$ output tokens each, prices $p_{in}$ and $p_{out}$ per million tokens, and fixed fee $F$:

$$C = F + r \cdot \frac{i \, p_{in} + o \, p_{out}}{10^6}$$

For Harper Joinery's quote assistant, about 600 requests a month of 2,000 input and 500 output tokens:

| Tool | Illustrative prices (in / out per million) | Fixed | Monthly cost |
|---|---|---|---|
| Frontier API | GBP 5.00 / GBP 25.00 | 0 | GBP 13.50 |
| Small API model | GBP 0.20 / GBP 1.00 | 0 | GBP 0.54 |
| Local model | none | GBP 30 (hardware and power, amortised) | GBP 30.00 |
| Free chat app | none | 0 | GBP 0.00 |
| No-code automation platform | none | GBP 20 | GBP 20.00 |

Volume changes the answer. The local model's fixed GBP 30 breaks even with the frontier API where $r \times 22{,}500 / 10^6 = 30$, about 1,333 requests a month; at 20,000 requests the frontier API would cost GBP 450. Output tokens usually cost several times input tokens, so tasks that write long answers are more expensive than tasks that read long documents and answer briefly.

### Capability notes for each category

**Frontier API models** lead on reasoning, long documents, and writing quality, and offer business terms that exclude training on customer data. **Small API models** handle classification, extraction, and short drafting at a fraction of the price and lower latency. **Local models**, run with tools such as Ollama, keep data on the client's own hardware, Module 10.13, at the cost of setup effort and lower quality on hard tasks. **Free consumer chat apps** are excellent for personal exploration but often use conversations for training by default and lack business agreements. **No-code automation platforms** connect apps and call models, and are chosen for wiring rather than intelligence.

### Red flags

Some properties rule a tool out for client work regardless of score:

| Red flag | Severity | Why |
|---|---|---|
| Trains on your data by default | critical | client data may end up in a model others use |
| No data processing agreement | critical | without one, using it for personal data is hard to justify under GDPR |
| No way to export your data | warning | lock-in; leaving means losing history |
| No status page or uptime history | warning | outages will surprise you and the client |

Critical flags exclude a tool whenever client data is involved; warnings are noted on the cheat sheet. A free chat app with critical flags is fine for brainstorming with no client information and unacceptable for processing client emails. Security issues specific to language model applications, such as prompt injection and sensitive information disclosure, are catalogued in the OWASP Top 10 for LLM applications, and NIST's AI Risk Management Framework gives a broader structure for governance.

### Choosing and the cheat sheet

For each task: keep the tools that support it; if client data is involved, drop those with critical flags; sort by weighted score descending, then monthly cost ascending, then name; pick the first. Drafting with Sam's weights is a tie at 3.7 between the frontier API and the local model, broken by cost, GBP 13.50 against GBP 30.00, so the frontier API wins. Classification goes to the local model, 3.7 against the small model's 3.5. Automation goes to the no-code platform, the only tool supporting it, and a task no tool supports is reported as "none suitable" rather than forced.

### Complexity

Scoring a tool is linear in the number of criteria; choosing for a task sorts the candidates, $O(n \log n)$ for $n$ tools; the cheat sheet repeats this for each task.

```python
WEIGHTS = {"quality": 4, "privacy": 3, "cost": 2, "ease": 1}

def weighted_score(tool, weights):
    return round(sum(w * tool["scores"][k] for k, w in weights.items()) / sum(weights.values()), 2)

print([weighted_score(t, WEIGHTS) for t in TOOLS])
print(weighted_score(TOOLS[2], {"quality": 2, "privacy": 5, "cost": 2, "ease": 1}))
```

- **3.7, 3.5, 3.7, 3.4, and 3.2** with the default weights.
- **The local model scores 4.1 with privacy-heavy weights.**
- **Iterating over the weights,** not the scores, means a criterion the client gives no weight is simply ignored.

Next, the monthly cost.

```python
def monthly_cost(tool, requests, in_tokens, out_tokens):
    return round(tool["monthly"] + requests * (in_tokens * tool["in_per_m"] + out_tokens * tool["out_per_m"]) / 1_000_000, 2)

print([monthly_cost(t, 600, 2000, 500) for t in TOOLS])
print(monthly_cost(TOOLS[0], 20000, 2000, 500))
```

- **GBP 13.50, 0.54, 30.00, 0.00, and 20.00** at 600 requests.
- **GBP 450 at 20,000 requests,** where the local model's fixed cost becomes the bargain.

Then, red flags.

```python
FLAGS = [("trains_on_data", True, "trains on your data by default", True),
         ("dpa", False, "no data processing agreement", True),
         ("export", False, "no way to export your data", False),
         ("status_page", False, "no status page or uptime history", False)]

def red_flags(tool):
    hits = [(text, crit) for field, bad, text, crit in FLAGS if tool[field] == bad]
    return [t for t, _ in hits], any(c for _, c in hits)

print(red_flags(TOOLS[3]))
print(red_flags(TOOLS[2]))
```

- **The free chat app has three flags, two critical.**
- **The local model has one warning,** no status page, which matters less when the client runs it themselves.
- **Each flag is data,** a field, the bad value, the text, and the severity, so adding a flag is one line.

Then, choosing a tool.

```python
def choose(task, tools, weights, requests, in_tokens, out_tokens, client_data=True):
    ok = [t for t in tools if task in t["tasks"] and not (client_data and red_flags(t)[1])]
    if not ok:
        return None
    ok.sort(key=lambda t: (-weighted_score(t, weights), monthly_cost(t, requests, in_tokens, out_tokens), t["name"]))
    return ok[0]["name"]

print(choose("drafting", TOOLS, WEIGHTS, 600, 2000, 500))
print(choose("analysis", TOOLS, {"cost": 1}, 600, 2000, 500, client_data=False))
print(choose("analysis", TOOLS, {"cost": 1}, 600, 2000, 500))
```

- **Drafting: the frontier API,** winning the 3.7 tie on cost.
- **Analysis on cost alone without client data: the free chat app;** with client data it is excluded and the frontier API is chosen.

Finally, the cheat sheet.

```python
def cheat_sheet(tasks, tools, weights, requests, in_tokens, out_tokens):
    by_name = {t["name"]: t for t in tools}
    lines = []
    for task in tasks:
        name = choose(task, tools, weights, requests, in_tokens, out_tokens)
        if name is None:
            lines.append(f"{task} -> none suitable")
        else:
            t = by_name[name]
            lines.append(f"{task} -> {name} (score {weighted_score(t, weights):.1f}, "
                         f"GBP {monthly_cost(t, requests, in_tokens, out_tokens):.2f} a month)")
    return lines

for line in cheat_sheet(["drafting", "classification", "automation", "translation"], TOOLS, WEIGHTS, 600, 2000, 500):
    print(line)
```

- **Four lines:** drafting to the frontier API at GBP 13.50, classification to the local model at GBP 30.00, automation to the no-code platform at GBP 20.00, and translation "none suitable".
- **"None suitable" is an honest answer** that prompts adding a tool to the list rather than stretching an unsuitable one.

**Complexity.** One sort per task.


## 4. Practitioner Wisdom & Edge Cases (Reddit / HN / Stack Overflow Synthesis)

**Choosing by brand loyalty.** The tool you know best is not always the right one. Run the matrix even when you think you know the answer; it is quick, and it documents the reason for the client.

**Scoring from marketing pages.** Quality scores should come from testing on the client's own examples, Module 10.11, not from benchmark headlines. A model that leads a public leaderboard may be no better at reading joinery price lists than one costing a tenth as much.

**Forgetting output tokens.** Output usually costs several times input. A task that writes a long proposal from a short brief costs more than one that summarises a long document into a paragraph.

**Ignoring volume.** A cost that looks trivial at a pilot's 50 requests a day becomes significant at full rollout. Recalculate at expected volume, and at three times that, before committing.

**Consumer terms for business data.** Free and personal plans often allow training on conversations. Business plans and APIs usually exclude it, but read the current terms rather than assuming; terms change.

**No data processing agreement.** If the tool handles personal data, such as customer names and emails, the client needs a data processing agreement with the provider. A missing one is a critical flag, not a paperwork detail.

**Lock-in through prompts and data.** Keep prompts, test sets, and data in the client's own storage, so switching tools later is a configuration change rather than a rebuild.

**Hidden costs.** Setup time, the client's staff time to learn the tool, platform task limits, and paid add-ons rarely appear on pricing pages. Add them to the comparison as a fixed monthly figure.

**Local models without a maintenance plan.** Hardware fails and models need updating. Someone must own that work, or the privacy benefit is lost to an unpatched machine.

**Stale cheat sheets.** Prices fall and models are replaced every few months. Date every cheat sheet and review it quarterly, like the portfolio, Module 13.7.

**One tool for everything.** A single tool simplifies billing but usually overpays for simple tasks or underperforms on hard ones. Two or three tools, each matched to its tasks, is normal.

**Over-weighting ease.** Easy setup matters for a pilot; over a year, quality and cost usually dominate.

## 5. Active Recall Check & Synthesis Summary

**Summary.** Tool selection is per task, not per client. A decision matrix scores each tool from 1 to 5 on quality, privacy, cost, and ease, weighted by the client's priorities agreed before scoring. Monthly cost is the fixed fee plus requests times input and output tokens times their prices per million, recalculated at real volume. Red flags, training on data by default and no data processing agreement, are critical and exclude a tool whenever client data is involved; no export and no status page are warnings. The chosen tool has the best score, then the lowest cost, then the first name, and a task with no suitable tool is reported honestly. The result is a dated one-line-per-task cheat sheet reviewed quarterly.

**Question 3.** Why does `choose` exclude tools with critical red flags before scoring rather than just lowering their score?

<details>
<summary>View Answer</summary>

A critical red flag, training on client data or having no data processing agreement, is a constraint, not a preference. If it merely lowered the score, a tool strong enough on quality, cost, and ease could still win, and Sam would be recommending a tool that may expose client data or breach data protection obligations, which no amount of quality offsets. Excluding first makes the rule absolute whenever client data is involved, while still allowing the tool for work with no client data, such as brainstorming, by passing `client_data=False`. Warnings, such as no export or no status page, remain on the cheat sheet as notes because they are trade-offs the client can accept knowingly. This mirrors the joiner's rule: a saw with a missing guard is not scored lower, it is taken off the wall.

    """The decision matrix score, using only the criteria the client weighted."""
    return round(sum(w * tool["scores"][k] for k, w in weights.items()) / sum(weights.values()), 2)


# ---------------------------------------------------------------- Step 2
def monthly_cost(tool, requests, in_tokens, out_tokens):
    """Fixed fee plus token charges at the given volume."""
    return round(tool["monthly"] + requests * (in_tokens * tool["in_per_m"] + out_tokens * tool["out_per_m"]) / 1_000_000, 2)


# ---------------------------------------------------------------- Step 3
def red_flags(tool):
    """Matched flag texts in order, and whether any is critical."""
    hits = [(text, crit) for field, bad, text, crit in FLAGS if tool[field] == bad]
    return [t for t, _ in hits], any(c for _, c in hits)


# ---------------------------------------------------------------- Step 4
def choose(task, tools, weights, requests, in_tokens, out_tokens, client_data=True):
    """Best score, then lowest cost, then name, among safe tools that support the task."""
    ok = [t for t in tools if task in t["tasks"] and not (client_data and red_flags(t)[1])]
    if not ok:
        return None
    ok.sort(key=lambda t: (-weighted_score(t, weights), monthly_cost(t, requests, in_tokens, out_tokens), t["name"]))
    return ok[0]["name"]


# ---------------------------------------------------------------- Step 5
def cheat_sheet(tasks, tools, weights, requests, in_tokens, out_tokens):
    """One line per task."""
    by_name = {t["name"]: t for t in tools}
    lines = []
    for task in tasks:
        name = choose(task, tools, weights, requests, in_tokens, out_tokens)
        if name is None:
            lines.append(f"{task} -> none suitable")
        else:
            t = by_name[name]
            lines.append(f"{task} -> {name} (score {weighted_score(t, weights):.1f}, "
                         f"GBP {monthly_cost(t, requests, in_tokens, out_tokens):.2f} a month)")
    return lines
